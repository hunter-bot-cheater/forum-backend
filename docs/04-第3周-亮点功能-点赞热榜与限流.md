### 0.5 装配链一次定死

用户之前明确反馈过「装配顺序太乱」「rdb 传入位置不清楚」。本章先把链子画死，前九步都不再改构造函数签名。唯一的例外是第 10 步：点赞写路径要通知 `ArticleService`，`NewLikeService` 会多收一个参数，理由与改法都在 4.10.2。

```text
main.go                          （本章零改动）
  -> config.InitDB(...)          得到 *gorm.DB
  -> config.InitRedis(...)       得到 *redis.Client
  -> jwt.NewManager(...)         得到 *jwt.Manager
  -> router.New(db, jwtManager, rdb)
       -> service.NewLikeService(db, rdb)          新增，第 1 步；第 10 步补 articleSvc
       -> service.NewHotService(db, rdb)           新增，第 1 步
       -> handler.NewLikeHandler(likeSvc, hotSvc)   新增，第 1 步
       -> middleware.RateLimit(rdb, cfg)            新增，第 1 步
       -> api.Use(limitBody(...))                  已有
       -> api.Use(RateLimit(...))                  第 1 步挂上，骨架期原样放行
       -> 公开读路由              GET /api/articles、/:id、/:id/comments、/articles/hot
       -> api.Group("", JWTAuth(...))              已有
            -> PUT/DELETE /api/articles/:id/like   第 1 步注册
```

三个设计决定值得先讲清。

第一，`LikeService` 与 `HotService` 在骨架阶段就同时收下 `db` 和 `rdb`，尽管 v1 只用到 `db`。结构体字段可以先放着不用，构造函数签名改起来要连带改 `router.New`。把依赖一次放好，后面加 Redis 能力只改方法体，装配代码不动。

第二，`LikeHandler` 同时持有两个 service，点赞接口与热榜接口放在同一个 handler 文件。它们共用一组 URL 前缀与同一套错误映射，拆成两个 handler 会多出两个构造函数和两处注册，学习阶段收益很小。

第三，`rdb` 只在 `router.New` 里创建一次并向下传。service 与 middleware 里都不许 `redis.NewClient`。多个 `Client` 各自开连接池，会让「连接池上限」这类配置失去意义。03 章 7.2 已经按这个口径接过一次，本章沿用。

### 0.7 一个实测：hot 路由能不能和 :id 共存

00 章的 API 合同写的是 `GET /api/articles/hot`，而读详情是 `GET /api/articles/:id`。同一层既有静态段 `hot` 又有通配段 `:id`，老版本 httprouter 会直接 panic。Gin 现在用自己的路由树，行为变了。开工前实测一次，别把别的版本的结论搬过来。

**概念伪代码**：下面是临时探测程序，放在项目外的临时目录跑，不要复制进项目。

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"

	"github.com/gin-gonic/gin"
)

func main() {
	gin.SetMode(gin.ReleaseMode)
	r := gin.New()
	api := r.Group("/api")
	api.GET("/articles/:id", func(c *gin.Context) { c.String(200, "WILDCARD:"+c.Param("id")) })
	api.GET("/articles/hot", func(c *gin.Context) { c.String(200, "STATIC_HOT") })
	paths := []string{"/api/articles/hot", "/api/articles/12", "/api/articles/hot?limit=10"}
	for _, p := range paths {
		w := httptest.NewRecorder()
		r.ServeHTTP(w, httptest.NewRequest(http.MethodGet, p, nil))
		fmt.Printf("%s -> %s\n", p, w.Body.String())
	}
}
```

本机 `gin v1.12.0` 的实测结果：

```text
/api/articles/hot          -> STATIC_HOT
/api/articles/12           -> WILDCARD:12
/api/articles/hot?limit=10 -> STATIC_HOT
```

静态段优先，注册顺序不影响结果。这个结论绑定 `go.mod` 里的 Gin 版本，升级 Gin 后要重跑这段探测。若换成会 panic 的路由实现，把热榜路径改成 `/api/hot/articles`，同时改 00 章 API 合同与本章的验收命令。

## 1. 点赞：先想清楚数据放在哪

这一节只做设计推演，不落盘。第 4.2 步开始才动手写代码。

### 1.1 为什么考虑 Redis

MySQL 执行 `like_count = like_count + 1` 时会对行加锁，多个写入排队，数据库表达式本身不会像「先读到应用内再写回旧值」那样轻易丢更新。高并发时的问题是热点行竞争和吞吐受限。选择 Redis 之前先测量，同时把 Redis 丢数据、同步和恢复的成本算进去。

Redis 的 Set 可以记录哪些用户点过赞。

| 命令 | 作用 | 返回 |
| --- | --- | --- |
| `SADD key member` | 加入成员 | 1 表示新增，0 表示已存在 |
| `SREM key member` | 移除成员 | 1 表示移除，0 表示本来就没有 |
| `SISMEMBER key member` | 判断成员是否存在 | 布尔值 |
| `SCARD key` | 统计成员数 | 整数 |

设计上用 `article:like:v1:{id}` 存点过赞的用户 id 集合。点赞执行 `SADD`，取消执行 `SREM`，查总数用 `SCARD`。

每条 Redis 命令在服务端原子执行，集合天然保证成员唯一。但「先 SADD 再 SCARD」是两条命令，两次调用之间可能有别的请求写入，返回的计数只是某个瞬时值。Set 为每个用户 id 占用空间，用户量很大时内存成本会增长。需要「更新与取数」严格一致时，用 Lua 把两步合成一个原子脚本，或明确告诉调用方这是瞬时值。

这一节只是把「Redis 能做什么」摊开看。上一段里「查总数用 `SCARD`」是初始设想，1.4 定方案时会把它推翻，4.3.1 给出完整理由。先认识命令，再判断该不该用。

### 1.2 概念伪代码：Redis Set 命令实验

下面这段用来单独观察 `SADD`、`SREM`、`SCARD` 的形状。它在临时目录里能编译，放进项目会和 4.2 步的 `LikeService` 重复定义。它没有 MySQL 关系持久化、文章存在校验、错误分类、HTTP 路由和重建能力。

**概念伪代码**：只用于观察，不要复制进项目。

```go
package service

import (
	"context"
	"strconv"

	"github.com/redis/go-redis/v9"
)

type LikeService struct {
	rdb *redis.Client
}

func NewLikeService(rdb *redis.Client) *LikeService {
	return &LikeService{rdb: rdb}
}

const likeKeyPrefix = "article:like:"

func likeKey(articleID uint) string {
	return likeKeyPrefix + strconv.FormatUint(uint64(articleID), 10)
}

func (s *LikeService) Like(ctx context.Context, articleID, userID uint) (int64, error) {
	_, err := s.rdb.SAdd(ctx, likeKey(articleID), userID).Result()
	if err != nil {
		return 0, err
	}
	return s.rdb.SCard(ctx, likeKey(articleID)).Result()
}

func (s *LikeService) Unlike(ctx context.Context, articleID, userID uint) (int64, error) {
	_, err := s.rdb.SRem(ctx, likeKey(articleID), userID).Result()
	if err != nil {
		return 0, err
	}
	return s.rdb.SCard(ctx, likeKey(articleID)).Result()
}
```

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `strconv.FormatUint(...)` | 把 id 转成十进制字符串 | key 里的 id 必须由已验证的整数生成，禁止拼接任意用户输入 |
| `SAdd(...).Result()` | 写入并返回新增个数 | 丢弃返回值只依赖集合去重，重复点赞不会加两次 |
| `SCard(...).Result()` | 单独读计数 | 与上一条命令分开发送，中间可能被其他请求改写；更麻烦的是 key 不存在时，它只数得到刚加进去的那一个成员 |
| `ctx` 贯穿每个调用 | 传递取消与超时 | Redis 命令也要能随请求取消 |

这段只用来认识命令形状。4.3.1 会说明为什么本项目不让 `SCARD` 参与 `like_count`，以及为了让它可信得付出什么代价。先记住问题，别急着改。

### 1.3 点赞数怎么和 MySQL 保持一致

Redis 通常把数据放在内存中，能否在重启后恢复取决于 AOF、RDB 等配置。即使开启持久化，也要考虑故障切换和数据回写。若 MySQL 是点赞数的持久化来源，需要定义同步策略。

| 方案 | 做法 | 边界 |
| --- | --- | --- |
| 定时回写 | 每分钟把 `SCARD` 结果写进 `articles.like_count` | 任务失败或 Redis 数据丢失会让计数回退 |
| 读时拼接 | 读详情时实时从 Redis 取计数 | 每次读都依赖 Redis 可用 |
| 派生缓存 | MySQL 关系表为事实来源，Redis 保存可重建的投影 | 要设计重建与失败重试 |

只有在实现可靠的异步回写、失败重试和恢复流程后，才能声称计数最终一致。单纯「每分钟读 SCARD 再写回」缺少这些保证。

### 1.4 本教程采用的方案

MySQL 点赞关系表作为事实来源，Redis 只保存一份可重建的「哪些用户点过赞」集合投影，计数始终以 MySQL 为准。新增 `article_likes` 表，包含 `article_id`、`user_id`、`created_at`，联合唯一索引 `(article_id, user_id)`。点赞用数据库唯一约束保证幂等，取消按两列条件删除。数据库成功后才更新 Redis，Redis 更新失败时保留数据库结果、记录日志，并允许从 MySQL 重建。已经提交的 MySQL 写入无法靠「回滚」来假装两边原子一致。

严格保证「数据库写入后 Redis 更新最终必达」需要 transactional outbox。在同一 MySQL 事务里写点赞关系和 outbox 事件，再由可重试 worker 投影到 Redis。本章不实现 outbox，所以把 Redis 集合明确标成可丢失的派生缓存，并说明写后读可能短暂延迟。「更新两次」算不上事务，也谈不上 exactly once。

`model.Article.LikeCount` 已经存在，但仓库里没有任何代码维护这一列。前九步**不给它赋值**。理由有两层：热榜 v1 直接从 `article_likes` 用 `GROUP BY` 算，唯一事实来源只有一份；在点赞事务里 `UPDATE articles SET like_count = ...` 会引入第三份需要对齐的数据，排查问题时又多一个变量。

4.10 步会让详情显示点赞数，那时也**只把它当内存载体**：`queryDetail` 回源时把 `COUNT(*)` 的结果装进这个字段，随文章一起写进缓存，数据库列仍然永远是 0。字段存在不等于事实来源。等 05 章做性能打磨时，再按「要不要冗余列」单独决定。

还有一处跨章节约束，**本轮已经兑现**。03a 章 7.4 写着「04 章点赞如果改动详情响应里的 `like_count`，点赞成功后要删文章详情缓存」。前九步把计数放在 `likeResp`，`articleResp` 本身不加 `like_count`，详情缓存不受点赞影响。第 10 步因为要在文章详情里显示点赞数，另建 `articleDetailResp` 把计数接进详情缓存，同时让 `ArticleService` 的缓存失效方法变成导出的 `InvalidateDetailCache`，由 `LikeService` 在点赞与取消成功后调用，03a 章 7.4 的那一行也改成已补。完整推演见 4.10，4.4 步末尾还有一次提醒。

### 1.5 点赞 API 的行为

路由放进 `JWTAuth` 组。`PUT /api/articles/:id/like` 点赞，`DELETE /api/articles/:id/like` 取消。当前用户只能从 JWT context 取得，请求体为空，客户端伪造的 `user_id` 没有落点。重复点赞与重复取消都返回成功，目标文章不存在返回 404。Service 返回关系是否发生变化与最终计数，handler 不直接访问 Redis 或数据库。

## 2. 热榜：先想清楚排序从哪来

### 2.1 为什么用 ZSET，以及为什么先用 GROUP BY

Sorted Set 的每个成员带一个 score，支持按分数排序和取前 N 名，契合热榜的形状。设计上 key 为 `hot:articles:v1`，成员为文章 id，score 为点赞数。

ZSET 只负责按 score 排序，它不会自动计算热度，也不会自动让新文章加分。要先选定明确的评分规则。否则旧文章的累计分数会一直压过新文章。

这里有个容易跳过的起步问题。点赞关系已经存在 MySQL，最直接的正确榜单就是 `SELECT article_id, COUNT(*) FROM article_likes GROUP BY article_id ORDER BY 分数 DESC LIMIT n`。它慢，但它一定对。先用它建立可核对的基准，再换 ZSET，才能验证投影有没有算错。若一上来就写 ZSET，Redis 为空时接口返回空列表，你分不清是「没人点赞」还是「投影没初始化」。

### 2.2 概念伪代码：ZSET 操作

下面代码展示 ZSET 命令，缺少文章批量回查、事件幂等、清理和重建，不能直接作为完整热榜 API。

**概念伪代码**：只用于观察命令形状，不要复制进项目。

```go
package service

import (
	"context"
	"fmt"
	"strconv"

	"github.com/redis/go-redis/v9"
)

type HotService struct {
	rdb *redis.Client
}

const hotKey = "hot:articles"

func (s *HotService) AddScore(ctx context.Context, articleID uint, delta float64) error {
	return s.rdb.ZIncrBy(ctx, hotKey, delta, strconv.FormatUint(uint64(articleID), 10)).Err()
}

func (s *HotService) Top(ctx context.Context, n int) ([]uint, error) {
	if n < 1 || n > 100 {
		return nil, fmt.Errorf("invalid top n %d: want 1..100", n)
	}
	vals, err := s.rdb.ZRevRange(ctx, hotKey, 0, int64(n-1)).Result()
	if err != nil {
		return nil, err
	}
	ids := make([]uint, 0, len(vals))
	for _, v := range vals {
		id, err := strconv.ParseUint(v, 10, 64)
		if err != nil {
			return nil, fmt.Errorf("parse article id %q: %w", v, err)
		}
		ids = append(ids, uint(id))
	}
	return ids, nil
}
```

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `ZIncrBy` | 给成员加分 | 单条命令原子，但增量写法要求分数起点正确；Redis 为空时会算错，4.6 步改用 `ZAdd` 写绝对值 |
| `if n < 1 \|\| n > 100` | 拒绝非法 N 并限制上限 | 范围校验集中在 service 一处，handler 只做字符串转整数 |
| `ZRevRange(..., 0, int64(n-1))` | 从高到低取闭区间 | 旧文档写 `ZREVRANGE key 0 N` 会多取一个成员，Redis 区间两端都包含 |
| `ParseUint` 并检查错误 | 把字符串 id 转回 uint | member 由本程序写入，这里只留最基本的转换错误检查 |
| `make([]uint, 0, len(vals))` | 长度 0、容量预分配 | 避免零值元素，也避免多次扩容 |

核心命令：

| 命令 | 作用 |
| --- | --- |
| `ZADD key score member` | 写入绝对分数，重复写会覆盖 |
| `ZINCRBY key delta member` | 在现有分数上累加 |
| `ZREVRANGE key 0 (N-1)` | 按分数从高到低取前 N 个成员 |
| `ZREM key member` | 删除指定的一个成员 |
| `ZREMRANGEBYSCORE key min max` | 按分数区间删除成员 |

ZSET 的插入与更新通常为 O(log N)，按排名取区间通常为 O(log N + M)。来源见 https://redis.io/docs/latest/develop/data-types/sorted-sets/ 。是否优于 MySQL 取决于数据规模、索引和访问量，笼统说 MySQL 每次都全表扫描并不准确。

### 2.3 从事件到响应的完整链路

1. 点赞、文章发布等业务在 MySQL 成功后产生热度事件，事件至少包含类型、文章 id、发生时间和幂等事件 id。
2. 消费事件时用 `ZINCRBY` 增分，重试时用事件 id 去重，一次业务重试不能重复加分。本章实现不走这条链路，改用 `ZADD` 写绝对值，理由见 4.6.3。
3. 定义评分公式、事件权重、统计窗口和时间衰减。公式变更要重建 ZSET，别把不同版本的分数混在一起。
4. 读取 Top N 时校验 `1 <= N <= 100`，先取 ID 再批量从 MySQL 加载文章。数据库返回顺序可能与 Redis 不同，要按 Redis 的 ID 顺序重排，并过滤已删除文章。
5. Redis 重启或数据清理后，从 MySQL 或事件表重建热榜。重建要由读路径自己发现并触发，不能等运维跑脚本。未实现自动重建前，这只能叫临时排行榜。

本章的 v2 只做第 4 条的形状，v3 做第 5 条，做法是读路径懒加载自愈：服务启动不查库，第一次读发现投影没建好才回源一次。第 1 到第 3 条里的事件表、幂等 id、时间衰减都列在 4.7.6 的边界里，不假装已经实现。

ZSET 直接累计分数不会自动过期或衰减。「按时间清理老文章」与 `ZREMRANGEBYSCORE` 之间还隔着一层语义差异。该命令按 score 区间删除成员，而本项目 score 是点赞数，按分数区间删会误删高赞文章。按发布时间清理要另建以时间戳为 score 的索引，或维护文章发布时间表再计算待移除成员。此外还要定义过期条件、执行者和失败重试。

### 2.4 三版分别解决什么

| 版本 | 落盘小节 | 这一版新增 | 这一版还留下的问题 |
| --- | --- | --- | --- |
| v1 | 4.5 | GROUP BY 算 Top N，批量回查文章，双重校验 N | 每次请求都做聚合，数据量上去会慢 |
| v2 | 4.6 | `ZADD` 写分数绝对值，Top 从 ZSET 取 ID 再按序回查 | 靠空榜回源，分不清空榜与投影丢失，全榜补齐要跑脚本 |
| v3 | 4.7 | `ready` 标记判空、`singleflight` 合并重建、空榜不回源、删掉手动脚本、评分边界 | 事件幂等、时间衰减、权重版本、旧值自愈未实现 |

## 3. 限流：先想清楚统计口径

### 3.1 为什么限流

登录、发帖这类接口可能被脚本频繁调用。限流在指定统计范围内控制请求速率，实现前先明确按用户、IP、路由还是全局统计。反向代理之后不能盲目信任客户端提交的 `X-Forwarded-For`，只信任自己配置的代理网段。超限通常返回 HTTP 429。

### 3.2 常见算法

| 算法 | 原理 | 特点 |
| --- | --- | --- |
| 固定窗口 | 每分钟最多 N 次 | 简单，窗口边界会瞬间双倍放行 |
| 滑动窗口 | 统计最近 N 秒 | 比固定窗口准，Redis 用 ZSET 可实现 |
| 令牌桶 | 按速率补令牌，有令牌才放行 | 允许一定突发，Web 服务常见选择 |
| 漏桶 | 请求排队后按固定速率流出 | 输出平滑，代价是排队延迟 |

旧版写「令牌桶最常用」属于无依据的绝对化表述，已删。

### 3.3 概念伪代码：一个反例

下面这段用于识别不完整实现，不能运行。`DECRBY` 只适用于整数，令牌计算含小数，时间单位、key 过期、浮点精度和异常处理都没有定义。

**概念伪代码**：明显标记不能运行，只用来练眼力。

```lua
-- 参数 KEYS[1]=key，ARGV[1]=容量，ARGV[2]=每秒补充数，ARGV[3]=当前时间
local key   = KEYS[1]
local limit = tonumber(ARGV[1])
local rate  = tonumber(ARGV[2])
local now   = tonumber(ARGV[3])

local tokens = tonumber(redis.call('get', key) or limit)
tokens = math.min(tokens + (now - (redis.call('get', key..':time') or now)) * rate, limit)
redis.call('set', key, tokens)
redis.call('set', key..':time', now)

if tokens >= 1 then
    redis.call('decrby', key, 1)
    return 1
else
    return 0
end
```

四个具体毛病。令牌数含小数却用 `DECRBY`。没有 `PEXPIRE`，空闲 key 永不清理。用客户端传的 `now`，多个应用实例时钟不一致。`get` 与 `set` 分两步，中间没有原子性保证。

### 3.4 令牌桶的原理，以及脚本放在哪

4.9 步会给完整可用的 Lua 与 Go 包装层。这里先把原理说清，免得照抄代码却不知道每行在防什么。

脚本用 Redis `TIME` 统一时钟，Hash 保存 `tokens` 与 `last_ms`，计算 `tokens = min(capacity, tokens + max(0, now - last_ms) * rate / 1000)`。有至少 1 个 token 时扣 1 并返回放行，否则返回拒绝和等待毫秒，最后给 key 设置大于补满时间的 TTL。Go 包装层校验 `capacity > 0` 与 `rate > 0`，解析脚本返回值，设置 `Retry-After`，并明确 Redis 错误时 fail open 或 fail closed。

脚本源码放在 Go 文件里的原始字符串常量，由 `redis.NewScript` 加载。这里有个取舍。单独存成 `.lua` 文件要用 `os.ReadFile` 或 `//go:embed`，部署时得多带一个文件，路径写错只在运行时报错。放进 Go 常量后，脚本和实现同在一个文件，编译期就能确定内容，`go build` 出来的二进制自带脚本。代价是 Lua 语法错误只能在真实 Redis 上跑出来，所以 4.9 步会配一条不连 Redis 的常量校验单测，以及一份需要真实 Redis 的验收清单。

`redis.NewScript` 内部先算 SHA-1 走 `EVALSHA`，Redis 返回 `NOSCRIPT` 时自动退化成 `EVAL`。来源见 go-redis v9.23.0 `script.go` 的 `Run` 实现，以及 https://redis.io/docs/latest/develop/interact/programmability/eval-intro/ 。

### 3.5 限流身份、代理与配置边界

登录与注册尚无 userID，通常按客户端 IP 限流，已登录写接口可按 `userID + route` 限流。本章把限流挂在 `api` 组，位置在 `JWTAuth` 之前，所以拿不到 userID，只能按 IP 全局共用一个桶。要按用户分桶，把 `api.Use(RateLimit(...))` 挪到 `auth` 组里，属于 4.9 步之后的改进方向。

反向代理环境只信任明确配置的代理网段。未经配置的 `X-Forwarded-For` 可以被客户端伪造，别直接取第一个逗号前的字符串当真实 IP。4.8 步会在 `router.New` 里调 `SetTrustedProxies(nil)`，让 `c.ClientIP()` 退回 RemoteAddr。

key 包含环境、应用和身份，例如 `forum:dev:rate:ip:127.0.0.1`，避免开发与生产共用 Redis 时撞 key。别把密码、token 或完整用户名放进 key 或日志。设置 key TTL，明确 `Retry-After` 的单位和取整，限制 key 长度，避免 key 注入和内存滥用。分布式限流要求所有实例共享同一 Redis，本机内存计数器只覆盖单进程。

### 3.6 两版分别解决什么

| 版本 | 落盘小节 | 这一版新增 | 这一版还留下的问题 |
| --- | --- | --- | --- |
| v1 | 4.8 | INCR 与 EXPIRE 合成 Lua，429 与 `Retry-After`，启动期参数校验 | 窗口边界会双倍放行，无法允许突发 |
| v2 | 4.9 | 令牌桶 Lua，TIME 统一时钟，Hash 存状态，按速率恢复 | 全局按 IP 单桶，代理信任与分桶策略仍可细化 |

```go
		return nil, errors.New("router: Redis client is required")
	}

	r := gin.Default()

	userSvc := service.NewUserService(db)
	userHandler := handler.NewUserHandler(userSvc, jwtManager)

	articleSvc := service.NewArticleService(db, rdb)
	commentSvc := service.NewCommentService(db)
	articleHandler := handler.NewArticleHandler(articleSvc)
	commentHandler := handler.NewCommentHandler(commentSvc)

	// 第 3 周新增的两个 service，共用一个 redis.Client。
	likeSvc := service.NewLikeService(db, rdb)
	hotSvc := service.NewHotService(db, rdb)
	likeHandler := handler.NewLikeHandler(likeSvc, hotSvc)

	rateCfg := middleware.RateLimitConfig{
		Capacity:  10,
		Rate:      2,
		KeyPrefix: "forum:dev:rate:",
	}

	api := r.Group("/api")
	api.Use(limitBody(1 << 20)) // 1 MiB
	api.Use(middleware.RateLimit(rdb, rateCfg))
	{
		api.POST("/register", userHandler.Register)
		api.POST("/login", userHandler.Login)

		// 读接口公开，不挂 JWTAuth。
		api.GET("/articles", articleHandler.List)
		api.GET("/articles/:id", articleHandler.Detail)
		api.GET("/articles/:id/comments", commentHandler.List)
		// 静态段 hot 与通配段 :id 同层，0.7 节实测静态优先。
		api.GET("/articles/hot", likeHandler.Hot)

		auth := api.Group("", middleware.JWTAuth(jwtManager))
		{
			auth.POST("/articles", articleHandler.Create)
			auth.DELETE("/articles/:id", articleHandler.Delete)
			auth.POST("/articles/:id/comments", commentHandler.Create)
			auth.DELETE("/comments/:id", commentHandler.Delete)
```

### 4.2 第 2 步：点赞 v1，先把 MySQL 事实来源做对

这一版完全不碰 Redis。目标只有一个，重复点赞在数据库里只留一行，任何情况下计数都能从 `COUNT(*)` 核对出来。

#### 4.2.1 先想清楚四个输入和一个顺序

| 输入 | 从哪来 | 客户端能不能改 |
| --- | --- | --- |
| 文章 id | URL 路径 `:id`，`ParseUint` 转数字 | 能指定点哪篇，不能塞 SQL 片段 |
| 用户 id | `currentUserID(c)`，来自 JWT | 不能。请求体为空，没有字段可伪造 |
| 关系是否存在 | MySQL 联合唯一索引 | 不能，由数据库判定 |
| 文章是否存在 | MySQL `COUNT` | 不能 |

顺序上先确认文章存在，再写关系。理由有两条。给不存在的文章点赞应该返回 404，这个判断要在写之前做。若先写后查，会先插进一条孤立关系，再回滚，白白占用一次唯一索引冲突判断。

**为什么不先查「有没有点过赞」再决定插不插**。两个并发请求可能同时查到「没点过」，然后同时插，数据库唯一索引会让第二个失败。这个失败是好事，它保证了幂等。但代码里若把「先查再插」当成幂等手段，就会在并发下随机报 500。本版直接插入，把唯一键冲突当成「已经点过」，一条 SQL 完成判断。

```go
package model

import "time"

// ArticleLike 一条点赞关系。
// 用自增 ID 加联合唯一索引，没有把两列做成复合主键。
// GORM 对复合主键的自增处理有额外规则，学习阶段先用最直白的形状。
type ArticleLike struct {
	ID        uint      `gorm:"primaryKey" json:"id"`
	ArticleID uint      `gorm:"not null;uniqueIndex:uk_article_user,priority:1" json:"article_id"`
	UserID    uint      `gorm:"not null;uniqueIndex:uk_article_user,priority:2" json:"user_id"`
	CreatedAt time.Time `json:"created_at"`

	// Article 只用来让 AutoMigrate 建外键，不参与 JSON 序列化。
	// RESTRICT 与 03 章 6.2 定下的策略一致：
	// 删文章前必须先清掉子表，不许数据库悄悄级联。
	Article Article `gorm:"constraint:OnUpdate:NO ACTION,OnDelete:RESTRICT;" json:"-"`
}
```

`uniqueIndex:uk_article_user,priority:1` 里的 `priority` 决定联合索引里列的先后顺序。两列写同一个索引名，GORM 会生成一条 `UNIQUE KEY uk_article_user (article_id, user_id)`。这条索引就是幂等的最终保证。

```go
package service

import (
	"context"
	"errors"
	"fmt"

	"github.com/redis/go-redis/v9"
	"gorm.io/gorm"

	"forum-backend/internal/model"
)

// LikeService 处理点赞。
// v1 只用 db，rdb 字段先放着，4.3 步才启用。
type LikeService struct {
	db  *gorm.DB
	rdb *redis.Client
}

func NewLikeService(db *gorm.DB, rdb *redis.Client) *LikeService {
	return &LikeService{db: db, rdb: rdb}
}

// LikeResult 是一次点赞或取消之后交给 handler 的结论。
// Changed 表示这次调用有没有改变关系，重复调用会是 false。
type LikeResult struct {
	ArticleID uint  `json:"article_id"`
	Count     int64 `json:"like_count"`
	Changed   bool  `json:"changed"`
	Liked     bool  `json:"liked"`
}

// articleExists 确认文章还在。用 COUNT 而不是 First，
// 因为这里只需要一个布尔结论，不需要把整行读出来。
func (s *LikeService) articleExists(ctx context.Context, articleID uint) error {
	var count int64
	err := s.db.WithContext(ctx).Model(&model.Article{}).
		Where("id = ?", articleID).Count(&count).Error
	if err != nil {
		return fmt.Errorf("check article %d: %w", articleID, err)
	}
	if count == 0 {
		// 转成项目内部的错误，handler 的 mapServiceError 会映射成 404。
		return fmt.Errorf("article %d: %w", articleID, ErrNotFound)
	}
	return nil
}

// Like 点赞。重复调用幂等。
func (s *LikeService) Like(ctx context.Context, articleID, userID uint) (LikeResult, error) {
	if err := s.articleExists(ctx, articleID); err != nil {
		return LikeResult{}, err
	}

	row := &model.ArticleLike{ArticleID: articleID, UserID: userID}
	err := s.db.WithContext(ctx).Create(row).Error
	changed := true
	if err != nil {
		// TranslateError 在 config.InitDB 里已开启，
		// MySQL 的 1062 会被 GORM 翻成 gorm.ErrDuplicatedKey。
		if errors.Is(err, gorm.ErrDuplicatedKey) {
			changed = false
		} else {
			return LikeResult{}, fmt.Errorf("insert article like: %w", err)
		}
	}

	count, err := s.countLikes(ctx, articleID)
	if err != nil {
		return LikeResult{}, err
	}
	return LikeResult{
		ArticleID: articleID,
		Count:     count,
		Changed:   changed,
		Liked:     true,
	}, nil
}

// Unlike 取消点赞。关系本来就不存在时算成功，计数不会变成负数。
func (s *LikeService) Unlike(ctx context.Context, articleID, userID uint) (LikeResult, error) {
	if err := s.articleExists(ctx, articleID); err != nil {
		return LikeResult{}, err
	}

	res := s.db.WithContext(ctx).
		Where("article_id = ? AND user_id = ?", articleID, userID).
		Delete(&model.ArticleLike{})
	if res.Error != nil {
		return LikeResult{}, fmt.Errorf("delete article like: %w", res.Error)
	}

	count, err := s.countLikes(ctx, articleID)
	if err != nil {
		return LikeResult{}, err
	}
	return LikeResult{
		ArticleID: articleID,
		Count:     count,
		Changed:   res.RowsAffected > 0,
		Liked:     false,
	}, nil
}

// countLikes 从唯一事实来源数一遍。
func (s *LikeService) countLikes(ctx context.Context, articleID uint) (int64, error) {
	var count int64
	err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
		Where("article_id = ?", articleID).Count(&count).Error
	if err != nil {
		return 0, fmt.Errorf("count article likes %d: %w", articleID, err)
	}
	return count, nil
}

// HasLiked 判断某用户是否点过赞，给以后的详情接口用。
func (s *LikeService) HasLiked(ctx context.Context, articleID, userID uint) (bool, error) {
	var count int64
	err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
		Where("article_id = ? AND user_id = ?", articleID, userID).
		Count(&count).Error
	if err != nil {
		return false, fmt.Errorf("check article like: %w", err)
	}
	return count > 0, nil
}
```

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `Create(row)` 直接插 | 一步完成幂等写入 | 先查再插在并发下会两边都判断为「没点过」 |
| `errors.Is(err, gorm.ErrDuplicatedKey)` | 把唯一键冲突当成功 | 重复调用与首次调用对客户端返回同一个形状 |
| `changed = false` | 告诉调用方这次没改变关系 | 验收时用它区分「真点赞」和「重复点赞」 |
| `Where("article_id = ? AND user_id = ?")` | 删除只带两列条件 | 不需要先查出来再删，也没有越权删除别人的关系 |
| `RowsAffected > 0` | 判断是否真的删掉一行 | 重复取消返回 `changed=false`，计数不动 |
| `articleExists` 先跑 | 给不存在的文章返回 404 | 写在插入之前，避免出现孤立关系 |
| `fmt.Errorf("%w", ErrNotFound)` | 用项目内部错误 | `mapServiceError` 已认识它，不用改 handler |

#### 4.3.1 先问「谁会读它」，再决定缓存什么

v1 的计数来自 `COUNT(*)`，每次点赞都查一次库。很自然会想到「把点赞集合放进 Redis，用 `SCARD` 代替 `COUNT(*)`」。动手前先把这笔账算完。

`SCARD` 要能当计数用，集合必须始终完整。可 key 会不存在：服务重启、Redis 清空、key 过期，甚至只是这篇文章半小时没人点赞。key 不存在时 `SADD` 会创建一个只含当前用户的集合，`SCARD` 返回 1，而 MySQL 里可能已经有 50 条关系。为了让它可信，就得配上 `EXISTS` 判定、空集合歧义处理、TTL、失败降级、单篇重建、删除清理和重建脚本。每加一层都是新的出错点，而且这些兜底全是为了修自己刚引入的问题。

更关键的是，把项目的读链路从头查一遍后，**这份计数没有业务消费者**。判断当前用户是否点过赞走 `HasLiked`（查 MySQL），热榜走独立的 `hot:articles:v1` ZSET，唯一会读 `SCARD` 的就是这条准备新增的计数路径本身。为一个没有读者的数字引入一整套一致性机制，代价是倒挂的。

所以这一版换个目标：Redis Set **只记录哪些用户点过赞**，给 `HasLiked` 用；`like_count` 仍然只认 MySQL `COUNT(*)`。集合少几个成员不会让计数出错，`HasLiked` 遇到 miss 回源一次就能补齐。

| 决定 | 理由 |
| --- | --- |
| 计数仍用 `countLikes` | 唯一事实来源只有一份，冷启动、重启、清空都不会算错 |
| 不设 TTL | key 一旦建立就由每次写入维护，人为过期反而周期性制造空投影 |
| 不写 `EXISTS` 与 `SCARD` 读路径 | 没有读者，写了就是死代码 |
| `HasLiked` 用 `SIsMember` + miss 回源 | key 不存在是常规状态（新文章没人赞），不是故障 |

`COUNT(*)` 走 `uk_article_user (article_id, user_id)` 的索引前缀，成本很低。等真的出现热点、并且有真实读流量时，再回来讨论要不要给计数单独加缓存，那时基准和压测数据都在。

```go
package service

import (
	"context"
	"errors"
	"fmt"
	"log"
	"strconv"

	"github.com/redis/go-redis/v9"
	"gorm.io/gorm"

	"forum-backend/internal/model"
)

// likeSetKeyPrefix 带 v1 版本号。以后改投影结构就换版本号，
// 老 key 没人再读会自然被淘汰，不用半夜跑脚本批量清理。
const likeSetKeyPrefix = "article:like:v1:"

func likeSetKey(articleID uint) string {
	return likeSetKeyPrefix + strconv.FormatUint(uint64(articleID), 10)
}

type LikeService struct {
	db  *gorm.DB
	rdb *redis.Client
}

func NewLikeService(db *gorm.DB, rdb *redis.Client) *LikeService {
	return &LikeService{db: db, rdb: rdb}
}

type LikeResult struct {
	ArticleID uint  `json:"article_id"`
	Count     int64 `json:"like_count"`
	Changed   bool  `json:"changed"`
	Liked     bool  `json:"liked"`
}

func (s *LikeService) articleExists(ctx context.Context, articleID uint) error {
	var count int64
	err := s.db.WithContext(ctx).Model(&model.Article{}).
		Where("id = ?", articleID).Count(&count).Error
	if err != nil {
		return fmt.Errorf("check article %d: %w", articleID, err)
	}
	if count == 0 {
		return fmt.Errorf("article %d: %w", articleID, ErrNotFound)
	}
	return nil
}

// syncLikeSet 把刚提交的关系投影到 Redis Set。
// 它只记录成员，不参与计数。数据库已经提交，
// 这里失败只记日志，不能把成功的点赞报成失败。
// 不设 TTL：key 由每次写入持续维护，人为过期只会制造空投影。
func (s *LikeService) syncLikeSet(ctx context.Context, articleID, userID uint, add bool) {
	key := likeSetKey(articleID)
	member := strconv.FormatUint(uint64(userID), 10)
	var err error
	if add {
		err = s.rdb.SAdd(ctx, key, member).Err()
	} else {
		err = s.rdb.SRem(ctx, key, member).Err()
	}
	if err != nil {
		log.Printf("sync like set %s: %v", key, err)
	}
}

func (s *LikeService) Like(ctx context.Context, articleID, userID uint) (LikeResult, error) {
	if err := s.articleExists(ctx, articleID); err != nil {
		return LikeResult{}, err
	}

	row := &model.ArticleLike{ArticleID: articleID, UserID: userID}
	err := s.db.WithContext(ctx).Create(row).Error
	changed := true
	if err != nil {
		if errors.Is(err, gorm.ErrDuplicatedKey) {
			changed = false
		} else {
			return LikeResult{}, fmt.Errorf("insert article like: %w", err)
		}
	}

	s.syncLikeSet(ctx, articleID, userID, true)

	count, err := s.countLikes(ctx, articleID)
	if err != nil {
		return LikeResult{}, err
	}
	return LikeResult{
		ArticleID: articleID,
		Count:     count,
		Changed:   changed,
		Liked:     true,
	}, nil
}

func (s *LikeService) Unlike(ctx context.Context, articleID, userID uint) (LikeResult, error) {
	if err := s.articleExists(ctx, articleID); err != nil {
		return LikeResult{}, err
	}

	res := s.db.WithContext(ctx).
		Where("article_id = ? AND user_id = ?", articleID, userID).
		Delete(&model.ArticleLike{})
	if res.Error != nil {
		return LikeResult{}, fmt.Errorf("delete article like: %w", res.Error)
	}

	s.syncLikeSet(ctx, articleID, userID, false)

	count, err := s.countLikes(ctx, articleID)
	if err != nil {
		return LikeResult{}, err
	}
	return LikeResult{
		ArticleID: articleID,
		Count:     count,
		Changed:   res.RowsAffected > 0,
		Liked:     false,
	}, nil
}

func (s *LikeService) countLikes(ctx context.Context, articleID uint) (int64, error) {
	var count int64
	err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
		Where("article_id = ?", articleID).Count(&count).Error
	if err != nil {
		return 0, fmt.Errorf("count article likes %d: %w", articleID, err)
	}
	return count, nil
}

// HasLiked 先问投影，miss 时回源 MySQL。
// key 不存在是常规状态（新文章没人赞），不是故障。
// 回源后把确实存在的关系补进 Set，下次同一用户就能命中。
func (s *LikeService) HasLiked(ctx context.Context, articleID, userID uint) (bool, error) {
	key := likeSetKey(articleID)
	member := strconv.FormatUint(uint64(userID), 10)
	hit, err := s.rdb.SIsMember(ctx, key, member).Result()
	if err == nil && hit {
		return true, nil
	}
	if err != nil {
		log.Printf("check like set %s: %v", key, err)
	}

	var count int64
	if err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
		Where("article_id = ? AND user_id = ?", articleID, userID).
		Count(&count).Error; err != nil {
		return false, fmt.Errorf("check article like: %w", err)
	}
	if count > 0 {
		if err := s.rdb.SAdd(ctx, key, member).Err(); err != nil {
			log.Printf("repair like set %s: %v", key, err)
		}
	}
	return count > 0, nil
}
```

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `likeSetKeyPrefix` 带 `v1` | key 版本化 | 改结构时换版本号，老 key 自然被淘汰 |
| `syncLikeSet` 无返回值、不设 TTL | 失败只记日志，key 不过期 | 数据库已提交不能报成失败；人为过期会周期性制造空投影 |
| 两处 `member` 都用 `FormatUint` | 写入与查询用同一种字符串 | 显式写清楚，不用猜 go-redis 怎么转 `uint` |
| `Count` 仍来自 `countLikes` | 计数只有一份事实来源 | 集合少几个成员也不会让响应算错 |
| `SIsMember` + miss 回源 | 投影只做加速 | key 不存在是常规状态，回源一次并补成员 |

#### 4.3.6 这一版留下的问题

第一，`Like` 与 `Unlike` 里「确认文章存在、写数据库、同步投影、数一遍」四步几乎逐字重复。下一步把它们收成一个方法。

第二，`syncLikeSet` 与 `countLikes` 之间仍是两次独立操作，投影可能短暂落后。因为 `HasLiked` 会回源、`like_count` 不读投影，这个窗口不会造成错误结果，只影响 `SMEMBERS` 的观测值。

第三，删文章时只清了 MySQL 关系，Redis 里的 `article:like:v1:{id}` 还留着。4.6 步补清理。

第四，`HasLiked` 本章还没有 HTTP 调用方，等 05 章做详情接口时接上。它不是死代码，但现阶段只有单测和未来接口会读它。

### 4.4 第 4 步：点赞 v3，把两处重复写入收成一个方法

这一版仍然只改 `internal/service/like.go`。

#### 4.4.1 为什么改，以及为什么不用 Lua

v2 里 `Like` 和 `Unlike` 除了「插入还是删除」以外几乎逐字相同。两个方法各写一遍「确认文章存在、写数据库、同步投影、数一遍」，以后多一个写路径就得再抄一遍；漏掉一步不会编译报错，只会在运行时表现不一致。这一版把共同流程收进 `apply`，两个公开方法各剩一行。

原先这一节打算「用 Lua 把 `SADD` 与 `SCARD` 合成一次原子调用，解决两条命令之间的瞬时值」。这一版把它删掉，理由要写清楚：`SCARD` 已经不参与计数，合成它没有收益；而为了让 `SCARD` 可信所配的 `EXISTS`、TTL、降级、重建，正是 4.3.1 算过账的那一整套代价。为了一个没有读者的数字引入脚本，属于为了修自己制造的问题继续加代码。

**Lua 没有从本章消失**。4.8 步的固定窗口、4.9 步的令牌桶都要靠它把「读状态、改状态、设过期」合成一次原子执行，那里有真实的并发问题要解决。判断标准始终一样：先看有没有必须原子的多步操作，再决定用不用脚本。

这一步也顺带修掉一个容易写错的地方。v1、v2 里 `Liked` 在两个方法中分别硬编码成 `true` 和 `false`，收成一个方法后由 `add` 直接给出，不会再出现「取消点赞却返回 `liked=true`」这类复制粘贴错误。

#### 4.4.2 与上一版相比改了哪几行

| 位置 | 改动 |
| --- | --- |
| 新增 | `apply` 收拢四步流程，`writeRelation` 只处理数据库写入 |
| `Like` / `Unlike` | 各缩成一行 `return s.apply(...)` |
| 删掉 | 两个方法里重复的 `articleExists`、`syncLikeSet`、`countLikes` 调用与两处硬编码 `Liked` |
| 保持不变 | `syncLikeSet`、`countLikes`、`HasLiked`、`articleExists`、`LikeResult`、所有常量、对外签名 |

`Like` 与 `Unlike` 的函数签名一个字没改，所以 `handler`、`router`、DTO 都不用动。

```go
import (
	"context"
	"errors"
	"fmt"
	"log"
	"strconv"

	"github.com/redis/go-redis/v9"
	"gorm.io/gorm"

	"forum-backend/internal/model"
)

const likeSetKeyPrefix = "article:like:v1:"

func likeSetKey(articleID uint) string {
	return likeSetKeyPrefix + strconv.FormatUint(uint64(articleID), 10)
}

type LikeService struct {
	db  *gorm.DB
	rdb *redis.Client
}

func NewLikeService(db *gorm.DB, rdb *redis.Client) *LikeService {
	return &LikeService{db: db, rdb: rdb}
}

type LikeResult struct {
	ArticleID uint  `json:"article_id"`
	Count     int64 `json:"like_count"`
	Changed   bool  `json:"changed"`
	Liked     bool  `json:"liked"`
}

func (s *LikeService) Like(ctx context.Context, articleID, userID uint) (LikeResult, error) {
	return s.apply(ctx, articleID, userID, true)
}

func (s *LikeService) Unlike(ctx context.Context, articleID, userID uint) (LikeResult, error) {
	return s.apply(ctx, articleID, userID, false)
}

// apply 是点赞与取消共用的流程：确认文章存在、写数据库、同步投影、数一遍。
// add 决定这次是插入还是删除，也直接决定响应里的 Liked。
func (s *LikeService) apply(ctx context.Context, articleID, userID uint, add bool) (LikeResult, error) {
	if err := s.articleExists(ctx, articleID); err != nil {
		return LikeResult{}, err
	}

	changed, err := s.writeRelation(ctx, articleID, userID, add)
	if err != nil {
		return LikeResult{}, err
	}

	s.syncLikeSet(ctx, articleID, userID, add)

	count, err := s.countLikes(ctx, articleID)
	if err != nil {
		return LikeResult{}, err
	}
	return LikeResult{
		ArticleID: articleID,
		Count:     count,
		Changed:   changed,
		Liked:     add,
	}, nil
}

// writeRelation 只负责数据库写入，返回这次有没有真的改动一行。
func (s *LikeService) writeRelation(ctx context.Context, articleID, userID uint, add bool) (bool, error) {
	if add {
		row := &model.ArticleLike{ArticleID: articleID, UserID: userID}
		err := s.db.WithContext(ctx).Create(row).Error
		if err == nil {
			return true, nil
		}
		// 唯一键冲突说明这个用户已经点过赞，当成成功，不改动关系。
		if errors.Is(err, gorm.ErrDuplicatedKey) {
			return false, nil
		}
		return false, fmt.Errorf("insert article like: %w", err)
	}

	res := s.db.WithContext(ctx).
		Where("article_id = ? AND user_id = ?", articleID, userID).
		Delete(&model.ArticleLike{})
	if res.Error != nil {
		return false, fmt.Errorf("delete article like: %w", res.Error)
	}
	return res.RowsAffected > 0, nil
}

func (s *LikeService) articleExists(ctx context.Context, articleID uint) error {
	var count int64
	err := s.db.WithContext(ctx).Model(&model.Article{}).
		Where("id = ?", articleID).Count(&count).Error
	if err != nil {
		return fmt.Errorf("check article %d: %w", articleID, err)
	}
	if count == 0 {
		return fmt.Errorf("article %d: %w", articleID, ErrNotFound)
	}
	return nil
}

func (s *LikeService) syncLikeSet(ctx context.Context, articleID, userID uint, add bool) {
	key := likeSetKey(articleID)
	member := strconv.FormatUint(uint64(userID), 10)
	var err error
	if add {
		err = s.rdb.SAdd(ctx, key, member).Err()
	} else {
		err = s.rdb.SRem(ctx, key, member).Err()
	}
	if err != nil {
		log.Printf("sync like set %s: %v", key, err)
	}
}

func (s *LikeService) countLikes(ctx context.Context, articleID uint) (int64, error) {
	var count int64
	err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
		Where("article_id = ?", articleID).Count(&count).Error
	if err != nil {
		return 0, fmt.Errorf("count article likes %d: %w", articleID, err)
	}
	return count, nil
}

func (s *LikeService) HasLiked(ctx context.Context, articleID, userID uint) (bool, error) {
	key := likeSetKey(articleID)
	member := strconv.FormatUint(uint64(userID), 10)
	hit, err := s.rdb.SIsMember(ctx, key, member).Result()
	if err == nil && hit {
		return true, nil
	}
	if err != nil {
		log.Printf("check like set %s: %v", key, err)
	}

	var count int64
	if err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
		Where("article_id = ? AND user_id = ?", articleID, userID).
		Count(&count).Error; err != nil {
		return false, fmt.Errorf("check article like: %w", err)
	}
	if count > 0 {
		if err := s.rdb.SAdd(ctx, key, member).Err(); err != nil {
			log.Printf("repair like set %s: %v", key, err)
		}
	}
	return count > 0, nil
}
```

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `apply` 收四步 | 两个公开方法共用一条流程 | 新增写路径时不会漏掉某一步 |
| `writeRelation` 返回 `changed` | 把「有没有改动」与「写什么」分开 | `apply` 不必知道插入与删除的细节 |
| `Liked: add` | 由动作直接得出 | 不再靠两处硬编码，复制粘贴写反的风险消失 |
| `errors.Is(err, gorm.ErrDuplicatedKey)` | 唯一键冲突当成功 | 重复点赞与首次调用对客户端返回同一个形状 |
| `syncLikeSet` 仍在 `countLikes` 之前 | 数据库提交后就投影 | 顺序与 4.3 一致，Redis 失败只记日志 |

#### 4.4.6 这一版留下的问题，以及一处跨章提醒

MySQL 写入与 Redis 投影之间仍然是两次独立操作。进程在两步之间崩溃，数据库里有一行关系，Redis 里没有对应成员。影响范围比上一版小：`like_count` 不受影响，`HasLiked` 会回源补齐，只有 `SMEMBERS` 的观测值短暂落后。要在写入后保证 Redis 最终必达，需要 1.4 节提到的 transactional outbox，本章不实现。

再提醒一次 1.4 的跨章约束，**本次已经兑现**。前九步把点赞计数放在 `likeResp`，`articleResp` 没有 `like_count`，详情缓存不受点赞影响。现在需求变成「在文章详情里显示点赞数」，所以 4.10 步另建 `articleDetailResp`、把计数接进详情缓存，给 `ArticleService` 提供导出的 `InvalidateDetailCache`，在点赞与取消成功后调用，并回头把 03a 章 7.4 的写路径清单改成已补。

这也是「文档跟着进度走」的一个实例：缓存一致性不是开工时就要一次性设计完的东西，等真的有一份会被写路径改动的缓存数据出现，再回来把链路闭合。提前写一堆用不上的失效代码，和漏写一样是问题。

#### 4.5.1 为什么先写「慢但一定对」的版本

点赞关系已经在 `article_likes` 里，`COUNT(*)` 就是唯一事实来源。用 `GROUP BY` 直接算出来的榜单，结果可以和 SQL 控制台逐行核对。这一版存在的价值是给 v2 当基准。等 v2 换成 ZSET，把两个版本的输出对一遍，就能确认投影有没有算错。

```go
package service

import (
	"context"
	"fmt"

	"github.com/redis/go-redis/v9"
	"gorm.io/gorm"

	"forum-backend/internal/model"
)

// HotArticle 是热榜里的一条结果。
// Score 与 LikeCount 在本章取同一个值，因为评分规则就是点赞数。
// 以后换成带时间衰减的公式，两者会分开，字段先留好。
type HotArticle struct {
	ArticleID uint    `json:"article_id"`
	Score     float64 `json:"score"`
	Title     string  `json:"title"`
	LikeCount int64   `json:"like_count"`
}

// hotRow 承接 GROUP BY 的聚合结果，以及 v2 从 ZSET 读出的分数。
type hotRow struct {
	ArticleID uint  `gorm:"column:article_id"`
	Score     int64 `gorm:"column:score"`
}

type HotService struct {
	db  *gorm.DB
	rdb *redis.Client
}

func NewHotService(db *gorm.DB, rdb *redis.Client) *HotService {
	return &HotService{db: db, rdb: rdb}
}

// checkTopN 是 limit 的唯一校验点。handler 只把字符串转成整数，
// 越界值在这里挡住，经 ErrInvalidInput 映射成 400。
func checkTopN(n int) error {
	if n < 1 || n > 100 {
		return fmt.Errorf("%w: limit must be between 1 and 100", ErrInvalidInput)
	}
	return nil
}

// Top 从唯一事实来源算 Top N。
func (s *HotService) Top(ctx context.Context, n int) ([]HotArticle, error) {
	if err := checkTopN(n); err != nil {
		return nil, err
	}
	rows, err := s.groupTop(ctx, n)
	if err != nil {
		return nil, err
	}
	return s.loadByIDs(ctx, rows)
}

// groupTop 只取 id 与分数，不在这里 JOIN 文章表。
// 榜单是排序问题，文章内容是回查问题，分开做更容易验证。
func (s *HotService) groupTop(ctx context.Context, n int) ([]hotRow, error) {
	var rows []hotRow
	err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
		Select("article_id, COUNT(*) AS score").
		Group("article_id").
		Order("score DESC, article_id ASC").
		Limit(n).
		Scan(&rows).Error
	if err != nil {
		return nil, fmt.Errorf("group top articles: %w", err)
	}
	return rows, nil
}

// loadByIDs 按 rows 的顺序回查文章，并过滤已删除的行。
// 数据库 IN 查询返回的顺序不保证与 rows 一致，
// 所以先放进 map，再按 rows 的顺序组装。
func (s *HotService) loadByIDs(ctx context.Context, rows []hotRow) ([]HotArticle, error) {
	if len(rows) == 0 {
		return []HotArticle{}, nil
	}
	ids := make([]uint, 0, len(rows))
	for _, r := range rows {
		ids = append(ids, r.ArticleID)
	}

	var articles []model.Article
	if err := s.db.WithContext(ctx).Where("id IN ?", ids).Find(&articles).Error; err != nil {
		return nil, fmt.Errorf("load hot articles: %w", err)
	}
	byID := make(map[uint]model.Article, len(articles))
	for _, a := range articles {
		byID[a.ID] = a
	}

	list := make([]HotArticle, 0, len(rows))
	for _, r := range rows {
		a := byID[r.ArticleID]
		list = append(list, HotArticle{
			ArticleID: r.ArticleID,
			Score:     float64(r.Score),
			Title:     a.Title,
			LikeCount: r.Score,
		})
	}
	return list, nil
}
```

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `Scan(&rows)` | 把聚合结果扫进结构体 | `Find` 会按模型主键去查，`Scan` 只做结果映射 |
| `Order("score DESC, article_id ASC")` | 分数相同时按 id 稳定排序 | 否则同分文章每次刷新顺序会跳 |
| `Limit(n)` | 限制返回条数 | N 已经在 `checkTopN` 里夹到 1 到 100 |
| `Where("id IN ?", ids)` | 一次回查所有文章 | 逐个查会产生 N 次数据库往返 |
| `byID` 加显式 for 循环 | 保持排序一致 | 数据库不保证按 `IN` 列表顺序返回 |
| 不检查 `byID` 是否命中 | 少一个不可能命中的分支 | 4.2.4 的删除事务已清 `article_likes`，RESTRICT 外键也挡住孤儿关系 |
| v1 不写 `TopFromMySQL` | 两个函数体逐字相同的别名没有价值 | 4.6 步 `Top` 改读 ZSET 后，回源方法才有独立职责，那时再加 |
| `return []HotArticle{}, nil` | 空榜返回空切片 | 响应序列化成 `[]`，不是 `null` |

### 4.6 第 6 步：热榜 v2，改用 ZSET 投影

这一版改三个文件，`internal/service/hot.go`、`internal/service/like.go`、`internal/service/article.go`。装配与 handler 全部不动。

#### 4.6.1 为什么把加分放在 LikeService

写入侧要同时更新两个投影，点赞 Set 与热榜 ZSET。若把加分放到 `HotService`，`LikeService` 就得持有 `HotService`，两个 service 互相依赖，构造函数也要跟着改。

本章采用的划分是：`LikeService` 负责所有写入侧的投影，`HotService` 负责读取与重建。两个 service 都在 `package service`，共享同一个包级常量 `hotArticlesKey`，不需要跨包接口，也不需要额外的构造函数参数。这是 0.5 节「装配链一次定死」能成立的原因。

4.5 步删掉的 `TopFromMySQL` 在这一版回来：`Top` 现在读 ZSET，回源降级与重建需要一条独立的 MySQL 路径，两个方法不再逐字相同，这时它才有存在价值。4.7 步保留这条路径，只把「什么时候走它」的判断换掉。

#### 4.6.2 完整文件：`internal/service/hot.go` 的 v2 版本

```go
package service

import (
	"context"
	"fmt"
	"log"
	"strconv"

	"github.com/redis/go-redis/v9"
	"gorm.io/gorm"

	"forum-backend/internal/model"
)

// hotArticlesKey 带版本号。评分公式变更时换成 v2，
// 老 key 没人再读，自然过期，不用混着两套分数。
// 它是包级常量，LikeService 写入加分时直接用同一个名字。
const hotArticlesKey = "hot:articles:v1"

type HotArticle struct {
	ArticleID uint    `json:"article_id"`
	Score     float64 `json:"score"`
	Title     string  `json:"title"`
	LikeCount int64   `json:"like_count"`
}

type hotRow struct {
	ArticleID uint  `gorm:"column:article_id"`
	Score     int64 `gorm:"column:score"`
}

type HotService struct {
	db  *gorm.DB
	rdb *redis.Client
}

func NewHotService(db *gorm.DB, rdb *redis.Client) *HotService {
	return &HotService{db: db, rdb: rdb}
}

func checkTopN(n int) error {
	if n < 1 || n > 100 {
		return fmt.Errorf("%w: limit must be between 1 and 100", ErrInvalidInput)
	}
	return nil
}

// Top 优先读 ZSET，投影为空或 Redis 故障时回源 MySQL。
func (s *HotService) Top(ctx context.Context, n int) ([]HotArticle, error) {
	if err := checkTopN(n); err != nil {
		return nil, err
	}

	// WithScores 一次拿到成员与分数，省掉逐个 ZSCORE 的往返。
	pairs, err := s.rdb.ZRevRangeWithScores(ctx, hotArticlesKey, 0, int64(n-1)).Result()
	if err != nil {
		log.Printf("read hot zset: %v", err)
		return s.TopFromMySQL(ctx, n)
	}
	if len(pairs) == 0 {
		// ZSET 为空，可能是还没人点赞，也可能是数据被清空。
		// 先回源拿到正确榜单，再顺手重建投影。
		list, err := s.TopFromMySQL(ctx, n)
		if err != nil {
			return nil, err
		}
		if err := s.Rebuild(ctx); err != nil {
			log.Printf("rebuild hot zset: %v", err)
		}
		return list, nil
	}

	rows := make([]hotRow, 0, len(pairs))
	for _, p := range pairs {
		id, err := strconv.ParseUint(p.Member.(string), 10, 64)
		if err != nil {
			return nil, fmt.Errorf("parse hot member %v: %w", p.Member, err)
		}
		rows = append(rows, hotRow{ArticleID: uint(id), Score: int64(p.Score)})
	}
	return s.loadByIDs(ctx, rows)
}

func (s *HotService) TopFromMySQL(ctx context.Context, n int) ([]HotArticle, error) {
	if err := checkTopN(n); err != nil {
		return nil, err
	}
	rows, err := s.groupTop(ctx, n)
	if err != nil {
		return nil, err
	}
	return s.loadByIDs(ctx, rows)
}

// Rebuild 从唯一事实来源全量重建 ZSET。4.7 步会把它改名私有并接进读路径。
func (s *HotService) Rebuild(ctx context.Context) error {
	var rows []hotRow
	if err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
		Select("article_id, COUNT(*) AS score").
		Group("article_id").
		Scan(&rows).Error; err != nil {
		return fmt.Errorf("load all like counts: %w", err)
	}

	pipe := s.rdb.TxPipeline()
	pipe.Del(ctx, hotArticlesKey)
	for _, r := range rows {
		member := strconv.FormatUint(uint64(r.ArticleID), 10)
		pipe.ZAdd(ctx, hotArticlesKey, redis.Z{Score: float64(r.Score), Member: member})
	}
	if _, err := pipe.Exec(ctx); err != nil {
		return fmt.Errorf("rebuild hot zset: %w", err)
	}
	return nil
}

func (s *HotService) groupTop(ctx context.Context, n int) ([]hotRow, error) {
	var rows []hotRow
	err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
		Select("article_id, COUNT(*) AS score").
		Group("article_id").
		Order("score DESC, article_id ASC").
		Limit(n).
		Scan(&rows).Error
	if err != nil {
		return nil, fmt.Errorf("group top articles: %w", err)
	}
	return rows, nil
}

func (s *HotService) loadByIDs(ctx context.Context, rows []hotRow) ([]HotArticle, error) {
	if len(rows) == 0 {
		return []HotArticle{}, nil
	}
	ids := make([]uint, 0, len(rows))
	for _, r := range rows {
		ids = append(ids, r.ArticleID)
	}

	var articles []model.Article
	if err := s.db.WithContext(ctx).Where("id IN ?", ids).Find(&articles).Error; err != nil {
		return nil, fmt.Errorf("load hot articles: %w", err)
	}
	byID := make(map[uint]model.Article, len(articles))
	for _, a := range articles {
		byID[a.ID] = a
	}

	list := make([]HotArticle, 0, len(rows))
	for _, r := range rows {
		a := byID[r.ArticleID]
		list = append(list, HotArticle{
			ArticleID: r.ArticleID,
			Score:     float64(r.Score),
			Title:     a.Title,
			LikeCount: r.Score,
		})
	}
	return list, nil
}
```

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `ZRevRangeWithScores` | 一次拿成员与分数 | `ZRevRange` 只给成员，还要再查分数 |
| `0, int64(n-1)` | 闭区间取前 N 个 | Redis 区间两端都包含，写 `n` 会多取一条 |
| `p.Member.(string)` 直接断言 | 成员由本程序 `FormatUint` 写入 | 类型不可能变，为它写一套报错分支没有收益 |
| `len(pairs) == 0` 回源并重建 | 区分不了空榜与投影丢失，就两种都照顾；4.7 步用 `ready` 标记修掉这个歧义 | 返回正确结果，同时把投影补回来 |
| `Rebuild` 用 `TxPipeline` | DEL 与所有 ZADD 一起发 | 重建时避免逐条往返 |
| `loadByIDs` 保持 rows 顺序 | 按 Redis 排名输出 | 数据库 `IN` 查询不保证顺序 |

```go
// syncHotScore 把热度写成分数绝对值。
// count 来自 MySQL，重复调用、Redis 清空、之前算错的分都会在下一次写入时被纠正。
// count 为 0 时直接删掉这一个成员，不做整榜扫描。
func (s *LikeService) syncHotScore(ctx context.Context, articleID uint, count int64) {
	member := strconv.FormatUint(uint64(articleID), 10)
	var err error
	if count > 0 {
		err = s.rdb.ZAdd(ctx, hotArticlesKey, redis.Z{Score: float64(count), Member: member}).Err()
	} else {
		err = s.rdb.ZRem(ctx, hotArticlesKey, member).Err()
	}
	if err != nil {
		log.Printf("sync hot score %s: %v", member, err)
	}
}
```

**为什么写绝对值而不是 `ZINCRBY`**。增量写法在 Redis 为空时会从 0 开始加：MySQL 里已经有 50 个赞，首次点赞却把分数写成 1。此后 `Top` 看到 ZSET 非空，不会走空榜回源重建，这个错误分数会一直留着，而且常规路径不会自愈。写绝对值就没有这个问题，每次写入都是一次自愈。

也不用 `ZREMRANGEBYSCORE` 清 0 分成员。那条命令按分数区间扫描整榜，而这里只需要删掉当前这一篇文章，`ZREM` 一个成员就够。`changed` 与 `RowsAffected` 同样不用判断：重复点赞把分数重新写成正确值，是这一版的特性，不是需要挡住的重复写入。

#### 4.6.6 这一版留下的问题

这一版有三个问题，4.7 步逐个修掉。

第一，`Rebuild` 是导出方法，却没有自动入口。Redis 被 `FLUSHDB` 之后，下一次点赞会用绝对值把当前这篇文章写回正确分数，`Top` 遇到空榜也会回源并重建；但要一次性把全榜补齐，还得有人去跑脚本。

第二，`Top` 用 `len(pairs) == 0` 判断，分不清「一个赞都没有」和「投影被清空」。空榜重建完 ZSET 还是空的，下一个请求又查两次库。

第三，空榜回源与重建是两件不同的事，被塞在同一个分支里。4.7 步用 `hotReadyKey` 把「有没有初始化过」单独记下来，重建只由读路径在必要时触发一次，服务启动和日常请求都不碰 MySQL 聚合。

点赞 Set 不需要批量重建：它不参与计数，`HasLiked` 遇到 miss 会回源 MySQL 并补成员。为它再写一遍全量遍历没有收益。

### 4.7 第 7 步：热榜 v3，让读路径自己发现并重建

这一版只改 `internal/service/hot.go` 一个文件，另加一组不依赖外部服务的单测。改写前的 4.7 会让你新建 `tmp/hot_rebuild_probe.go` 手动跑一次全量重建，那份脚本现在**不要创建**：这一版没有任何需要手动运行的重建脚本。装配、handler、写入侧全部不动。

#### 4.7.1 先把三种做法摆在一起

| 做法 | 什么时候查 MySQL | 代价 | 本章判断 |
| --- | --- | --- | --- |
| 启动预热 | 每次进程启动都全量聚合一次 | 启动时间随 `article_likes` 行数增长；起 3 个实例就查 3 次；一个请求都没有也要查 | 不选 |
| 手动脚本 | 运维发现 Redis 空了，跑一次 `go run ./tmp/...` | 要有人记得跑；跑之前榜单一直是残缺的；脚本要能连到生产库 | 不选，改写前的 4.7 就是这么做的 |
| 懒加载自愈 | 只有第一个读请求发现投影没初始化时聚合一次 | 第一次读会慢一点 | **选用** |

这里要认准一条：**查不查 MySQL 由 Redis 的当前状态决定，与进程什么时候启动、运维有没有执行过某条命令都无关**。服务启动时不碰热榜数据，第一次 `GET /api/articles/hot` 发现 ZSET 还没建好，才回源一次，之后所有请求只读 Redis。Redis 被清空后，下一次读会再发现一次，再自动补齐。

上一版其实已经有一半自愈：`Top` 遇到 `len(pairs) == 0` 会回源并 `Rebuild`。但它有三个真实缺陷，4.6.2 的表格也承认了第一条。

1. **分不清空榜和投影丢失**。ZSET 里一条数据都没有时，Redis 会把整个 key 删掉。于是「论坛一个赞都没有」和「Redis 被 `FLUSHDB` 清空」在 `ZREVRANGE` 眼里长得一样，都返回空切片。
2. **空榜时每个请求都查两次库**。空榜重建完 ZSET 还是空的，下一次请求照样 `len(pairs) == 0`，又走一遍 `TopFromMySQL` 加 `Rebuild`。最省事的场景反而变成最费事的场景。
3. **全榜补齐要人去触发**。`Rebuild` 是导出方法，唯一的调用者是改写前那版 4.7 的临时脚本。不清空 Redis、只重启进程时，榜单靠 `syncHotScore` 一篇一篇补，什么时候补齐没人知道。

#### 4.7.2 用 ready 标记区分「没数据」和「没建过」

ZSET 空了 key 就不存在，所以 `EXISTS hot:articles:v1` 帮不上忙。要区分上面两种情况，得有一个独立于 ZSET 的标记。

```text
hot:articles:v1           ZSET    榜单本体，写入侧每次点赞都 ZADD 绝对分数
hot:articles:v1:ready     String  已经按 MySQL 全量建过一次，带 1 小时 TTL
hot:articles:v1:tmp       ZSET    重建落料区，写完用 RENAME 原子换榜
hot:articles:v1:cooldown  String  重建失败后的退避标记，30 秒
```

规则只有三条，写进代码前先记牢。

| 规则 | 原因 |
| --- | --- |
| `ready` 只在 `rebuild` 成功时写，写入侧不碰它 | `syncHotScore` 只更新一篇文章，不能冒充「全榜已建好」 |
| `ready` 要带 TTL，取 1 小时 | 永不过期会让榜单冻结成首建快照。到期即宣告投影失效，下一次读自动重建 |
| `rebuild` 即使聚合结果为空也要写 `ready` | 这样空榜时 ZSET 虽然不存在，标记仍在，下一次读不会重复回源 |

还有一个并发问题要顺手解决。Redis 刚被清空时，可能同时来 100 个热榜请求，100 个都看到 `ready` 不存在。不做合并的话，就是 100 次全量 `GROUP BY` 打在 MySQL 上。03a 章 5.2 的表格里留过一句「04 章热榜会碰类似思路，这里不做」，这一版兑现它：用 `singleflight.Group` 把同一时刻的重建合并成一次。`golang.org/x/sync` 已经在 `go.mod` 里，`singleflight.Group` 零值可用，加一个结构体字段就行，构造函数签名不变，0.5 节定死的装配链一行都不用改。

`singleflight` 只合并同一个 Go 进程内的调用，多实例最坏各重建一次，03a 5.2 已经算过这笔账。跨实例严格合并要分布式锁，本章不做。

#### 4.7.3 完整文件：`internal/service/hot.go` 的 v4 版本

完整覆盖 4.6.2 的文件。`HotArticle`、`hotRow`、`groupTop`、`loadByIDs` 四个定义内容没变，照这份一起写进去。

v3 交出去之后，压测又暴露了四个问题，全部在这一版修掉。四处改动都在 `rebuild` 与它的调用链上，读路径的形状没有变。

| # | v3 的问题 | v4 的修法 | 为什么 |
| --- | --- | --- | --- |
| 1 | `GROUP BY` 没有 `LIMIT`，千万级点赞会扫穿全表 | 加 `ORDER BY score DESC` 与 `Limit(hotRebuildTop)` | 排序改走优先队列，写 Redis 的条数从「全部被赞文章」降到 500 |
| 2 | 重建先 `DEL` 正式 key，再逐条 `ZADD` | 写 `hot:articles:v1:tmp`，最后 `RENAME` 原子换榜 | 并发读看不到残缺榜，重建期间的点赞也不会被全量覆盖冲掉 |
| 3 | `ready` 写死 TTL 0，永不过期 | `hotReadyTTL` 设 1 小时 | 永不过期会让榜单冻结成首建快照，热度排序逐渐失真 |
| 4 | 重建超时后每个请求都去重试 | 失败时写 `hot:articles:v1:cooldown`，冷却 30 秒 | 降级路径本身会变成新的压力源，把数据库打得更死 |

`hotRebuildTop` 取 500 的理由。对外接口最多要 100 条，这里留 5 倍余量，让「榜单外但正在升温」的文章被点赞时能直接进榜，不用等下一轮重建。

`RENAME` 消除的是「读侧看到残缺榜」和「大面积覆盖」这两件事。它没消除一个窄缝：从 SQL 返回结果到 `RENAME` 执行之间，落在这段间隙里的点赞写进的是旧 key，换榜一覆盖就丢了。这段间隙通常是毫秒级，偏差会在该文章下一次被点赞时由 `syncHotScore` 用 MySQL 真实计数修正回来，一小时后重建再整体归位。

```go
package service

import (
	"context"
	"fmt"
	"log"
	"strconv"
	"time"

	"github.com/redis/go-redis/v9"
	"golang.org/x/sync/singleflight"
	"gorm.io/gorm"

	"forum-backend/internal/model"
)

// hotArticlesKey 带版本号。评分公式变更时换成 v2，
// 老 key 没人再读，自然过期，不用混着两套分数。
// 它是包级常量，LikeService 写入加分时直接用同一个名字。
const hotArticlesKey = "hot:articles:v1"

// hotReadyKey 记的是「已经按 MySQL 全量建过一次」，不是缓存值。
// ZSET 一条数据都没有时 Redis 会把 key 删掉，
// 只看 ZSET 分不清「榜单真空」和「投影丢失」。
// 这个独立的 String key 由 rebuild 写入，写入侧的 syncHotScore 不碰它，
// 空榜时也照样存在，下一次读就不会再回源。
//
// 它必须带 TTL。永不过期意味着这个榜单会一直停留在第一次重建的那一刻，
// 之后新出现的爆款文章永远进不来，榜单变成「历史榜」。
// 过期即宣告投影失效，下一次读触发一次重建，代价是每小时多一次轻量 GROUP BY。
// TTL 只给 ready，不给 ZSET：ZSET 若先于 ready 消失，
// 中间会出现「key 没了但标记还在」的窗口，那一窗口里的榜单会静默变空。
const hotReadyKey = "hot:articles:v1:ready"

// hotReadyTTL 兼顾新鲜度与重建频率。太短则重建次数上去，
// 太长则榜单更新慢；一小时是论坛热度量级下比较合适的折中。
const hotReadyTTL = time.Hour

// hotTempKey 是重建时的落料区。重建期间所有 ZADD 写在这里，
// 写完之后用一条 RENAME 原子换掉正式 key。
// 直接在正式 key 上 Del 再 ZAdd，中间会有一段榜单为空的窗口，
// 并发读会看到空榜。
const hotTempKey = "hot:articles:v1:tmp"

// hotRebuildTop 是重建时从 MySQL 捞取的上限。
// 对外接口最多要 100 条，这里取 5 倍余量：
// 榜单之外的冷门文章被点赞时，syncHotScore 会把它补进 ZSET，
// 不必等下一轮重建才能上榜。
const hotRebuildTop = 500

// hotCooldownKey 是重建失败后的退避标记。
// 没有它，一次超过超时预算的重建会变成雪崩：
// 每个请求都发现 ready 缺失，每个都去尝试重建，每个都失败。
// 冷却期内直接走 MySQL 降级，让数据库喘口气。
const hotCooldownKey = "hot:articles:v1:cooldown"

// hotCooldownTTL 取 30 秒，比一次重建的超时预算（3 秒）大一个数量级，
// 足够把突发的重建尝试压下去，又不至于让临时的网络抖动挡住太久。
const hotCooldownTTL = 30 * time.Second

type HotArticle struct {
	ArticleID uint    `json:"article_id"`
	Score     float64 `json:"score"`
	Title     string  `json:"title"`
	LikeCount int64   `json:"like_count"`
}

type hotRow struct {
	ArticleID uint  `gorm:"column:article_id"`
	Score     int64 `gorm:"column:score"`
}

type HotService struct {
	db    *gorm.DB
	rdb   *redis.Client
	group singleflight.Group // 零值可用，合并同一时刻的并发重建
}

func NewHotService(db *gorm.DB, rdb *redis.Client) *HotService {
	return &HotService{db: db, rdb: rdb}
}

func checkTopN(n int) error {
	if n < 1 || n > 100 {
		return fmt.Errorf("%w: limit must be between 1 and 100", ErrInvalidInput)
	}
	return nil
}

// Top 优先读 ZSET。只有投影没初始化时才回源 MySQL 全量重建，
// 建好之后所有请求只读 Redis。Redis 故障时降级到 GROUP BY 基准路径。
func (s *HotService) Top(ctx context.Context, n int) ([]HotArticle, error) {
	if err := checkTopN(n); err != nil {
		return nil, err
	}

	// 绝大多数请求只花一次 EXISTS 就返回，不进重建分支。
	ready, err := s.rdb.Exists(ctx, hotReadyKey).Result() //只要全量重建过一次（哪怕是 0 条数据），
	//就会把这个 Key 设为 "1"。以后看到它，就知道“缓存系统是健康的，榜单空是真没人点赞”
	if err != nil {
		log.Printf("check hot ready key: %v", err)
		return s.TopFromMySQL(ctx, n)//如果 Redis 报错了（比如网络断了），直接降级去 MySQL 查
	}
	if ready == 0 {//如果 ready == 0（说明系统刚启动或 Redis 被清空了），
		//进入 ensureHotZSet 去重建缓存。如果重建失败，同样降级去查 MySQL
		// 冷却期内不再尝试重建，直接降级。见 hotCooldownKey 上的注释。
		cool, err := s.rdb.Exists(ctx, hotCooldownKey).Result()
		if err == nil && cool > 0 {
			return s.TopFromMySQL(ctx, n)
		}
		if err := s.ensureHotZSet(ctx); err != nil {
			log.Printf("rebuild hot zset: %v", err)
			s.markCooldown(ctx)
			return s.TopFromMySQL(ctx, n)
		}
	}

	pairs, err := s.rdb.ZRevRangeWithScores(ctx, hotArticlesKey, 0, int64(n-1)).Result()//按分数（Score）从大到小，取出前 N 名，并且带出分数
	if err != nil {
		log.Printf("read hot zset: %v", err)
		return s.TopFromMySQL(ctx, n)
	}

	rows := make([]hotRow, 0, len(pairs))
	for _, p := range pairs {
		id, err := strconv.ParseUint(p.Member.(string), 10, 64)
		if err != nil {
			return nil, fmt.Errorf("parse hot member %v: %w", p.Member, err)
		}
		rows = append(rows, hotRow{ArticleID: uint(id), Score: int64(p.Score)})
	}
	return s.loadByIDs(ctx, rows)
}

// ensureHotZSet 把同一时刻发现「投影丢失」的请求合并成一次重建。
// 没有它，FLUSHDB 之后 100 个并发请求会各查一次 MySQL。
func (s *HotService) ensureHotZSet(ctx context.Context) error {//拦截并发重建（防击穿）
	_, err, _ := s.group.Do("hot:rebuild", func() (interface{}, error) {
		// fn 用的是第一个请求的 ctx。它被取消会连累所有等待者，
		// 03a 5.3 讲过这个坑：脱离取消，另给 3 秒超时。
		loadCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 3*time.Second)
		defer cancel()

		// 等待者醒来时，第一个请求可能已经把投影建好了。
		ready, err := s.rdb.Exists(loadCtx, hotReadyKey).Result() //双重检查
		if err != nil {
			return nil, err
		}
		if ready > 0 {
			return nil, nil
		}
		return nil, s.rebuild(loadCtx)
	})
	return err
}

func (s *HotService) TopFromMySQL(ctx context.Context, n int) ([]HotArticle, error) {
	rows, err := s.groupTop(ctx, n)
	if err != nil {
		return nil, err
	}
	return s.loadByIDs(ctx, rows)
}

// markCooldown 在一次重建失败后打上退避标记。
// 用 WithoutCancel：触发它的那个请求可能已经超时断开，
// 但「别再重试」这个结论要留下来给后面的请求看。
func (s *HotService) markCooldown(ctx context.Context) {
	if err := s.rdb.Set(context.WithoutCancel(ctx), hotCooldownKey, "1", hotCooldownTTL).Err(); err != nil {
		log.Printf("mark hot cooldown: %v", err)
	}
}

// rebuild 从唯一事实来源全量重建 ZSET，最后打上已初始化标记。
// 只由 ensureHotZSet 调用，不对外暴露，也不再有脚本调用它。
//
// 三次改写留下的两条铁律：
// 1. SQL 必须带 LIMIT。不带的话，点赞表涨到千万级，
//    这条 GROUP BY 会扫穿整张表，MySQL 的 CPU 直接被打满。
//    聚合本身仍然要过一遍索引，LIMIT 省下的是结果集和后续的 ZADD 条数。
// 2. 新榜必须落在临时 key 上，写完 RENAME 换过去。
//    直接在正式 key 上 Del 再逐条 ZAdd，中途任何一次读都会拿到残缺的榜单，
//    而重建期间的点赞也会被后面的全量覆盖冲掉。
func (s *HotService) rebuild(ctx context.Context) error {
	var rows []hotRow
	if err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
		Select("article_id, COUNT(*) AS score").
		Group("article_id").
		Order("score DESC, article_id ASC").
		Limit(hotRebuildTop).
		Scan(&rows).Error; err != nil {
		return fmt.Errorf("load all like counts: %w", err)
	}

	pipe := s.rdb.TxPipeline()
	// 上一轮重建失败可能在临时 key 里留了半成品，先清掉。
	pipe.Del(ctx, hotTempKey)
	if len(rows) > 0 {
		for _, r := range rows {
			member := strconv.FormatUint(uint64(r.ArticleID), 10)
			pipe.ZAdd(ctx, hotTempKey, redis.Z{Score: float64(r.Score), Member: member})
		}
		// RENAME 在 MULTI 里执行，对读侧是原子的：
		// 读到的是换之前那份，或者换之后那份，不会读到空。
		pipe.Rename(ctx, hotTempKey, hotArticlesKey)
	} else {
		// 一条点赞都没有时临时 key 不存在，RENAME 会报 key 不存在。
		// 空榜本来就该是空，直接删正式 key。
		pipe.Del(ctx, hotArticlesKey)
	}
	// rows 为空也要写标记。否则 ZSET 依然不存在，
	// 空榜的每个请求都会重新走到这里。
	// TTL 让榜单每小时自然失效一次，避免变成历史快照。
	pipe.Set(ctx, hotReadyKey, "1", hotReadyTTL)
	if _, err := pipe.Exec(ctx); err != nil {
		return fmt.Errorf("rebuild hot zset: %w", err)
	}
	return nil
}

func (s *HotService) groupTop(ctx context.Context, n int) ([]hotRow, error) {
	var rows []hotRow
	err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
		Select("article_id, COUNT(*) AS score").
		Group("article_id").
		Order("score DESC, article_id ASC").
		Limit(n).
		Scan(&rows).Error
	if err != nil {
		return nil, fmt.Errorf("group top articles: %w", err)
	}
	return rows, nil
}

func (s *HotService) loadByIDs(ctx context.Context, rows []hotRow) ([]HotArticle, error) {
	if len(rows) == 0 {
		return []HotArticle{}, nil
	}
	ids := make([]uint, 0, len(rows))
	for _, r := range rows {
		ids = append(ids, r.ArticleID)
	}

	var articles []model.Article
	if err := s.db.WithContext(ctx).Where("id IN ?", ids).Find(&articles).Error; err != nil {
		return nil, fmt.Errorf("load hot articles: %w", err)
	}
	byID := make(map[uint]model.Article, len(articles))
	for _, a := range articles {
		byID[a.ID] = a
	}

	list := make([]HotArticle, 0, len(rows))
	for _, r := range rows {
		a := byID[r.ArticleID]
		list = append(list, HotArticle{
			ArticleID: r.ArticleID,
			Score:     float64(r.Score),
			Title:     a.Title,
			LikeCount: r.Score,
		})
	}
	return list, nil
}
```

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `hotReadyKey` | 独立于 ZSET 的初始化标记 | ZSET 空了 key 就不存在，只看 ZSET 分不清空榜与投影丢失 |
| `hotReadyTTL` | 标记的生命周期，1 小时 | 到期即宣告投影失效，下一次读自动重建，成本摊到每小时一次 |
| `hotTempKey` | 重建落料区 | 写正式 key 会让并发读看到残缺榜 |
| `hotRebuildTop` | 重建上限，500 | 接口上限 100 的 5 倍余量，避免第 101 名死区 |
| `hotCooldownKey` | 重建失败后的退避标记 | 没有它，超时后每次请求都去试一次全表聚合 |
| `EXISTS hotReadyKey` | 判断是否要回源 | 标记存在就直接读 Redis，启动与正常运行都不查 MySQL 聚合 |
| `EXISTS hotCooldownKey` | 判断是否在冷却期 | 冷却期内直接降级，不再尝试重建 |
| `ensureHotZSet` 加 `singleflight` | 合并同一时刻的重建 | `FLUSHDB` 后并发请求只触发一次 `GROUP BY` |
| `fn` 里二次 `EXISTS` | 等待者醒来后不重复重建 | 03a 5.4 的「双重检查」在这里同样成立 |
| `context.WithoutCancel` 加 3 秒 | 重建不被首个请求的取消连累 | 03a 5.3 的 context 陷阱 |
| `Rename(tmp, hotArticlesKey)` | 原子换榜 | Redis 单线程执行，读侧只能看到旧榜或新榜 |
| `TxPipeline` 而非 `Pipeline` | `RENAME` 与 `SET ready` 不被插入 | 否则会出现「榜换了标记没写」或「标记写了榜没换」 |
| `len(rows) == 0` 走 `Del` | 空榜时临时 key 不存在 | `RENAME` 一个不存在的 key 会报错，整个重建失败 |
| `markCooldown` 用 `WithoutCancel` | 失败请求的 ctx 已取消 | 直接用原 ctx 写 Redis 会失败，退避形同虚设 |
| `Rebuild` 改名私有 `rebuild` | 重建只属于读路径内部 | 不再有脚本调用方，导出没有意义 |
| `TopFromMySQL` 去掉重复的 `checkTopN` | 它只被 `Top` 调用 | `Top` 入口已经校验过一次 |
| `ZRevRangeWithScores` 与 `loadByIDs` 不变 | 读的形状没变 | 这一版只改「什么时候回源」与「怎么建榜」 |

写入侧的 `syncHotScore` 与删文章时的 `ZRem` 都不碰 `hotReadyKey`，这一点很关键。`FLUSHDB` 之后如果先有人点赞、再有人看热榜，ZSET 里会先出现这一篇文章，但 `ready` 仍不存在，第一次读会全量重建覆盖成完整榜单。把标记交给写入侧，这个保证就没了。

`syncHotScore` 写的是 MySQL 算出来的绝对分数，没有用 `ZINCRBY` 累加。这个选择在这里多了一层收益：上面说的重建窄缝，以及 Redis 被清空后丢掉的分数，都会在该文章下一次被点赞时自动纠正。

#### 4.7.6 评分边界，写得诚实一点

| 已经做到 | 还没做到 |
| --- | --- |
| score 等于点赞数，且每次写入都用绝对值纠正 | 事件表、幂等事件 id、重试去重 |
| key 带版本号，换公式时另起 key | 时间衰减，旧文章分数不会随时间下降 |
| 投影丢失后读路径自动重建，不需要启动预热或手动脚本 | 定时重算、后台刷新、跨实例分布式锁 |
| `ready` 带 1 小时 TTL，榜单每小时按当前数据重排一次 | 更实时的刷新（可以降到 10 分钟，但重建次数会涨） |
| `FLUSHDB` 后并发重建由 `singleflight` 合并到每进程一次 | 多实例最坏各重建一次（03a 5.2），合并次数没有实测 |
| 重建失败打 30 秒冷却，冷却期内不再重试 | 重建失败的告警与人工介入流程 |
| 空榜不反复回源 | 发布文章、评论、浏览等其它事件的权重 |
| 同分时按 id 稳定排序的基准 | 自定义的并列排序规则，比如按发布时间 |
| 删除文章时清理 ZSET 成员 | 重建窗口（SQL 返回至 `RENAME`）内点赞的毫秒级丢失 |

清理 ZSET 成员用的是 `ZREM`，只删指定的一篇文章。若想按「发布时间超过 30 天」清理老文章，`ZREMRANGEBYSCORE` 帮不上忙：它按 score 区间删，而本项目 score 是点赞数，按分数区间删会误删高赞文章。2.3 节讲过这层语义差异，这里再标一次，避免把清理逻辑照抄过去。

写绝对值让「业务重试重复加分」不再是个问题：重复调用只是把同一个分数再写一遍。但 MySQL 与 Redis 之间仍有双写窗口，数据库提交成功后进程崩溃，分数会停在旧值。加了 `ready` 标记之后，常规读路径不会发现这件事，因为标记还在，要等下一次写入，或者删掉 `hot:articles:v1:ready` 让读路径重新全量重建，或者等它一小时自然过期。要保证写入最终必达，需要 1.4 节的 transactional outbox 与可重试 worker，本章不实现。这一条比旧版更该写清楚：自动重建解决的是「Redis 空了」，解决不了「Redis 里是旧值」。

### 4.8 第 8 步：限流 v1，固定窗口先跑起来

这一版改两个文件，`internal/middleware/ratelimit.go` 与 `internal/router/router.go`。

#### 4.8.1 为什么先写固定窗口

固定窗口只用 `INCR` 与 `EXPIRE`，逻辑一眼能看完。先把它接通，能验证四件事：Lua 脚本能被 `redis.NewScript` 正确加载、429 能返回、`Retry-After` 能设置、Redis 断开时降级策略生效。这四件事与算法选择无关，若在令牌桶版本里一起写，出问题时分不清是哪一环。

固定窗口的缺陷也很容易实测。窗口边界前后各发 N 次请求，两批都放行，短时间内实际通过 2N 次。这个缺陷就是 4.9 步换算法的理由。

#### 4.8.2 完整文件：`internal/middleware/ratelimit.go` 的 v1 版本

```go
package middleware

import (
	"log"
	"net/http"
	"strconv"
	"time"

	"github.com/gin-gonic/gin"
	"github.com/redis/go-redis/v9"

	"forum-backend/pkg/response"
)

// RateLimitConfig 是限流参数。Rate 在固定窗口版本里用不到，
// 4.9 步换令牌桶时启用，提前放好是为了不改构造签名。
type RateLimitConfig struct {
	Capacity  int
	Rate      float64
	KeyPrefix string
}

// fixedWindowLua 在 Redis 里一次完成 INCR 与首次 EXPIRE。
// KEYS[1] 是带窗口编号的 key，ARGV[1] 是窗口秒数。
// 只有第一次 INCR 会设过期，避免每次请求都刷新 TTL 让窗口永不结束。
const fixedWindowLua = `
local key = KEYS[1]
local ttl = tonumber(ARGV[1])
local current = redis.call('INCR', key)
if current == 1 then
  redis.call('EXPIRE', key, ttl)
end
return current
`

// RateLimit 固定窗口限流。参数在构造时校验，
// 出错直接 panic，让服务启动期失败，比运行时悄悄放行更容易发现。
func RateLimit(rdb *redis.Client, cfg RateLimitConfig) gin.HandlerFunc {
	if cfg.Capacity < 1 {
		panic("RateLimit: Capacity must be positive")
	}
	if cfg.KeyPrefix == "" {
		panic("RateLimit: KeyPrefix is required")
	}

	script := redis.NewScript(fixedWindowLua)
	windowSeconds := int64(60)

	return func(c *gin.Context) {
		// 全局按 IP 共用一个桶。限流挂在 api 组，位置在 JWTAuth 之前，
		// 此时拿不到 userID，见 3.5 的边界说明。
		key := cfg.KeyPrefix + "ip:" + c.ClientIP()
		window := time.Now().Unix() / windowSeconds
		fullKey := key + ":" + strconv.FormatInt(window, 10)

		current, err := script.Run(c.Request.Context(), rdb, []string{fullKey}, windowSeconds).Int64()
		if err != nil {
			// fail-open：Redis 故障时放行，避免缓存故障放大成全站不可用。
			// 更严格的场景可以改成 fail-closed，代价是 Redis 一挂所有接口 503。
			log.Printf("rate limit check %s: %v", key, err)
			c.Next()
			return
		}

		if current > int64(cfg.Capacity) {
			retry := windowSeconds - time.Now().Unix()%windowSeconds
			c.Header("Retry-After", strconv.FormatInt(retry, 10))
			response.Error(c, http.StatusTooManyRequests, "请求太频繁，请稍后再试")
			c.Abort()
			return
		}
		c.Next()
	}
}
```

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `if current == 1 then EXPIRE` | 只在窗口第一次请求设过期 | 每次都 EXPIRE 会让 key 永不过期，计数一直累加 |
| `windowSeconds` 拼进 key | 每个窗口一个 key | 窗口切换时计数自然归零 |
| 构造时 `panic` 校验参数 | 只校验配置，不重复校验依赖 | `rdb` 已由 `router.New` 判空，再判一次是同一件事做两遍 |
| `c.Abort()` | 阻断后续 handler | 只写 `response.Error` 不 Abort，请求会继续往下走 |
| `c.Header("Retry-After", ...)` | 告诉客户端等多久 | 单位按秒，取整到当前窗口结束 |
| `log.Printf` 后 `c.Next()` | fail-open | Redis 故障时保住可用性，同时留下日志证据 |

`c.ClientIP()` 默认会信任 `X-Forwarded-For` 里的一串代理地址。客户端可以直接伪造这个头绕过分桶，所以 4.8.3 要在 router 里关掉信任列表。

### 4.9 第 9 步：限流 v2，令牌桶 Lua 与完整 Go 包装

这一版只改 `internal/middleware/ratelimit.go`，再加一条单测。`router.go` 里的 `RateLimit(rdb, rateCfg)` 调用与 `RateLimitConfig` 结构都不动。

#### 4.9.1 为什么换成令牌桶

令牌桶按固定速率补令牌，桶里最多存 `capacity` 个。空闲一段时间后攒下的令牌允许一次突发，之后按 `rate` 匀速放行。它把「平均速率」与「允许的突发量」拆成两个参数，比固定窗口更贴近 Web 服务的流量形状。

三个实现细节决定它能不能用。时钟要来自 Redis `TIME`，多个应用实例不能各用自己的机器时间。状态要存在同一个 key 里，读写必须在一次脚本内完成，否则并发请求会读到同一个旧值再各自扣一次。key 要有 TTL，长期空闲的身份不该永远占内存。

#### 4.9.2 与上一版相比改了哪几行

| 位置 | 改动 |
| --- | --- |
| import | 去掉 `time` |
| 常量 | 用 `tokenBucketLua` 换掉 `fixedWindowLua` |
| `RateLimit` | 校验补上 `Rate > 0`，脚本换成令牌桶，返回值从整数改成两个整数 |
| 删掉 | Lua 里对 `capacity`、`rate` 的重复校验，Go 侧对返回值长度与类型的三层兜底，`retrySec` 的最小值兜底 |
| 新增 | `Retry-After` 按毫秒向上取整到秒 |
| 保持不变 | `RateLimitConfig`、构造签名、fail-open、429、`c.Abort()` |

#### 4.9.3 完整文件：`internal/middleware/ratelimit.go` 的 v2 版本

```go
package middleware

import (
	"log"
	"net/http"
	"strconv"

	"github.com/gin-gonic/gin"
	"github.com/redis/go-redis/v9"

	"forum-backend/pkg/response"
)

// RateLimitConfig 是限流参数。
// Capacity 是桶容量，也是允许的瞬时突发量。
// Rate 是每秒补充的令牌数，决定长期平均速率。
type RateLimitConfig struct {
	Capacity  int
	Rate      float64
	KeyPrefix string
}

// tokenBucketLua 在 Redis 服务端一次完成读状态、补令牌、扣令牌、写回与设过期。
// KEYS[1] 是限流 key，ARGV[1] 是容量，ARGV[2] 是每秒补充速率。
// 返回 { allowed, retry_ms }，两个都是整数，交给 Go 层组装 HTTP 响应。
const tokenBucketLua = `
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])

-- Redis TIME 让多个应用实例共享同一个时钟，避免本机时间偏差。
local t = redis.call('TIME')
local now_ms = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)
local tokens = tonumber(redis.call('HGET', key, 'tokens')) or capacity
local last_ms = tonumber(redis.call('HGET', key, 'last_ms')) or now_ms
local elapsed_ms = math.max(0, now_ms - last_ms)

-- 按经过时间补令牌，上限是容量。时钟回拨时 elapsed_ms 被夹成 0。
tokens = math.min(capacity, tokens + elapsed_ms * rate / 1000)
local allowed = 0
local retry_ms = 0
if tokens >= 1 then
  tokens = tokens - 1
  allowed = 1
else
  -- 还差多少令牌，换算成需要等多少毫秒。
  retry_ms = math.ceil((1 - tokens) * 1000 / rate)
end

redis.call('HSET', key, 'tokens', tokens, 'last_ms', now_ms)
-- TTL 至少 1 秒，且大于补满整桶所需时间的两倍，避免活跃 key 被提前清掉。
local ttl_ms = math.max(1000, math.ceil(capacity * 2000 / rate))
redis.call('PEXPIRE', key, ttl_ms)
return { allowed, retry_ms }
`

// RateLimit 令牌桶限流。参数在构造时校验，出错让服务启动期失败。
func RateLimit(rdb *redis.Client, cfg RateLimitConfig) gin.HandlerFunc {
	if cfg.Capacity < 1 {
		panic("RateLimit: Capacity must be positive")
	}
	if cfg.Rate <= 0 {
		panic("RateLimit: Rate must be positive")
	}
	if cfg.KeyPrefix == "" {
		panic("RateLimit: KeyPrefix is required")
	}

	script := redis.NewScript(tokenBucketLua)

	return func(c *gin.Context) {
		key := cfg.KeyPrefix + "ip:" + c.ClientIP()
		res, err := script.Run(c.Request.Context(), rdb, []string{key}, cfg.Capacity, cfg.Rate).Slice()
		if err != nil {
			log.Printf("rate limit check %s: %v", key, err)
			c.Next() // fail-open，与 4.8 步口径一致
			return
		}
		allowed := res[0].(int64)
		retryMs := res[1].(int64)

		if allowed == 0 {
			// tokens < 1 时 retry_ms 至少为 1，向上取整后必然 >= 1 秒。
			retrySec := (retryMs + 999) / 1000
			c.Header("Retry-After", strconv.FormatInt(retrySec, 10))
			response.Error(c, http.StatusTooManyRequests, "请求太频繁，请稍后再试")
			c.Abort()
			return
		}
		c.Next()
	}
}
```

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `redis.call('TIME')` | 取 Redis 服务器时间 | 多实例共享同一时钟，来源见 https://redis.io/docs/latest/develop/reference/commands/time/ |
| `math.max(0, now_ms - last_ms)` | 夹住时间差 | 时钟回拨时不会产生负补充 |
| `math.min(capacity, ...)` | 限制令牌上限 | 长期空闲后桶不会无限累积 |
| `HGET` 缺失时用 `or capacity` | 首次请求桶是满的 | 新身份第一次访问不该被当成 0 令牌 |
| `HSET` 与 `PEXPIRE` | 保存状态并设过期 | 空闲 key 最终会被清理 |
| `return { allowed, retry_ms }` | 给 Go 层两个整数 | HTTP 状态码与响应头由 Go 决定 |
| `Slice()` 后直接取两项 | 脚本是本仓库写死的常量 | 返回形状由自己的代码决定，不必每次请求校验长度和类型 |
| `(retryMs + 999) / 1000` | 毫秒向上取整 | `Retry-After` 按秒计，向下取整会让客户端过早重试 |

这一版删掉了三处防御，理由都一样：**先问这个状态在本系统里有没有可能产生**。`capacity`、`rate` 由构造时的 `panic` 保证为正，Lua 不必再判一次；脚本是本仓库写死的原始字符串常量，返回 `{ allowed, retry_ms }` 两个整数，`Slice()` 的长度与类型检查永远为真；`tokens < 1` 时 `math.ceil((1 - tokens) * 1000 / rate)` 至少是 1，`Retry-After` 不可能是 0。真要担心脚本被改坏，应该改 4.9.4 的常量单测，而不是在每次请求里加分支。

反过来，固定窗口的 `if current == 1 then EXPIRE`、令牌桶的 `math.max(0, now_ms - last_ms)`，以及 Go 里的 `c.Abort()` 都留着。它们挡的是真实会发生的状态：窗口第一次请求、时钟回拨、429 之后必须阻断后续 handler。判断依据落在「这个状态在本系统里有没有可能产生」，「这段像不像兜底」不构成依据。

脚本只实现限流算法本身。身份与 key 生成、参数校验、429 与 `Retry-After`、错误策略、日志脱敏都在 Go 层。Lua 保证脚本在 Redis 中整体执行，系统里仍有其它并发、可用性和持久化问题。

### 4.10 第 10 步：让文章详情显示点赞数（兑现 1.4 的跨章约束）

#### 4.10.1 先问「这个数字要不要进缓存」

有两种做法，先把账算清楚再动手。

| 做法 | 怎么写 | 代价 |
| --- | --- | --- |
| A 每次现算 | 详情读路径拿到文章后，单独 `SELECT COUNT(*)` 塞进响应，不写进缓存 | 一致性零成本，但每次读详情多一条 SQL |
| B 跟文章一起缓存 | 回源时算一次，随文章 JSON 写进详情缓存；点赞成功后删这个 key | 命中缓存不多查库，但写路径必须记得删 |

本章选 B。理由在于这份教程从头到尾在讲「事实来源 + 派生副本 + 写路径失效」，03a 章 7.4 的写路径清单也早把「点赞」这一行留好了，这一步正好把整条链子闭上。方案 A 同样正确：如果你更看重零心智负担，把 4.10.5 的计数改成读路径每次现算、并删掉 4.10.7 的失效调用即可。只是要注意 `singleflight` 合并时多个请求拿到的是同一个 `*model.Article` 指针，别直接改它，拷贝一份再填，否则并发写会打架。这也是本章选 B 的一个附带理由：回源阶段赋值天然只有一个执行者。

接着定三条边界，避免为了一个数字把代码写复杂。

第一，**事实来源仍然只有一份**。`articles.like_count` 这一列永远不维护，不要在点赞事务里写 `UPDATE articles SET like_count = ...`，那会多出第三份需要对齐的数据，1.4 已经算过这笔账。`model.Article.LikeCount` 在这里只是回源时临时装数字的内存字段，缓存里那份是它的副本，真相永远是 `article_likes` 的行数。

第二，**不换 key 版本号**。JSON 的形状没变：`model.Article` 一直带 `like_count` 字段和同名 tag，老缓存里只是值恒为 0。03a 定的是「加字段、改 tag 才升 `v1` → `v2`」，这里没触发。老缓存靠点赞时的 `DEL` 和最多 12 分钟 TTL 自然被换掉，本地验收前先 `FLUSHDB` 一次就能立刻看到新值。为一次取值语义变化去批量换 key，收益配不上多出来的一堆排查命令。

第三，**只在真的改了关系时删缓存**。`changed=false` 的重复点赞不会改变计数，不该让缓存白白失效一次。删失败只记日志、靠 TTL 兜底，不翻转已经提交的数据库结果。03a 7.5 那个「回源拿到旧值、写删缓存、读再回填旧值」的窗口在这里同样存在，不假装它消失了，TTL 给出上界。

```go
func (s *ArticleService) queryDetail(ctx context.Context, id uint) (*model.Article, error) {
	var a model.Article
	err := s.db.WithContext(ctx).Preload("User").First(&a, id).Error
	if err != nil {
		if errors.Is(err, gorm.ErrRecordNotFound) {
			return nil, fmt.Errorf("article %d: %w", id, ErrNotFound)
		}
		return nil, fmt.Errorf("query article %d: %w", id, err)
	}

	// 详情要显示点赞数。articles.like_count 列始终不维护，
	// 这里从 article_likes 现算一次，装进内存字段随文章一起写进缓存。
	var likeCount int64
	if err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
		Where("article_id = ?", id).Count(&likeCount).Error; err != nil {
		return nil, fmt.Errorf("count article likes %d: %w", id, err)
	}
	a.LikeCount = likeCount
	return &a, nil
}
```

这段只在**缓存未命中**时执行。命中缓存的请求走 `readArticleCache`，拿到的是上次回源时连同计数一起写进去的 JSON，不会多查库。计数走 `uk_article_user (article_id, user_id)` 的索引前缀，成本很低，4.3.1 已经算过这笔账。

#### 4.10.6 增量修改：把缓存失效方法改名导出

03a 章里这个方法是私有的 `invalidateArticleCache`，只有 `Create` 与 `Delete` 调它。现在点赞写路径成了第二个调用方，本轮把全库文档的名字统一成导出的 `InvalidateDetailCache`，让「ArticleService 提供一个可被调用的失效入口」变成明确契约。下面这段是最终形状，函数体和原来完全一样。

**增量修改**：完整替换 `internal/service/article.go` 的方法定义。

```go
// InvalidateDetailCache 删除详情缓存。数据库写入或事务提交成功之后才调用。
// 导出是因为会改动详情内容的写路径不止 ArticleService 自己：
// LikeService 点赞与取消成功后也要调用它。
// 空标记和真实文章用的是同一个 key，所以这一句也能清掉空标记。
// 失败只记录，不改变已提交的数据库结果；TTL 是最后一道兜底。
func (s *ArticleService) InvalidateDetailCache(ctx context.Context, id uint) {
	key := articleDetailKey(id)
	if err := s.rdb.Del(ctx, key).Err(); err != nil {
		s.metrics.Degrades.Add(1)
		log.Printf("invalidate article cache %s: %v", key, err)
	}
}
```

如果你的工作树里还是旧名字，把方法定义改名为 `InvalidateDetailCache`，并把 `Create`、`Delete` 两处 `s.invalidateArticleCache(ctx, ...)` 同步改成 `s.InvalidateDetailCache(ctx, ...)`。若已经是导出名，这一步就只剩「确认两处调用点都在」这一件事。

#### 4.10.12 这一版留下的问题

第一，03a 7.5 的经典脏数据窗口仍然存在：某个读请求在点赞提交前回源拿到旧计数，删缓存之后才把旧值回填进去，之后所有请求会读到旧数字，直到 TTL 到期。TTL 给出上界，本章不引入延迟双删。

第四，列表接口仍不显示点赞数。真要显示，得给列表加一次 `GROUP BY` 或在 `article_likes` 上做批量聚合，是另一个取舍，本章不做。
