# 00 · 完整项目实施总图

> 本文是整套教程的导航和验收合同。按 01 到 05 的顺序完成，第 2 周之后的 `03a` 是缓存加固进阶专题，第 3 周之后的 `04a` 到 `04c` 是三个进阶专题（异步消息、API 文档、WebSocket 实时通知），都不占周次，`07` 章是完成后的纵向复盘与面试速查。每个阶段先实现、再运行、再测试、最后记录结果。文档里出现某个技术名词，不能当作项目已经具备该能力。

## 这套教程最终要交付什么

一个可本机运行、可重复测试、具备基本安全和运维准备的论坛后端：

- 用户注册、登录、JWT 鉴权、当前用户资料。
- 文章创建、详情、分页列表、作者删除；评论创建、列表、作者删除。
- MySQL 持久化、Redis 文章详情缓存、点赞、热榜和限流。
- 参数校验、统一错误响应、日志、超时、分页上限、访问控制。
- 单元测试、MySQL 与 Redis 集成测试、HTTP 测试、并发与故障场景测试。
- 可复现的本地启动、构建、配置、数据库迁移、部署前检查和回滚说明。
- 点赞、评论后的异步站内通知：事务发件箱、Redis Stream 消费组、幂等消费、后台 worker 优雅关闭（04a）。
- 从 handler 注解生成的 Swagger 2.0 文档与可交互 UI，配套契约防漂移检查（04b）。
- 点赞、评论之后服务端主动推送到浏览器，连接登记、心跳、慢客户端剔除、在线统计（04c）。

「本机能启动」与「具备上线能力」之间还有很大距离。本教程完成的是上线前的工程准备，能否承载真实生产流量要看部署环境、容量、威胁模型、备份恢复演练和监控告警实测。

## 本套文档怎么写

每个功能点按同一套顺序讲解，方便新手形成稳定的阅读节奏：

| 顺序 | 章节 | 你会得到什么 |
| --- | --- | --- |
| 1 | 目标与规则 | 这个接口要解决什么问题，要守住哪些边界 |
| 2 | 最小概念 | 只讲本接口用得到的术语，配一个请求到 SQL 的链路图 |
| 3 | 完整可运行代码 | 逐行中文注释，说明「做什么」和「为什么」 |
| 4 | 逐行拆解表 | 每行代码对应作用与设计理由，可以逐行对照读 |
| 5 | 设计决策 | 讲清取舍，包括被放弃的方案和它的代价 |
| 6 | 常见错误对照 | 把编译错误、机制误解、安全漏洞列成表 |
| 7 | 验证命令与用例 | 给出可复制的命令和边界输入 |
| 8 | 参考来源 | 英文权威链接，结论可回溯 |

这套结构借鉴了 Go 官方 Effective Go 在代码旁边逐段解释的写法 [来源: https://go.dev/doc/effective_go#commentary]，Go by Example 的「一段代码加一段输出」格式 [来源: https://gobyexample.com/structs]，以及 GORM 官方文档「规则 → 可执行示例 → 安全与不安全写法对比」的组织方式 [来源: https://gorm.io/docs/method_chaining.html]。**「逐行拆解表」属于教程惯例**，Go 官方并没有规定这种讲解格式。

Go 代码注释遵循官方约定：导出标识符的注释以名字开头，写成完整句，错误字符串不大写开头、不带句号 [来源: https://go.dev/wiki/CodeReviewComments]。本章代码片段里的中文注释保留同样的信息结构。

### 文档跟着进度长

前面章节写的是「当时的起点」。后面动手之后仓库会变，早期描述就会过时。这是学习项目的常态，一次性把四周的细节全塞进第 1 章，新手会失去主线。

三条规矩：

1. 每章开头先看该章的「当前仓库起点」表，重新跑一次 `go version`、`go test ./...`、`go build ./cmd/server`。表上标了快照日期，过期就重看源码。
2. 文档里写「新建 X 文件」「往 var 块新增 Y」时，先打开仓库确认它是否已经存在。已存在就改成核对与规范化，粘贴第二份会造成重复定义或覆盖已有代码。
3. 判断完成度用「路由已注册且端到端验收通过」。service 写好了但 router 没接线，接口仍然不存在。

遇到文档与源码不一致，以源码为准，并把该处记进章末的勘误汇总。勘误表记录的就是这类修正，读者能看见文档怎么跟着进度长起来，也能照同样方法维护自己的笔记。

### 官方明文与工程惯例要分开

读文档时把这两类结论分开记，能避免把惯例当成铁律，也能避免把铁律当成可选项。

| 结论 | 归属 | 依据 |
| --- | --- | --- |
| Context 作为函数第一个参数显式传递 | Go 官方明文 | https://go.dev/wiki/CodeReviewComments |
| Chain、Finisher、New Session 三类方法与不安全复用 | GORM 官方明文 | https://gorm.io/docs/method_chaining.html |
| `NewDB: true` 清空条件、无 WHERE 删除返回 `ErrMissingWhereClause`、含 `gorm.DeletedAt` 时软删除 | GORM 官方明文 | https://gorm.io/docs/session.html 、 https://gorm.io/docs/delete.html |
| Must bind 会直接写 400，Should bind 把错误交给开发者 | Gin 官方明文 | https://gin-gonic.com/en/docs/binding/binding-and-validation |
| 每层都传 ctx 的具体写法 | 工程惯例 | 由 Go 官方 Context 规则推导 |
| `Preload` 解决 N+1 | 工程推论 | GORM 官方页面用 eager loading 与 separate query 描述，未出现 N+1 术语 |
| 分页必须稳定排序、设置 pageSize 上限、返回空切片 | 数据库与 API 工程惯例 | 官方文档把 Order、Limit、Offset 分开描述，未写这条规则 |
| 目标 → 代码 → 逐行拆解 → 决策 → 反例 → 验证 | 教程结构惯例 | 本套文档自定的讲解约定 |

### 教程代码块的统一标识

每个要复制进项目、或要按说明合并进项目的 Go、Lua、SQL 代码块，必须在代码块前标注以下一种，三种不能混用：

1. **完整文件**：提供仓库相对路径和完整内容，可复制后保存，写完立刻执行该节的编译或测试命令。
2. **增量修改**：指出要打开的文件、插入或替换的函数范围、要保留的现有内容，最后给出完整目标签名及验证命令。
3. **概念伪代码**：只讲原理，或是从源码截取下来供讲解的示意片段，显著标记「不能运行」，同一章必须另有实际可运行实现和测试。

验证与审查用的 SQL 查询、建库语句，以及 bash、PowerShell、curl、text、json 等命令与输出示例，属于可直接执行的命令示例，不需要标注文件类型。判断标准只有一条：**这段代码要不要落盘进项目？要，就标；不要，就不用标。** 例如「查一眼数据库确认作者 id」的 `SELECT` 不算，03 章那条「等值 SQL 供审查」的 `ALTER TABLE` 也不算；如果哪一章给出一条**要保存成迁移脚本文件**的 `ALTER TABLE`，它就要标。

章节示例不能引用不存在的构造函数、Service、Repository、配置字段或 API。每次改变函数签名，都要列出所有调用点并逐个更新。

## 目标 API 合同

所有受保护接口从 JWT 中间件读取身份，客户端不能提交或覆盖 `user_id`。日期统一使用 RFC3339，ID 使用正整数。列表默认每页 10 条，最大 50 条。越界参数返回 400，服务端不静默替换成另一个值。

下表是**完成后的目标状态**。当前 `pkg/response.OK` 固定返回 HTTP 200，所以括号里同时标出当前实现。要落地目标状态，先给 `pkg/response` 增加 `Created`（201）与 `NoContent`（204），再同步改 handler、测试和验收脚本。旧版文档在 00、02、03、05 章写了互相冲突的状态码，现已按这条口径统一。

| 方法 | 路径 | 登录 | 成功状态 | 说明 |
| --- | --- | --- | --- | --- |
| POST | `/api/register` | 否 | 201（当前 200） | 创建用户，用户名唯一，不返回密码哈希 |
| POST | `/api/login` | 否 | 200 | 登录成功返回 access token，错误凭据统一 401 |
| GET | `/api/me` | 是 | 200 | 返回当前用户公开资料 |
| POST | `/api/articles` | 是 | 201（当前 200） | 创建文章，作者来自 token |
| GET | `/api/articles` | 否 | 200 | 分页列表，校验 page 与 page_size |
| GET | `/api/articles/:id` | 否 | 200 | 详情，不存在返回 404；04 章 4.10 起响应带 `like_count` |
| DELETE | `/api/articles/:id` | 是 | 204（当前 200） | 仅作者删除，明确选择 404 隐藏资源或 403 表示无权 |
| POST | `/api/articles/:id/comments` | 是 | 201（当前 200） | 给存在的文章发表评论 |
| GET | `/api/articles/:id/comments` | 否 | 200 | 按时间分页列出评论 |
| DELETE | `/api/comments/:id` | 是 | 204（当前 200） | 仅评论作者删除 |
| PUT | `/api/articles/:id/like` | 是 | 200 | 点赞，重复调用幂等 |
| DELETE | `/api/articles/:id/like` | 是 | 200 | 取消点赞，重复调用幂等 |
| GET | `/api/articles/hot` | 否 | 200 | 热度排序 Top N，限制最大 N |
| GET | `/api/notifications` | 是 | 200 | 分页列出当前用户通知，带 `unread_count`（04a） |
| PUT | `/api/notifications/read-all` | 是 | 200 | 标记全部已读，返回受影响行数（04a） |
| GET | `/api/ws/stats` | 否 | 200 | 当前在线用户数与连接数，只统计本进程（04c） |
| GET | `/api/ws/notifications` | 自行校验 | 101 | WebSocket 升级，token 走查询参数，不带 token 返回 401（04c） |

所有响应遵循 `pkg/response` 的实际格式 `{ code, message, data }`。统一响应封装与本表冲突时，先统一实现和文档，再开始 Postman 测试。

`/swagger/index.html` 与 `/swagger/doc.json` 由 04b 章的 `gin-swagger` 提供，只在调试模式暴露，不属于业务 API 合同。生成物放 `api/swagger/`，不要落进 `docs/`。

## 数据与业务规则（实现前先确认）

- MySQL 保存用户、文章、评论的事实数据。Redis 保存可重建的缓存与派生数据，丢失后要能从 MySQL 重建。重建要由读路径自己发现并触发，04 章 4.7 给出热榜的懒加载自愈实现，不依赖启动预热或手动脚本。
- 用户名在数据库有唯一索引。应用层预检查只改善提示，并发注册由数据库约束兜底。
- 密码只存 bcrypt 哈希。登录对「用户不存在」和「密码不匹配」返回相同外部信息。密码按字节校验 bcrypt 上限，字符数与字节数在中文场景下不同。
- 文章与评论删除规则必须明确。初学版本采用事务删除文章和评论，避免孤儿数据，数据库外键和索引要与该规则一致。
- 点赞操作必须幂等。Redis Set 保证成员唯一，MySQL 保留点赞关系或可靠的事件账本，才能支持 Redis 丢失后的重建。
- 热榜分数要有具体公式、事件权重、时间衰减或重算策略、并列排序规则。仅执行 `ZINCRBY` 会让历史分持续累积，算不上完整热度模型。
- 缓存失效发生在数据库提交成功之后。Redis 故障时详情可以回源 MySQL。写入缓存失败不能把已经成功的数据库写入报成失败。TTL 加抖动，负缓存用短 TTL。写路径清单见 03a 章 7.4：04 章 4.10 让详情响应带 `like_count` 之后，点赞与取消也成了要删缓存的写路径。
- 所有 DB 与 Redis 操作接收 `context.Context`，配置连接池、请求超时和关闭资源。失败路径写明降级行为，错误不能被吞掉。
- 点赞与评论产生的领域事件要和业务写入放进同一个 MySQL 事务（`outbox_events`，见 04a）。Redis Stream 只做投递通道，投递语义是至少一次，消费端用 `event_id` 唯一索引保证幂等。Redis 不参与 MySQL 事务，别把 `XADD` 写进事务函数。
- API 文档由 handler 注解生成，生成物纳入版本控制并用 CI diff 守住同步；生产环境关闭 Swagger UI（见 04b）。
- 实时推送只是加速手段，通知的真相源仍是 `notifications` 表。连接断开期间的推送会丢，重连后靠 HTTP 接口补齐（见 04c）。

## 分阶段路线和必须通过的门槛

### 阶段 A：基础链路（第 1 周，文档 02）

注册、登录、JWT、`/api/me`，错误分类和状态码稳定。MySQL 启动、配置检查、请求体大小限制和密钥管理可用。用 Postman 或 curl 覆盖成功、参数错误、重复注册、错误密码、无 token、无效 token、过期 token，再写 handler 与 service 测试。

### 阶段 B：关系型业务（第 2 周，文档 03 前半）

文章、评论接口先只依赖 MySQL，不提前引入缓存。完成分页边界、所有权校验、关联删除事务、索引和 API 错误映射。通过正常流程、越权、缺失资源、非法 ID、超长输入、数据库失败场景。

### 阶段 C：基础缓存（第 2 周，文档 03 后半）

接通 Cache Aside 读路径与写路径失效，明确 key 格式和失效时机。分别测试命中、未命中、坏 JSON、缓存服务故障、写后读。旧版把序列化版本、TTL 抖动、负缓存、降级规格和观测指标也写在这一段，实际 03 章 7 节只完成了基础读写路径。

### 阶段 C+：缓存工程化加固（第 2 周进阶专题，文档 03a）

不占周次，接在阶段 C 之后，第 3 周仍是阶段 D。用时间轴推出穿透、击穿、雪崩三类故障，落地 key 版本化、TTL 随机抖动、空值缓存哨兵、singleflight 请求合并、`ErrRecordNotFound` 错误翻译、写路径一致性时序、Redis 超时与连接池、降级分级表和原子计数器。验收要拿到 TTL 分布、空标记命中、并发回源次数和故障降级四类证据。多实例一致性、布隆过滤器、熔断限流明确列为未做。

### 阶段 D：点赞、热榜、限流（第 3 周，文档 04）

04 章已改写成十步跟做版：4.1 骨架先行，4.2 到 4.4 点赞三版，4.5 到 4.7 热榜三版（4.7 把全量重建接进读路径，Redis 空了才回源，不需要启动预热或手动脚本），4.8 到 4.9 限流两版，4.10 把点赞数接进文章详情并回头补写路径缓存失效（03a 章 7.4 的那一行同步改成已补），每步给该阶段完整文件或增量、改动点表、设计理由与验证命令。开工前先决定 MySQL 与 Redis 的权威数据和恢复路径，再实现幂等点赞。Redis Lua 脚本要有整数与时间单位定义、原子读改写、key 过期、参数校验和脚本测试。限流要声明按 IP、用户还是路由统计、算法参数、代理信任边界、Redis 故障时 fail-open 或 fail-closed。验证 429、Retry-After、并发重复请求及 Redis 故障。

### 阶段 D+：异步消息、站内通知与 API 文档（第 3 周进阶专题，文档 04a、04b）

不占周次，接在阶段 D 十步之后，第 4 周仍是阶段 E。04a 用时间轴推出「写库后发消息」的失败窗口，落地 Transactional Outbox、Redis Stream relay、消费组 PEL 重放、`event_id` 幂等、通知读接口、`signal.NotifyContext` 与 `WaitGroup` 优雅关闭。验收要拿到事务原子、停机补投、重复投递不产生重复通知、未读数归零四类证据。04b 落地声明式注解、`swag init` 生成 Swagger 2.0、调试模式下的可交互 UI、生成物入库与 CI diff 检查。多实例抢占、CDC、Kafka、OpenAPI 3.x、契约测试自动化明确列为未做。

### 阶段 D++：实时推送（文档 04c）

接在阶段 D+ 之后，第 4 周仍是阶段 E。04c 把通知从「下次刷新可见」升级成服务端主动推送，落地连接登记中心、读写分离、心跳与超时、慢客户端剔除、在线统计，并处理 `http.Server.Shutdown` 关不掉已升级连接的坑。多实例广播明确列为未做。

### 阶段 E：测试与发布准备（第 4 周，文档 05）

完成单元测试、集成测试、HTTP 契约测试、并发测试、`go test -race ./...`、静态检查和可复现构建。提供最小权限 DB 用户、版本化 schema migration、环境变量密钥、健康与就绪检查、优雅关闭、日志脱敏、备份恢复演练、部署与回滚步骤。未做压测不写性能数字，未做恢复演练不声称备份可靠。

### 阶段 F：性能数字与数据对账（第 4 周进阶专题，文档 05a、05b）

不占周次，接在阶段 E 之后。05a 把「我用了缓存」变成可复现的数字：先处理六个会把结论带偏的干扰项（`gin.Default()` 的访问日志、`Capacity=10` 的令牌桶、MySQL 连接池未设上限、客户端 `MaxIdleConnsPerHost` 默认 2、同机压测抢 CPU、空库压空路径），给出五条链路的压法与一张结果表模板，再用 Little's Law 与两个连接池的参数推算容量上限，并算出 relay「200ms 一轮、每轮 100 条」对应的每秒 500 条投递上限。05b 落地热榜对账：只查榜单前 200，四道检查（投影丢失、分数漂移、僵尸成员、消息积压），修正只写绝对值，`-fix` 与 dry-run 分离，退出码区分「系统有问题」与「任务坏了」，判定逻辑抽成纯函数并配十个单测。这两个专题都不改任何已有写入路径，只加观测与兜底。

### 阶段 G：前端验收页（第 5 周，文档 08，可选）

不占周次，接在阶段 F 之后。用 Vue 3 加 Vite 给每个已实现的接口配一个能点得动的页面，覆盖登录注册、文章与评论、点赞热榜、通知列表和 WebSocket 实时推送。目的在让限流、缓存、Outbox 与 Hub 的效果能在浏览器里连续观察，同时把「列表没有点赞数」「没有查询点赞状态的接口」「通知只有 actor_id」这类契约缺口暴露出来。这一阶段不改任何 Go 业务源码，唯一需要动的后端是 `internal/handler/ws.go` 的 Origin 白名单加一个本地开发地址。前端本身不做组件库、TypeScript、状态管理与测试，写简历时定位成后端链路的验收工具。

## 每个阶段的跟做闭环

1. 看本阶段目标、先决条件和预计会修改的文件。
2. 先运行当前测试并保存结果，知道起点是否正常。
3. 一次只实现一个可验证的垂直切片，顺序是路由、handler、service、repository、DB 或 Redis。
4. 执行文档给出的 `gofmt`、针对性测试、`go test ./...` 和构建。
5. 启动依赖和服务，用 Postman collection 或明确的 `curl.exe` 请求验收状态码、响应体与数据副作用。
6. 制造至少一个失败场景，观察客户端响应、服务端日志和数据一致性。
7. 通过验收才勾选交付，记录未解决限制。下一节不能假装已经完成。

## 上线前总检查（学习项目目标，生产承诺另论）

- [ ] 配置有类型、范围和必填校验，不使用仓库里的示例密钥或密码。
- [ ] DB migration 可版本化、可回滚，生产账号最小权限，重要数据有恢复演练。
- [ ] 所有输入有尺寸与范围限制，认证、授权、错误响应和速率限制均测试过。
- [ ] JWT issuer、audience、过期和算法校验明确，密钥轮换和用户登出策略有决定。
- [ ] Redis 数据丢失后有自动重建策略（读路径懒加载自愈，见 04 章 4.7），缓存不可用行为和告警有定义。
- [ ] 热榜重建带 `ORDER BY ... LIMIT` 与临时 key 换榜，`ready` 标记有 TTL，重建失败有冷却退避（04 章 4.7、07 章第 8 章）。
- [ ] 事件链路的消息不丢可验证：业务写入与 outbox 同事务，停机后重启能自动补投，死信有状态可查（04a）。
- [ ] 事件契约变更后 Stream 里没有残留旧格式消息，或已给 `StreamKey` 升版本号，旧 key 自然过期（04a）。
- [ ] `swag init` 生成物与注解同步，CI 有重跑加 diff 的检查；生产构建关闭 Swagger UI（04b）。
- [ ] WebSocket 连接随信号断开而不靠进程退出回收，Origin 校验只放行本站，慢客户端有上限与剔除（04c）。
- [ ] 后台 worker 随信号退出，连接池在 goroutine 收尾之后关闭（04a）。
- [ ] 日志有请求关联信息且不含密码、token、敏感 SQL 参数，错误只在边界记录一次。
- [ ] 服务有启动失败退出、健康和就绪检查、优雅关闭、资源超时和连接池限制。
- [ ] CI 能跑测试、静态检查、构建，镜像或二进制可重复构建，部署和回滚有步骤。
- [ ] 压测和容量结论写明硬件、数据规模、并发数、版本和测量方法。
- [ ] 压测前处理过六个干扰项（访问日志、限流、MySQL 连接池、客户端连接池、同机抢 CPU、空库），结果表里有这六项的实际值（05a）。
- [ ] 热榜对账能定期跑，能发现投影丢失与僵尸成员，修正后复查收敛；死信只报告不自动重放（05b）。
