# 第 3 周进阶 E：全文搜索与倒排索引

论坛帖子过了几千篇，搜索就成了刚需。用 `LIKE '%关键词%'` 查，MySQL 会放弃索引扫全表，一篇帖子几百毫秒，二十个人同时搜就把数据库拖住。

本章引入搜索引擎，把「扫描」换成「查表」。同步走 04a 那套 Outbox + Stream，不阻塞发帖。

## 0. 为什么要加这一章

### 0.1 `LIKE '%x%'` 为什么救不了

先看一个事实。B+ 树索引的排序依据是「前缀」，`WHERE title LIKE 'redis%'` 能用索引，因为前缀确定，可以在树里定位。`LIKE '%redis%'` 的前缀是任意字符，树里没法定位，只能逐行读出来比对。

执行计划会直接显示 `type: ALL`，也就是全表扫描。几千行还行，几十万行就是几秒。

还有三层代价容易被忽略：

| 代价 | 说明 |
| --- | --- |
| 无法按相关性排序 | `LIKE` 只能回答「含不含」，回答不了「哪篇更相关」 |
| 中文分词 | `LIKE '%数据库%'` 匹配不到「数据库」被写成「数据 库」的情况，也不理解同义词 |
| 全文索引的局限 | MySQL 的 `FULLTEXT` 支持中文需要 `ngram` 分词器，配置繁琐，相关性与高级查询能力远不如专用引擎 |

### 0.2 倒排索引一句话

正排是「文档 → 包含哪些词」，倒排是「词 → 出现在哪些文档」。

```text
正排（MySQL 表）
  id=1  title="Redis 缓存穿透"     content="用空值缓存解决..."
  id=2  title="缓存一致性"          content="删除缓存还是更新缓存..."

倒排（搜索引擎内部）
  "redis"  → [1]
  "缓存"   → [1, 2]
  "穿透"   → [1]
  "一致性" → [2]

查询「缓存」：直接拿 [1, 2]，不用看任何一篇正文。
```

有了这张表，搜索的代价从「扫全部文档」变成「查一次词表 + 求交集」。这就是搜索引擎快的原因，和用什么语言写没关系。

### 0.3 选型：ES 还是 Meilisearch

| 维度 | Elasticsearch | Meilisearch |
| --- | --- | --- |
| 运行方式 | JVM，需要独立集群或单节点 | 单个二进制，一条 docker 命令 |
| 起步内存 | 建议 2 GB 以上，实际常给 4 GB | 几十 MB 起 |
| 中文分词 | 需要装 IK 分词器插件，版本要和 ES 严格对应 | 内置 charabia，中文用 jieba 词典分词 |
| 查询能力 | 极强，聚合、脚本、向量、复杂布尔 | 够用，前缀、容错、过滤、排序 |
| 学习成本 | 高，DSL 与集群概念多 | 低，REST 加 JSON |
| 简历分量 | 高，招聘 JD 出现频率最高 | 中 |
| 适合本项目 | 过重 | 合适 |

本章选 Meilisearch，理由是它能在本机一条命令跑起来，不需要装 Java 和插件。中文开箱可用这一点很关键，ES 装 IK 分词器那一步通常要折腾半小时。

这个选择要说清代价：如果面试官问的是 ES 的倒排结构、分片、副本、`_source`、DSL 聚合，用 Meilisearch 的经历答不上。所以本章的写法是「原理通用，实现按 Meilisearch 讲」，讲清倒排索引与同步链路，这两块换 ES 也一样。

反过来，如果目标岗位明确要求 ES，那就该用 ES。选型的依据是使用场景与成本，与哪个词更有面子无关。

## 1. 架构：异步同步

### 1.1 三种同步方式对比

| 方式 | 做法 | 问题 |
| --- | --- | --- |
| 同步双写 | 发帖时先写 MySQL，再调搜索引擎，两个都成功才返回 | 搜索引擎超时就把发帖拖死；两边不一致时没法回滚 |
| 定时全量重建 | 每 10 分钟扫一遍全表，全量推给索引 | 延迟十分钟；每次重建都全量，数据量大时扛不住 |
| 变更事件异步同步 | 业务写入与事件同事务提交，消费者异步写索引 | 有秒级延迟；需要处理重复与乱序 |

第三种是唯一说得通的。前两种的毛病都是「把搜索的可用性绑到了发帖的可用性上」，而搜索是增强功能，不该决定论坛能不能发帖。

这里能直接复用 04a 的成果，因为那套机制解决的问题完全一样：**跨系统的一致性问题，用一个事务里的本地消息表兜住**。搜索引擎只是换了一个下游。

### 1.2 第二个消费组

Redis Stream 的核心概念是消费组。一条 Stream 可以被多个消费组同时消费，每个组有自己的游标，互不干扰，也不会抢消息。

```text
forum:events:v1
      │
      ├──► 消费组 forum:notify:v1（游标 A）──► NotificationWorker ──► MySQL notifications
      │
      └──► 消费组 forum:search:v1（游标 B）──► SearchWorker ────────► Meilisearch
```

这和「同一个组里加消费者」是两件完全不同的事：

| 做法 | 效果 | 适用 |
| --- | --- | --- |
| 同组多消费者 | 消息分给其中一个，每条只被处理一次 | 扩容，提高吞吐 |
| 多消费组 | 每个组各收到一份完整消息流 | 不同下游各取所需 |

如果给 `forum:notify:v1` 加一个消费者做索引，会出现「一半事件写通知、另一半写索引」的错乱。这一点必须分清楚。

### 1.3 一个必须先修的耦合问题

加第二个消费组之前，有一个隐患要先修，否则会立刻出问题。

**当前状态**：这个隐患已经在事件契约重构时修掉。`NotificationWorker.handle` 现在按 `p.Type` 查 `resolverByType`，未注册的类型记日志后直接 ACK，回查文章作者的逻辑收在 `resolveArticleAction` 里。下面的推演记录修之前的形态，保留它是为了说明「共享一条流的消费者必须声明自己关心哪些类型」这条纪律。

修之前，`handle` 的逻辑是：解析事件，回查文章作者，插入通知。它**不检查事件类型**。当时 Stream 上只有 `like.created` 和 `comment.created`，两种都要发通知，所以没出错。

本章会往 Stream 上增加 `article.created` 和 `article.deleted`。这两个事件一旦被通知消费者读到，会发生什么：

```text
article.created 事件
  │
  ├─ 回查文章 article.UserID
  ├─ 判断 article.UserID == p.ActorID  →  作者自己发的，相等，直接 return nil
  │
  └─ 结论：恰好没出问题，但这是巧合
```

自赞自评会被那条判断挡住，所以「自己发文章不通知自己」碰巧成立。但如果将来加了「编辑他人文章」这类事件，`ActorID` 和 `UserID` 不相等，就会给作者发一条「有人动了你的文章」，而事件本身根本没有这个语义。

正确的做法是显式声明关心哪些事件类型。这是「多个消费者共享一条流」的必备纪律：**每个消费者都要对自己不关心的事件明确说「我处理完了」，同时不产生任何副作用**。

## 2. 第 1 步：修通知消费者的类型白名单

### 2.1 已经落地：notification worker 的分发

**当前实现**：`internal/worker/notify_resolver.go` 的 `resolverByType`，`handle` 在解析事件之后查这张表。

```go
var resolverByType = map[string]resolver{
	event.TypeLikeCreated:    resolveArticleAction,
	event.TypeCommentCreated: resolveArticleAction,
}

resolve, ok := resolverByType[p.Type]
if !ok {
	// 搜索同步用的 article.created 走到这里，记日志后直接 ACK。
	log.Printf("no notification resolver for %s, ack event %s", p.Type, msg.ID)
	return nil
}
```

返回 `nil` 而不是 error 很关键。`consumeLoop` 的逻辑是「handle 返回 nil 才 ACK」，返回 error 会让消息留在 PEL 里反复重读。不关心的事件必须被 ACK 掉。

注册表比原来的 `switch` 多买了一个扩展点：将来接入关注事件，写一个 `resolveFollow` 再加一行注册即可，`handle` 不动。

这一处改动只有七行，但它是本章最重要的设计点之一。多个消费者共享一条消息流时，「谁负责 ACK」「不关心的事件怎么办」这两个问题必须先答清楚。

### 2.2 增量修改：抽出公共消费循环

两个消费者的读循环逐行相同，差别只有消费组名和处理函数。复制一份等于把「空 PEL 重读」「失败不 ACK」这些细节维护两遍，改一处漏一处是迟早的事。

**完整文件**：`internal/worker/consumer.go`

```go
package worker

import (
	"context"
	"errors"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

// consumeLoop 是消费组读循环的公共骨架。
// 04a 只有一个消费者时它写在 NotificationWorker 里；
// 加索引消费者时两段循环逐行相同，差别只有消费组名和处理函数，
// 于是抽到这里，两个 worker 各持一份配置即可。
type consumeLoop struct {
	rdb    *redis.Client
	stream string
	group  string
	name   string // 消费者名，同一个组内要唯一
	batch  int64
	block  time.Duration
	handle func(ctx context.Context, msg redis.XMessage) error
}

// run 先确保消费组存在，再循环处理 PEL 与新消息。
// 不同消费组各有各的游标，同一条 Stream 会被各自完整读一遍。
func (l *consumeLoop) run(ctx context.Context) {
	// 重复启动会返回 BUSYGROUP，组已存在正是我们要的状态，忽略即可。
	_ = l.rdb.XGroupCreateMkStream(ctx, l.stream, l.group, "0").Err()

	for {
		if ctx.Err() != nil {
			return
		}
		l.read(ctx, "0") // 先补上次没 ACK 的
		l.read(ctx, ">") // 再阻塞读新消息
	}
}

// read 读一批消息，逐条处理，成功才 ACK。
func (l *consumeLoop) read(ctx context.Context, start string) {
	block := l.block
	if start == "0" {
		// go-redis v9 里只有 Block >= 0 才发 BLOCK 参数。
		// 传 -1 让这次读立即返回，不阻塞循环。
		block = -1
	}

	streams, err := l.rdb.XReadGroup(ctx, &redis.XReadGroupArgs{
		Group:    l.group,
		Consumer: l.name,
		Streams:  []string{l.stream, start},
		Count:    l.batch,
		Block:    block,
	}).Result()
	if errors.Is(err, redis.Nil) {
		return
	}
	if err != nil {
		if ctx.Err() != nil {
			return
		}
		log.Printf("read group %s from %s: %v", l.group, start, err)
		return
	}

	for _, stream := range streams {
		for _, msg := range stream.Messages {
			if err := l.handle(ctx, msg); err != nil {
				// 不 ACK，消息留在 PEL，下一轮用 "0" 重新读到。
				log.Printf("handle %s %s: %v", l.group, msg.ID, err)
				continue
			}
			if err := l.rdb.XAck(ctx, l.stream, l.group, msg.ID).Err(); err != nil {
				log.Printf("ack %s %s: %v", l.group, msg.ID, err)
			}
		}
	}
}
```

**增量修改**：`NotificationWorker.Run` 换成三行委托，原来的 `Run` 与 `consume` 方法整段删除。


### 2.3 为什么现在才抽

04a 只有一处循环，抽出来是过度设计。现在有了第二处，两段逐行相同，抽出来才是消除重复。

这个时机判断比抽象本身重要。提前抽象会因为「尚未稳定的需求」猜错边界，无端造出一层没人用的抽象。等到第二次出现时再抽，边界已经被两处实现验证过了。

抽完之后 `notification.go` 少了约 50 行，`search.go` 可以直接复用，第三个消费者（比如将来的审核队列）也只需要写一个 `handle`。

`ArticleService.Create` 现在是单条 `Create`，没有事务。要加事件就必须包事务，否则「文章写成功、事件没写」会让索引永远缺这篇。

**增量修改**：`internal/service/article.go` 的 import 与 `Create` 方法体。

```go
	"forum-backend/internal/event"
```

```go
	a := &model.Article{
		UserID:  userID,
		Title:   title,
		Content: content,
	}
	// 文章与事件在同一个事务里：文章存在而事件丢失，索引就会永远缺这篇。

	return a, nil
```

注意 `a.ID` 在 `tx.Create` 之后才有值。GORM 插入成功会把自增主键回填到结构体上，所以 `Target` 那行能拿到正确的 ID。这个顺序不能反。

### 3.3 增量修改：删除文章

**增量修改**：`internal/service/article.go` 的 `Delete` 事务内，删文章成功之后。

```go
		if res.RowsAffected == 0 {
			// 文章不存在与无权删除对外合并成同一个错误，避免泄露归属。
			// 此时评论已被删，返回错误会让事务把评论一并回滚。
			return ErrNotFound
		}

		// 删除也要发事件，否则索引里会留下一篇点进去 404 的文章。
		// 删除类事件走 NewPayload 加 Emit 两步，不挤进 EmitCreated。
		target := event.Target{Type: event.TargetArticle, ID: id}
		p, err := event.NewPayload(event.TypeArticleDeleted, userID, target, nil)
		if err != nil {
			return err
		}
		return event.Emit(ctx, tx, p)
	})
```

顺序要求：先删评论、删点赞（因为外键是 RESTRICT），再删文章，最后发事件。事件放在最后，是因为前面的删除都可能失败，失败时事务回滚，事件也不该存在。

### 3.4 事件为什么还只带 ID

04a 的事件契约是「瘦事件只带 ID，消费端回查」。这里继续沿用，没有把标题正文塞进 payload。

三个理由：

| 理由 | 说明 |
| --- | --- |
| 契约稳定 | 将来索引需要多存一个字段（比如作者名），改的是消费者，不动生产端 |
| 体积可控 | 正文可能 5 万字，塞进事件会让 Stream 和 outbox 表迅速膨胀 |
| 时序正确 | 消费者回查的是「消费时刻」的最新数据，而不是「发布时刻」的快照 |

第三条有利也有弊。如果文章在事件排队期间被编辑过，索引写到的是新版本，这是对的；如果被删除，回查会 `ErrRecordNotFound`，此时应当删索引而不是报错重试。这个分支在 5.2 的 `upsert` 里处理。

## 4. 第 3 步：搜索客户端

### 4.1 为什么手写 HTTP 不用 SDK

Meilisearch 有官方 Go SDK `meilisearch-go`，用它能少写一百多行。本章没用，理由是：

| 维度 | 手写 | SDK |
| --- | --- | --- |
| 依赖 | 零 | 多一个模块，随上游发版 |
| 可讲的内容 | 请求长什么样、202 与任务的关系、错误码怎么读 | 都被封装了，只能讲「调了个方法」 |
| 出错时排查 | 打印一下请求体就能定位 | 要翻 SDK 源码看它拼了什么 |
| 适合范围 | 只用到四五个接口 | 要用聚合、多索引、向量检索 |

本项目只用到「建索引、写文档、删文档、搜索」四个动作，每个都是一次 HTTP 调用。手写完全可控，还顺便把 Meilisearch 的异步任务模型讲清楚了，这是它和 MySQL 最大的不同。

如果将来接口数量涨到十几个，就该换 SDK。手写四十个端点的封装，收益已经不如直接读 SDK 文档。

### 4.2 完整文件：`internal/search/client.go`

新建目录与文件，包名写 `package search`：

```bash
mkdir -p internal/search
```

这个包只依赖标准库 `net/http` 与 `encoding/json`，不引用项目内其它包，所以单独落盘就能编译，可以先写它再写别的。

```go
// Package search 用 HTTP 直连 Meilisearch，只封装本项目用到的几个动作。
// 不引入官方 SDK：接口只有四五个，自己写反而更容易看清请求到底长什么样。
package search

import (
	"bytes"
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"io"
	"net/http"
	"strconv"
	"strings"
	"time"
)

// IndexArticles 是文章索引的固定名字。
const IndexArticles = "articles"

const (
	// Meilisearch 的写入都是「入队即返回」，任务跑完才算真写完。
	// 这里等一小会儿，好让消费者知道本次同步到底成没成。
	taskWaitTimeout  = 3 * time.Second
	taskPollInterval = 50 * time.Millisecond
)

// ArticleDoc 是进索引的文档形状。
// 只放可搜索与展示必需的字段：作者、点赞数这些易变数据不进来，
// 否则每次点赞都要重建索引。
type ArticleDoc struct {
	ID      uint   `json:"id"`
	Title   string `json:"title"`
	Content string `json:"content"`
}

// SearchResult 是搜索接口回来的那一部分字段。
// 用 page/hitsPerPage 分页时，totalHits 是精确值；
// 用 offset/limit 时只有估算值 estimatedTotalHits。
type SearchResult struct {
	Hits       []ArticleDoc `json:"hits"`
	TotalHits  int64        `json:"totalHits"`
	TotalPages int          `json:"totalPages"`
}

// enqueuedTask 是写入类接口的 202 响应。
// 注意它的字段叫 taskUid，查询任务详情的响应里才叫 uid，两处名字不同。
type enqueuedTask struct {
	TaskUID int64 `json:"taskUid"`
}

// taskResp 是任务详情，字段名是 uid。
type taskResp struct {
	UID    int64  `json:"uid"`
	Status string `json:"status"`
	Error  struct {
		Message string `json:"message"`
		Code    string `json:"code"`
	} `json:"error"`
}

// APIError 是服务端返回的非 2xx 响应。
type APIError struct {
	Status  int
	Code    string
	Message string
}

func (e *APIError) Error() string {
	return fmt.Sprintf("meilisearch %d %s: %s", e.Status, e.Code, e.Message)
}

// Client 是最小可用的 Meilisearch 客户端。
type Client struct {
	baseURL string
	apiKey  string
	http    *http.Client
}

func New(baseURL, apiKey string, timeout time.Duration) *Client {
	return &Client{
		baseURL: strings.TrimRight(baseURL, "/"),
		apiKey:  apiKey,
		http:    &http.Client{Timeout: timeout},
	}
}

// EnsureIndex 保证索引存在，返回 true 表示这次是新建的。
// 调用方据此决定要不要再下发一次索引设置，避免每次启动都写一遍。
func (c *Client) EnsureIndex(ctx context.Context) (bool, error) {
	err := c.do(ctx, http.MethodGet, "/indexes/"+IndexArticles, nil, nil)
	if err == nil {
		return false, nil
	}
	var apiErr *APIError
	// 先探一次，而不是直接创建：创建已存在的索引会返回 409，
	// 与其去匹配错误码，不如把「存在」当成正常路径。
	if !errors.As(err, &apiErr) || apiErr.Status != http.StatusNotFound {
		return false, err
	}
	// 建索引也是异步任务，不等待的话紧接着的 settings 请求可能撞上
	// 「索引还不存在」而返回 404。
	var task enqueuedTask
	err = c.do(ctx, http.MethodPost, "/indexes", map[string]interface{}{
		"uid":        IndexArticles,
		"primaryKey": "id",
	}, &task)
	if err != nil {
		return false, err
	}
	if err := c.WaitTask(ctx, task.TaskUID); err != nil {
		return false, err
	}
	return true, nil
}

// UpdateSettings 指定哪些字段参与检索。
// 不设置的话所有字段都可搜，正文里的 id 数字也会被当成关键词。
func (c *Client) UpdateSettings(ctx context.Context, searchable []string) error {
	var task enqueuedTask
	err := c.do(ctx, http.MethodPatch, "/indexes/"+IndexArticles+"/settings", map[string]interface{}{
		"searchableAttributes": searchable,
	}, &task)
	if err != nil {
		return err
	}
	return c.WaitTask(ctx, task.TaskUID)
}

// Upsert 写入或覆盖一篇文档，并等任务落定。
// 用 POST 而不是 PUT：两者都是写入，POST 的语义是新增或覆盖整条文档，
// 正是这里想要的。
func (c *Client) Upsert(ctx context.Context, doc ArticleDoc) error {
	var task enqueuedTask
	err := c.do(ctx, http.MethodPost, "/indexes/"+IndexArticles+"/documents",
		[]ArticleDoc{doc}, &task)
	if err != nil {
		return err
	}
	return c.WaitTask(ctx, task.TaskUID)
}

// Delete 从索引里删掉一篇文档。文章不存在时 Meilisearch 也返回成功，天然幂等。
func (c *Client) Delete(ctx context.Context, id uint) error {
	var task enqueuedTask
	path := "/indexes/" + IndexArticles + "/documents/" + strconv.FormatUint(uint64(id), 10)
	if err := c.do(ctx, http.MethodDelete, path, nil, &task); err != nil {
		return err
	}
	return c.WaitTask(ctx, task.TaskUID)
}

// Search 执行一次检索，只取回文档 id。
// 取全文会让搜索接口和文章表各存一份内容，容易漂移；
// 只取 id 再回 MySQL 拿完整数据，代价是一次 IN 查询。
func (c *Client) Search(ctx context.Context, q string, page, hitsPerPage int) (SearchResult, error) {
	var out SearchResult
	err := c.do(ctx, http.MethodPost, "/indexes/"+IndexArticles+"/search", map[string]interface{}{
		"q":                    q,
		"page":                 page,
		"hitsPerPage":          hitsPerPage,
		"attributesToRetrieve": []string{"id"},
	}, &out)
	if err != nil {
		return SearchResult{}, err
	}
	return out, nil
}

// WaitTask 轮询异步任务直到落定。
// 不等待的话，写入失败（比如 id 类型不对）会被静默吞掉，
// 索引里少一篇文档，谁也不会知道。
func (c *Client) WaitTask(ctx context.Context, taskUID int64) error {
	deadline := time.Now().Add(taskWaitTimeout)
	path := "/tasks/" + strconv.FormatInt(taskUID, 10)
	for {
		var task taskResp
		if err := c.do(ctx, http.MethodGet, path, nil, &task); err != nil {
			return err
		}
		switch task.Status {
		case "succeeded":
			return nil
		case "failed", "canceled":
			return fmt.Errorf("meilisearch task %d %s: %s (%s)", taskUID, task.Status, task.Error.Message, task.Error.Code)
		}
		if time.Now().After(deadline) {
			return fmt.Errorf("meilisearch task %d still %s after %s", taskUID, task.Status, taskWaitTimeout)
		}
		select {
		case <-ctx.Done():
			return ctx.Err()
		case <-time.After(taskPollInterval):
		}
	}
}

// do 是所有请求的唯一出口：拼头、发请求、判状态码、解响应。
func (c *Client) do(ctx context.Context, method, path string, body interface{}, out interface{}) error {
	var reader io.Reader
	if body != nil {
		data, err := json.Marshal(body)
		if err != nil {
			return fmt.Errorf("marshal %s %s: %w", method, path, err)
		}
		reader = bytes.NewReader(data)
	}

	req, err := http.NewRequestWithContext(ctx, method, c.baseURL+path, reader)
	if err != nil {
		return fmt.Errorf("build %s %s: %w", method, path, err)
	}
	if body != nil {
		req.Header.Set("Content-Type", "application/json")
	}
	if c.apiKey != "" {
		req.Header.Set("Authorization", "Bearer "+c.apiKey)
	}

	resp, err := c.http.Do(req)
	if err != nil {
		return fmt.Errorf("%s %s: %w", method, path, err)
	}
	defer resp.Body.Close()

	if resp.StatusCode < 200 || resp.StatusCode >= 300 {
		return decodeAPIError(resp)
	}
	if out == nil {
		// 不读空响应体，连接就回不到池子里复用。
		_, _ = io.Copy(io.Discard, resp.Body)
		return nil
	}
	if err := json.NewDecoder(resp.Body).Decode(out); err != nil {
		return fmt.Errorf("decode %s %s: %w", method, path, err)
	}
	return nil
}

func decodeAPIError(resp *http.Response) error {
	apiErr := &APIError{Status: resp.StatusCode}
	var payload struct {
		Code    string `json:"code"`
		Message string `json:"message"`
	}
	if err := json.NewDecoder(resp.Body).Decode(&payload); err == nil {
		apiErr.Code = payload.Code
		apiErr.Message = payload.Message
	}
	if apiErr.Message == "" {
		apiErr.Message = resp.Status
	}
	return apiErr
}
```

### 4.3 逐行拆解

**`enqueuedTask` 与 `taskResp` 为什么分开**

这是我在实测中踩到的坑，值得单独讲。

Meilisearch 的写操作返回 202，响应体长这样：

```json
{"taskUid": 147, "indexUid": null, "status": "enqueued", "type": "documentAdditionOrUpdate"}
```

注意字段是 `taskUid`。而查询任务详情的 `GET /tasks/147` 返回：

```json
{"uid": 147, "status": "succeeded", ...}
```

字段是 `uid`。两个名字不一样。

最初我只有一个 `taskResp` 结构体，字段名写 `uid`，用来解 202 响应。结果 `taskUid` 解不出来，`task.UID` 永远是 0，于是去轮询 `GET /tasks/0`，拿到 404，报了一个跟真实原因完全无关的错。

这个 bug 在单测里立刻暴露了（`unexpected GET /tasks/0`），但如果没有单测，会表现为「索引一直写不进去，日志里说任务不存在」。

**为什么必须等任务**

Meilisearch 的写是异步的：接口返回 202 只表示「任务入队了」。文档什么时候真正可搜，取决于后台任务什么时候跑完。

不等的话有三个后果：

1. 写入失败（id 类型不对、字段超长）被静默吞掉，索引里少一篇，没人知道。
2. 消费者以为成功了去 ACK，消息丢了，索引永久缺失。
3. 发完文章立刻搜，搜不到，被当成 bug 排查半天。

等任务的代价是每条消息多几次 HTTP 往返。实测 Meilisearch 索引进度通常几十毫秒，`50ms` 的轮询间隔配上 `3s` 超时，绝大多数情况下两三次轮询就结束。

**`attributesToRetrieve: ["id"]` 的意义**

只取 id，不取标题正文。这是本章一个关键设计，理由在 5.3 详述。

**`page` 与 `hitsPerPage` 而不是 `offset` 与 `limit`**

Meilisearch 支持两套分页参数，行为不同：

| 参数 | 响应字段 | 总数性质 |
| --- | --- | --- |
| `offset` + `limit` | `estimatedTotalHits` | 估算值 |
| `page` + `hitsPerPage` | `totalHits` + `totalPages` | 精确值 |

项目其他地方都用 `page` 与 `page_size`，响应里带 `total`。用 `page` 模式能拿到精确的 `totalHits`，直接塞进现有的 `articleListResp`，前端不用区分「这是估算的」。

代价是精确计数更慢。数据量大到几十万条时，每次搜索都精确计数会成为负担。那时的做法是改用 `offset` 模式，响应里加一个 `total_is_estimated: true` 让前端知道数字是近似的。这是典型的「精确性与延迟」取舍。

**`io.Copy(io.Discard, resp.Body)`**

`out` 为 nil 时（`Health`、`EnsureIndex` 的部分调用）不解析响应体。但必须把它读完，否则底层的 TCP 连接不会回到连接池，下次请求要重新握手。这种问题不会报错，只会让延迟悄悄变高。

**`strings.TrimRight(baseURL, "/")`**

配置里写成 `http://127.0.0.1:7700/` 和 `http://127.0.0.1:7700` 都是常见的。不处理的话拼出来是 `http://127.0.0.1:7700//indexes/articles`，Meilisearch 会把双斜杠当成路径的一部分返回 404。这种错误信息很有迷惑性，看起来像索引不存在。

## 5. 第 4 步：索引消费者

### 5.1 完整文件：`internal/worker/search.go`

新建文件，落在 `internal/worker/` 下，包名 `package worker`。它调用 2.2 抽出来的 `consumeLoop`，两个文件同包，所以这一节必须在 2.2 之后做。

```go
package worker

import (
	"context"
	"errors"
	"fmt"

	"github.com/redis/go-redis/v9"
	"gorm.io/gorm"

	"forum-backend/internal/event"
	"forum-backend/internal/model"
	"forum-backend/internal/search"
)

const searchConsumer = "search-1"

// SearchWorker 把文章变更同步进搜索引擎。
// 它与 NotificationWorker 读同一条 Stream，但用不同消费组，
// 各自有一份游标，互不影响，也不会抢走对方的消息。
type SearchWorker struct {
	db     *gorm.DB
	rdb    *redis.Client
	client *search.Client
}

func NewSearchWorker(db *gorm.DB, rdb *redis.Client, client *search.Client) *SearchWorker {
	return &SearchWorker{db: db, rdb: rdb, client: client}
}

func (w *SearchWorker) Run(ctx context.Context) {
	l := &consumeLoop{
		rdb:    w.rdb,
		stream: event.StreamKey,
		group:  event.SearchGroup,
		name:   searchConsumer,
		batch:  readBatchSize,
		block:  readBlock,
		handle: w.handle,
	}
	l.run(ctx)
}

// handle 按事件类型决定写索引还是删索引。
func (w *SearchWorker) handle(ctx context.Context, msg redis.XMessage) error {
	raw, ok := msg.Values["payload"].(string)
	if !ok {
		return fmt.Errorf("event %s: payload is not a string", msg.ID)
	}
	p, err := event.Decode(raw)
	if err != nil {
		return err
	}

	switch p.Type {
	case event.TypeArticleCreated:
		return w.upsert(ctx, p.Target.ID)
	case event.TypeArticleDeleted:
		return w.client.Delete(ctx, p.Target.ID)
	default:
		// 点赞、评论这些事件与本消费者无关。
		// 返回 nil 表示「我确实处理完了」，让它被 ACK 掉，
		// 否则它会一直躺在 PEL 里被反复重读。
		return nil
	}
}

// upsert 回查数据库拿最新内容再写索引。
// 事件里只带 ID，标题正文在消费时才读，避免正文在两处各存一份。
func (w *SearchWorker) upsert(ctx context.Context, articleID uint) error {
	var a model.Article
	err := w.db.WithContext(ctx).Select("id", "title", "content").First(&a, articleID).Error
	if errors.Is(err, gorm.ErrRecordNotFound) {
		// 事件排队期间文章已被删掉，索引里也不该留它。
		return w.client.Delete(ctx, articleID)
	}
	if err != nil {
		return fmt.Errorf("load article %d: %w", articleID, err)
	}
	return w.client.Upsert(ctx, search.ArticleDoc{
		ID:      a.ID,
		Title:   a.Title,
		Content: a.Content,
	})
}
```

### 5.2 逐行拆解

**`default: return nil` 是必须的**

这是本章第二个关键点。不关心的事件要返回 `nil` 让它被 ACK。

如果返回 error，`consumeLoop` 会认为处理失败，不 ACK，消息留在 PEL。下一轮用 `"0"` 重读，还是这条点赞事件，还是返回 error，无限循环。PEL 会越积越多，最后这条 Stream 基本瘫痪。

如果返回 `nil` 但从 switch 里漏掉，行为是对的，但没人知道「这里是故意的」。写一个显式的 `default` 加注释，半年后回来看得懂。

**`Select("id", "title", "content")`**

只查三个字段。`articles` 表还有 `like_count`、`created_at`、`updated_at`，不查能省一次宽行读取。索引里根本不需要这些字段，查出来再丢掉是浪费。

**`ErrRecordNotFound` 转成删索引**

事件从产生到被消费有秒级延迟。这段时间里文章可能已经被删了。此时回查失败，正确反应是「索引里也别留它」，于是转成 `client.Delete`。

这个分支容易被写成 `return nil`（当成无害情况跳过），后果是索引里留一篇永远 404 的文档，用户搜到点进去报错。

**为什么不用 `ArticleService` 的方法**

`upsert` 里直接查库，没有调 `articleSvc.Detail`。原因有两个：

1. `Detail` 走缓存。索引需要的是数据库里的权威内容，从缓存拿可能拿到旧值。
2. `Detail` 会额外算点赞数，多一次 `COUNT` 查询，索引不需要。

跨层调用看着「复用」，实际引入了不必要的耦合和多余的查询。

### 5.3 瘦索引与宽索引

这是本章最重要的一个设计取舍。

| 方案 | 索引里存什么 | 搜索后的动作 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| 瘦索引 | id、标题、正文 | 回 MySQL 查完整数据 | 数据只有一份真相源，不会漂移 | 多一次查询 |
| 宽索引 | 全部展示字段 | 直接返回 | 一次查询，快 | 内容重复，任何字段改动都要重建索引 |

选瘦索引，因为「数据漂移」的代价远大于一次 `IN` 查询。

具体想一下宽索引会遇到什么：作者改了用户名，索引里存的是旧名，搜索列表显示的还是旧名，除非遍历全站文章重建索引。点赞数更麻烦，每点一次赞都要更新索引，等于把读多写少的索引变成了高频写入。

回查的代价可以量化：一次 `WHERE id IN (...)` 查 10 条，走主键索引，通常 1 毫秒以内。相比搜索本身的几毫秒，可以接受。

代价也有一个副作用要提前说明：**返回条数可能少于 `total`**。索引里有、MySQL 里已经删掉的 id，回查查不出来，会被跳过。这种情况下 `list` 的长度小于 `page_size`，但 `total` 还是索引给的数字。前端做分页时要知道这一点，否则会以为最后一页坏了。

### 6.1 完整文件：`internal/service/search.go`

```go
package service

import (
	"context"
	"fmt"
	"strings"

	"gorm.io/gorm"

	"forum-backend/internal/model"
	"forum-backend/internal/search"
)

// SearchService 把「关键词检索」和「文章数据」拼在一起。
// 搜索引擎只负责找 id，文章内容仍以 MySQL 为准。
type SearchService struct {
	db     *gorm.DB
	client *search.Client
}

func NewSearchService(db *gorm.DB, client *search.Client) *SearchService {
	return &SearchService{db: db, client: client}
}

// Search 先问搜索引擎要一页 id，再回 MySQL 拿完整文章。
func (s *SearchService) Search(ctx context.Context, q string, page, pageSize int) ([]*model.Article, int64, error) {
	q = strings.TrimSpace(q)
	if q == "" {
		// 空关键词交给搜索引擎会退化成「列出全部文档」，
		// 那不是搜索，是另一个列表接口，直接拒掉更清楚。
		return nil, 0, fmt.Errorf("%w: q is required", ErrInvalidInput)
	}
	if page < 1 || pageSize < 1 || pageSize > 50 {
		return nil, 0, fmt.Errorf("%w: invalid pagination", ErrInvalidInput)
	}

	res, err := s.client.Search(ctx, q, page, pageSize)
	if err != nil {
		return nil, 0, fmt.Errorf("search articles: %w", err)
	}
	if len(res.Hits) == 0 {
		return []*model.Article{}, res.TotalHits, nil
	}

	ids := make([]uint, 0, len(res.Hits))
	for _, hit := range res.Hits {
		ids = append(ids, hit.ID)
	}

	found := make([]*model.Article, 0, len(ids))
	err = s.db.WithContext(ctx).Preload("User").Where("id IN ?", ids).Find(&found).Error
	if err != nil {
		return nil, 0, fmt.Errorf("load searched articles: %w", err)
	}

	// IN 查询不保证顺序，而搜索结果的价值一半在顺序上。
	// 按 id 建索引再照着 ids 取一遍，把相关性顺序还回来。
	// 索引里有、库里已删的 id 会被自然跳过，所以条数可能少于 total。
	byID := make(map[uint]*model.Article, len(found))
	for _, a := range found {
		byID[a.ID] = a
	}
	ordered := make([]*model.Article, 0, len(ids))
	for _, id := range ids {
		if a, ok := byID[id]; ok {
			ordered = append(ordered, a)
		}
	}
	return ordered, res.TotalHits, nil
}
```

### 6.2 顺序必须显式还原

`WHERE id IN (7, 3, 11)` 返回的顺序是按主键排列的，不是按 `IN` 列表里给的顺序。MySQL 没有任何义务保持你给的顺序。

如果直接把 `found` 返回，搜索结果的顺序就是 id 顺序，相关性排序完全失效。用户搜「缓存」，「Redis 缓存」和「缓存一致性」哪个在前，取决于谁先建立。

这段重排代码看起来笨，但它是搜索能不能用的关键。`byID` 用 map 做 O(1) 查找，遍历 `ids` 一次，复杂度 O(n)。如果用双层循环去 `found` 里找，10 条结果就是 100 次比较，没必要。

```go
	"github.com/gin-gonic/gin"

	"forum-backend/internal/service"
	"forum-backend/pkg/response"

	svc *service.SearchService
}

func NewSearchHandler(svc *service.SearchService) *SearchHandler {
	return &SearchHandler{svc: svc}
}

// Search godoc
// @Summary      按关键词搜索文章
// @Tags         search
// @Produce      json
// @Param        q          query  string  true   "关键词，不能为空"
// @Param        page       query  int     false  "页码，默认 1"
// @Param        page_size  query  int     false  "每页条数，默认 10，最大 50"
// @Success      200  {object}  handler.SwaggerEnvelope{data=handler.articleListResp}
// @Failure      400  {string}  string    "q 为空或分页参数越界"
// @Failure      500  {string}  string    "搜索引擎不可用"
// @Router       /search [get]
func (h *SearchHandler) Search(c *gin.Context) {
	page, pageSize, err := parsePage(c)
	if err != nil {
		mapServiceError(c, "search articles", err)
		return
	}

	list, total, err := h.svc.Search(c.Request.Context(), c.Query("q"), page, pageSize)
	if err != nil {
		mapServiceError(c, "search articles", err)
		return
	}

	// 复用文章列表的响应形状：前端拿到的结构与分页参数完全一致，
	// 只有数据来源不同，切换列表与搜索不需要改渲染代码。
	items := make([]articleResp, 0, len(list))
	for _, a := range list {
		items = append(items, toArticleResp(a))
	}
	response.OK(c, articleListResp{
		List:     items,
		Total:    total,
		Page:     page,
		PageSize: pageSize,
	})
}
```

### 7.4 为什么初始化失败不退出

这是一个有意的降级。`EnsureIndex` 失败意味着 Meilisearch 没起或者配置错了。此时有两种选择：

| 选择 | 后果 |
| --- | --- |
| `log.Fatalf` 退出 | 整个论坛不可用，只因为搜索没好 |
| 打警告继续跑 | 发帖、点赞、评论全部正常，`/api/search` 会返回 500 |

选后者。判断依据是「这个组件的不可用是否应该连带核心功能不可用」。搜索是增强能力，答案是否。

`EnsureIndex` 里要等任务这一点容易漏。`POST /indexes` 也是异步的，返回 `taskUid`。不等它，紧接着的 `PATCH settings` 会撞上「索引不存在」返回 404，日志上看起来像设置写错了，实际是时序问题。我第一版就是这样写的，靠单测里那条 `unexpected GET /tasks/0` 才发现整个 `taskUid` 与 `uid` 的字段差异。

### 7.5 索引设置的内容

`UpdateSettings` 传的是 `["title", "content"]`，意思是只有这两个字段参与检索。

不设置会怎样：Meilisearch 默认把所有字段设为可搜，包括 `id`。用户搜「123」会匹配到 id 为 123 的文章，看起来莫名其妙。这类「搜数字出无关结果」的问题在真实产品里很常见，根因就是忘了配可搜字段。

中文分词不需要额外配置。Meilisearch 内置的 charabia 分词器对中文用 jieba 词典分词，开箱可用。这一点比 Elasticsearch 友好很多，ES 要装 IK 插件，插件版本还要和 ES 主版本严格对应。

分词效果实测能到什么程度：搜「缓存」能命中「Redis 缓存穿透」，搜「穿透」也能命中。但搜「缓穿」这种跨词组合不行，因为分词后是两个独立的词，倒排里没有这个组合。这是所有词典分词的共性，不是 Meilisearch 的缺陷。

### 7.6 全量重建

索引是派生数据，任何时候都可以从 MySQL 重建。写一个临时脚本或一次性的管理接口：

```go
// 伪代码：把 MySQL 里的文章全量推进索引，用于索引损坏或换引擎后的重建。
rows := 从 articles 分页读（每批 500 条）
for 每批 {
	批量调用 POST /indexes/articles/documents
}
```

要点两条：

1. 分批，不要一次全读。十万篇正文一次读进内存是几 GB。
2. 重建期间搜索会返回不完整结果，要么在低峰期做，要么建到临时索引再原子切换（Meilisearch 支持 `swap indexes`）。

本章不做重建脚本，但要说清一件容易误解的事：**删掉 `data.ms` 并不能靠 Stream 自己恢复**。

只有没被 ACK 的消息才会留在 PEL 里重放。已经被 ACK 的历史事件不会回来，索引会永久缺那些文章。所以「索引丢了」的唯一出路是全量重建。这个认知很重要，面试时问「索引数据丢了怎么办」，答「靠消息队列重放」是错的。

单机学习项目的补救办法很土：把 `forum:events:v1` 和索引一起清掉，然后写一个循环把 `articles` 全表推一遍。生产的做法是常备一个重建命令，随时能跑。

```go
		t.Fatal("expected an error")
	}
	var apiErr *APIError
	if !errors.As(err, &apiErr) {
		t.Fatalf("want *APIError, got %T", err)
	}
	if apiErr.Code != "invalid_search_q" || apiErr.Status != http.StatusBadRequest {
		t.Fatalf("apiErr = %+v", apiErr)
	}
}
```

### 8.2 这些测试为什么值得写

没有真实 Meilisearch 也能测，靠的是 `httptest`。它会起一个真实的 HTTP 服务，客户端的代码路径（拼 URL、设头、序列化、读响应）全部走到，只有「对面是谁」被换掉了。

这套测试抓住过两个真实缺陷：

| 缺陷 | 测试怎么发现 |
| --- | --- |
| 202 响应的字段是 `taskUid`，我用 `uid` 去解，拿到 0 然后去查 `/tasks/0` | `unexpected GET /tasks/0` |
| 建索引后没等任务就去写 settings，时序上会 404 | `TestEnsureIndexCreatesOnlyWhenMissing` 里没有 `/tasks/1` 的分支就被访问了 |

第一个如果没有测试，线上表现是「索引一直写不进去，日志说任务不存在」，和真实原因毫无关系，可能要查一个下午。

期望 `data.list` 里有一条，`data.total` 为 1，`data.list[0].like_count` 有值（说明回查了 MySQL）。

## 9. 边界与面试追问

### 9.1 这套方案的固有延迟

发帖到能搜到，中间要经过：事务提交、relay 最多 200ms 轮询、Stream 投递、消费者轮询（`readBlock` 2 秒，但消息到达会立即唤醒）、HTTP 写索引、任务完成。

实际观测在 300ms 到 1 秒之间。这个延迟对论坛可以接受，对「下单后立刻按关键词查订单」的场景不行。

要缩短延迟，只有两条路：relay 轮询间隔调小（增加 MySQL 压力），或者把 Stream 投递做成同步的（就回到了双写的老问题）。这是一个必须承认的物理限制。

### 9.2 三种不一致情形

| 情形 | 表现 | 处理 |
| --- | --- | --- |
| 索引有、库已删 | 搜到点进去 404 | 查询时跳过的 id 直接不返回，见 6.1 |
| 库有、索引缺 | 搜不到 | 消费者重试；永久缺失要靠全量重建 |
| 索引内容旧 | 搜到旧标题 | 需要 `article.updated` 事件，本项目没有编辑接口 |

第一种已经在代码里处理了。第二种靠 PEL 重试兜住大部分，消费者崩溃时消息不 ACK，重启后重放。第三种要等有了编辑功能再说，这个边界要说清楚，别声称「永远一致」。

### 9.3 明确不做

| 未做 | 原因 |
| --- | --- |
| 搜索建议与自动补全 | 需要额外的 `/search/suggest` 接口与前缀查询，属于另一个功能 |
| 高亮片段 | Meilisearch 支持 `attributesToHighlight`，但响应要加字段，前端要改，本章只给 id |
| 按作者、时间过滤 | Meilisearch 需要先配 `filterableAttributes`，再加查询参数，可以做，本章省了 |
| 搜索历史与热词 | 属于产品功能，与搜索引擎无关 |
| 多索引与别名切换 | 单索引够用，需要不停机重建时才引入 |
| 中文同义词与停用词 | Meilisearch 支持 `synonyms` 设置，需要人工维护词表 |
| 全量重建脚本 | 见 7.6，能力要有，本章不落代码 |

### 9.4 面试追问

**问：为什么不用 MySQL 的 FULLTEXT？**
答：MySQL 5.7 之后支持 `ngram` 分词器做中文全文索引，能用。问题在三点：相关性排序能力弱（只有 TF-IDF 的简化版）、不支持前缀模糊与容错、索引和数据在同一台库上，搜索压力会挤占写入。几千篇的规模 FULLTEXT 够用，规模上去就得换。

**问：倒排索引具体怎么存的？**
答：一个词典加一个倒排表。词典是从词到倒排表偏移的映射，倒排表里放文档 id 列表，通常还会带词频和位置用来算相关性。查询时对每个词查倒排表，然后按 AND 或 OR 求交集并集，最后按评分排序。用前缀压缩和跳表可以进一步压小体积、加快求交。

**问：为什么不双写，非要绕一圈消息队列？**
答：双写的问题是不一致无法回滚。MySQL 写成功、搜索引擎超时，两个系统的状态就分叉了，而且没有可靠的办法知道分叉了。用 outbox 之后，事件和业务在同一个事务里，只要事务提交了事件就一定在，剩下的是「什么时候同步」的时间问题，不是「是否会丢」的正确性问题。

**问：多个消费者读同一条 Stream，消息会不会重复处理？**
答：不会重复「投递」，但会重复「处理」在不同语义上。同一消费组内，一条消息只会分给一个消费者；不同消费组各收到一份完整流。所以通知消费者处理一次点赞事件，索引消费者也处理一次，两边各干各的，都是期望行为。真正的重复风险在消费者崩溃重投，那个由各自的幂等机制兜（通知靠唯一索引，索引靠覆盖写入天然幂等）。

**问：索引写入失败会怎样？**
答：消息不 ACK，留在 PEL，下一轮用 `"0"` 重读。`WaitTask` 会把失败转成 error，所以 Meilisearch 返回任务失败时消费者知道。如果一直失败（比如字段超长），这条消息会永久卡在 PEL，需要人工介入。这一点是缺陷，生产要加最大重试次数和死信处理，本章没做。

**问：搜索能不能立刻搜到刚发的文章？**
答：不能保证。链路有 300ms 到 1 秒的延迟。产品上的处理是：发帖成功后前端直接跳详情页，不走搜索；搜索框加一个「结果可能延迟」的提示。硬要实时只能用双写，而双写的可靠性代价更大。

**问：为什么搜索只取 id 不取全文？**
答：为了避免内容在两处各存一份。宽索引的问题是任何字段改动都要重建索引，作者改名、点赞数变化都会让索引里的数据过时。瘦索引只存可搜索的字段，展示数据回 MySQL 拿，代价是一次主键 IN 查询，通常 1 毫秒以内。

**问：相关性排序是怎么算的？**
答：Meilisearch 默认按一组规则排序：词距越近越靠前、字段权重（`searchableAttributes` 里的顺序决定，标题比正文权重高）、精确度、词频。可以调，也可以用 `showRankingScore` 看每条的分数。Elasticsearch 是 BM25，Meilisearch 的实现细节不同但思路接近。
