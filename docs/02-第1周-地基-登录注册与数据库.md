## 第 1 步：工程与依赖

项目骨架已经建好 `go.mod`，模块名 `forum-backend`，所以**不要再执行 `go mod init`**。

### 1.1 模块名为什么可以是一个短名字

Go 模块名是项目的唯一导入标识，不要求对应真实网址。很多教程写 `github.com/你的名字/项目名`，因为那些项目打算推到 GitHub。本项目暂时不放 GitHub，用短名字最省事，本地开发完全够用。将来发布到 GitHub 时，模块路径要改成仓库完整导入路径，同时更新项目内部所有 import 并运行 `go mod tidy`。只改 `go.mod` 一行会让内部 import 全部失效。

### 1.2 两个依赖文件

| 文件 | 作用 | 怎么维护 |
| --- | --- | --- |
| `go.mod` | 依赖清单，记录包名与版本 | `go get` 加包，`go mod tidy` 统一整理 |
| `go.sum` | 依赖内容的校验指纹，防止包被篡改 | 由命令维护，不要手改 |

```powershell
go mod tidy
go build ./...
go test ./...
```

判断成功的依据是这三条命令退出码为 0，终端没有报错输出。旧版文档写「看到没有红色报错就是成功」，终端配色因人而异，已改成可验证的命令。

## 第 2 步：配置加载（internal/config/config.go）

**为什么要有配置文件**：地址、端口、密钥这些运行参数写在代码里，换一台机器就要改代码重新编译。放到配置文件里，同一份二进制可以跑在不同环境。

### 2.1 完整文件（与仓库源码一致）

```go
package config

import (
	"errors"
	"fmt"
	"io/fs"
	"os"
	"strings"

	"github.com/spf13/viper"
)

// Load 从 config/config.yaml 读取配置，并用环境变量覆盖敏感项。
func Load() (*Config, error) {
	v := viper.New()

	// 配置文件里没写的项用默认值兜底，避免端口为 0、过期时间为 0。
	v.SetDefault("server.port", 8080)
	v.SetDefault("jwt.expire", 24)

	// CONFIG_PATH 允许部署时传绝对路径；默认路径相对于进程工作目录。
	configPath := os.Getenv("CONFIG_PATH")
	if configPath == "" {
		configPath = "config/config.yaml"
	}
	v.SetConfigFile(configPath)

	// 读配置。用 errors.As 与 errors.Is 同时覆盖两种「文件不存在」的返回形态。
	if err := v.ReadInConfig(); err != nil {
		var notFound viper.ConfigFileNotFoundError
		if errors.As(err, &notFound) || errors.Is(err, fs.ErrNotExist) {
			return nil, fmt.Errorf("config file not found: %w", err)
		}
		return nil, fmt.Errorf("read config: %w", err)
	}

	// AutomaticEnv 加 BindEnv 让 JWT_SECRET、MYSQL_PASSWORD 覆盖 yaml 里的值。
	v.AutomaticEnv()
	v.SetEnvKeyReplacer(strings.NewReplacer(".", "_"))
	_ = v.BindEnv("jwt.secret")
	_ = v.BindEnv("mysql.password")

	cfg := &Config{}
	if err := v.Unmarshal(cfg); err != nil {
		return nil, fmt.Errorf("unmarshal config: %w", err)
	}

	// 空密钥会让所有 token 形同虚设，启动时直接拒绝。
	if cfg.JWT.Secret == "" {
		return nil, fmt.Errorf("config: jwt.secret is required")
	}
	return cfg, nil
}
```

### 2.2 逐行拆解

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `v := viper.New()` | 创建一个独立实例 | 避免全局 Viper 状态被别的包意外修改 |
| `v.SetDefault(...)` | 设置兜底值 | 配置文件漏写端口时服务仍能启动 |
| `os.Getenv("CONFIG_PATH")` | 允许外部指定路径 | 从别的目录启动二进制时，相对路径会失效 |
| `v.SetConfigFile(configPath)` | 明确指定文件 | 不依赖按当前目录搜索，行为可预测 |
| `errors.As(err, &notFound)` | 识别 Viper 的搜索模式错误 | `FindConfigFile` 找不到时返回该类型 |
| `errors.Is(err, fs.ErrNotExist)` | 识别文件系统错误 | **见 2.3 勘误**，`SetConfigFile` 下缺文件返回 `*os.PathError` |
| `fmt.Errorf("...: %w", err)` | 包装错误 | 上层能看出失败发生在读配置还是反序列化 [来源: https://go.dev/wiki/CodeReviewComments] |
| `v.AutomaticEnv()` 与 `BindEnv` | 读取环境变量覆盖 | 真实密码和密钥不必写进被 Git 跟踪的文件 |
| `strings.NewReplacer(".", "_")` | 把 `jwt.secret` 映射成 `JWT_SECRET` | 环境变量名不能含点 |
| `v.Unmarshal(cfg)` | 按 `mapstructure` 标签填结构体 | 字段名与 yaml 层级解耦 |
| `if cfg.JWT.Secret == ""` | 必填校验 | 空密钥签出的 token 任何人都能伪造 |

### 2.3 勘误：旧版示例漏掉了 `fs.ErrNotExist`

旧版 02 章的示例只写 `errors.As(err, &viper.ConfigFileNotFoundError)`，并据此讲「区分缺文件和格式错误」。这个判断在 `SetConfigFile` 模式下会漏判。指定明确文件路径后，`ReadInConfig` 打不开文件时返回的是 `*fs.PathError`，`errors.As` 到 `ConfigFileNotFoundError` 会失败，于是缺文件被归到「read config」分支。仓库源码已经用 `errors.Is(err, fs.ErrNotExist)` 补齐，本章示例已同步。

判断错误类型的通用做法：先看这个库在该调用路径下实际返回什么类型，再决定用 `errors.As` 还是 `errors.Is`。照搬别的示例容易踩这类坑。

### 2.4 配置字段怎么和 yaml 对上

Viper 用结构体上的 `mapstructure` 标签映射，例如 `server.port` 对应 `Config.Server.Port`。`config/config.yaml` 里有一份占位的 MySQL 密码和示例 JWT secret，学习时用 `MYSQL_PASSWORD`、`JWT_SECRET` 环境变量覆盖，提交前确认没有写入真实凭据。当前项目只用了读 YAML 和环境变量覆盖，没有实现配置热加载，讲项目时只说自己实际用到的能力。

## 第 3 步：连接数据库与自动建表

先在 MySQL 里创建数据库。`InitDB` 连接指定数据库后调用 `AutoMigrate` 建表，它不会创建数据库本身。

```sql
CREATE DATABASE forum CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

### 3.1 完整文件（与仓库源码一致）

```go
package config

import (
	"fmt"
	"time"

	mysqlDriver "github.com/go-sql-driver/mysql"
	gormmysql "gorm.io/driver/mysql"
	"gorm.io/gorm"
	gormlogger "gorm.io/gorm/logger"

	"forum-backend/internal/model"
)

// InitDB 用配置创建 MySQL 连接并自动建表。
func InitDB(cfg *MySQLConfig) (*gorm.DB, error) {
	// 用驱动提供的 Config 拼 DSN，避免手工拼接时漏掉转义。
	dsnConfig := mysqlDriver.Config{
		User:      cfg.User,
		Passwd:    cfg.Password,
		Net:       "tcp",
		Addr:      fmt.Sprintf("%s:%d", cfg.Host, cfg.Port),
		DBName:    cfg.DBName,
		Params:    map[string]string{"charset": "utf8mb4"},
		ParseTime: true, // 让时间列能扫描进 time.Time
		Loc:       time.Local,
	}
	dsn := dsnConfig.FormatDSN()

	db, err := gorm.Open(gormmysql.Open(dsn), &gorm.Config{
		// 把唯一键冲突等常见数据库错误转成可用 errors.Is 判断的 GORM 错误。
		TranslateError: true,
		// Warn 级别会记录错误与慢查询，应用侧在边界再记录一次业务上下文。
		Logger: gormlogger.Default.LogMode(gormlogger.Warn),
	})
	if err != nil {
		return nil, fmt.Errorf("failed to connect to database: %w", err)
	}

	// AutoMigrate 建表或补列，学习阶段够用。
	if err := db.AutoMigrate(&model.User{}, model.Article{}, model.Comment{}); err != nil {
		return nil, fmt.Errorf("failed to auto-migrate database: %w", err)
	}
	return db, nil
}
```

### 3.2 逐行拆解

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `mysqlDriver.Config{...}` | 结构化拼 DSN | 密码里含特殊字符时手工拼接容易出错 |
| `ParseTime: true` | 解析 MySQL 时间类型 | 不开会把 DATETIME 读成字节串 |
| `Params: charset=utf8mb4` | 指定连接字符集 | 支持中文与 emoji |
| `TranslateError: true` | 转换数据库错误 | `errors.Is(err, gorm.ErrDuplicatedKey)` 才能可靠判断重名 |
| `Logger: ...Warn` | 记录错误与慢 SQL | 见 3.3 勘误 |
| `AutoMigrate(...)` | 建表、加列 | 学习阶段方便；`Article{}` 与 `Comment{}` 传值也能被 GORM 解析，惯例传指针，两者都能工作 |
| 两处 `%w` | 包装错误 | 日志能区分连接失败与迁移失败 |

`AutoMigrate` 适合本地学习时创建或补充表结构。它缺少版本化、回滚和数据迁移能力，字段重命名、删列、改类型这类操作要交给版本化 migration，并先备份重要数据。

### 3.3 勘误：日志级别与源码不一致

旧版 02 章示例写 `Logger: gormlogger.Default.LogMode(gormlogger.Silent)`，并用一大段文字论述「GORM 的 SQL 错误日志已关闭，不会重复打印」。仓库源码实际是 `gormlogger.Warn`，Warn 级别会输出错误与慢查询。本章示例已改成与源码一致。

由此得到的正确表述：GORM 在 Warn 级别会记录它自己看到的 SQL 层错误；应用层在 handler 或 main 记录一次业务上下文。两者关注点不同，排查时都要看。若确实要关闭 GORM 日志，改成 Silent 并同步修改本节说明，别让文档和代码各说一套。

## 第 4 步：理解数据模型

`internal/model/models.go` 已定义三张表，逐字段读一遍：

| 表 | 字段 | 关键 tag | 作用 |
| --- | --- | --- | --- |
| users | ID | `gorm:"primaryKey"` | 自增主键 |
| users | Username | `gorm:"size:64;uniqueIndex;not null"` | 唯一约束兜底并发重名 |
| users | Password | `json:"-"` | 序列化时永远不返回哈希 |
| articles | UserID | `gorm:"index;not null"` | 外键列加索引，按用户查文章才快 |
| articles | User | `json:"user,omitempty"` | 关联查询填充，见下方提醒 |
| comments | ArticleID、UserID | `gorm:"index;not null"` | 按文章或用户过滤 |

三个容易忽略的点：

1. `User.Password` 的 `json:"-"` 保护的是序列化输出，数据库里仍存哈希。
2. `Article.User` 是值类型 `User`。Go 的 `encoding/json` 对结构体零值不会因 `omitempty` 而省略，所以未调用 `Preload("User")` 时，响应里仍会带出一个全零 user 对象。第 03 章用 DTO 处理这个问题。
3. 业务校验允许用户名最长 32，GORM 列宽是 64。教程目标应让业务规则、数据库字段和 API 文档采用同一个上限（本项目选 32），并在已有数据库中用版本化迁移调整列宽。只改 Go 校验会让已有 schema 与新安装 schema 不一致。用户名限定为 ASCII 字母、数字、下划线时，字节数与字符数相同；将来允许 Unicode 要重新定义长度规则。

> bcrypt 是带随机盐的密码哈希，验证用 `CompareHashAndPassword`，没有「解密」这一步。它提高离线猜测成本，同时仍要限制尝试频率、鼓励不易猜的密码并保护数据库。

## 第 5 步：用户业务逻辑（internal/service/user.go）

### 5.1 完整文件（与仓库源码一致）

```go
// Package service 业务逻辑层：核心规则都在这层，便于单测。
package service

import (
	"context"
	"errors"
	"fmt"
	"forum-backend/internal/model"
	"regexp"

	"golang.org/x/crypto/bcrypt"
	"gorm.io/gorm"
)

// UserService 用户业务逻辑
type UserService struct {
	db *gorm.DB // 小写字段，包外不能直接改，外部只能通过方法操作
}

func NewUserService(db *gorm.DB) *UserService {
	return &UserService{db: db}
}

// 哨兵错误，handler 用 errors.Is 判断并映射成 HTTP 状态码。
var (
	ErrInvalidInput       = errors.New("invalid input")
	ErrUserNameTaken      = errors.New("username already taken")
	ErrInvalidCredentials = errors.New("invalid username or password")
)

const bcryptMaxBytes = 72 // bcrypt 按字节限制输入长度，超过会报错

var usernameRe = regexp.MustCompile(`^[a-zA-Z0-9_]+$`)

// Register 注册用户：校验输入、哈希密码、写入数据库。
func (s *UserService) Register(ctx context.Context, username, password string) (*model.User, error) {
	if err := validateCredentials(username, password); err != nil {
		return nil, err
	}
	// 先哈希再插入，数据库里只有哈希，没有明文。
	hashed, err := bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)
	if err != nil {
		return nil, fmt.Errorf("hash password: %w", err)
	}

	user := &model.User{Username: username, Password: string(hashed)}
	if err := s.db.WithContext(ctx).Create(user).Error; err != nil {
		// 唯一索引负责兜底并发注册，应用层「先查再插」挡不住竞态。
		if errors.Is(err, gorm.ErrDuplicatedKey) {
			return nil, ErrUserNameTaken
		}
		return nil, fmt.Errorf("create user: %w", err)
	}
	return user, nil
}

// validateCredentials 只做纯输入校验，方便写表驱动测试。
func validateCredentials(username, password string) error {
	if l := len(username); l < 3 || l > 32 {
		return fmt.Errorf("%w: username length must be 3-32", ErrInvalidInput)
	}
	if !usernameRe.MatchString(username) {
		return fmt.Errorf("%w: username contains illegal characters", ErrInvalidInput)
	}
	// len(string) 得到的就是字节数，与 bcrypt 的限制单位一致。
	if len(password) < 8 || len(password) > bcryptMaxBytes {
		return fmt.Errorf("%w: password length invalid", ErrInvalidInput)
	}
	return nil
}

// Login 查找用户并用 bcrypt 比对密码。
func (s *UserService) Login(ctx context.Context, username, password string) (*model.User, error) {
	var user model.User
	if err := s.db.WithContext(ctx).Where("username = ?", username).First(&user).Error; err != nil {
		if errors.Is(err, gorm.ErrRecordNotFound) {
			return nil, ErrInvalidCredentials
		}
		// 数据库故障属于服务端问题，保留上下文供排查。
		return nil, fmt.Errorf("find user: %w", err)
	}

	if err := bcrypt.CompareHashAndPassword([]byte(user.Password), []byte(password)); err != nil {
		if errors.Is(err, bcrypt.ErrMismatchedHashAndPassword) {
			return nil, ErrInvalidCredentials
		}
		// 已存哈希格式损坏属于数据问题，不能伪装成密码错误。
		return nil, fmt.Errorf("compare password hash: %w", err)
	}
	return &user, nil
}
```

### 5.2 逐行拆解（注册）

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `db *gorm.DB` 小写字段 | 隐藏依赖 | 包外无法绕过 service 直接改连接 |
| `errors.New(...)` 三个哨兵 | 定义可判断的错误 | handler 用 `errors.Is` 映射状态码，不靠字符串比较 |
| `bcryptMaxBytes = 72` | 记录 bcrypt 上限 | 中文字符占多个字节，`len(string)` 按字节算才对 |
| `regexp.MustCompile` 放包级 | 只编译一次 | 每次请求重新编译正则纯属浪费 |
| `validateCredentials` | 纯函数校验 | 无需数据库即可写表驱动测试 |
| `GenerateFromPassword` | 生成带随机盐的哈希 | 相同密码每次哈希不同，无法从库里直接比对明文 |
| `WithContext(ctx)` | 传递取消信号 | 请求超时后查询跟着取消 |
| `errors.Is(err, gorm.ErrDuplicatedKey)` | 判断唯一键冲突 | 由数据库约束兜底并发注册 |
| `fmt.Errorf("create user: %w", err)` | 包装其他错误 | 保留错误链，日志可定位 |

### 5.3 逐行拆解（登录的三个分支）

| 分支 | 对外结果 | 为什么 |
| --- | --- | --- |
| `gorm.ErrRecordNotFound` | `ErrInvalidCredentials` → 401 | 与密码错误合并提示，避免泄露账号是否存在 |
| 其他数据库错误 | `fmt.Errorf("find user: %w", err)` → 500 | 数据库故障不能伪装成密码错误，否则客户端会反复重试 |
| `bcrypt.ErrMismatchedHashAndPassword` | `ErrInvalidCredentials` → 401 | 密码不匹配 |
| 哈希格式损坏 | `fmt.Errorf("compare password hash: %w", err)` → 500 | 属于服务端数据问题 |

`First` 在查不到记录时返回 `gorm.ErrRecordNotFound` [来源: https://gorm.io/docs/query.html]。用 `errors.Is` 判断，别用字符串包含匹配。

### 5.4 常见错误对照

| 写法 | 后果 | 正确做法 |
| --- | --- | --- |
| `if user exists { return taken }` 然后插入 | 并发下两个请求同时通过预检查，仍可能插重 | 依赖唯一索引并捕获冲突 |
| 用 `len([]rune(password))` 判断长度 | 中文密码按字符数算会超过 bcrypt 的 72 字节上限 | `len(password)` |
| 把明文密码直接和哈希字符串比较 | 永远不相等，且逻辑错误 | `CompareHashAndPassword` |
| 把数据库错误统一转成 401 | 客户端以为密码错，运维看不到故障 | 区分哨兵错误与内部错误 |

建议先给 `validateCredentials` 写表驱动测试，再观察 bcrypt 对相同密码多次生成的哈希为何不同。当前仓库还没有为这些规则添加测试。

## 第 6 步：JWT 生成与解析（pkg/jwt/jwt.go）

`go.mod` 已包含 `github.com/golang-jwt/jwt/v5`。只有新增或删除依赖时才需要 `go get` 或 `go mod tidy`。

### 6.1 完整文件（与仓库源码一致）

```go
// Package jwt 负责签发和验证本服务使用的 JWT。
package jwt

import (
	"errors"
	"fmt"
	"time"

	jwtlib "github.com/golang-jwt/jwt/v5"
)

const (
	issuer                = "forum-backend"
	accessTokenType       = "access"
	maxTokenLifetimeHours = 24 * 365
)

var errInvalidToken = errors.New("token is invalid or expired")

// Manager 持有本服务的 JWT 配置，由启动装配层创建一个实例并注入签发方与验证方。
type Manager struct {
	secret      string
	expireHours int
}

// NewManager 校验配置并创建 JWT 管理器。
func NewManager(secret string, expireHours int) (*Manager, error) {
	if secret == "" {
		return nil, errors.New("JWT secret is required")
	}
	if expireHours <= 0 || expireHours > maxTokenLifetimeHours {
		return nil, fmt.Errorf("expireHours must be between 1 and %d", maxTokenLifetimeHours)
	}
	return &Manager{secret: secret, expireHours: expireHours}, nil
}

// Claims 是本服务 token 中允许携带的身份信息。
type Claims struct {
	UserID    uint   `json:"user_id"`
	TokenType string `json:"token_type"`
	jwtlib.RegisteredClaims
}

// Sign 为指定用户签发 access token。
func (m *Manager) Sign(userID uint) (string, error) {
	if userID == 0 {
		return "", errors.New("userID must be greater than zero")
	}
	// 只取一次当前时间，保证 iat 与 exp 使用同一个基准。
	now := time.Now()
	ttl := time.Duration(m.expireHours) * time.Hour
	claims := Claims{
		UserID:    userID,
		TokenType: accessTokenType,
		RegisteredClaims: jwtlib.RegisteredClaims{
			Issuer:    issuer,
			Subject:   fmt.Sprintf("%d", userID),
			IssuedAt:  jwtlib.NewNumericDate(now),
			ExpiresAt: jwtlib.NewNumericDate(now.Add(ttl)),
		},
	}
	token := jwtlib.NewWithClaims(jwtlib.SigningMethodHS256, claims)
	return token.SignedString([]byte(m.secret))
}

// Parse 验证签名、算法、issuer、过期时间和 token 类型，成功时返回 userID。
func (m *Manager) Parse(tokenStr string) (uint, error) {
	if tokenStr == "" {
		return 0, errInvalidToken
	}
	claims := &Claims{}
	token, err := jwtlib.ParseWithClaims(
		tokenStr,
		claims,
		func(token *jwtlib.Token) (any, error) {
			return []byte(m.secret), nil
		},
		jwtlib.WithValidMethods([]string{jwtlib.SigningMethodHS256.Alg()}),
		jwtlib.WithIssuer(issuer),
		jwtlib.WithExpirationRequired(),
		jwtlib.WithIssuedAt(),
	)
	if err != nil || token == nil || !token.Valid {
		return 0, errInvalidToken
	}
	if claims.UserID == 0 || claims.TokenType != accessTokenType || claims.Subject != fmt.Sprintf("%d", claims.UserID) {
		return 0, errInvalidToken
	}
	return claims.UserID, nil
}
```

### 6.2 逐行拆解

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `NewManager` 校验 secret 与时长 | 启动时拒绝坏配置 | 空密钥等于没有鉴权；`time.Duration` 纳秒乘法在极大值时可能溢出 |
| `now := time.Now()` 只取一次 | 统一时间基准 | `iat` 与 `exp` 的差值正好等于配置的整小时数 |
| `jwtlib.NewNumericDate` | 转成 JWT 数字时间 | 精度截到秒，从实际签发时刻到过期点最多少不足 1 秒 |
| `TokenType: "access"` | 标记用途 | 将来加 refresh token 时，解析端会拒绝把刷新令牌当访问令牌 |
| `WithValidMethods` | 限定 HS256 | 阻止攻击者用 `alg: none` 或其他算法绕过校验 |
| `WithIssuer` | 校验签发方 | 拒绝别的服务签发的同密钥 token |
| `WithExpirationRequired` | 强制要求 exp | 没有过期时间的 token 会永久有效 |
| `WithIssuedAt` | 让验证端参与 iat 校验 | 是否拒绝未来 iat 依 golang-jwt/jwt v5 的具体版本实现，建议造一个 iat 在未来的 token 实测后再把结论写进简历 |
| 末尾三个 claims 检查 | 交叉校验 userID、subject、type | 签名合法也要验证内容符合本服务约定 |
| `errInvalidToken` 统一返回 | 不暴露失败细节 | 签名错误、格式错误、过期都给同一个对外提示 |

### 6.3 JWT 是什么

一段由三部分组成的字符串 `header.payload.signature`。

| 部分 | 内容 | 提醒 |
| --- | --- | --- |
| header | 算法，本项目是 HS256 | 验证端必须限定允许的算法 |
| payload | user_id、token_type、issuer、subject、签发时间、过期时间 | 只是 Base64 编码，客户端能读，不能放密码等秘密 |
| signature | 用 secret 对前两部分签名 | secret 泄露等于任何人都能签发 token |

**面试点的辩证说法**：JWT 让服务不必保存会话状态，多台机器都能独立验签，横向扩展方便。代价是 token 在过期前难以主动吊销，用户改密或管理员封禁后旧 token 可能继续可用。所以要有较短过期时间，或另行设计撤销列表。加上这次 claims 校验后，旧格式 token 因缺少 issuer、过期时间或 token type 可能无法通过验证，用户需要重新登录。

### 7.1 完整文件（与仓库源码一致）

```go
// Package middleware 存放 Gin 中间件。
package middleware

import (
	"net/http"
	"strings"

	"github.com/gin-gonic/gin"

	"forum-backend/pkg/jwt"
	"forum-backend/pkg/response"
)

// JWTAuth 校验 Authorization: Bearer <token>，并把 userID 放入 Gin context。
func JWTAuth(jwtManager *jwt.Manager) gin.HandlerFunc {
	return func(c *gin.Context) {
		authorization := c.GetHeader("Authorization")
		scheme, tokenString, ok := strings.Cut(authorization, " ")
		if !ok || !strings.EqualFold(scheme, "Bearer") || strings.TrimSpace(tokenString) == "" {
			response.Error(c, http.StatusUnauthorized, "未登录")
			c.Abort()
			return
		}

		userID, err := jwtManager.Parse(strings.TrimSpace(tokenString))
		if err != nil {
			response.Error(c, http.StatusUnauthorized, "登录已过期，请重新登录")
			c.Abort()
			return
		}

		// 后续 handler 用 c.GetUint("userID") 取当前用户。
		c.Set("userID", userID)
		c.Next()
	}
}
```

### 7.2 逐行拆解

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `strings.Cut(header, " ")` | 拆出 scheme 与 token | 比手写下标安全，缺少空格直接返回 ok=false |
| `EqualFold(scheme, "Bearer")` | 忽略大小写比较 | HTTP 认证方案名大小写不敏感 |
| `TrimSpace` | 去掉多余空白 | 避免把尾随空格带进签名校验 |
| `c.Abort()` | 阻止后续 handler 执行 | 鉴权失败必须终止链路 |
| `c.Set("userID", userID)` | 把身份放进 context | handler 从 token 判定作者，不接受客户端传的 user_id |
| `c.Next()` | 放行到下一个 handler | 中间件链继续 |

`c.Next()` 表示校验通过继续往下走，`c.Abort()` 表示终止。鉴权失败统一返回 401，不把签名错误、格式错误、过期的细节暴露给客户端。JWT payload 只是编码后可读的数据，别放密码或其他秘密。

## 第 8 步：控制器与对外响应（internal/handler/）

### 8.0 先把一件事定下来：DTO 要不要单独放一个文件

改动前的 handler 直接把数据库模型交给响应包。

**概念伪代码**：下面这行是改动前的写法，仓库里已经替换掉，不要复制进项目。

```go
// 概念伪代码：改动前的写法，仓库里已经替换掉。
response.OK(c, user) // user 是 *model.User
```

`model.User` 的 `Password` 带 `json:"-"`，眼下不会泄露 bcrypt 哈希。真正的隐患在别处：响应的字段形状被表结构绑死。以后给 `User` 加一个内部字段并写上 json tag，客户端会自动多收到这个字段，服务端没有任何一道关卡能拦住。

本步做法：在 `internal/handler/` 下新建 `dto.go`，把所有对外响应结构体和转换函数集中放进去。不新建 `internal/dto` 包。

| 方案 | 依赖方向 | 当前规模下的判断 |
| --- | --- | --- |
| 类型散落在各 handler 文件里 | 无新增 | 契约不可见，同一个响应形状容易被复制出好几份 |
| `internal/handler/dto.go` 同包独立文件 | 无新增包 | 采用。契约在目录树里可见，新增响应类型有唯一去处 |
| `internal/dto` 独立包 | 多一条 import 边 | 暂不采用。只有 handler 一个包需要这些类型 |

**为什么只拆文件，暂不拆包**。看依赖方向，别看文件数。`service` 返回 `*model.User`，`handler` 负责转成 `userResp`，整条链路上只有 handler 一个包需要这些类型。Go 官方反过来提醒过，把程序里所有对外类型塞进一个叫 `api`、`types`、`interfaces` 的包是错误做法，这类包会无限膨胀且不表达职责 [来源: https://go.dev/blog/package-names]。`internal/dto` 按「这是什么种类的类型」命名，性质接近。等出现 gRPC 与 HTTP 双入口、v1 与 v2 响应共存，或 service 需要直接产出 DTO，才值得付一个新包的成本。

**官方明文与工程惯例要分开**。Go 官方没有「一个结构体一个文件」的规则。`CodeReviewComments` 明文要求的是，所有导出的顶层名字要有 doc comment，非平凡的非导出类型与函数也建议写 [来源: https://go.dev/wiki/CodeReviewComments]。所以下面每个小写类型都写了注释，这部分属于官方要求。「单独放一个文件」属于团队约定，目的是让契约可见。把约定说成官方规定，是学习文档常见的失真。

完整文件：`internal/handler/dto.go` 在第 1 周结束时的快照。03 章 3.8 会往同一个文件追加文章相关 DTO，6.3 再追加评论与列表 DTO，追加后仍保持一个文件。本代码块作为第 1 周的状态保留，不用回头改。对照当前仓库时看「多了哪些声明」，别把快照当成永久现状。

```go
package handler

import (
	"time"

	"forum-backend/internal/model"
)

// 本文件集中存放对外响应的结构体，以及从 model 到响应结构体的转换函数。
// 单独成文件是为了让「客户端能看见哪些字段」在目录树里一眼可查，
// 也避免把数据库模型直接交给 response.OK 序列化。

// userResp 是注册与登录接口对外返回的用户信息。
// 字段逐个列出，model.User 以后加字段不会自动出现在响应里。
// 这里刻意不写 Password：model.User 的 Password 带 json:"-"，
// 但 DTO 从源头就不给这个字段留位置，少一层依赖运气。
type userResp struct {
	ID        uint      `json:"id"`
	Username  string    `json:"username"`
	CreatedAt time.Time `json:"created_at"`
	UpdatedAt time.Time `json:"updated_at"`
}

// loginResp 是登录成功后 data 的形状。
// Token 与 User 平级，客户端解析一次就能拿到两份数据。
// User 用值类型，登录成功时一定有用户，不需要指针和 omitempty。
type loginResp struct {
	Token string   `json:"token"`
	User  userResp `json:"user"`
}

// toUserResp 把数据库模型转换成对外结构体。
// 转换只发生在 handler 层：service 继续只认识 model.User，
// 不需要 import handler 包，依赖方向保持单向。
func toUserResp(u *model.User) userResp {
	return userResp{
		ID:        u.ID,
		Username:  u.Username,
		CreatedAt: u.CreatedAt,
		UpdatedAt: u.UpdatedAt,
	}
}
```

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `package handler` | 与 `user.go` 同包 | 不新增 import 边，`user.go` 直接调用 `toUserResp` |
| `import "forum-backend/internal/model"` | 只依赖数据模型 | handler 认识 model，service 不认识 handler，依赖保持单向 |
| `userResp` 的四个字段 | 逐个列出允许公开的字段 | 数据库加字段不会自动扩散到 API |
| 结构体里没有 `Password` | 从源头不给敏感字段留位置 | `json:"-"` 是第二道防线，DTO 是第一道 |
| `loginResp` | 把 `token` 与 `user` 合成一个结构体 | 字段名拼错时编译器报错，`gin.H` 要等到运行时才暴露 |
| `User userResp` 值类型 | 登录成功必有用户 | 省掉指针与 `omitempty`，少一层空值判断 |
| `toUserResp(u *model.User)` | 模型到 DTO 的转换 | 转换集中在 handler，service 继续只处理业务规则 |
| 每个小写类型都写注释 | 满足 doc comment 要求 | `CodeReviewComments` 明文要求非平凡的非导出声明也写注释 |

**验证形状没有变**。这次是内部重构，客户端收到的 JSON 必须和改动前逐字一致。可以临时在 `internal/handler` 包里写一个测试，用 `json.Marshal` 分别序列化 `model.User` 与 `toUserResp(u)`，比较两个字符串相等；登录侧再比一次 `gin.H{"token": ..., "user": u}` 与 `loginResp`。`encoding/json` 对 map 的键按字典序输出，`token` 排在 `user` 前面，与结构体字段顺序一致，所以两边可以直接比字符串 [来源: https://pkg.go.dev/encoding/json]。本项目实测结果如下，跑完记得删掉临时测试文件。

### 8.1 完整文件：internal/handler/user.go（与仓库源码一致）

```go
// Package handler 控制器层：接收 HTTP 请求、校验参数、调用 service。
package handler

import (
	"errors"
	"log"
	"net/http"

	"github.com/gin-gonic/gin"

	"forum-backend/internal/service"
	"forum-backend/pkg/jwt"
	"forum-backend/pkg/response"
)

// UserHandler 用户相关接口
type UserHandler struct {
	svc *service.UserService
	jwt *jwt.Manager
}

// NewUserHandler 注入用户 service 和 JWT 管理器。
func NewUserHandler(svc *service.UserService, jwtManager *jwt.Manager) *UserHandler {
	return &UserHandler{svc: svc, jwt: jwtManager}
}

type registerReq struct {
	Username string `json:"username" binding:"required"` // Gin 内置的参数校验，字段没传或为空就自动报参数错误
	Password string `json:"password" binding:"required"`
}

// Register POST /api/register
func (h *UserHandler) Register(c *gin.Context) {
	var req registerReq
	if err := c.ShouldBindJSON(&req); err != nil {
		response.Error(c, http.StatusBadRequest, "参数错误:"+err.Error())
		return
	}
	user, err := h.svc.Register(c.Request.Context(), req.Username, req.Password)
	if err != nil {
		switch {
		case errors.Is(err, service.ErrInvalidInput):
			response.Error(c, http.StatusBadRequest, "用户名或密码格式不符合要求")
		case errors.Is(err, service.ErrUserNameTaken):
			response.Error(c, http.StatusConflict, "用户名已被使用")
		default:
			logRequestError(c, "register", err)
			// 详细数据库错误留在服务端日志，客户端只收到通用提示。
			response.Error(c, http.StatusInternalServerError, "注册失败，请稍后重试")
		}
		return
	}
	// 只把 DTO 交给响应包，字段形状由 dto.go 统一定义。
	response.OK(c, toUserResp(user))
}

// Login POST /api/login
func (h *UserHandler) Login(c *gin.Context) {
	var req registerReq
	if err := c.ShouldBindJSON(&req); err != nil {
		response.Error(c, http.StatusBadRequest, "参数错误:"+err.Error())
		return
	}
	user, err := h.svc.Login(c.Request.Context(), req.Username, req.Password)
	if err != nil {
		switch {
		case errors.Is(err, service.ErrInvalidInput):
			response.Error(c, http.StatusBadRequest, "用户名或密码格式不符合要求")
		case errors.Is(err, service.ErrInvalidCredentials):
			response.Error(c, http.StatusUnauthorized, "用户名或密码错误")
		default:
			logRequestError(c, "login", err)
			response.Error(c, http.StatusInternalServerError, "登录失败，请稍后重试")
		}
		return
	}
	// 登录成功才签发 token。
	token, err := h.jwt.Sign(user.ID)
	if err != nil {
		logRequestError(c, "sign access token", err)
		response.Error(c, http.StatusInternalServerError, "登录失败，请稍后重试")
		return
	}
	// 用结构体代替 gin.H，字段写错时编译器会报出来，运行时才发现的拼写错误少一类。
	resp := loginResp{
		Token: token,
		User:  toUserResp(user),
	}
	response.OK(c, resp)
}

// logRequestError 只记录内部错误，Gin Logger 已负责每个请求的访问日志。
func logRequestError(c *gin.Context, operation string, err error) {
	log.Printf("%s failed: method=%s route=%s error=%v", operation, c.Request.Method, c.FullPath(), err)
}
```

### 8.2 逐行拆解与错误映射

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `ShouldBindJSON(&req)` | 解析 JSON 并检查 `required` | Gin 内置校验省掉逐字段判空，但纯空白字符串会通过 |
| `c.Request.Context()` | 取出请求 ctx | 一路传给 service 与 GORM |
| `errors.Is(err, ...)` | 判断哨兵错误 | 业务错误映射成 400、409、401 |
| `default` 分支 | 记录内部错误并返回 500 | 数据库错误文本不发给客户端 |
| `h.jwt.Sign(user.ID)` | 签发 token | Handler 只需调用 `Sign`，不必知道 secret 与算法 |
| `toUserResp(user)` | 把 model 转成 DTO | 只在 handler 层转换，字段形状见 8.0 |
| `loginResp{...}` | 组装登录响应 | 结构体字段拼错由编译器拦截，见 8.0 |
| `response.OK(c, ...)` | 统一响应封装 | 当前固定发 HTTP 200，见 00 章状态码口径 |

错误映射表：

| service 返回 | HTTP | 客户端提示 |
| --- | --- | --- |
| `ErrInvalidInput` | 400 | 用户名或密码格式不符合要求 |
| `ErrUserNameTaken` | 409 | 用户名已被使用 |
| `ErrInvalidCredentials` | 401 | 用户名或密码错误 |
| 其他错误 | 500 | 通用提示，详细信息进服务端日志 |

`binding:"required"` 只做必填校验，长度与字符规则仍由 service 判断。`err.Error()` 回显的是字段级绑定错误，内部数据库错误走 `default` 分支，两者边界要分清。

**为什么选 `ShouldBindJSON`**。Gin 官方把绑定分成 Must bind 与 Should bind 两组。`BindJSON` 出错时会调用 `AbortWithError(400, err)`，直接把状态码写成 400 并把 Content-Type 设为 `text/plain`，之后再改状态码会触发 `[GIN-debug] [WARNING] Headers were already written`；`ShouldBindJSON` 则返回错误，由开发者决定怎么响应 [来源: https://gin-gonic.com/en/docs/binding/binding-and-validation]。本项目要用统一响应包输出 `{code, message, data}`，所以选 Should 系列。官方也提醒，字段本身是结构体时，嵌套字段也要写 `binding:"required"` 才会参与校验。

构造函数不应为普通配置错误随意 `panic`，`NewManager` 返回 error，main 在启动时检查并退出。`UserHandler` 目前依赖具体的 `*UserService`，做隔离单测要先把依赖改成最小接口，学习阶段可用测试数据库做集成测试。

### 8.3 日志该记什么

| 情况 | 记录位置 | 用途 |
| --- | --- | --- |
| 启动配置、迁移、JWT、路由或监听失败 | main 记录一次并退出 | 这些错误发生在请求之外 |
| 每个请求的方法、路由、状态码、耗时 | `gin.Default()` 的 Logger | 访问日志，覆盖成功与 4xx、5xx |
| handler 未捕获的 panic | `gin.Default()` 的 Recovery | 阻止单个请求拖垮进程 |
| 注册、登录、签发 token 的内部故障 | handler 的 `logRequestError` | 保留内部错误原因 |
| 参数错误、重名、凭据错误、无效 token | 只由访问日志记录状态码 | 预期客户端错误，逐条打印会被刷屏 |

`logRequestError` 只写操作名、HTTP 方法、路由模板和内部错误，不记录请求体、密码、Authorization 头或 JWT。这样既保留排查信息，也避免敏感数据进入日志。GORM 在 Warn 级别记录 SQL 层错误，与应用日志记录的业务上下文用途不同。

## 第 9 步：路由注册（internal/router/router.go）

**增量修改**：下面这段替换 `router.go` 的 `New` 函数体。文件里还要有 `package router` 和 import：`errors`、`github.com/gin-gonic/gin`、`gorm.io/gorm`，以及 handler、middleware、service、jwt 四个内部包。

```go
// New 注册全部路由。db 由 main 创建后传入，错误处理集中在 main。
func New(db *gorm.DB, jwtManager *jwt.Manager) (*gin.Engine, error) {
	if db == nil {
		return nil, errors.New("router: database is required")
	}
	if jwtManager == nil {
		return nil, errors.New("router: JWT manager is required")
	}

	r := gin.Default()
	userSvc := service.NewUserService(db)
	userHandler := handler.NewUserHandler(userSvc, jwtManager)

	api := r.Group("/api")
	{
		api.POST("/register", userHandler.Register)
		api.POST("/login", userHandler.Login)

		// 受保护分组，第 2 周把文章、评论接口放这里。
		auth := api.Group("", middleware.JWTAuth(jwtManager))
		_ = auth
	}
	return r, nil
}
```

`db` 由 main 创建后传进来。在 router 里写 `db, _ := config.InitDB(...)` 会吞掉连接错误，连不上库也照常注册路由，排查时很痛苦。当前文件里没有 `/ping` 路由，README 与 01 章旧版的 `/ping` 说法已删除。

## 第 10 步：入口把一切接起来（cmd/server/main.go）

### 10.1 完整文件（与仓库源码一致）

```go
package main

import (
	"fmt"
	"log"

	"forum-backend/internal/config"
	"forum-backend/internal/router"
	"forum-backend/pkg/jwt"
)

func main() {
	cfg, err := config.Load()
	if err != nil {
		log.Fatalf("加载配置失败: %v", err)
	}

	// 数据库在入口创建，错误就地处理。
	db, err := config.InitDB(&cfg.MySQL)
	if err != nil {
		log.Fatalf("连接数据库失败: %v", err)
	}

	jwtManager, err := jwt.NewManager(cfg.JWT.Secret, cfg.JWT.Expire)
	if err != nil {
		log.Fatalf("JWT 配置错误: %v", err)
	}
	r, err := router.New(db, jwtManager)
	if err != nil {
		log.Fatalf("注册路由失败: %v", err)
	}

	// 端口从配置读，不写死 :8080。
	addr := fmt.Sprintf(":%d", cfg.Server.Port)
	log.Printf("server start at %s", addr)
	if err := r.Run(addr); err != nil {
		log.Fatalf("启动服务失败: %v", err)
	}
}
```

main 只做四件事：读配置、连数据库、建路由、启动监听。业务规则一行都不放这里。

> 上面是第 1 周的两参数版本。第 2 周按 03 章 7.2 装配 Redis 后，`main.go` 会多一次 `config.InitRedis` 调用，`router.New` 变成 `router.New(db, jwtManager, rdb)`，`ArticleService` 结构体也会多一个 `rdb` 字段。看到当前仓库源码已是三参数时，按 03 章 7.2 的三层清单核对，不要为了对齐本节改回去。

### 10.2 勘误：不要「先注释掉 InitDB」

旧版 02 章建议「MySQL 还没装好时，先注释掉 `InitDB` 那段，只验证配置读取和端口启动」。照做会编译失败：注释后变量 `db` 未定义，下面 `router.New(db, jwtManager)` 直接报 `undefined: db`。

想单独验证配置读取，正确做法是写一个小测试或临时程序只调用 `config.Load()` 并打印结果，然后运行完就删掉，不改 main。也可以先装好 MySQL，按验收步骤从头跑通。改入口代码来验证配置，代价是引入一个新的编译错误。

## 本周验收

### A. 启动前检查

1. 启动 MySQL，确认端口与 `config/config.yaml` 一致（默认 3306）。
2. 创建数据库（仅首次）：`CREATE DATABASE forum CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;`。用户名、密码和库名要与配置对应。
3. 从项目根目录启动服务：

```powershell
$env:MYSQL_PASSWORD = "你的本机MySQL密码"
$env:JWT_SECRET = "换成随机生成的长字符串"
go run ./cmd/server
```

服务成功启动后保持终端窗口打开。看到配置、连接或迁移错误时先修错误，再打开 Postman。

### B. 注册

1. `POST http://localhost:8080/api/register`，Body 选 raw → JSON：

```json
{
  "username": "learner_001",
  "password": "StudyGo_2026"
}
```

2. 选择 JSON 后 Postman 通常自动加 `Content-Type: application/json`，可在 Headers 里确认。
3. 成功时返回 HTTP 200，统一响应里 `code` 为 0，`data` 含新用户信息，且不出现 `password`。00 章合同表的 201 属于目标状态，扩展 `pkg/response` 后再改验收期望。
4. 再发一次相同请求，期望 HTTP 409。
5. 用 `ab` 加 `1234567`、错误 JSON 分别验证 400，服务不能因此退出。

每次重测注册换一个用户名，或在确认是本地学习数据库后清理测试用户，别清空不属于练习的数据。

### C. 登录

1. `POST http://localhost:8080/api/login`，使用刚注册的用户名与正确密码，期望 200 和 token。
2. 把密码改错，期望 401，提示「用户名或密码错误」。换成不存在的用户名，客户端收到的提示应相同。
3. 在 MySQL 检查：

```sql
SELECT id, username, password FROM users WHERE username = 'learner_001';
```

`password` 列应是 bcrypt 哈希，通常以 `$2a$` 或 `$2b$` 开头。别把哈希或 token 贴到公开地方。

### D. JWT 鉴权

拿到 token 只能证明登录 handler 返回了字符串。当前受保护分组里没有业务路由，所以这一节只能验证签发。第 2 周挂上 `/api/me` 或文章接口后，再按下面方式做端到端验证：Postman 的 Authorization → Bearer Token 粘贴 token，正确 token 放行，删掉或改坏一个字符应返回 401，过期 token 也应返回 401。

### E. 出错时按顺序排查

| 现象 | 先查什么 |
| --- | --- |
| 连接失败，无响应 | Go 服务是否还在运行、地址端口、终端启动错误 |
| 404 | 请求路径与 router 注册是否一致，服务是否重启 |
| 400 | Body 是否为 raw JSON、字段名、JSON 格式、输入规则 |
| 500 或启动报数据库错误 | MySQL 服务、账号密码、端口、`forum` 库是否存在 |
| 登录总是 401 | 注册是否成功、是否同一个库、存的是否是 bcrypt 哈希 |
| 有 token 仍 401 | 是否发到受保护路由、Header 格式、签发与解析的 secret 是否一致、token 是否过期 |

### F. 命令行快速验证

```bash
go run ./cmd/server
```

```bash
curl.exe -X POST localhost:8080/api/register -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"12345678"}'

curl.exe -X POST localhost:8080/api/login -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"12345678"}'

curl.exe -X POST localhost:8080/api/login -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"wrong"}'
```

上面三条是 Git Bash 写法，单引号里的 JSON 双引号会原样传给 `curl.exe`。若在 PowerShell 里跑，内联 JSON 要写成 `'{\"username\":...}'`，或把 JSON 存成文件后用 `-d @body.json`，实测与原因见 03 章 6.6.5。
