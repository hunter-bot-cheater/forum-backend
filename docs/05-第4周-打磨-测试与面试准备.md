## 第 1 步：怎么让代码可测试

### 1.1 单元测试示例：校验注册输入

**完整文件**，保存为 `internal/service/user_test.go`：

```go
package service

import "testing"

func TestValidateCredentials(t *testing.T) {
	// 表驱动测试：一行是一个用例，新增边界只需加一行。
	tests := []struct {
		name     string
		username string
		password string
		wantErr  bool
	}{
		{name: "valid", username: "new_user1", password: "12345678"},
		{name: "username too short", username: "ab", password: "12345678", wantErr: true},
		{name: "illegal username character", username: "user-name", password: "12345678", wantErr: true},
		{name: "password too short", username: "new_user1", password: "1234567", wantErr: true},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			err := validateCredentials(tt.username, tt.password)
			// 只比较「有没有错误」，避免把测试绑死在错误文本上。
			if (err != nil) != tt.wantErr {
				t.Fatalf("validateCredentials() error = %v, wantErr %v", err, tt.wantErr)
			}
		})
	}
}
```

| 代码 | 作用 | 为什么这样设计 |
| --- | --- | --- |
| `package service` | 同包测试 | 能直接调用未导出的 `validateCredentials` |
| `tests := []struct{...}` | 定义用例表 | 输入、期望集中在一处，边界好补 |
| `t.Run(tt.name, ...)` | 每个用例独立子测试 | 失败时能定位到具体用例，可用 `-run` 单独跑 |
| `(err != nil) != tt.wantErr` | 比较错误有无 | 错误文本改动不会让测试误报 |
| `t.Fatalf` | 失败即终止该子测试 | 避免后续断言在无效状态下继续 |

后续可以补的边界：用户名 3 与 32 字符、密码 8 与 72 字节、中文密码按字节超限、超长标题。真实的重复注册检查依赖数据库唯一索引，要测它需要专门的测试数据库，或先把 service 的数据库操作抽象成接口再注入 fake。内存 mock 测不出 MySQL 的行为。

> 面试点「怎么保证代码质量」：分层加接口抽象让 service 能脱离数据库测试，表驱动测试覆盖边界，`go test -race` 查并发问题。要同时说清哪些部分还没测到。

04a 到 04c 三章各自新增了一个测试文件，共三类，本周要把它们一起纳入 `go test ./...`：

| 测试 | 位置 | 测什么 | 依赖 |
| --- | --- | --- | --- |
| 事件 payload 往返与瘦事件字段数 | `internal/worker/event_test.go` | 序列化、事件 ID 长度、状态常量 | 纯逻辑，无外部依赖 |
| Swagger 核心路径清单 | `internal/router/swagger_contract_test.go` | `swagger.json` 的版本、`basePath`、十个关键路径 | 读生成物，生成物缺失时直接失败 |
| 连接登记与慢客户端剔除 | `internal/realtime/hub_test.go` | 一人多端投递、重复注销、离线静默、缓冲满踢人、真实 socket 一条 | 纯逻辑加 httptest，无外部依赖 |

worker 的投递与消费、通知接口的端到端验收仍需要真实 MySQL 与 Redis，按 04a 章 8.2 的脚本跑，别把它算进单元测试覆盖率。

## 第 2 步：接口测试（httptest）

`httptest` 在进程内调用 Gin 引擎，不需要占用真实端口。当前 `router.New` 的签名是 `New(deps Deps) (*gin.Engine, error)`，`Deps` 里有 `DB`、`JWT`、`Redis`、`Hub`、`WSOrigins`、`RateLimit`、`TrustedProxies` 七个字段。写测试前先核对 `internal/router/router.go`。这个签名在 04c 章从三参数改成了结构体，理由是依赖涨到四个之后位置参数容易传错顺序；`rdb` 由 `config.InitRedis` 创建，测试环境要能连到 Redis 或提供可用的客户端。

步骤：

1. 准备专用测试数据库，例如 `forum_test`，不要对日常开发或生产数据库执行测试写入。
2. 用测试配置调用 `config.InitDB` 建表，创建 `jwt.Manager`、Redis 客户端与 `realtime.NewHub()`，再调用 `router.New(router.Deps{DB: db, JWT: jwtManager, Redis: rdb, Hub: hub, Filter: filter.New([]string{"测试词"})})` 得到 Gin 引擎。`Search` 留空即可，`/api/search` 不会注册，不影响其余接口。
3. 用 `httptest.NewRecorder()` 创建响应记录器，用 `httptest.NewRequest()` 创建请求，设置 JSON 请求体与 `Content-Type`，调用 `engine.ServeHTTP(recorder, request)`。
4. 检查 HTTP 状态码和响应 JSON。先测错误输入期望 400，再测正确注册与登录期望 200。每个测试用独立用户名。响应体里顺带断言 `data` 不出现 `password` 字段，以及字段集合恰好是 02 章 8.0 里 `userResp` 列出的四个，这样以后给 `model.User` 加字段时测试会拦住意外的形状变化。

关于状态码：当前 `pkg/response.OK` 固定发 200，所以注册与登录都是 200。00 章 API 合同表里注册的 201 属于目标状态，扩展响应包之后测试期望要同步修改。旧版 05 章与 00 章在这一点的口径不一致，已按当前实现统一。

想让 handler 测试完全不依赖 MySQL，要先把 handler 与 service 的依赖改成接口再注入 fake。当前构造函数接收具体的 `*UserService`，所以本章不提供一个假装能直接注入 mock 的代码片段。

```powershell
go test ./...
go test ./... -cover
go test -race ./...
```

## 第 3 步：本机运行（学习项目的练习方式）

项目不依赖 Docker，MySQL 与 Redis 直接装在本机，Go 服务也在本机启动。

### 3.1 安装 MySQL（Windows）

1. 从 MySQL 官网下载 Community Server 的 MSI 安装包。
2. 安装时记下 root 密码，端口默认 3306。
3. 打开 MySQL 命令行，建项目用的库：

```sql
CREATE DATABASE forum CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

这里与 02 章用同一条 SQL，字符集和排序规则保持一致，避免两处文档给出不同建库语句。

### 3.2 安装 Redis（Windows）

Redis 服务端在 Windows 上的安装方式和兼容实现可能变化。初学阶段优先用 WSL2 中的 Linux 发行版，或选择仍受维护且与客户端兼容的 Redis 服务，不要从不明来源下载旧版安装包。若用 WSL2，在 Linux 终端安装并启动服务，再确认 Windows 上的 Go 程序能连到配置的地址和端口。

连通性验证：在能访问 Redis 的终端执行 `redis-cli ping`，收到 `PONG` 表示该终端到 Redis 可用。若 Go 服务在 Windows、Redis 在 WSL2，WSL 内成功并不能自动证明 Windows 主机也能连通，还要从 Windows 侧验证 `127.0.0.1:6379` 或按 WSL 网络配置填写实际地址。

### 3.3 配置并启动服务

旧版 05 章让用户「打开 `config/config.yaml` 把 mysql.user / mysql.password 改成你本机的」。该文件被 Git 跟踪，写真实密码有泄露风险，也与 README、00、02 章的安全说明冲突。正确做法是用环境变量或未跟踪的本地配置提供真实值：

```powershell
$env:MYSQL_PASSWORD = "你的本机MySQL密码"
$env:JWT_SECRET = "换成随机生成的长字符串"
$env:CONFIG_PATH = "config/config.local.yaml"  # 使用本地配置时
go run ./cmd/server
```

### 3.4 可选：写一个启动脚本

在项目根目录新建 `start.bat`：

```bat
@echo off
rem 切到脚本所在目录，双击时工作目录不对也能跑
cd /d "%~dp0"
echo 启动论坛服务...
go run ./cmd/server
pause
```

> 部署通常还包含生产环境的配置、安全、进程管理、日志、备份和监控。这里只练习本机依赖安装和启动。

### 3.5 从本机运行到上线前准备还缺什么

本机 MySQL、Redis 加 `go run` 只能证明开发环境能启动。真正部署前至少完成这些工作：

1. **配置隔离**：生产配置通过密钥管理服务或受限环境变量注入，JWT secret 用密码学安全随机值，DB 与 Redis 使用最小权限账号，限制配置文件和环境变量读取权限。
2. **数据库变更**：生产禁用启动时随意 `AutoMigrate`，改为版本化 migration，发布前备份，记录迁移是否向前与向后兼容，明确失败时的恢复步骤。先在 staging 用接近生产规模的数据演练。
3. **构建制品**：在干净环境运行 `go mod download`、`go test ./...`、`go test -race ./...`、`go vet ./...`、`go build -trimpath -o forum-server ./cmd/server`。记录 Go 版本、commit、依赖版本和产物校验值，不要在生产机临时 `go run`。
4. **服务运行**：配置非 root 系统用户、工作目录、环境文件权限、自动重启策略和资源限制。服务收到 SIGTERM 后停止接收新请求、设置超时并关闭 DB 与 Redis 连接。04a 章 7.1 已经给出 `signal.NotifyContext` 加 `WaitGroup` 的可落盘实现，把「后台 worker 是否真的退出」加进发布检查；没有验证过之前，不能声称滚动发布不中断请求。
5. **网络与 TLS**：由受控反向代理终止 HTTPS，只开放必要端口，Gin 的可信代理列表只配真实代理网段，限制请求体、连接和请求处理时长。
6. **健康检查**：实现并区分 liveness（进程活着）与 readiness（必要依赖可用）。启动探针要允许迁移耗时，健康检查不返回密钥、连接串或堆栈，平台探针路径与 router 注册一致。
7. **日志与观测**：日志输出到 stdout、stderr 或已配置的采集器，含时间、级别、路由模板、状态码、耗时和 request ID，不记录密码、Authorization、JWT、原始请求体或敏感 SQL 参数。为 5xx、DB 与 Redis 错误、限流拒绝和缓存命中率设告警阈值。
8. **数据保护**：明确 MySQL 备份频率、保留期、异地副本和加密，定期在隔离环境恢复并校验行数与业务可用性。Redis 若只存缓存可以重建，点赞或热榜若还没有可靠的自动重建流程（热榜见 04 章 4.7 的读路径懒加载自愈），不能只靠持久化配置当备份。
9. **发布与回滚**：staging 先部署，采用兼容型 DB migration，监控错误率和延迟，准备应用版本回滚与 DB 变更回滚或前向修复方案。二进制回滚无法安全撤销破坏性 schema 变更。
10. **API 文档与事件积压**：`swag init` 放进构建步骤，生成物入库并用 `git diff --exit-code -- api/swagger` 检查同步；生产构建用 `GIN_MODE=release` 关闭 Swagger UI。给 `outbox_events` 的 `pending`、`failed` 行数与消费组 PEL 长度设告警，确认停机重启能自动补投（04b 章 6.1、04a 章 9.2）。

逐项记录「配置或实现在哪里、怎么验证、失败时怎么处理」。缺少任一项时，描述成「学习项目的上线准备」或「staging 验证」。

## 第 5 步：整理面试讲稿

每个亮点准备三段式，练到能脱稿讲 2 分钟：

1. **背景与问题**：当时遇到什么问题，最好有可复现的观察。
2. **方案**：怎么解决，为什么选它，放弃了什么。
3. **效果与限制**：在什么条件下观察到什么结果，还有哪些已知问题。

完成并验证缓存、点赞或限流后，才把对应功能作为面试素材。缓存加固已在源码落盘；点赞、热榜、限流的十步跟做实现见 04 章，落盘并跑过 4.1 到 4.10 的验收前不能当面试素材。04a 的异步通知与 04b 的 API 契约同样要跑完各自验收才能写进简历，06 文档已补上这两段讲稿模板。
