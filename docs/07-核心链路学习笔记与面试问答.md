### 0.1 六个可以主动抛出的亮点

面试里最亏的一种情况是活干完了，讲的时候只讲出「我用 Redis 做了缓存」。下面六条是这套代码里真正能拉开差距的部分，每条都配了一句可以直接说出口的话和一个证据位置。

| # | 亮点 | 一句话讲法 | 证据 |
| --- | --- | --- | --- |
| 1 | Transactional Outbox + Redis Stream 消费组 | 点赞通知不走「写完库再发消息」，而是把事件和业务写在同一事务里，用 outbox 表兜住崩溃窗口，relay 轮询搬进 Stream，消费组加 PEL 保证至少一次 | 10.2、10.5、10.6 |
| 2 | 缓存击穿的三道闸 | 无锁读一次、singleflight 合并回源、fn 内二次确认，再把重建的 ctx 从请求取消里摘出来，避免一个用户断开带走所有等待者 | 6.6、6.7 |
| 3 | 热榜投影的四次返工 | ZSET 不能只做到「查出来塞进去」，先撞全表聚合，再撞重建期覆盖，再撞标记永不过期，再撞重建风暴，四次都有具体数字和取舍 | 第 8 章全章 |
| 4 | Redis Lua 令牌桶 | 限流判断与扣减必须原子，放在 Lua 里一次执行；Redis 挂掉时选择放行，因为限流是保护手段，不该成为新的故障点 | 9.2、9.4 |
| 5 | 幂等落在唯一索引 | 重复投递不靠内存去重也不靠先查后插，交给 `uk_notify_event` 唯一索引裁决，`OnConflict DoNothing` 一行搞定 | 10.7 |
| 6 | 契约测试锁住 swagger | 用测试断言 swagger 里必须有约定好的那几条路径，改路由忘了改注解会直接红 | 04b 章 |

六条的排列顺序按「被追问的深度」来，不是按重要性。第 1 条和第 3 条能撑起十分钟的深聊，第 6 条三十秒讲完，适合用来过渡。

**第 1 条怎么讲。**

> 点赞成功后要通知作者。最直白的写法是写完库再 `XADD`，但这两步不在一个事务里，进程崩在中间就永久丢一条通知，而且没人知道丢了。
>
> 所以我把「要发通知」变成 `outbox_events` 表里的一行，和点赞在同一个事务提交。数据库的原子性保证「业务成功则事件必在」。之后 relay 每 200 毫秒扫一次 `pending`，`XADD` 进 Stream，成功才改成 `published`。
>
> 消费侧用消费组加 PEL。消息投出去先进 PEL，业务写成功才 `XACK`。消费者崩了，重启后先读 `"0"` 把 PEL 里的补完，再读 `">"` 拿新消息。重复投递靠 `event_id` 唯一索引挡住。
>
> 最终结果是恰好一次，机制上是至少一次加幂等。

**第 3 条怎么讲。**

> 热榜最初我用 `GROUP BY` 查出来塞进 ZSET，上线前压测发现千万级点赞要十几秒，顺手查出四个问题：聚合没带 `LIMIT`、重建先 `DEL` 再 `ZADD` 会让并发读看到残缺榜、`ready` 标记永不过期导致榜单冻结、重建超时后每个请求都去重试把库打得更死。
>
> 四个修法分别是加 `LIMIT 500` 配覆盖索引、写临时 key 再 `RENAME` 原子换榜、给 `ready` 设一小时 TTL、失败后打三十秒冷却标记。最后一条尤其关键，因为降级路径本身可能成为新的压力源。

这两段可以直接背。细节在对应章节。

## 1. 全景：一个请求走过的九层

本章给六条链路的完整时序。1.2 是最长的读路径，1.3 是最典型的写路径，这两条按顺序逐步展开；1.4 用同一副骨架压缩另外四条（登录、发文章、发评论、热榜），只写与前面不同的地方。先把这六条背下来，后面各章讲的都是其中某一步的「为什么」。

### 1.1 分层与依赖方向

```text
                    ┌──────────────────────────────┐
                    │ cmd/server/main.go           │ 装配：配置、连接池、路由、worker、信号
                    └──────────────┬───────────────┘
                                   │ 显式传参，不用全局单例
                    ┌──────────────▼───────────────┐
                    │ internal/router              │ 路由表、全局中间件、Swagger 挂载
                    └──────────────┬───────────────┘
                                   │ gin.HandlerFunc 链
        ┌──────────────────────────┼──────────────────────────┐
        │ limitBody  RateLimit     │ JWTAuth                  │ 中间件
        └──────────────────────────┼──────────────────────────┘
                    ┌──────────────▼───────────────┐
                    │ internal/handler             │ 绑定、校验、DTO 转换、错误映射
                    └──────────────┬───────────────┘
                    ┌──────────────▼───────────────┐
                    │ internal/service             │ 业务规则、事务、缓存策略
                    └───────┬──────────────┬───────┘
                            │              │
                 ┌──────────▼───┐   ┌──────▼────────┐
                 │ GORM → MySQL │   │ go-redis      │
                 └──────────────┘   └───────────────┘
                            │              │
                    ┌───────▼──────────────▼───────┐
                    │ pkg/response                 │ { code, message, data }
                    └──────────────────────────────┘
```

依赖方向只有一条：外层认识内层，内层不认识外层。service 不认识 gin，handler 不认识 GORM 的查询构造。唯一例外是 `mapServiceError` 里出现了 `gorm.ErrRecordNotFound`，那是对 GORM 错误类型的统一翻译，放在边界处集中处理，比让每个 handler 各写一遍好。

### 1.2 读文章详情的完整链路

`GET /api/articles/1`，缓存未命中。这是最长的一条读路径，也是面试最常被要求「从头讲一遍」的那条。

1. **路由匹配（`gin.Engine`）**
   1. Gin 在路由树里找到 `GET /api/articles/:id`。这一步只决定用哪条处理链，还没碰任何业务代码。
   2. 底层是 Radix Tree（前缀树），同一层的静态段优先于参数段。`/api/articles/hot` 注册在 `/api/articles/:id` 之后，仍然走热榜 handler，不会被 `:id` 当成 id 为 `hot` 的文章。
   3. 匹配到的处理链是 `limitBody → RateLimit → ArticleHandler.Detail`，中间件按注册顺序排在 handler 前面。

2. **请求体限制（`limitBody`）**
   1. `c.Request.Body` 被包成 `http.MaxBytesReader(c.Writer, c.Request.Body, 1<<20)`，上限 1 MiB。
   2. GET 没有 body，这一层在这里是空转。它真正挡的是同组路由上的 POST，别因为读路径用不上就以为它多余。
   3. 超限时读到一半就返回错误，服务端随后关闭连接，不继续读剩余字节。没有这一层，一个几百 MB 的 JSON 会在 `c.ShouldBindJSON` 里整段进内存。

3. **限流（`middleware.RateLimit`）**
   1. key 是 `forum:dev:rate:ip:<ClientIP>`，按 IP 算，不区分用户。参数在 router 里一次性给死，`Capacity` 10、`Rate` 2。
   2. 一次 `EVAL` 在 Redis 里完成五件事：`TIME` 取服务端时间、按经过毫秒补令牌、扣一个、`HSET` 写回、`PEXPIRE` 续期。整段原子执行，多个实例共享同一个桶。
   3. 令牌不足返回 429，带 `Retry-After`，值由 `retry_ms` 向上取整成秒。
   4. `script.Run` 出错（Redis 挂了、超时）走 `c.Next()` 放行。这个选择叫 fail-open，判据是「限流组件失效不该等于全站不可用」。代价是故障期间没有限流，这一点在面试里要主动说。

4. **handler 参数校验（`ArticleHandler.Detail`）**
   1. `strconv.ParseUint(c.Param("id"), 10, 64)`，`abc`、`-1`、超过 64 位的数字都在这里被拦掉，返回 400。
   2. 全程没碰数据库和 Redis。参数错误是最便宜的拒绝，越早返回越好。
   3. 转成 `uint(id)` 交给 service。用无符号类型，负 id 在类型层面就不存在。

5. **service 查缓存与防击穿（`ArticleService.Detail`）**
   1. **算 key**。`articleDetailKey(id)` 拼出 `article:detail:v1:1`。版本号 `v1` 单独一段，改缓存结构时把版本号改成 `v2`，旧 key 自然过期，不用写脚本批量删。
   2. **第一遍读缓存，不加锁**。`readArticleCache` 直接 `GET`。九成以上请求在这里结束，让它们去排队等待没有任何收益。
   3. **命中就返回**。读到 JSON 反序列化后返回；读到空标记 `__ARTICLE_NOT_FOUND__` 直接返回 `ErrNotFound`，这次连数据库都不碰，这是防穿透。坏 JSON 会顺手 `DEL` 掉，下一次请求自然重建。
   4. **未命中才排队**。`s.group.Do(key, fn)` 用 `singleflight` 合并同 key 的并发请求，只有一个进 `fn`，其余挂起等它的结果。`shared` 为真表示结果被多个请求领取，计一次 `Shares`。
   5. **给这次回源换一个 ctx**。`context.WithTimeout(context.WithoutCancel(ctx), 3*time.Second)`。`WithoutCancel` 去掉第一个请求者的取消信号，否则他一断开，所有等待者会一起收到 `context.Canceled`；3 秒超时防止回源无限跑下去。
   6. **二次读缓存**。等锁的这段时间里，可能已经有别的请求把数据写进去了。不查这一遍，稍晚到达的请求会各自再回源一次，合并就白做。
   7. **回源查库**。`s.metrics.Loads.Add(1)` 记一次真实回源，再 `queryDetail` 做两次查询：`Preload("User").First` 拿文章与作者，`COUNT(*)` 现算点赞数。`articles.like_count` 列始终不维护，计数每次现算。
   8. **只对「确实不存在」写空标记**。`errors.Is(err, ErrNotFound)` 成立才 `markArticleAbsent`，TTL 60 秒。数据库超时、连接断了绝不能写空标记，否则故障期间查过的 id 会在恢复后继续错 60 秒。
   9. **回填缓存**。`writeArticleCache` 用 `json.Marshal` 后 `SET`，TTL 取 `[10m, 12m)` 的随机值，每次重新取随机数，避免一批 key 同时过期。写入失败只记日志和降级计数，不能把一次成功的查库变成接口失败。

6. **数据组装与响应**
   1. service 返回错误时走 `mapServiceError`，`ErrNotFound` 映射成 404，其余映射成 500，日志只在边界记一次。
   2. 成功时在 handler 层转 DTO。`toArticleResp` 只挑 `id`、`title`、`content`、`author`、`created_at` 五个字段，`model.User` 里的密码哈希与邮箱不会出门。
   3. **这里有一处尚未落地的差别**。`dto.go` 里已经写好 `articleDetailResp` 与 `toArticleDetailResp`（比列表多一个 `like_count`），`Detail` 现在调的仍是 `toArticleResp`，所以此刻请求详情拿不到点赞数。04 章 4.10 的目标是切成 `toArticleDetailResp`，04b 章也留了「切换后同步改注解」的待办。面试被问到这个字段，按工作树的实际状态答。
   4. `response.OK(c, ...)` 包成 `{code:0, message:"ok", data:{...}}`，由 `c.JSON` 一次写出，状态码在写出前已经定死。

### 1.3 点赞的完整链路

`PUT /api/articles/1/like`，带 Bearer token。写路径比读路径多两件事：事务，和事务之后的投影同步。

1. **认证（`middleware.JWTAuth`）**
   1. 只挂在 `auth` 子组上。同一条 `/api/articles/:id` 路径，GET 不需要登录，PUT 需要，差别只在注册时落在哪个组。
   2. 校验算法白名单、`iss`、`exp`、`token_type`，通过后 `c.Set("userID", id)`。
   3. 任一项不过返回 401 并 `Abort`，后面的中间件与 handler 都不执行。

2. **二次确认身份（`currentUserID`）**
   1. handler 再取一次 userID，取不到或为 0 就当成未登录，返回 401。
   2. 这是刻意加的冗余。将来有人调整路由分组、漏挂 JWTAuth，也不会把 0 号用户写进 `article_likes`。

3. **service 确认文章存在（`articleExists`）**
   1. `COUNT(*) WHERE id = ?`，为 0 返回 `ErrNotFound`，映射成 404。
   2. 为什么不直接插、靠外键报错？外键报错只能给出 500，语义上错。先查一次才能给出准确的 404。

4. **事务：关系表与事件表一起写（`writeRelation`）**
   1. `db.Transaction(func(tx))` 包住两步，同一个事务里要么全成要么全滚。
   2. 点赞走 `tx.Create(&ArticleLike{...})`。唯一索引 `(article_id, user_id)` 冲突时 GORM 返回 `ErrDuplicatedKey`，这里把它当重复点赞吞掉，`changed` 保持 false。幂等靠数据库约束，不靠先查后插。
   3. 取消点赞走 `DELETE`，`changed` 由 `RowsAffected > 0` 决定。
   4. 只有真的新增了一行、并且这次是点赞，才 `event.EmitCreated(ctx, tx, TypeLikeCreated, userID, Target{article, articleID}, nil)` 写 `outbox_events` 一行，状态 `pending`。重复点赞与取消点赞都不通知作者。评论走同一个公共入口，`Target` 同样是文章，`Created` 指向刚插入的那条评论。
   5. 事件必须和业务写在同一个事务里，这是本地消息表的核心。先提交业务、再发消息，中间崩了就永久丢事件。

5. **提交之后：删缓存与同步投影（`apply`）**
   1. `changed` 为真才 `InvalidateDetailCache`，`DEL article:detail:v1:1`。关系没变就没有旧值，不必删。
   2. 删除失败只记日志，靠 10 分钟 TTL 兜底。数据库已经提交，这时候返回 500 会让客户端以为没点成功。
   3. `syncLikeSet`：点赞 `SADD article:like:v1:1 <uid>`，取消 `SREM`。这份 Set 目前没有任何读路径在用，留着是为了「我是否点过赞」这个需求。
   4. `countLikes` 从 MySQL `COUNT(*)` 拿权威值，不信 Redis 里的增量计数。多一次查询换来不会被算错的数字，这笔交易划算。
   5. `syncHotScore`：`count > 0` 时 `ZADD hot:articles:v1 <count> <id>`，写绝对分数；`count` 为 0 时 `ZREM` 把这个成员删掉。写增量会在丢一次更新后永久偏移，写绝对值下一次操作就自动纠正，Redis 被清空也能自愈。
   6. 第 3 到第 5 步都是 Redis 写，失败只记日志。它们全是派生数据，丢了能从 MySQL 重建，不该影响已经提交的结果。

6. **响应**
   1. 返回 `{article_id, like_count, changed, liked}`。
   2. `liked` 是这次操作之后的状态，由 `add` 直接得出，所以取消点赞后是 `false`。
   3. **`liked` 不表示「我之前点没点过」**。`HasLiked` 已经写好但没有任何 handler 调用它，接进去的位置是详情接口。

7. **异步收尾（不在这次请求里）**
   1. `relay` 每 200ms 扫一批 `pending`，`XADD forum:events:v1`，成功后标 `published`。
   2. `NotificationWorker` 用消费组 `forum:notify:v1` 读出来，`ON CONFLICT DO NOTHING` 写 `notifications` 一行，同一事件重复投递不会产生第二条通知。
   3. 这条链路断了不影响点赞结果，它只决定作者多久看到红点。当前源码到此为止，04c 章才把「写库后主动推给在线作者」接上。

### 1.4 另外四条链路的骨干

同一套骨架，差别在中间那几层。以下只写「跟 1.2、1.3 不一样的地方」，中间件与响应封装完全相同。

**登录：`POST /api/login`**

1. 路由在公开组，不挂 `JWTAuth`。`auth` 组要求带 token，登录接口自己就是为了拿到 token，放进那个组会死循环。
2. `limitBody` 与 `RateLimit` 照常执行。限流是按 IP 全局限一个桶，登录没有额外的更严配额，这一层只能抬高爆破成本，挡不住分布式撞库。
3. handler `ShouldBindJSON` 绑定到 `registerReq`，登录与注册共用这个结构体。两个字段只有 `binding:"required"`，缺字段或空字符串在这里变成 400。长度与字符集规则在 `validateCredentials` 里，注册路径会调它，登录路径没有调，空密码到 service 之后靠查不到用户返回 401。
4. service 用 `Where("username = ?").First` 查用户。`ErrRecordNotFound` 翻译成 `ErrInvalidCredentials`，不告诉调用方「用户不存在」，避免账号枚举。
5. `bcrypt.CompareHashAndPassword` 比对密文。密码错误与用户不存在返回同一个 401，响应文本也相同。
6. handler 在 service 返回之后才签 token（`h.jwt.Sign(user.ID)`）。签发放到最后一步，前面任何失败都不会产生一个有效 token。
7. 响应 `{token, user}`。`user` 走 `toUserResp`，只出 `id`、`username`、`created_at` 这类字段，密码哈希不出门。

**发文章：`POST /api/articles`**

1. `JWTAuth` 验过，`currentUserID` 取出作者 id。
2. handler 绑定 `{title, content}`，交给 service。
3. service 先 `TrimSpace` 再判空，然后判长度：`len(title) > 128`、`len(content) > 50000`。`len()` 算的是字节，一个汉字 3 字节，所以标题实际上限约 42 个汉字。这个坑在 03 章提过，接口文档若写「128 字」会误导前端。
4. `db.Create(a)` 写库，`id` 由 MySQL 自增回填。
5. 写完立刻 `InvalidateDetailCache(a.ID)`。这一步看起来多余，新建的文章本来没有缓存。真实原因是空的 id 可能被人遍历过，`__ARTICLE_NOT_FOUND__` 这个空标记会挂 60 秒，不删掉新文章会短暂「查不到」。
6. 返回 `toArticleResp`。列表与新建共用同一个 DTO，都不带 `like_count`。
7. **当前源码到这里就结束了**。事务发件箱等进阶写入尚未全部接线，这里仍是单条 `INSERT`，没有包事务（完整版见 04a 章）。

**发评论：`POST /api/articles/1/comments`**

1. `JWTAuth` 与 `currentUserID` 同上。路径参数先用 `ParseUint` 转成文章 id，非法 id 直接 400。`{id}` 在这里是**文章 id**，与删除评论的 `{id}`（评论 id）含义不同。
2. service 先 `TrimSpace`、判空、判长度 10000。
3. 再查一次文章是否存在。这一步只为了给出准确的 404，真正的并发兜底是 `comments.article_id` 上的 RESTRICT 外键：查完到插入之间文章被删，插入会失败。
4. `db.Transaction` 里做两件事：`tx.Create(comment)` 与 `event.EmitCreated(ctx, tx, TypeCommentCreated, userID, Target{article, articleID}, &Target{comment, m.ID})` 写 `outbox_events`。`Target` 是评论作用的文章，`Created` 是刚插入的评论，评论 id 必须 INSERT 之后才拿得到。点赞走同一个公共入口，`Target` 指向文章，`Created` 传 nil。
5. 事务提交后返回评论。这一步没有 `Preload("User")`，`m.User` 是零值，`toCommentResp` 会省掉 `author` 字段，前端拿到的新评论没有作者信息，要等列表接口再补齐。
6. 评论不进文章详情缓存，所以这里没有删缓存的动作。删除评论走 `WHERE id = ? AND user_id = ?`，把所有权判断放进 SQL，`RowsAffected == 0` 统一返回 404，不区分「不存在」与「不是你的」，避免泄露评论归属。

**热榜：`GET /api/articles/hot`**

1. 公开路由，与 `/api/articles/:id` 同层。静态段优先，不会被当成 id 为 `hot` 的文章。
2. handler 读 `?limit`，缺省 10，不是整数直接 400。`checkTopN` 再把范围卡在 1 到 100。
3. `EXISTS hot:articles:v1:ready`。绝大多数请求只花这一次 Redis 往返就往下走。
4. `ready` 为 0 说明投影没建过（进程刚起、Redis 刚被清）。先看 `hot:articles:v1:cooldown` 在不在，冷却期内直接降级；不在才走 `ensureHotZSet`，用 `singleflight` 把同一时刻的请求合并成一次重建，`WithoutCancel` 加 3 秒超时，进 `fn` 后再查一次 `ready` 做双重检查。
5. `rebuild` 从 MySQL 取前 500 名（`GROUP BY` 加 `ORDER BY score DESC` 与 `LIMIT 500`），写进临时 key `hot:articles:v1:tmp`，再用一条 `RENAME` 原子换掉正式榜，最后写带 1 小时 TTL 的 `hot:articles:v1:ready`。标记单独存在，是因为 ZSET 没有成员时 Redis 会把 key 删掉，只看 ZSET 分不清「榜真空」与「投影丢了」。重建失败会写 30 秒冷却标记，避免下一个请求立刻再试一次。
6. `ZRevRangeWithScores` 取前 n 名的 id 与分数。
7. `loadByIDs` 用一次 `IN` 查询拿标题。`IN` 不保证返回顺序，所以用 map 按原 id 顺序重新拼装，顺序由 Redis 决定，不由 MySQL 决定。
8. Redis 任何一步报错都降级到 `TopFromMySQL`，走 `GROUP BY` 直接出榜。降级路径慢，但榜单不会挂。
9. 响应是 `{list: [...]}`，空榜时 `list` 是 `[]`，不是 `null`。前端不用为「没数据」单独判空。

### 1.5 一句话记住每层职责

| 层 | 唯一职责 | 不该做的事 |
| --- | --- | --- |
| main | 装配与生命周期 | 写业务判断 |
| router | URL 到 handler 的映射 | 查库 |
| middleware | 横切关注点 | 改业务数据 |
| handler | 协议适配 | 拼 SQL、定业务规则 |
| service | 业务规则与一致性 | 读 `gin.Context` |
| config | 连接与配置 | 承载业务常量 |
| worker | 异步推进 | 直接响应 HTTP |

## 2. 启动链路：main 到连接池

### 2.1 main 的九个步骤

`cmd/server/main.go` 做九件事，顺序不能换。前四步是 02 章就有的，后五步由进阶专题逐步加上来。

1. `config.Load()` 读配置。失败 `log.Fatalf`，进程起不来比带错配置跑起来安全。
2. `config.InitDB()` 建连接池并 `AutoMigrate`。
3. `config.InitRedis()` 建客户端并 `Ping`。
4. `jwt.NewManager()` 校验密钥与有效期。
5. `realtime.NewHub()` 建连接登记中心（04c）。它必须早于 router 与 worker，因为路由要用它接连接、消费者要用它找收件人。
6. `router.New(router.Deps{...})` 组装路由，依赖一次传进去。
7. `signal.NotifyContext` 接住 Ctrl+C 与 SIGTERM；起 relay、notification 两个 worker，再起 HTTP server，最后 `wg.Wait()`。

第 1 到第 4 步任何一步失败都直接退出，这个选择叫 fail fast：配置错、库连不上、密钥为空，都属于「启动了也没用或带病运行」的情况。第 5 步（Hub）及之后的装配步骤失败同样直接退出，没有「软降级」例外。

**口径说明**：这七步是当前 `main.go` 的实际形态。敏感词过滤与全文搜索两个进阶专题已不纳入本项目，对应的启动步骤已删除；实际跑起来是「加载配置、建库、建 Redis、建 JWT、建 Hub、组装路由、起两个 worker」。

### 2.2 配置加载的四个决定

`internal/config/config.go`。

| 决定 | 代码 | 理由 |
| --- | --- | --- |
| 显式指定文件，不用 `AddConfigPath` 搜 | `v.SetConfigFile(configPath)` | 搜路径依赖工作目录，从别的目录启动会读不到 |
| 区分文件不存在与格式错误 | `errors.As(err, &notFound)` 加 `errors.Is(err, fs.ErrNotExist)` | 两种错的处理方式不同，提示要能指向原因 |
| 敏感项走环境变量 | `BindEnv("jwt.secret")`、`BindEnv("mysql.password")` | 密码不进仓库 |
| 必填项缺失直接报错 | `if cfg.JWT.Secret == "" { return nil, ... }` | 空密钥签名等于没有鉴权 |

viper v1.21.0 里 `ConfigFileNotFoundError` 已不再由 `ReadInConfig` 抛出，所以同时判了 `fs.ErrNotExist`。这一点在 02 章勘误里有记录。

### 2.3 MySQL 连接：DSN 的三个关键参数

```go
// 源码摘录：internal/config/db.go
dsnConfig := mysqlDriver.Config{
    User:      cfg.User,
    Passwd:    cfg.Password,
    Net:       "tcp",
    Addr:      fmt.Sprintf("%s:%d", cfg.Host, cfg.Port),
    DBName:    cfg.DBName,
    Params:    map[string]string{"charset": "utf8mb4"},
    ParseTime: true,
    Loc:       time.Local,
}
```

| 参数 | 不设会怎样 |
| --- | --- |
| `charset=utf8mb4` | 默认可能是 latin1，中文与 emoji 都会坏。`utf8` 三字节存不下 emoji |
| `ParseTime=true` | `DATETIME` 扫进 `time.Time` 会失败，GORM 报类型不匹配 |
| `Loc=time.Local` | 时区按 UTC 解释，写进去的时间和读出来差 8 小时 |

`TranslateError: true` 让 GORM 把驱动错误翻译成 `ErrDuplicatedKey`、`ErrForeignKeyViolated` 这类哨兵错误。没有它，业务层就得判断 MySQL 的 1062 错误码，数据库一换就全废。

`Logger: gormlogger.Warn` 只打慢查询和错误。`Info` 级别会把每条 SQL 打出来，压测时日志本身就是瓶颈。

### 2.4 AutoMigrate 的边界

```go
// 源码摘录：internal/config/db.go
db.AutoMigrate(&model.User{}, &model.Article{}, &model.Comment{},
    &model.ArticleLike{}, &model.OutboxEvent{}, &model.Notification{})
```

它做的事：表不存在就建，字段缺了就加，索引缺了就补。

它不做的事：删字段、改字段类型、改索引、数据迁移。

学习项目用它合适，改模型重启就生效。生产环境要换成版本化迁移工具（goose、migrate、atlas），理由有三条。第一，AutoMigrate 的判断依据是当前结构体，不知道历史上发生过什么。第二，它没有回滚概念。第三，多实例同时启动可能并发执行 DDL。

真实状态提醒一句：本机 `forum` 库目前只有 `users`、`articles`、`comments`、`article_likes` 四张表。`outbox_events` 与 `notifications` 还没建，因为 04a 的模型加进去之后服务没有重启过。下次 `go run ./cmd/server` 会自动补上。

### 2.5 Redis 客户端的五个参数

```go
// 源码摘录：internal/config/redis.go
rdb := redis.NewClient(&redis.Options{
    Addr:                  cfg.Addr,
    Password:              cfg.Password,
    DB:                    cfg.DB,
    PoolSize:              10,
    MinIdleConns:          2,
    DialTimeout:           2 * time.Second,
    ReadTimeout:           500 * time.Millisecond,
    WriteTimeout:          500 * time.Millisecond,
    ContextTimeoutEnabled: true,
})
```

每个参数对应一种故障。

| 参数 | 值 | 对应问题 |
| --- | --- | --- |
| `PoolSize` | 10 | 默认 `10 * GOMAXPROCS`，16 核机器会开 160 条连接。学习阶段调小，连接耗尽时容易定位 |
| `MinIdleConns` | 2 | 冷启动第一波请求不用现拨号 |
| `DialTimeout` | 2s | 建连阶段网络不通时快速失败 |
| `ReadTimeout` | 500ms | Redis 卡住时，HTTP 请求不会被拖 5 秒 |
| `WriteTimeout` | 500ms | 同上 |
| `ContextTimeoutEnabled` | true | 关键开关。默认 false 时 go-redis 把调用方 ctx 换成 Background，`context.WithTimeout` 到不了 socket |

最后一条最容易被忽略。不开它，你在 service 里写的 3 秒超时只是一句注释。

### 2.6 为什么用显式 new，不引入 wire

`router.New` 的签名经过两次变化：02 章到 04b 章是三参数 `New(db, jwtManager, rdb)`；04c 章加 `hub` 时改成结构体 `New(deps Deps)`，此后若再加依赖也只是往结构体里加字段，调用点只需补一个键值对。改成结构体的理由不是「参数太多不好看」，是位置参数传错顺序编译器不报错，六个依赖里有四个都是指针，写反了只会运行时 panic。

显式装配的好处是读代码时能一眼看到依赖图，不用理解代码生成产物。代价是 main 会变长。当前十来个组件的规模，显式写更好维护。等组件超过二十个再考虑 wire。

service 之间有一处横向依赖：`NewLikeService(db, rdb, articleSvc)`。点赞成功后要删详情缓存，这件事属于 `ArticleService` 的知识，让它自己提供 `InvalidateDetailCache`，`LikeService` 只调用，不复制 key 拼接逻辑。

### 2.7 优雅关闭的三段

```go
// 源码摘录：cmd/server/main.go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
```

三段配合。

1. `NotifyContext` 把信号变成 ctx 取消。
2. `srv.Shutdown(shutdownCtx)` 停止接收新连接，等存量请求最多 5 秒。`ListenAndServe` 返回 `http.ErrServerClosed` 属于正常退出，不当错误。
3. `hub.CloseAll()` 先断掉全部 WebSocket 连接。连接在握手后已被 hijack，`Shutdown` 管不到它们，不显式关会留下永远阻塞在 `ReadMessage` 上的 goroutine。
4. `wg.Wait()` 等三个 worker 收手。

worker 里的循环都写成 `select { case <-ctx.Done(): return }`，所以取消后能立刻退出。`relay` 的 `XAdd` 与两个消费者的 `XReadGroup` 都带 ctx，不会卡在阻塞读上。

关闭顺序有讲究：`CloseAll` 必须在 `Shutdown` 之前。反过来的话，`Shutdown` 等存量请求的那几秒里 WebSocket 还活着，客户端可能正好在发消息，多出一次没必要的往返。

### 2.8 启动链路面试问答

| 问题 | 回答要点 |
| --- | --- |
| 为什么配置文件不用相对路径搜索 | 相对路径依赖工作目录。用 `CONFIG_PATH` 传绝对路径，容器里更可控 |
| 密钥为空为什么直接崩 | 空密钥签出的 token 任何人都能伪造，等于没有鉴权。宁可起不来 |
| `ParseTime` 不设会怎样 | `DATETIME` 无法扫进 `time.Time`，GORM 报 scan 错误 |
| 连接池大小怎么定 | 从数据库最大连接数倒推。MySQL 默认 `max_connections=151`，单实例留 20 到 30 条足够，多实例要按实例数分摊 |
| Redis 为什么单独设 500ms 超时 | 缓存是加速手段，不能变成故障源。超时就降级回源 |
| `ContextTimeoutEnabled` 是什么 | 控制 go-redis 是否把调用方 ctx 传到 socket 读写。默认关闭，开了超时才真正生效 |
| 为什么 main 里没有全局 db 变量 | 全局变量让依赖不可见，也让测试无法替换。显式传参能画出依赖图 |
| AutoMigrate 能上生产吗 | 不能。没有版本记录、没有回滚、并发 DDL 有风险。换 goose 或 atlas |
| 关闭时为什么先停 HTTP 再等 worker | 先切断新请求来源，再让后台把手上任务做完。反过来会有新请求进来却没人处理 |
| worker 卡在阻塞读怎么办 | `XReadGroup` 的 `Block` 带 ctx，取消后返回。代码里还额外判了 `ctx.Err()` |

## 3. 数据层设计：表、外键、索引

### 3.1 六张表的关系

```text
users 1 ─────< articles        fk_articles_user，默认 RESTRICT
  │                │
  │                ├────< comments        fk_comments_article，ON DELETE RESTRICT
  │                │         └── fk_comments_user
  │                │
  │                └────< article_likes   fk_article_likes_article，ON DELETE RESTRICT
  │                          uk_article_user(article_id, user_id)
  │
  └────< notifications          user_id 是收件人，actor_id 是动作发起人（无外键）
              │
outbox_events ─┘  event_id 唯一，业务行与它同事务写入
```

`notifications.actor_id` 与 `article_id` 故意不加外键。通知是历史记录，被点赞的文章删掉之后，这条通知仍然应该存在，只是点进去 404。加外键会让删文章失败，或者被迫级联删通知。

### 3.2 逐表设计意图

**users**

```sql
CREATE TABLE `users` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT,
  `username` varchar(64) NOT NULL,
  `password` varchar(128) NOT NULL,
  `created_at` datetime(3) DEFAULT NULL,
  `updated_at` datetime(3) DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `idx_users_username` (`username`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

| 字段 | 选择 | 理由 |
| --- | --- | --- |
| `id` | `bigint unsigned` 自增 | 自增主键插入有序，B+ 树不分裂。无符号把可用范围翻倍 |
| `username` | `varchar(64)` | 业务限制 3 到 32 字符，留一倍余量。`varchar` 按实际长度存，不浪费 |
| `password` | `varchar(128)` | bcrypt 输出固定 60 字符，留余量方便换算法（argon2id 更长） |
| 唯一索引 | `idx_users_username` | 重名由数据库拦截，不靠「先查再插」 |

`varchar(64)` 配 `utf8mb4`，索引键长 64 × 4 = 256 字节，在 InnoDB 单列索引 3072 字节限制内。如果 username 允许 255 字符，索引会变厚，缓存命中率下降。

**articles**

```sql
CREATE TABLE `articles` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT,
  `user_id` bigint unsigned NOT NULL,
  `title` varchar(128) NOT NULL,
  `content` text NOT NULL,
  `like_count` bigint DEFAULT '0',
  `created_at` datetime(3) DEFAULT NULL,
  `updated_at` datetime(3) DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_articles_user_id` (`user_id`),
  CONSTRAINT `fk_articles_user` FOREIGN KEY (`user_id`) REFERENCES `users` (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

| 设计点 | 理由 |
| --- | --- |
| `content` 用 `text` | 上限 64KB，够放长文。再长要换 `mediumtext`，或者把正文拆到独立表 |
| `user_id` 建索引 | 「某个作者的文章」是必然出现的查询。外键本身不建索引，MySQL 只要求被引用列有索引 |
| `like_count` 存在但不维护 | 见 3.7 |
| 没有 `(created_at, id)` 联合索引 | 真实缺口，见 3.6 |

`title` 用 `varchar(128)` 与 service 的 `len(title) > 128` 对齐。注意 Go 的 `len` 数字节，中文一个字三字节，所以 128 字节约等于 42 个汉字。这个不一致在中文场景下会提前触发校验，属于已知粗糙点。

**comments**

```sql
CREATE TABLE `comments` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT,
  `article_id` bigint unsigned NOT NULL,
  `user_id` bigint unsigned NOT NULL,
  `content` text NOT NULL,
  `created_at` datetime(3) DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_comments_article_id` (`article_id`),
  KEY `idx_comments_user_id` (`user_id`),
  CONSTRAINT `fk_comments_article` FOREIGN KEY (`article_id`) REFERENCES `articles` (`id`) ON DELETE RESTRICT,
  CONSTRAINT `fk_comments_user` FOREIGN KEY (`user_id`) REFERENCES `users` (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

两个外键，删除策略都落在默认值 RESTRICT。`ON DELETE RESTRICT` 的价值在于把「删文章要不要连带删评论」这个业务决策挡在数据库层。代码里必须显式先删子表，顺序写错会立刻报错，不会留下孤儿行。

**article_likes**

```sql
CREATE TABLE `article_likes` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT,
  `article_id` bigint unsigned NOT NULL,
  `user_id` bigint unsigned NOT NULL,
  `created_at` datetime(3) DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_article_user` (`article_id`,`user_id`),
  CONSTRAINT `fk_article_likes_article` FOREIGN KEY (`article_id`) REFERENCES `articles` (`id`) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

这是全库最关键的一张表。

为什么不把 `(article_id, user_id)` 做成联合主键，省掉自增 `id`。两个原因。第一，GORM 的 `Create` 与 `OnConflict` 在无主键模型上行为不直观。第二，未来如果要加分表或加软删除字段，自增主键更好操作。代价是多 8 字节与一次二级索引回表。

`uk_article_user` 承担三件事。第一，防重复点赞，重复插入直接报 1062。第二，支撑 `COUNT(*) WHERE article_id = ?`，走最左前缀且是覆盖索引。第三，给外键提供索引。

`user_id` 没有独立索引，这是真实缺口。见 3.6。

**outbox_events**

```sql
-- 由 AutoMigrate 在下次启动时创建，字段来自 model.OutboxEvent
id, event_id varchar(36) unique, event_type varchar(32),
aggregate_type varchar(32), aggregate_id bigint,
payload text, status varchar(16) index, attempts int,
created_at, updated_at
```

`status` 上的索引是给 relay 用的。它每 200ms 执行一次 `WHERE status = 'pending' ORDER BY id LIMIT 100`，没有索引就是全表扫。

`event_id` 唯一索引不是给查询用的，是给排查用的。出问题时能按 id 精确定位一条事件经过了几次投递。

**notifications**

```sql
-- 由 AutoMigrate 创建，换成 target_type 加 target_id 后重启服务会补列
id, user_id bigint, event_id varchar(36) unique, actor_id bigint,
type varchar(32), article_id bigint default 0,
target_type varchar(32), target_id bigint default 0,
is_read tinyint(1), created_at
KEY idx_notify_user_read (user_id, is_read)
UNIQUE KEY uk_notify_event (event_id)
```

`target_type` 加 `target_id` 表达这条通知指向什么，新增行为不用再加列。`article_id` 是列表展示用的文章上下文，非文章域事件存 0。这几个关联列都不加外键，通知是历史记录，文章或评论被删之后它仍然应该保留，点进去 404 即可。

`idx_notify_user_read(user_id, is_read)` 是联合索引。列表查询 `WHERE user_id = ? ORDER BY id DESC` 用最左前缀 `user_id` 定位，未读数 `WHERE user_id = ? AND is_read = false` 两个列都用上。

`uk_notify_event` 是消费端幂等的最后一道保证。同一条事件被投递两次，第二次插入报冲突，`OnConflict DoNothing` 静默跳过。

### 3.3 字段类型的通用规则

| 场景 | 选择 | 理由 |
| --- | --- | --- |
| 主键 | `bigint unsigned` 自增 | 有序插入，避免页分裂。无符号扩大范围 |
| 短文本 | `varchar(n)` | 按实际长度存，n 按业务上限乘 2 |
| 长正文 | `text` | 不进索引，不占行内空间 |
| 布尔 | `tinyint(1)` | MySQL 没有原生 bool，GORM 映射到 `tinyint` |
| 时间 | `datetime(3)` | 毫秒精度，`TIMESTAMP` 有 2038 问题且受时区影响 |
| 金额 | `decimal(m,n)` | 本库没有，但要知道不能用 `float` |
| 枚举 | `varchar` 加应用层常量 | 不用 MySQL `ENUM`，改值要 DDL |

### 3.4 外键：留还是不留

互联网公司常见做法是「逻辑外键，物理不加」，理由是高并发下外键检查会加锁、影响写入、妨碍分库分表。

这个项目保留物理外键，理由也成立。

1. 数据一致性由数据库兜底，代码写错时立刻暴露。删文章忘删评论，会直接报 `ErrForeignKeyViolated`。
2. 学习阶段的写入量远达不到外键成为瓶颈的程度。
3. `RESTRICT` 把业务决策显式化，比在代码里靠自觉更可靠。

什么时候该去掉。分库分表之后、单表写入超过几千 TPS、或者需要跨库引用时。去掉之后一致性要靠事务脚本与对账任务补。

`articles.user_id` 的外键没有显式写 `ON DELETE`，用的是 MySQL 默认 `RESTRICT`。`comments.article_id` 与 `article_likes.article_id` 显式写了 `ON DELETE RESTRICT`。效果一样，后者意图更清楚。

删除顺序是被外键强制的。

```go
// 源码摘录：internal/service/article.go
tx.Where("article_id = ?", id).Delete(&model.Comment{})
tx.Where("article_id = ?", id).Delete(&model.ArticleLike{})
res := tx.Where("id = ? AND user_id = ?", id, userID).Delete(&model.Article{})
```

三步在同一个事务里。第二步或第三步失败，前面删掉的评论会回滚。这是「先清子表」这个顺序唯一正确的写法。

### 3.5 索引：五条实测

本机 `forum` 库数据量：`users` 2 行、`articles` 1 行、`comments` 0 行、`article_likes` 0 行。样本极小，`rows` 列没有参考价值，看 `type`、`key`、`Extra` 三列。

```sql
-- 1. 按文章数点赞
EXPLAIN SELECT COUNT(*) FROM article_likes WHERE article_id = 1;
```

| type | key | Extra |
| --- | --- | --- |
| `ref` | `uk_article_user` | `Using index` |

`Using index` 是覆盖索引。`COUNT(*)` 只需要索引里的 `article_id`，不用回表读整行。这是点赞数能直接查 MySQL 的前提。

```sql
-- 2. 按用户查点赞
EXPLAIN SELECT * FROM article_likes WHERE user_id = 1;
```

| type | key | Extra |
| --- | --- | --- |
| `ALL` | NULL | `Using where` |

全表扫描。`uk_article_user` 的最左列是 `article_id`，`user_id` 单独查用不上。这是真实缺口，见 3.6。

```sql
-- 3. 文章分页
EXPLAIN SELECT * FROM articles ORDER BY created_at DESC, id DESC LIMIT 10;
```

| type | key | Extra |
| --- | --- | --- |
| `ALL` | NULL | `Using filesort` |

没有 `(created_at, id)` 联合索引，排序要额外一趟。数据量小感觉不到，十万行以上会明显。

```sql
-- 4. 评论列表
EXPLAIN SELECT * FROM comments WHERE article_id = 1 ORDER BY created_at ASC, id ASC LIMIT 10;
```

| type | key | Extra |
| --- | --- | --- |
| `ref` | `idx_comments_article_id` | `Using filesort` |

定位走了索引，排序没走。因为索引只有 `article_id` 一列，满足不了 `created_at` 的顺序要求。

```sql
-- 5. 热榜基准
EXPLAIN SELECT article_id, COUNT(*) AS score FROM article_likes
GROUP BY article_id ORDER BY score DESC, article_id ASC LIMIT 10;
```

| type | key | Extra |
| --- | --- | --- |
| `index` | `uk_article_user` | `Using index; Using temporary; Using filesort` |

`Using index` 说明聚合能走覆盖索引，`Using temporary` 说明要建临时表做分组。这条查询是全量聚合，文章越多越慢。这正是热榜把结果投影到 Redis ZSET 的理由。

`type = index` 值得单独说一句。它表示扫整条二级索引，不扫聚簇索引，`COUNT(*)` 只读索引条目、不回表，代价比全表扫描低一个档次。`LIMIT` 作用在聚合**之后**，减少的是排序结果与后续 `ZADD` 的条数，扫描行数不变。这一层区别在 8.5 展开。

### 3.6 三个真实缺口

面试时主动讲缺口，比被追问「你这索引有什么问题」再答要好。

| 缺口 | 现象 | 补法 | 什么时候补 |
| --- | --- | --- | --- |
| `article_likes` 按 `user_id` 查全表扫 | 「我点赞过的文章」列表会慢 | 加 `idx_likes_user(user_id, article_id)` | 做个人主页时 |
| `articles` 分页要 filesort | 深翻页变慢 | 加 `idx_articles_created(created_at, id)` | 文章过十万后 |
| `comments` 按文章查仍 filesort | 单篇评论多时慢 | 把 `idx_comments_article_id` 换成 `(article_id, created_at, id)` | 单篇评论过千后 |

第三条有个细节。换成联合索引后，原来的单列索引就多余了，因为最左前缀已经覆盖 `article_id`。多留一个只会增加写入成本。

### 3.7 为什么 articles.like_count 不维护

列存在，值恒为 0。这不是忘了写，是有意为之。

理由：点赞事实在 `article_likes` 表里，`COUNT(*)` 永远正确。如果再维护一个 `articles.like_count`，就出现了两个数据源，必须靠事务或异步任务保证一致。一旦不一致，没人知道该信哪个。

代价是详情要多查一次 `COUNT(*)`。这条查询走覆盖索引，还能接受。而且结果随文章一起进缓存，热点文章只算一次。

如果点赞量到了十万级、详情 QPS 上万，`COUNT(*)` 会成为瓶颈。那时的做法是给 `articles` 加计数列，用 outbox 事件异步累加，再用定时对账任务修正。这是用一致性换性能的典型场景，当前不做。

`likeResp` 里的 `like_count` 直接来自这次 `COUNT(*)`。详情接口的 `like_count` 来自 `queryDetail` 里的另一次 `COUNT(*)`。两处口径一致，都是事实表。

### 3.8 分页的深翻页问题

当前实现是 `LIMIT 10 OFFSET (page-1)*10`。

`OFFSET 100000` 会让 MySQL 先读出 100010 行再丢掉前 100000 行。翻到第 1000 页时，耗时是第 1 页的几百倍。

三种改法。

| 改法 | 做法 | 代价 |
| --- | --- | --- |
| 游标分页 | `WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 10` | 不能跳页，前端要改成「加载更多」 |
| 延迟关联 | 先用覆盖索引查出 id，再 `WHERE id IN (...)` 回表 | 多一次查询，SQL 变复杂 |
| 限制最大页 | `page <= 500` | 简单，但用户翻不到底 |

本项目选了第三种，见 `parsePage` 里的 `page > (1<<31-1)/pageSize` 判断。那条判断的本意是防 int 溢出，顺带限制了极端翻页。生产项目通常上第二种或第一种。

### 3.9 数据层面试问答

| 问题 | 回答要点 |
| --- | --- |
| 为什么用自增主键不用 UUID | 自增有序，B+ 树插入集中在最右页，减少页分裂；UUID 随机插入会打散索引，且 16 字节比 8 字节厚。分布式场景才需要 UUID 或雪花 ID |
| 联合唯一索引的列顺序怎么定 | 按查询频率与选择性。`(article_id, user_id)` 让「按文章查」走最左前缀，这是最高频的查询 |
| 唯一索引和普通索引的区别 | 唯一索引除了加速还要维护唯一性约束，插入时多一次冲突检查。`uk_article_user` 同时承担去重职责 |
| 外键会影响性能吗 | 会。每次插入要检查被引用行，加共享锁。高并发写入时可能成为瓶颈，这是互联网公司去掉物理外键的主因 |
| 为什么删除要先删子表 | 外键是 RESTRICT，先删父表会被拒绝。代码里三步同事务，任一步失败整体回滚 |
| `text` 能建索引吗 | 能，但必须指定前缀长度，比如 `KEY (content(100))`。全文检索要用 `FULLTEXT` 或外部搜索引擎 |
| `datetime(3)` 的 3 是什么意思 | 毫秒精度。默认 `datetime` 只到秒，同秒内多条记录排序会不稳定 |
| 为什么 `notifications` 不加外键到 articles | 通知是历史记录，文章删了通知仍应保留，点进去 404 即可。加外键会让删文章失败 |
| `articles.like_count` 为什么是 0 | 有意不维护，避免双数据源。详情的点赞数由 `queryDetail` 从 `article_likes` 现算，装进 `model.Article.LikeCount` 内存字段 |
| 大表加索引会锁表吗 | MySQL 8.0 的 `ALTER TABLE` 支持 Online DDL，加二级索引通常不锁写，但仍要评估执行时间与主从延迟 |
| 索引是不是越多越好 | 不是。每个索引都增加写入成本与磁盘占用。低选择性列（如性别）单独建索引意义不大 |
| 怎么发现慢查询 | 开 `slow_query_log`，设 `long_query_time`，用 `EXPLAIN` 看执行计划，再看 `rows` 与 `filtered` 估算 |
| 分库分表之后自增 id 怎么办 | 雪花 ID、号段模式、Redis `INCR`。同时要处理跨库 join 与分布式事务 |
| 为什么 `comments` 有两个单列索引 | 一个给「按文章查评论」，一个给「按用户查评论」。如果只按文章查，第二个可以去掉 |

## 4. 认证链路

### 4.1 注册时序

```text
POST /api/register
  ├─ handler: ShouldBindJSON → registerReq{Username, Password}
  │            binding:"required" 缺字段直接 400
  ├─ service: validateCredentials
  │            username 3~32 且 ^[a-zA-Z0-9_]+$
  │            password 8~72 字节
  ├─ bcrypt.GenerateFromPassword(cost=10)  → 约 60 字符
  ├─ INSERT INTO users
  │            1062 冲突 → gorm.ErrDuplicatedKey → ErrUserNameTaken → 409
  └─ response.OK(toUserResp(user))        只返回 id / username / 时间
```

`bcrypt` 的上限是 72 字节，这是算法本身的限制，超了会报错。所以校验里写了 `len(password) > bcryptMaxBytes`。

重名判断没有「先 SELECT 再 INSERT」。那条路有竞态：两个请求同时查到「不存在」，然后都去插，其中一个必然失败。直接插，让唯一索引裁决，代码更短也更准。

```go
// 源码摘录：internal/service/user.go
if err := s.db.WithContext(ctx).Create(user).Error; err != nil {
    if errors.Is(err, gorm.ErrDuplicatedKey) {
        return nil, ErrUserNameTaken
    }
    return nil, fmt.Errorf("create user: %w", err)
}
```

`ErrDuplicatedKey` 能出现，前提是 `db.go` 里开了 `TranslateError: true`。

### 4.2 登录时序

```text
POST /api/login
  ├─ SELECT * FROM users WHERE username = ? LIMIT 1
  │            没查到 → ErrInvalidCredentials
  ├─ bcrypt.CompareHashAndPassword
  │            不匹配 → ErrInvalidCredentials
  └─ jwt.Sign(userID) → { token, user }
```

「用户不存在」与「密码错误」返回同一个错误，同一个 401 文案。这是防止用户名枚举。攻击者无法通过错误信息判断某个用户名是否注册过。

代价是排查时看不出是哪一步失败。缓解办法是服务端日志里区分，客户端不区分。当前代码没有打这条日志，属于可接受的简化。

### 4.3 JWT 的六个声明

```go
// 源码摘录：pkg/jwt/jwt.go
claims := Claims{
    UserID:    userID,
    TokenType: accessTokenType,
    RegisteredClaims: jwtlib.RegisteredClaims{
        Issuer:    issuer,
        Subject:   fmt.Sprintf("%d", userID),
        IssuedAt:  jwtlib.NewNumericDate(now),
        ExpiresAt: jwtlib.NewNumericDate(now.Add(ttl)),
    },
}
```

| 声明 | 作用 |
| --- | --- |
| `user_id` | 业务身份，中间件取出来放进 context |
| `token_type` | 固定 `access`。将来加 refresh token 时，防止它被当访问令牌用 |
| `iss` | 签发方 `forum-backend`，解析时校验 |
| `sub` | 与 `user_id` 重复存一份，解析时交叉验证，防止 payload 被改 |
| `iat` | 签发时间，`WithIssuedAt()` 会校验它不在未来 |
| `exp` | 过期时间，`WithExpirationRequired()` 强制要求存在 |

`sub` 与 `user_id` 交叉验证看起来冗余。它的价值在于：如果密钥泄漏、攻击者用别的工具构造 token，只改 `user_id` 不改 `sub` 会被拦下。这不是强防护，属于提高伪造成本的细节。

### 4.4 解析时的五个约束

```go
// 源码摘录：pkg/jwt/jwt.go
jwtlib.ParseWithClaims(
    tokenStr, claims, keyFunc,
    jwtlib.WithValidMethods([]string{jwtlib.SigningMethodHS256.Alg()}),
    jwtlib.WithIssuer(issuer),
    jwtlib.WithExpirationRequired(),
    jwtlib.WithIssuedAt(),
)
```

| 约束 | 挡住的攻击 |
| --- | --- |
| `WithValidMethods(["HS256"])` | 算法混淆攻击。攻击者把 header 的 `alg` 改成 `none` 或 `RS256`，用公钥当 HMAC 密钥伪造 |
| `WithIssuer("forum-backend")` | 拿别的系统的 token 来用 |
| `WithExpirationRequired()` | 不带 `exp` 的永久 token |
| `WithIssuedAt()` | `iat` 在未来的 token |
| `token_type != access` 检查 | refresh token 被当访问令牌 |

第一条最关键。JWT 库默认会接受 header 里声明的算法，不限定算法就等于把签名验证交给攻击者选择。

### 4.5 无状态的收益与代价

| 维度 | JWT | Session |
| --- | --- | --- |
| 服务端存储 | 不需要 | 需要 Redis 或数据库 |
| 水平扩展 | 任意加实例，无共享状态 | 需要共享 session 存储 |
| 主动吊销 | 做不到，只能等过期 | 删 session 即可 |
| 携带信息 | 可以放 userId、角色 | 只放 sessionId |
| 体积 | 几百字节，每次请求都带 | 一个 cookie |

当前实现没有吊销机制。用户改密码或封号之后，旧 token 在 24 小时内仍然有效。

三种补救方案。

1. 缩短有效期到 15 分钟，配 refresh token。成本是前端要处理续期。
2. 维护 Redis 黑名单，key 是 `jwt:blacklist:<jti>`。每次校验多一次 Redis 查询，回到有状态。
3. 用户表加 `token_version`，签进 claims，校验时比对。改密码时版本加一，旧 token 全部失效。多一次查询，但可以缓存。

本项目选「什么都不做」，因为学习项目的封号场景不存在。面试时要能说出这三条。

### 4.6 userID 在链路上的传递

```text
JWTAuth      c.Set("userID", userID)     中间件写入
handler      currentUserID(c)            取出并判 0
service      Create(ctx, userID, ...)    作为参数传入
```

为什么 handler 还要判一次 0。`c.GetUint` 在 key 不存在或类型不对时返回 0，不报错。如果直接把 0 传给 service，会写出一条 `user_id = 0` 的脏数据，而外键会拦住它，报 500。判 0 变成 401，错误信息更准。

为什么 service 不自己读 gin context。service 要能被单测直接调用，不该依赖 HTTP 框架。这是分层的核心价值。

### 4.7 认证面试问答

| 问题 | 回答要点 |
| --- | --- |
| 为什么密码用 bcrypt 不用 MD5 | MD5 是快速哈希，GPU 每秒能算几十亿次。bcrypt 有工作因子，cost=10 时单次约 50 到 100ms，暴力破解成本高几个数量级 |
| bcrypt 的 salt 存哪 | 混在哈希串里，格式 `$2a$10$<22字符salt><31字符hash>`。不需要单独字段 |
| 为什么 password 字段是 `json:"-"` | 防止误把 model 序列化出去时泄露哈希。DTO 里干脆不定义这个字段，双保险 |
| 登录错误为什么合并 | 防用户名枚举。能区分「无此用户」与「密码错」，等于给攻击者一个用户名探测接口 |
| JWT 存 localStorage 还是 cookie | localStorage 怕 XSS，cookie 怕 CSRF。当前项目前端未定，token 放响应体由客户端自己保存 |
| 为什么限定 HS256 | 防算法混淆。不限定算法时，攻击者可以把 alg 改成 none 或非对称算法绕过验签 |
| token 过期了怎么办 | 当前要求重新登录。生产方案是 access token 15 分钟加 refresh token 7 天 |
| 怎么实现「退出登录」 | JWT 本身做不到。要么客户端删 token（服务端仍认），要么上黑名单或 token_version |
| 密钥怎么管理 | 环境变量注入，不进仓库。多实例必须用同一个密钥。轮换时要支持新旧双密钥并存一段时间 |
| 中间件里为什么先 Abort 再 return | `Abort` 阻止后续 handler 执行，`return` 退出当前中间件。缺一个都会出问题 |

## 5. 文章读写链路

### 5.1 列表：两条查询与一次 Preload

```go
// 源码摘录：internal/service/article.go
var total int64
s.db.WithContext(ctx).Model(&model.Article{}).Count(&total)
if total == 0 {
    return []*model.Article{}, 0, nil
}
articles := make([]*model.Article, 0)
s.db.WithContext(ctx).Preload("User").Order(articleListOrder).
    Offset((page - 1) * pageSize).Limit(pageSize).Find(&articles)
```

三个细节。

`total == 0` 时提前返回，省掉第二条查询。空列表是常见情况（新站、翻到最后一页之后）。

`make([]*model.Article, 0)` 而不是 `var articles []*model.Article`。后者在没有结果时是 `nil`，JSON 序列化成 `null`。前端处理 `null` 要额外判空。handler 里再用 `make([]articleResp, 0, len(...))` 兜一次，保证输出 `[]`。

`Preload("User")` 是第二条 SQL，`WHERE id IN (...)`。不是 N+1，GORM 会一次把关联用户查回来。代价是两次往返。如果列表不需要作者信息，去掉 Preload 能省一次。

`articleListOrder` 是常量 `"created_at DESC, id DESC"`。

```go
// 源码摘录：internal/service/article.go
const articleListOrder = "created_at DESC, id DESC"
```

为什么不能 `Order(c.Query("sort"))`。用户输入直接拼进 ORDER BY 就是注入口。白名单映射是唯一安全做法，比如 `map[string]string{"new": "created_at DESC", "hot": "like_count DESC"}`。

为什么带 `id DESC` 兜底。`created_at` 只到毫秒，同毫秒的多条记录排序不确定，翻页时会出现重复或漏项。加主键做第二排序键，顺序才稳定。

### 5.2 详情：三段式

逐步骤版本见 1.2，这里只留结构。

```text
第一段  读缓存
  ├─ 命中真实文章 → 直接返回（绝大多数请求到这里结束）
  ├─ 命中空标记   → 返回 ErrNotFound，不查库
  └─ 未命中/故障  → 进第二段

第二段  singleflight 合并
  ├─ 二次读缓存（等待者可能已被别人填好）
  ├─ queryDetail：Preload + COUNT 点赞数
  ├─ 查无此文 → 写空标记（60s）
  └─ 查到     → 写缓存（10m 加随机 2m）

第三段  类型断言与返回
```

把整个 Detail 塞进 `singleflight.Do` 是常见错误。那样缓存命中的请求也要排队，本来 1ms 的请求被拖成串行。

### 5.3 创建：三道校验与一次失效

```go
// 源码摘录：internal/service/article.go
title = strings.TrimSpace(title)
content = strings.TrimSpace(content)
if title == "" || content == "" { ... }
if len(title) > 128 || len(content) > 50000 { ... }
a := &model.Article{UserID: userID, Title: title, Content: content}
s.db.WithContext(ctx).Create(a)
s.InvalidateDetailCache(ctx, a.ID)
```

`TrimSpace` 在 service 层，不在 handler。内部调用绕过 handler 时同样生效。

长度上限与数据库列对齐：`title varchar(128)`、`content text`（64KB）。`len` 数字节，中文三字节，所以 128 字节约 42 个汉字。这是粗糙点，严格做法是 `utf8.RuneCountInString`。

`InvalidateDetailCache` 在插入之后调用。新建的文章理论上不可能有缓存，但如果有客户端提前请求过这个 id 并被写成空标记，这一句正好清掉它。

### 5.4 删除：事务里的三刀

```go
// 源码摘录：internal/service/article.go
err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
    tx.Where("article_id = ?", id).Delete(&model.Comment{})
    tx.Where("article_id = ?", id).Delete(&model.ArticleLike{})
    res := tx.Where("id = ? AND user_id = ?", id, userID).Delete(&model.Article{})
    if res.RowsAffected == 0 {
        return ErrNotFound
    }
    return nil
})
```

四个决策点。

**顺序**。子表先删。外键 RESTRICT 会拦住反向操作。

**所有权放进 WHERE**。`WHERE id = ? AND user_id = ?` 一次完成判断与删除，没有「先查归属再删」之间的竞态。

**`RowsAffected == 0` 合并两种原因**。文章不存在、文章是别人的，都返回 404。分开返回 403 会泄露「这个 id 存在但不属于你」。

**缓存删除在事务外**。

```go
if err != nil { return ... }
s.InvalidateDetailCache(ctx, id)
s.rdb.Del(ctx, likeSetKey(id))
s.rdb.ZRem(ctx, hotArticlesKey, strconv.FormatUint(uint64(id), 10))
```

事务提交成功才删缓存。事务里删的话，一旦回滚，缓存已经没了，下一次读会回源读到旧数据再写回去，等于白删。

三处 Redis 清理都是「失败只记日志」。数据库已经提交，不能让 Redis 故障把成功的删除变成 500。残留的 Set 和 ZSET 成员是脏数据，靠后续访问与 TTL 处理。

### 5.5 文章链路面试问答

| 问题 | 回答要点 |
| --- | --- |
| 列表为什么要查两次 | 一次 `COUNT(*)` 拿总数，一次 `LIMIT` 拿当前页。合并成一次要写窗口函数，MySQL 8.0 支持但可读性差 |
| `total == 0` 提前返回有什么风险 | 几乎没有。唯一影响是「刚插入又被删」的瞬间可能少一次查询，结果仍然正确 |
| 排序为什么不能拼接用户输入 | SQL 注入。ORDER BY 不能用参数占位符，只能白名单映射 |
| 为什么要加 `id DESC` | 时间戳精度有限，同值排序不稳定，翻页会重复或漏项 |
| 深翻页怎么优化 | 游标分页、延迟关联、限制最大页。当前用限制最大页，代价是翻不到底 |
| 详情为什么不在事务里 | 纯读操作，不需要事务。加事务只会多一次 BEGIN/COMMIT 往返 |
| 删除为什么要动 Redis | 详情缓存、点赞 Set、热榜 ZSET 三处都有这篇文章的痕迹。不清会返回 404 文章或幽灵热榜条目 |
| 删除失败一半怎么办 | 三步在同一事务，任一步失败整体回滚。Redis 清理在事务外，失败只记日志 |
| 为什么 404 不返回 403 | 防资源枚举。403 等于告诉对方「这个 id 存在」 |
| 新建文章为什么也删缓存 | 清掉可能存在的空标记。客户端提前猜 id 请求过会被写成 60 秒的空值 |
| `Preload` 会不会有 N+1 | 不会。GORM 的 Preload 是独立的 `WHERE id IN (...)` 查询，N 条主记录只多一次往返 |
| 作者信息为什么要 DTO | 直接序列化 model 会把 `password`、`updated_at` 一起带出去。DTO 从源头控制字段 |

## 6. 缓存链路：Redis 与 MySQL 怎么配合

### 6.1 读写分工

```text
读：Redis 命中 → 返回
    Redis 未命中 → MySQL 查 → 写回 Redis → 返回

写：MySQL 写成功 → 删除 Redis key → 返回
```

这叫 Cache Aside。写路径删缓存，不更新缓存。

为什么不更新。两个并发写 A、B，A 先写库后更新缓存，B 后写库先更新缓存，最终缓存里是 A 的旧值，数据库里是 B 的新值，长期不一致。删缓存只有「删」一个动作，不存在覆盖顺序问题，下一次读会自然回源到最新值。

### 6.2 删缓存失败怎么办

```go
// 源码摘录：internal/service/article.go
func (s *ArticleService) InvalidateDetailCache(ctx context.Context, id uint) {
    key := articleDetailKey(id)
    if err := s.rdb.Del(ctx, key).Err(); err != nil {
        s.metrics.Degrades.Add(1)
        log.Printf("invalidate article cache %s: %v", key, err)
    }
}
```

失败了就是失败了，不重试、不回滚数据库。三层兜底。

| 兜底 | 生效时间 |
| --- | --- |
| TTL 到期 | 最长 12 分钟 |
| 下一次写操作再删一次 | 取决于写入频率 |
| 人工或定时任务清理 | 不确定 |

生产环境的第四层是订阅 MySQL binlog（Canal、Debezium），把行变更转成缓存删除消息。这样即使应用层删失败，也能补一次。代价是引入新组件，当前不做。

### 6.3 key 设计

| key | 类型 | TTL | 内容 |
| --- | --- | --- | --- |
| `article:detail:v1:<id>` | String | 10~12 分钟 | 文章 JSON 或空标记 |
| `article:like:v1:<id>` | Set | 无 | 点过赞的 userID |
| `hot:articles:v1` | ZSet | 无 | articleID → 点赞数 |
| `hot:articles:v1:ready` | String | 1 小时 | 投影已初始化标记 |
| `hot:articles:v1:tmp` | ZSet | 无 | 重建落料区，写完 `RENAME` 换榜 |
| `hot:articles:v1:cooldown` | String | 30 秒 | 重建失败后的退避标记 |
| `forum:events:v1` | Stream | 无 | 领域事件 |
| `forum:dev:rate:ip:<ip>` | Hash | 动态 | tokens、last_ms |

命名规则：`业务:对象:版本:标识`。版本号那一段是为了改结构时平滑过渡。

```go
// 源码摘录：internal/service/article_cache.go
const articleDetailKeyPrefix = "article:detail:"
const articleDetailCacheVersion = "v1"
```

给 `model.Article` 加字段、改 JSON tag 时，把 `v1` 改成 `v2`。新代码只读 v2，老 key 没人读会自然过期。不需要半夜跑脚本清理，也不会把旧格式解析成新结构体。

### 6.4 TTL 抖动

```go
// 源码摘录：internal/service/article_cache.go
const articleDetailTTLBase = 10 * time.Minute
const articleDetailTTLJitter = 2 * time.Minute

func articleDetailTTL() time.Duration {
    jitter := rand.Int64N(int64(articleDetailTTLJitter))
    return articleDetailTTLBase + time.Duration(jitter)
}
```

固定 TTL 的问题：一批文章在同一秒被写入缓存，10 分钟后同时过期。如果这批文章是热点，同一秒会有大量请求同时回源，把 MySQL 打满。

抖动把这批 key 的过期时刻摊到 2 分钟窗口里。120 秒分摊，瞬时压力降到 1/120。

生产环境抖动范围通常取 TTL 的 10% 到 30%。取太大，旧数据存活时间变长；取太小，摊不开。

### 6.5 空值缓存

```go
// 源码摘录：internal/service/article_cache.go
const articleEmptySentinel = "__ARTICLE_NOT_FOUND__"
const articleEmptyTTL = 60 * time.Second
```

挡的是缓存穿透：请求一个不存在的 id，每次都穿到数据库。

为什么不能用 `"null"`。`json.Unmarshal([]byte("null"), &a)` 不报错，`a` 会留成全零结构体，客户端收到一篇 `id=0` 的假文章。哨兵值以下划线开头，永远不可能与真实文章的 JSON 混淆，因为后者一定以 `{` 开头。

为什么 TTL 只有 60 秒。空标记赌的是「这个 id 确实不存在」。如果 60 秒内它被创建了，用户最多等 60 秒才能看到。写路径的 `InvalidateDetailCache` 会主动清掉它，正常情况下不会等满。

为什么数据库故障时不能写空标记。

```go
// 源码摘录：internal/service/article.go
if errors.Is(err, ErrNotFound) {
    s.markArticleAbsent(loadCtx, key)
}
```

只有确认「确实不存在」才写。把数据库超时也写成空标记，故障期间查过的 id 会在恢复后继续报 60 秒的 404，故障影响被放大。

### 6.6 singleflight 的三次检查

```text
请求 A 读缓存 miss
请求 B 读缓存 miss
请求 C 读缓存 miss
     ↓
A、B、C 都调用 group.Do(key, fn)
     ↓
只有 A 执行 fn，B、C 挂起等结果
     ↓
A 内二次读缓存（还是 miss）
A 查 MySQL，写缓存，返回
     ↓
B、C 被唤醒，拿到 A 的返回值
```

三次检查分别防三件事。

| 检查 | 位置 | 防什么 |
| --- | --- | --- |
| 第一次读缓存 | `Do` 之外 | 让命中缓存的请求不进合并队列 |
| 第二次读缓存 | `Do` 之内 | 等待者被唤醒时，别人可能已经填好 |
| `shared` 计数 | `Do` 返回后 | 只用于统计合并了几次，不影响正确性 |

没有第二次检查会怎样。A 正在查库时，B 读缓存 miss 进入 `Do` 等待；A 写完缓存返回，B 被唤醒后直接拿 A 的结果，这没问题。但如果 B 是稍晚一点才调用 `Do`，此时 A 已经完成，`Do` 会认为没有进行中的调用，B 自己执行 fn。第二次读缓存让它直接命中，不再查库。

`singleflight` 只在本进程内生效。三个实例各有一份 `Group`，同一时刻最多合并成三次回源。跨实例合并需要分布式锁，代价更高。

### 6.7 WithoutCancel 这个坑

```go
// 源码摘录：internal/service/article.go
loadCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 3*time.Second)
defer cancel()
```

`fn` 的闭包捕获的是第一个请求的 ctx。如果这个请求被客户端取消（关页面、超时），ctx 变成 `Canceled`，所有等待者都会拿到同一个 `context.Canceled`，即使它们自己的连接还好着。

`context.WithoutCancel` 剥掉取消信号，保留 ctx 里的值（trace id、用户信息）。再套 3 秒超时，避免回源无限跑。

这个坑在 `hot.go` 的 `ensureHotZSet` 里同样存在，同样处理。

### 6.8 四类缓存故障对照

| 问题 | 成因 | 本项目的解法 | 有效性 |
| --- | --- | --- | --- |
| 缓存击穿 | 单个热点 key 过期，瞬间大量请求回源 | singleflight 合并 | 单实例有效，多实例最多合并成 N 次 |
| 缓存穿透 | 查不存在的 key，缓存永远不命中 | 空值标记 60 秒 | 有效，但攻击者用随机 id 会撑大 Redis |
| 缓存雪崩 | 大量 key 同时过期 | TTL 抖动 2 分钟 | 有效，摊到 120 秒窗口 |
| Redis 整体故障 | 断连、超时 | 读降级回源，写只记日志 | 有效，但 MySQL 会承压 |

第四种情况容易被忽略。Redis 挂了之后所有读都打 MySQL，如果 MySQL 也扛不住，服务整体雪崩。生产环境要在 MySQL 前面加限流或熔断。当前只有 IP 维度的限流，挡不住这种放大。

### 6.9 降级的三条规则

| 场景 | 处理 | 代码位置 |
| --- | --- | --- |
| 读缓存出错（非 `redis.Nil`） | 计 `Degrades`，回源 MySQL | `readArticleCache` |
| 写缓存失败 | 只记日志，不影响本次返回 | `writeArticleCache` |
| 删缓存失败 | 只记日志，靠 TTL | `InvalidateDetailCache` |

共同原则：缓存是加速手段，它的故障不能变成接口故障。数据库是权威，只要数据库读得到，接口就该成功。

反例是把缓存当唯一数据源。点赞 Set 就不能这么用，冷启动时 Set 是空的，`SCARD` 会返回 0。所以计数一律走 MySQL 的 `COUNT(*)`。

### 6.10 缓存与事务的顺序

```text
写库 → 提交 → 删缓存
```

不能反过来。事务里删缓存，事务回滚后缓存已经没了，下一次读回源读到旧值再写回去，看起来没坏，实际上多了一次无谓的回源。

也不能「先删缓存再写库」。两个并发请求：A 删缓存、B 读缓存 miss 回源读到旧值、B 写回旧值、A 写完库。缓存里是旧值，且不知道什么时候能修正。

标准做法就是 Cache Aside 的写路径：先提交事务，再删缓存。中间那个极短的窗口（提交成功、删除未完成）读到旧值，是这套方案接受的不一致窗口，靠 TTL 兜底。

### 6.11 缓存面试问答

| 问题 | 回答要点 |
| --- | --- |
| 为什么删缓存不更新缓存 | 并发写会因更新顺序错乱产生脏数据，删除只有单向动作，下一次读自然回源 |
| 删除失败怎么办 | TTL 兜底、下次写再删、binlog 订阅补偿。不重试是因为重试也失败时没有更好办法 |
| 先删缓存还是先写库 | 先写库并提交，再删缓存。反过来会有更长的脏窗口 |
| TTL 为什么加随机值 | 防止批量 key 同时过期造成雪崩。抖动幅度取 TTL 的 10% 到 30% |
| 空值缓存为什么不能用 null | `json.Unmarshal("null")` 不报错，会得到全零结构体，客户端收到假数据 |
| 空值缓存 TTL 为什么短 | 真实数据可能很快被创建，空标记留太久会让用户看不到 |
| singleflight 能跨实例吗 | 不能，它基于进程内 map。跨实例要分布式锁或请求合并网关 |
| 为什么要在 Do 里再读一次缓存 | 等待者醒来时别人可能已经填好，不查会重复回源 |
| `WithoutCancel` 解决什么 | 第一个请求取消会连累所有等待者。剥离取消信号保留 ctx 值 |
| Redis 挂了会怎样 | 读全部回源 MySQL，写只记日志。接口仍可用，但数据库压力骤增 |
| 缓存计数器和数据库计数不一致怎么办 | 以数据库为准。点赞数一律 `COUNT(*)`，不用 `SCARD` |
| 缓存 key 为什么要版本号 | 改数据结构时切到 v2，老 key 自然过期，不用批量清理 |
| 缓存预热怎么做 | 启动时或定时任务把热点数据灌进 Redis。当前没有预热，靠首请求回源 |
| 热点 key 怎么发现 | 用 `redis-cli --hotkeys` 或监控命令统计。发现后可以本地缓存或拆分 key |

## 7. 点赞链路：事实表加投影

### 7.1 七步的因果

```go
// 源码摘录：internal/service/like.go
func (s *LikeService) apply(ctx, articleID, userID uint, add bool) (LikeResult, error) {
    s.articleExists(ctx, articleID)          // 1 确认文章在
    changed, _ := s.writeRelation(...)        // 2 事务：关系 + outbox
    if changed { s.articleSvc.InvalidateDetailCache(...) }  // 3 删详情缓存
    s.syncLikeSet(...)                        // 4 同步 Set 投影
    count, _ := s.countLikes(...)             // 5 MySQL 数一遍
    s.syncHotScore(ctx, articleID, count)     // 6 写 ZSET 绝对分数
    return LikeResult{...}                    // 7 返回
}
```

每一步的顺序都有理由。

**先确认文章存在**，为了给出 404 而不是让外键报 500。这一步不是并发安全的最终保证，真正的兜底是 `fk_article_likes_article`。

**关系与事件同事务**。插入点赞行和写 `outbox_events` 在同一个事务里，要么都成功，要么都失败。这是「点赞一定会有通知」的唯一保证。

**只在 `changed` 时删缓存**。重复点赞没有改变数据，删缓存是浪费。

**计数一律走 MySQL**。第 5 步的 `COUNT(*)` 是权威值。Set 的 `SCARD` 不能用，因为 Redis 被清空后 Set 是空的，会返回 0。

**ZSET 写绝对值**。`ZAdd` 而不是 `ZIncrBy`。绝对值天然幂等，重复写、Redis 清空后重建都不会漂移。

### 7.2 幂等靠唯一索引

```go
// 源码摘录：internal/service/like.go
err := tx.Create(&model.ArticleLike{ArticleID: articleID, UserID: userID}).Error
if err == nil {
    changed = true
} else if errors.Is(err, gorm.ErrDuplicatedKey) {
    return nil
}
```

重复点赞不报错，返回 `changed = false`。前端拿到 `changed: false` 可以提示「已经点过了」，或者直接忽略。

靠应用层「先查再插」不行，两个并发请求会同时查到「没点过」。唯一索引在数据库层裁决，是唯一可靠的方案。

取消点赞用 `RowsAffected > 0` 判断是否真的删掉了。没点过赞就取消，返回 `changed = false`，同样幂等。

### 7.3 COUNT(*) 是权威

```go
// 源码摘录：internal/service/like.go
func (s *LikeService) countLikes(ctx, articleID uint) (int64, error) {
    var count int64
    err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
        Where("article_id = ?", articleID).Count(&count).Error
    return count, err
}
```

这条查询走 `uk_article_user` 的最左前缀，`Extra: Using index`，不回表。十万点赞的单篇文章，`COUNT(*)` 也是毫秒级。

为什么不用 `SCARD article:like:v1:<id>`。SET 卡片的复杂度是 O(1)，快得多。问题在冷启动：Redis 被清空或重启后，Set 是空的，`SCARD` 返回 0，作者会看到点赞数瞬间归零。

一旦用 Redis 计数，就得维护「Redis 与 MySQL 一致」这件事，需要定时对账、需要处理 Redis 故障期间的增量。当前选择不做。

### 7.4 Set 的作用与现状

`article:like:v1:<id>` 是一个 SET，成员是 userID。

```go
// 源码摘录：internal/service/like.go
func (s *LikeService) HasLiked(ctx, articleID, userID uint) (bool, error) {
    hit, err := s.rdb.SIsMember(ctx, key, member).Result()
    if err == nil && hit { return true, nil }
    // 未命中或出错：回源 MySQL，命中则顺手补 Set
}
```

它解决的是「当前用户是否点过这篇」。`SISMEMBER` 是 O(1)，不用查 8000 万行的点赞表。

真实状态要讲清楚：`HasLiked` 已经实现，但还没有任何 handler 调用它，`likeResp` 里只有 `liked`（这次操作的结果），没有「我是否点过赞」的字段。接上它的位置是详情接口，给 `articleDetailResp` 加一个 `liked` 字段，从 JWT 取 userID 后调 `HasLiked`。

这也解释了为什么现在的 Set 是「写了没人读」。它提前建好了，等详情页需要时直接接。

Set 的容量边界：一篇爆款文章有 100 万点赞，Set 占约 8 到 10 MB。单个 Set 超过千万成员时，`SISMEMBER` 仍然 O(1)，但内存与主从同步成本变高。那时的做法是改用布隆过滤器加抽样，或者干脆只查 MySQL。

### 7.5 热度写绝对值

```go
// 源码摘录：internal/service/like.go
if count > 0 {
    err = s.rdb.ZAdd(ctx, hotArticlesKey, redis.Z{Score: float64(count), Member: member}).Err()
} else {
    err = s.rdb.ZRem(ctx, hotArticlesKey, member).Err()
}
```

`ZIncrBy` 的问题是冷启动漂移。Redis 清空后，ZSET 里没有这个成员，`ZIncrBy +1` 得到 1，而真实值是 5000。要修正必须全量重建。

`ZAdd` 直接写 5000，不管之前是什么。重复调用结果相同，天然幂等。

`count == 0` 时 `ZRem`，避免榜单里出现 0 分的条目。这里没有做全榜扫描，只动当前这一个成员。

### 7.6 事务边界与事件

```go
// 源码摘录：internal/service/like.go
err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
    // 插入或删除 article_likes
    if !changed || !add { return nil }
    target := event.Target{Type: event.TargetArticle, ID: articleID}
    return event.EmitCreated(ctx, tx, event.TypeLikeCreated, userID, target, nil)
})
```

三个判断。

**只有新增点赞才发事件**。重复点赞没有产生新事实，取消点赞也不该通知作者「有人取消赞了」。

**事件和业务行同事务**。这是 outbox 模式的核心。如果先提交点赞再发消息，中间崩溃就会有点赞没通知。

**`tx` 必须是事务句柄**。传 `s.db` 进来，两条写入就不在同一事务，保证立刻失效。`event.Emit` 的注释专门写了这一点。

## 8. 热榜链路：一次 ZSET 投影的四次返工

这一章是全篇最值得细读的部分。热榜最初只有三十行，看起来是「查出来丢进 ZSET」这么简单，实际上在四个地方各踩了一脚。每个坑都对应一类典型面试追问。

四次的顺序按严重程度排。

| 次序 | 缺陷 | 触发条件 | 后果 |
| --- | --- | --- | --- |
| 一 | 全表 `GROUP BY` | 点赞表过百万 | MySQL CPU 打满，重建超时 |
| 二 | 重建时先 `DEL` 再逐条 `ZADD` | 重建窗口内有读或写 | 读侧看到残缺榜单，写侧增量被覆盖 |
| 三 | `ready` 永不过期 | 上线数小时后 | 榜单冻结成历史快照 |
| 四 | 重建失败无退避 | 聚合超过 3 秒预算 | 每个请求都重试，重试全部失败 |

### 8.1 为什么不在 MySQL 里排

热榜的基准查询是这一句。

```sql
SELECT article_id, COUNT(*) AS score
FROM article_likes
GROUP BY article_id
ORDER BY score DESC, article_id ASC
LIMIT 10;
```

先纠正一个常见说法。这条语句**不会锁表**。InnoDB 的普通 `SELECT` 走 MVCC 快照读，不加行锁也不加表锁，`LOCK IN SHARE MODE` 才会加锁。

它真实的开销是另外三样。

1. **扫描量是 O(点赞总数)**。`GROUP BY article_id` 要先按 `article_id` 把所有行过一遍，行数就是整张点赞表。
2. **临时表**。分组结果放在临时表里，条目数等于「被点过赞的文章数」。超过 `tmp_table_size` 就从内存落到磁盘。
3. **filesort**。按 `score` 排序。带 `LIMIT` 时 MySQL 用优先队列只维护 Top N，内存占用可控，但比较次数仍然是 O(分组数)。

执行计划里能看到三个标记：`Using index`、`Using temporary`、`Using filesort`。

按 1000 万行点赞、20 万篇被赞文章估算。

| 项目 | 量级 |
| --- | --- |
| 索引扫描行数 | 1.0 × 10⁷ |
| 临时表条目 | 2.0 × 10⁵ |
| 排序比较次数 | 2.0 × 10⁵ × log₂(500) ≈ 1.8 × 10⁶ |
| 单次耗时（估） | 3 秒到 15 秒，取决于磁盘与缓冲池命中率 |

这个量级的问题在于它是一个**单点全表操作**。十个请求并发就是十份扫描，缓冲池瞬间被冲穿，同库的其它查询一起变慢。用户看到的「CPU 飙红」就是这么来的。

热榜是读极多、写极少、允许秒级延迟的场景。把聚合结果做成投影放进 Redis ZSET，读路径只剩 `ZREVRANGE`，复杂度 O(log N + n)。这个方向从一开始就是对的，问题出在投影的**建设过程**。

### 8.2 三个 key 的分工

热榜用到四个 key，各管一件事。

| key | 类型 | 含义 | TTL |
| --- | --- | --- | --- |
| `hot:articles:v1` | ZSET | 榜单本体，member 是文章 id，score 是热度 | 无 |
| `hot:articles:v1:ready` | String | 投影已按 MySQL 建过一次的标记 | 1 小时 |
| `hot:articles:v1:tmp` | ZSET | 重建落料区，只在重建时存在 | 无 |
| `hot:articles:v1:cooldown` | String | 重建失败后的退避标记 | 30 秒 |

`ready` 的必要性在这里。

ZSET 一条成员都没有时，Redis 会把整个 key 删掉。于是 `EXISTS hot:articles:v1` 返回 0 有两种完全不同的含义。

1. 论坛一个赞都没有，榜单确实是空的。
2. Redis 被清空过，投影丢了。

第一种不该回源，第二种必须重建。只看 ZSET 分不清。加一个独立的 String key 当标记，`rebuild` 写完榜之后连它一起写，空榜也写。之后 `EXISTS ready` 就能把两种情况分开。

这也是为什么标记不放在 ZSET 里当特殊成员。塞一个 `score=-1, member="__ready__"` 之类的哨兵，会污染 `ZREVRANGE` 的结果，还要在解析时特判。

### 8.3 读路径：一条 EXISTS 挡住 99% 的请求

```go
// 源码摘录：internal/service/hot.go
func (s *HotService) Top(ctx context.Context, n int) ([]HotArticle, error) {
	if err := checkTopN(n); err != nil {
		return nil, err
	}

	ready, err := s.rdb.Exists(ctx, hotReadyKey).Result()
	if err != nil {
		log.Printf("check hot ready key: %v", err)
		return s.TopFromMySQL(ctx, n)
	}
	if ready == 0 {
		cool, err := s.rdb.Exists(ctx, hotCooldownKey).Result()
		if err == nil && cool > 0 {
			return s.TopFromMySQL(ctx, n)
		}
		if err := s.ensureHotZSet(ctx); err != nil {
			log.Printf("rebuild hot zset: %v", err)
			s.markCooldown(ctx)
			return s.TopFromMySQL(ctx, n)
		}
	}

	pairs, err := s.rdb.ZRevRangeWithScores(ctx, hotArticlesKey, 0, int64(n-1)).Result()
	if err != nil {
		log.Printf("read hot zset: %v", err)
		return s.TopFromMySQL(ctx, n)
	}
	// 解析 member 为 id，再 loadByIDs 回查标题
}
```

四个判断，四条出路。

| 判断 | 结果 | 出路 |
| --- | --- | --- |
| `EXISTS ready` 报错 | Redis 不可用 | 降级 `TopFromMySQL` |
| `ready == 0` 且冷却中 | 刚失败过 | 降级，不再尝试重建 |
| `ready == 0` 且未冷却 | 投影缺失 | `ensureHotZSet` 重建 |
| 重建失败 | 聚合超时或 SQL 错 | 打冷却标记，降级 |
| `ZREVRANGE` 报错 | Redis 半途挂了 | 降级 |

正常请求只走第一条 `EXISTS` 加一条 `ZREVRANGE`。两次 Redis 往返，无数据库参与。

降级路径 `TopFromMySQL` 走的仍然是 8.1 那条 `GROUP BY`，只是带了 `LIMIT n`（n 最大 100）。它慢，但保证榜单不会挂。这是「宁可慢，不能空」的选择。

### 8.4 写路径：点赞怎么进榜

榜单不靠定时任务刷新，靠点赞时同步写。

```go
// 源码摘录：internal/service/like.go
func (s *LikeService) syncHotScore(ctx context.Context, articleID uint, count int64) {
	member := strconv.FormatUint(uint64(articleID), 10)
	var err error
	if count > 0 {
		err = s.rdb.ZAdd(ctx, hotArticlesKey, redis.Z{Score: float64(count), Member: member}).Err()
	} else {
		err = s.rdb.ZRem(ctx, hotArticlesKey, member).Err()
	}
	if err != nil {
		log.Printf("sync hot score %s: %v", member, err)
	}
}
```

两个细节值得讲。

**第一，`count` 来自 MySQL 的实时 `COUNT(*)`，写进去的是绝对值。**

如果用 `ZINCRBY +1` 累加，会省掉那次 `COUNT(*)`。代价是分数变成「Redis 自己记的账」，Redis 一旦被清、重建漏了一条、并发写丢了，错误就永久留下来了，没有任何自愈路径。

写绝对值等于每次点赞都用数据库的真实值覆盖一次 Redis。重复调用无害，Redis 被清后下一次点赞自动补回，之前算错的分自动纠正。这个性质后面还会用到，它顺手补住了重建的窗口问题。

**第二，`count == 0` 时用 `ZREM`，不做整榜扫描。**

取消点赞后计数归零，这一条从榜上移走。`ZREM` 是 O(log N)，比「重建整个榜」便宜五个数量级。

删文章时同样直接 `ZREM`。

```go
// 源码摘录：internal/service/article.go
if err := s.rdb.ZRem(ctx, hotArticlesKey, strconv.FormatUint(uint64(id), 10)).Err(); err != nil {
	// 只记日志
}
```

失败不阻塞删除。残留成员的问题在 8.10 兜底。

### 8.5 第一次返工：全表 GROUP BY

原来的 `rebuild` 长这样。

```go
// 旧版，本节要修掉
var rows []hotRow
if err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
	Select("article_id, COUNT(*) AS score").
	Group("article_id").
	Scan(&rows).Error; err != nil {
	return fmt.Errorf("load all like counts: %w", err)
}

pipe := s.rdb.TxPipeline()
pipe.Del(ctx, hotArticlesKey)
for _, r := range rows {
	pipe.ZAdd(ctx, hotArticlesKey, redis.Z{Score: float64(r.Score), Member: member})
}
```

三个问题叠在一起：没有 `LIMIT`，没有排序，逐条 `ZADD` 到正式 key。

先修第一层。加上 `ORDER BY` 与 `LIMIT`。

```go
// 源码摘录：internal/service/hot.go
if err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
	Select("article_id, COUNT(*) AS score").
	Group("article_id").
	Order("score DESC, article_id ASC").
	Limit(hotRebuildTop).
	Scan(&rows).Error; err != nil {
	return fmt.Errorf("load all like counts: %w", err)
}
```

`LIMIT` 买到了什么，没买到什么，必须分清。面试时这是最容易吹过头的地方。

| 项目 | 加 `LIMIT 500` 之前 | 加之后 |
| --- | --- | --- |
| 索引扫描行数 | 全表 | 仍然是全表 |
| 排序 | 全部条目参与 | 优先队列，只维护 500 个 |
| 结果集 | 全部被赞文章 | 500 条 |
| Redis `ZADD` 次数 | 全部被赞文章 | 500 次 |
| 单次耗时 | 秒级 | 百毫秒级 |

扫描量没有降。`GROUP BY` 必须过一遍所有行才能算出每个分组的计数，这是聚合的定义决定的，`LIMIT` 作用在聚合**之后**。

真正把扫描成本压下去的是索引。`article_likes` 上有联合唯一索引 `uk_article_user (article_id, user_id)`。

- **最左前缀**。`GROUP BY article_id` 可以用上这个索引的左列，走索引扫描而不是聚簇索引扫描。
- **覆盖**。`COUNT(*)` 只需要「这一行存在」，`article_id` 和主键都在二级索引里，不用回表。

所以这条语句的执行计划预期是 `Using index; Using temporary; Using filesort`，扫描的是**二级索引**而不是整张表，单位成本低一个档次。这一条没在真库上跑过 `EXPLAIN`，见 16.2。

`hotRebuildTop` 取 500 的理由。

接口上限是 100（`checkTopN` 卡的 1 到 100）。取 5 倍余量，是为了让「榜单外但正在升温」的文章有位置。第 501 名被点赞时，`syncHotScore` 会把它直接 `ZADD` 进榜，下一次读就能看到，不用等下一轮重建。取 100 的话，一次重建只覆盖当前 Top 100，第 101 名永远进不来，只能等它自己涨到前 100，这在高并发下会形成死区。

更彻底的做法是加一列 `articles.like_count` 并建索引，重建就变成 `ORDER BY like_count DESC LIMIT 500`，走索引直接取前 500 行，扫描量从 O(点赞总数) 降到 O(500)。代价是每次点赞要多维护一列，还要处理双写不一致。当前选了「不加列，靠 TTL 把重建频率压到每小时一次」这条路，因为论坛量级下一次小时级重建的开销可以接受。

### 8.6 第二次返工：重建期间的脏写被覆盖

这是四个问题里最隐蔽的一个。先看原来的写法在时间轴上的表现。

```text
t0  rebuild 开始：DEL hot:articles:v1
t1  SELECT ... GROUP BY 返回，读到的是 t1 时刻的快照：文章 1 有 100 个赞
t2  用户点赞，MySQL 计数变 101，syncHotScore 执行 ZINCRBY/ZADD 写入 101
t3  rebuild 继续逐条 ZADD，把 t1 快照里的 100 写进去
t4  重建结束，SET ready 1
```

t4 之后，文章 1 的分数是 100，而数据库里是 101。用户点的那一赞在榜上消失了。

还有第二个问题更直接。t0 到 t4 之间的任何一次读，`EXISTS ready` 返回 0（因为 `DEL` 已经执行，`SET ready` 还没执行），`ready == 0` 又进重建分支，被 singleflight 挡住后等待，等到的是重建完成。但如果重建分多条 pipeline 提交，中间某个瞬间的读会看到「部分成员已写入」的榜单，名次是乱的。

修法是把新榜写在临时 key 上，最后一次原子替换。

```go
// 源码摘录：internal/service/hot.go
pipe := s.rdb.TxPipeline()
pipe.Del(ctx, hotTempKey)
if len(rows) > 0 {
	for _, r := range rows {
		member := strconv.FormatUint(uint64(r.ArticleID), 10)
		pipe.ZAdd(ctx, hotTempKey, redis.Z{Score: float64(r.Score), Member: member})
	}
	pipe.Rename(ctx, hotTempKey, hotArticlesKey)
} else {
	pipe.Del(ctx, hotArticlesKey)
}
pipe.Set(ctx, hotReadyKey, "1", hotReadyTTL)
if _, err := pipe.Exec(ctx); err != nil {
	return fmt.Errorf("rebuild hot zset: %w", err)
}
```

三个点。

**为什么 `RENAME` 是原子的。** Redis 单线程执行命令，`RENAME old new` 内部完成「删除 new 的旧值 + 把 old 的键值挂到 new 名下」，中间不会被其它命令插入。任何并发的 `ZREVRANGE` 要么在 `RENAME` 之前执行读到旧榜，要么在之后执行读到新榜，不存在读到空或读到一半。

**为什么用 `TxPipeline` 而不是普通 `Pipeline`。** `TxPipeline` 外面套了 `MULTI/EXEC`，整组命令连续执行不被插入。普通 `Pipeline` 只保证「一次发出」，中间仍可能被其它客户端的命令插进来。这里 `RENAME` 与 `SET ready` 必须挨在一起，否则会出现「榜换了但标记没写」或「标记写了但榜没换」的中间态。

**为什么 `len(rows) == 0` 要单独处理。** 一条点赞都没有时临时 key 根本不存在，`RENAME` 会返回 `ERR no such key`，整个 `EXEC` 报错，重建失败，然后进入冷却。空榜是合法状态，直接删正式 key 就好。

**残余窗口必须诚实交代。** `RENAME` 消除的是「重建期间读侧看到残缺榜」和「大面积覆盖」。它没有消除一个窄缝：从 `SELECT` 返回（t1）到 `RENAME` 执行（t3）之间，落在这段间隙里的点赞写进的是旧 key，`RENAME` 一覆盖就丢了。

这段间隙通常在几毫秒到几十毫秒，取决于 500 条 `ZADD` 在一个 pipeline 里的执行时间。它造成的偏差有两条自愈路径。

1. 该文章下一次被点赞时，`syncHotScore` 用 MySQL 的真实计数覆盖回来，因为写的是绝对值。
2. `ready` 一小时后过期，下一次读触发重建，整体归位。

也可以把间隙彻底消掉，用 `ZUNIONSTORE ... AGGREGATE MAX` 把旧榜和新榜合并。这条路走不通，原因在分数语义：榜单存的是**绝对值**，`MAX` 在「取消点赞导致分数变小」时会保留旧的较大值，把一个真实的降序改错。`AGGREGATE MAX` 只适合增量计分的场景。

另一个思路是给重建加分布式锁，让点赞写路径在重建期间排队。这把一个几十毫秒的窗口换成了全局写阻塞，吞吐代价远大于收益。

### 8.7 第三次返工：ready 永不过期

原来的 `pipe.Set(ctx, hotReadyKey, "1", 0)` 第二个参数是 0，表示永不过期。

后果是这样的。系统上线第一天重建了一次，此后 `ready` 一直在，`Top` 永远走「读 ZSET」分支。ZSET 里的分数靠点赞写路径更新，看起来没问题。

问题出在「新文章的进入」和「老文章的退出」。

- 一篇新文章涨到 500 赞，但重建从未发生，它能不能进 Top 10 取决于 `Top` 有没有读它。`ZREVRANGE` 读的是整个 ZSET，`syncHotScore` 已经把它 `ZADD` 进去了，所以它能进。
- 一篇三年前的爆款有 10 万赞，`ZADD` 进去之后永久留在榜上。没有任何机制把它挤下去。
- 更严重的是**排序失真**。榜单只在被点赞的文章上更新，其余文章停留在第一次重建的分数。热度分布会越来越偏离现实。

一句话概括：`ready` 永不过期，榜单就变成「第一次重建时刻的快照 + 之后的增量补丁」，两者混在一张表里，谁也说不清当前分数是什么时间的。

修法是给 `ready` 一个 TTL。

```go
// 源码摘录：internal/service/hot.go
const hotReadyTTL = time.Hour
// ...
pipe.Set(ctx, hotReadyKey, "1", hotReadyTTL)
```

`ready` 一过期，下一个读请求发现 `ready == 0`，触发一次重建，整张榜按当前数据库状态重排。重建成本被摊到每小时一次。

**TTL 只给 `ready`，不给 ZSET。** 这个选择需要解释。

如果 `ready` 和 ZSET 都设 1 小时，两者在同一时刻过期。Redis 的过期删除是惰性的，可能 `ready` 已被删除而 ZSET 还没被删，也可能反过来。后者更糟：ZSET 没了但 `ready` 还在，`Top` 认为投影健康，直接 `ZREVRANGE` 一个不存在的 key，返回空列表，榜单静默变空，而且要等到 1 小时后 `ready` 过期才会自愈。

只给 `ready` 设 TTL，ZSET 由 `rebuild` 负责整体替换，就不存在「key 没了但标记还在」的组合。`ready` 的语义就是「这份投影仍然可信」，让它单独决定生命周期，逻辑最干净。

一小时这个数字的取舍。

| TTL | 重建频率 | 榜单新鲜度 | 数据库压力 |
| --- | --- | --- | --- |
| 5 分钟 | 每小时 12 次 | 很高 | 偏大 |
| 1 小时 | 每小时 1 次 | 可接受 | 小 |
| 24 小时 | 每天 1 次 | 差 | 极小 |

热榜的业务容忍度是「分钟级延迟可接受」。一小时是保守值，想更实时可以降到 10 分钟，只要重建足够便宜（8.5 的 `LIMIT` 与索引就是为这个准备的）。

### 8.8 第四次返工：重建失败会引发重试风暴

`ensureHotZSet` 给重建的预算是 3 秒。

```go
// 源码摘录：internal/service/hot.go
loadCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 3*time.Second)
defer cancel()
```

这个 3 秒是有理由的：它在请求路径上同步执行，第一个请求要等它。无限等会把用户连接拖死。

问题在于超时之后的连锁反应。8.5 的估算里，1000 万行点赞的聚合可能需要 3 秒到 15 秒。一旦超过 3 秒，`rebuild` 的 `Exec` 或 `Scan` 返回 `context deadline exceeded`，`Top` 降级返回，`ready` 依然是 0。

下一个请求进来，`ready` 还是 0，又去重建，又超时。QPS 100 就是每秒 100 次全表聚合，每次都在 3 秒后放弃，MySQL 上的查询堆成山。**降级路径本身成了压垮数据库的东西。**

修法是失败退避。

```go
// 源码摘录：internal/service/hot.go
const hotCooldownKey = "hot:articles:v1:cooldown"
const hotCooldownTTL = 30 * time.Second

func (s *HotService) markCooldown(ctx context.Context) {
	if err := s.rdb.Set(context.WithoutCancel(ctx), hotCooldownKey, "1", hotCooldownTTL).Err(); err != nil {
		log.Printf("mark hot cooldown: %v", err)
	}
}
```

`Top` 在进入重建之前先查冷却标记。

```go
if ready == 0 {
	cool, err := s.rdb.Exists(ctx, hotCooldownKey).Result()
	if err == nil && cool > 0 {
		return s.TopFromMySQL(ctx, n)
	}
	// ...重建
}
```

三个设计点。

**冷却期 30 秒，重建预算 3 秒，差一个数量级。** 冷却期要足够长，让堆积的查询散掉；又不能太长，否则一次网络抖动会让榜单在半小时内都用降级路径。

**`markCooldown` 用 `WithoutCancel`。** 触发重建失败的那个请求，`ctx` 大概率已经超时取消了。如果直接用 `ctx` 去 `SET`，Redis 会返回 `context canceled`，冷却标记根本写不进去，退避失效。这里必须脱离取消信号。

**冷却期内走 `TopFromMySQL`，不是直接报错。** 榜单仍能返回，只是走慢路径。这条降级路径本身也带 `LIMIT`，不会被 `n` 拖垮。

冷却标记是「整个榜单」维度的，不是「某个文章」。热榜是全局资源，重建失败也是全局失败，粒度对齐。

### 8.9 修完之后的 rebuild 完整形态

```go
// 源码摘录：internal/service/hot.go
func (s *HotService) rebuild(ctx context.Context) error {
	var rows []hotRow
	if err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
		Select("article_id, COUNT(*) AS score").
		Group("article_id").
		Order("score DESC, article_id ASC").
		Limit(hotRebuildTop).
		Scan(&rows).Error; err != nil {
		return fmt.Errorf("load all like counts: %w", err)
	}

	pipe := s.rdb.TxPipeline()
	pipe.Del(ctx, hotTempKey)
	if len(rows) > 0 {
		for _, r := range rows {
			member := strconv.FormatUint(uint64(r.ArticleID), 10)
			pipe.ZAdd(ctx, hotTempKey, redis.Z{Score: float64(r.Score), Member: member})
		}
		pipe.Rename(ctx, hotTempKey, hotArticlesKey)
	} else {
		pipe.Del(ctx, hotArticlesKey)
	}
	pipe.Set(ctx, hotReadyKey, "1", hotReadyTTL)
	if _, err := pipe.Exec(ctx); err != nil {
		return fmt.Errorf("rebuild hot zset: %w", err)
	}
	return nil
}
```

逐段对照四次修复。

| 代码段 | 对应修复 | 不做会怎样 |
| --- | --- | --- |
| `Order(...)` + `Limit(500)` | 一 | 千万级聚合，3 秒预算扛不住 |
| `Del(hotTempKey)` | 二 | 上次失败留下的半成品混进新榜 |
| `ZAdd` 到 `hotTempKey` | 二 | 写正式 key 会污染正在被读的榜 |
| `Rename` | 二 | 读侧看到残缺榜，写侧增量被覆盖 |
| 空榜走 `Del` | 二 | `RENAME` 报 key 不存在，重建必失败 |
| `Set(ready, TTL)` | 三 | 榜单冻结成历史快照 |
| 返回值交给 `markCooldown` | 四 | 超时后请求风暴 |

### 8.10 懒加载自愈完整时序

把四条分支画全。

```text
GET /api/articles/hot?limit=10
  │
  ├─ EXISTS hot:articles:v1:ready
  │    err  → TopFromMySQL（降级，慢但可用）
  │    1    → 直接往下
  │    0    ↓
  │
  ├─ EXISTS hot:articles:v1:cooldown
  │    1    → TopFromMySQL（刚失败过，别再试）
  │    0    ↓
  │
  ├─ singleflight.Do("hot:rebuild")      ← 并发请求在这里合并
  │    ├─ 二次 EXISTS ready
  │    │    1 → 别人已经建好，直接返回
  │    │    0 ↓
  │    └─ rebuild
  │         ├─ SELECT article_id, COUNT(*) GROUP BY article_id
  │         │    ORDER BY score DESC LIMIT 500
  │         ├─ MULTI
  │         │    DEL  tmp
  │         │    ZADD tmp <500 条>
  │         │    RENAME tmp → hot:articles:v1
  │         │    SET  ready 1 EX 3600
  │         │  EXEC
  │         └─ 失败 → markCooldown(30s)
  │
  ├─ ZREVRANGE hot:articles:v1 0 n-1 WITHSCORES
  │    err  → TopFromMySQL
  │
  └─ SELECT * FROM articles WHERE id IN (...) → 重新按 ZSET 顺序排 → 返回
```

整个过程不需要人工介入。`FLUSHDB` 之后下一个读请求会自己把投影建回来。这叫懒加载自愈，代价是第一个请求要等一次聚合。

想消掉这次等待，可以在启动时预热：`main` 里起一个 goroutine 异步调一次 `ensureHotZSet`。当前没做，因为预热会让冷启动的 `main` 多一条失败分支。

### 8.11 两次查询与顺序还原

```text
ZREVRANGE hot:articles:v1 0 9 WITHSCORES
  → [(12, 88.0), (7, 55.0), (31, 42.0), ...]

SELECT * FROM articles WHERE id IN (12, 7, 31, ...)
  → 三条记录，顺序由 MySQL 决定，可能完全不是 12, 7, 31
```

`loadByIDs` 做的是「先建 map，再按 `rows` 的顺序输出」。

```go
// 源码摘录：internal/service/hot.go
byID := make(map[uint]model.Article, len(articles))
for _, a := range articles {
	byID[a.ID] = a
}

list := make([]HotArticle, 0, len(rows))
for _, r := range rows {
	a := byID[r.ArticleID]
	list = append(list, HotArticle{
		ArticleID: r.ArticleID,
		Score:     float64(r.Score),
		Title:     a.Title,
		LikeCount: r.Score,
	})
}
```

循环的是 `rows`（来自 ZSET，已按分数降序），取的是 `byID`。`IN` 查询返回的顺序被完全丢弃。这一句是整个热榜能不能正确排序的关键，很容易在重构时被「优化」成 `for _, a := range articles`，然后榜单顺序随机。

同一段代码有个真实缺口。如果 ZSET 里有个 id 对应的文章已被删除，`byID[id]` 取不到，`a` 是零值，榜单里出现一条标题为空的条目。正常流程删文章会 `ZREM`，只有 Redis 故障导致那次 `ZREM` 失败时才会残留。

修法一行。

```go
if _, ok := byID[r.ArticleID]; !ok {
	continue
}
```

当前没加。理由是加了会掩盖「Redis 与数据库不一致」这个信号。实际生产应该加上并打日志，两者不冲突。

### 8.12 评分口径与时间衰减

当前分数就是点赞总数，没有时间衰减。

后果是 `ZSET` 的排序等价于「历史累计热度榜」。一篇三年前 10 万赞的文章，永远压着今天涨了 1000 赞的新文章。

三种改进。

| 方案 | 公式 | 特点 |
| --- | --- | --- |
| Hacker News | `(votes - 1) / (age + 2)^1.8` | 衰减快，新内容容易上榜 |
| Reddit | `log10(votes) + age/45000` | 投票取对数，时间项线性 |
| 滑动窗口 | 只统计最近 24 小时 | 最公平，要多一张表或定时任务 |

三种方案都有一个共同代价：**分数随时间变化，ZSET 里的绝对值会过期**。今天算出的 88 分，明天应该变成 40 分，但 ZSET 不会自己变。必须引入定时重算任务，把 Top N 重新算一遍写回去。

这也是为什么当前不做。加了衰减就要加一个后台任务，加了任务就要处理任务失败、任务与重建并发、任务与点赞写的冲突。复杂度上一个台阶，收益是可解释性更强。等有真实流量再说。

### 8.13 已知边界

| 边界 | 影响 | 正式方案 |
| --- | --- | --- |
| 重建窗口（SQL 返回 → RENAME）内的点赞 | 分数暂时少 1 | 下次点赞按绝对值修正 |
| 多实例各有一份 singleflight | 最多 N 次并发重建 | Redis 分布式锁 |
| 聚合仍是 O(点赞总数) | 每小时一次重活 | 加 `articles.like_count` 列走索引 |
| 已删文章的残留成员 | 空标题条目 | `loadByIDs` 里跳过 |
| 没有时间衰减 | 老文章长期占榜 | 定时重算 |
| `ready` 与 ZSET 不同步 | 极端时序下可能读到空榜 | 两者用同一 pipeline 写入（已做） |

第二条值得展开。`singleflight` 是进程内的，四实例部署时，`FLUSHDB` 后最多四个重建同时跑。用 `SET hot:rebuild:lock 1 NX EX 5` 做分布式锁能压到一个，代价是多一次 Redis 往返和锁超时的边界处理。当前量级下四次重建可接受。

### 8.14 热榜面试问答

| 问题 | 回答要点 |
| --- | --- |
| 为什么用 ZSET 不用 List | List 只能按下标取，不能按分数排序。`ZREVRANGE` 天然支持 Top N，插入 O(log N) |
| 空 ZSET 和投影丢失怎么区分 | 独立 `ready` 标记，空榜也写。只看 ZSET 分不清「真空」与「丢失」 |
| 为什么 `ready` 要设 TTL | 永不过期会让榜单冻结成「首建快照 + 增量补丁」，热度排序逐渐失真 |
| TTL 为什么只给 `ready` 不给 ZSET | ZSET 先消失而 `ready` 还在时，榜单会静默变空，且要等 `ready` 过期才自愈 |
| 为什么要单个 `tmp` key | 写正式 key 会让并发读看到残缺榜，也会被后续全量 `ZADD` 覆盖掉重建期间的点赞 |
| `RENAME` 为什么能保证一致 | Redis 单线程，`RENAME` 内部是整体替换，读侧只能看到旧值或新值 |
| 为什么用 `TxPipeline` | 外面套 `MULTI/EXEC`，`RENAME` 与 `SET ready` 不被其它命令插入 |
| 重建期间的点赞会不会丢 | 有窄缝会丢，靠 `syncHotScore` 写绝对值在下次点赞时修正，一小时后重建整体归位 |
| 能不能用 `ZUNIONSTORE AGGREGATE MAX` 补 | 不行。分数是绝对值，`MAX` 会让取消点赞的降序失效 |
| 全表 `GROUP BY` 会锁表吗 | 不会，MVCC 快照读不加锁。开销是索引扫描、临时表、filesort 三样 |
| 加 `LIMIT` 能降多少成本 | 排序和结果集降下来，扫描量不降。聚合必须过全部行 |
| 怎么把扫描量也降下来 | 加 `articles.like_count` 列建索引，重建变成 `ORDER BY like_count DESC LIMIT 500` |
| 为什么 `LIMIT` 取 500 不是 100 | 接口上限 100，多留余量让快升上来的文章有位置，避免第 101 名死区 |
| 重建超时了会怎样 | 打 30 秒冷却，冷却期内直接降级，避免每个请求都去试一次全表聚合 |
| 冷却标记为什么用 `WithoutCancel` | 触发失败的请求 `ctx` 已取消，用它写 Redis 会失败，退避失效 |
| 重建为什么要 `singleflight` | `FLUSHDB` 后并发请求会同时扫全表，合并成一次 |
| 降级路径怎么保证不慢 | `groupTop` 带 `ORDER BY ... LIMIT n`，n 最大 100 |
| 为什么写绝对值不写增量 | 绝对值每次用 MySQL 真值覆盖，自带纠错与自愈；增量一旦出错永久留存 |
| 榜单顺序怎么保证 | `IN` 查询不保序，循环 `rows`（ZSET 顺序）取 map，不循环 `articles` |
| 多实例怎么办 | 接受 N 次重建，或加分布式锁。当前接受 |
| 怎么加时间衰减 | 改公式加定时重算，ZSET 存绝对值就必须周期性重写 |
| 热榜延迟多少 | 点赞写路径同步更新，毫秒级。重建触发时有百毫秒级等待 |

## 9. 限流链路

### 9.1 令牌桶与固定窗口

| 算法 | 做法 | 问题 |
| --- | --- | --- |
| 固定窗口 | 每分钟计数，超过阈值拒绝 | 窗口边界双倍流量。59 秒打满 100，01 秒再打 100 |
| 滑动窗口 | 按最近 60 秒统计 | 要存每个请求的时间戳，内存大 |
| 漏桶 | 请求排队，匀速流出 | 会引入延迟，不适合 HTTP |
| 令牌桶 | 桶里放令牌，按速率补充，请求取一个 | 允许突发，长期速率可控 |

当前用令牌桶，容量 10，速率每秒 2 个。含义是最多允许 10 个瞬时突发，长期平均每秒 2 次。

### 9.2 Lua 脚本逐段

```lua
-- 源码摘录：internal/middleware/ratelimit.go
local now_ms = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)
local tokens = tonumber(redis.call('HGET', key, 'tokens')) or capacity
local last_ms = tonumber(redis.call('HGET', key, 'last_ms')) or now_ms
local elapsed_ms = math.max(0, now_ms - last_ms)
tokens = math.min(capacity, tokens + elapsed_ms * rate / 1000)
```

| 行 | 作用 |
| --- | --- |
| `redis.call('TIME')` | 用 Redis 的时间，不用应用服务器的时间 |
| `HGET tokens` | 取当前令牌数，没有就按满桶算 |
| `HGET last_ms` | 取上次访问时间，没有就按当前算 |
| `math.max(0, ...)` | 时钟回拨时把经过时间夹成 0，不倒扣 |
| `math.min(capacity, ...)` | 补充上限是桶容量 |

为什么用 Redis 的 `TIME`。多个应用实例的本地时钟可能有几百毫秒偏差。用本地时间算经过时间，同一个用户在不同实例上会得到不同结果。`TIME` 让所有实例共享一个时钟。

为什么整段必须是 Lua。读令牌数、算补充、扣减、写回，四步必须原子。分四次调用 Redis，中间可能插入别的请求，导致超发。

### 9.3 TTL 与续期

```lua
local ttl_ms = math.max(1000, math.ceil(capacity * 2000 / rate))
redis.call('PEXPIRE', key, ttl_ms)
```

`capacity * 2000 / rate` 是「补满整桶所需时间的两倍」。

当前值 `10 * 2000 / 2 = 10000ms`，即 10 秒。含义是一个 IP 停止请求 10 秒后，这个 key 自动消失，不占内存。

每次请求都会重置 TTL，这是滑动过期。活跃用户永远不过期，停止请求后自然回收。

### 9.4 fail-open 的取舍

```go
// 源码摘录：internal/middleware/ratelimit.go
if err != nil {
    log.Printf("rate limit check %s: %v", key, err)
    c.Next()
    return
}
```

Redis 故障时放行所有请求。

理由：限流是保护手段，不能变成单点故障。Redis 挂了就让整个论坛 503，代价比短时间不限流大。

反面观点也成立。如果是被攻击，Redis 挂了正好等于不设防。生产环境通常两条路：本地内存兜底限流，或者 Redis 故障时切到更严格的固定阈值。

### 9.5 单 IP 维度的三个问题

| 问题 | 现象 |
| --- | --- |
| NAT 后面共享 IP | 公司、学校出口 IP 相同，一个人的行为影响所有人 |
| IPv6 地址空间大 | 攻击者可以换地址绕过 |
| 只按 IP 不按用户 | 登录用户换 IP 就能重置额度 |

改进方向：登录用户按 userID 限流，未登录按 IP；关键接口叠加维度（如 `POST /api/articles` 加用户维度）；IPv6 按 /64 前缀聚合。

### 9.6 限流面试问答

| 问题 | 回答要点 |
| --- | --- |
| 为什么选令牌桶 | 允许突发又不失控。固定窗口有边界双倍流量问题 |
| Lua 里为什么用 Redis TIME | 多实例时钟不一致，用服务端时间才有全局一致性 |
| 为什么不用应用层内存限流 | 多实例各算各的，总额度变成 N 倍。除非按实例分摊 |
| key 为什么带 IP 前缀 | 避免和其他业务 key 冲突，也方便按前缀排查 |
| TTL 怎么定 | 补满整桶时间的两倍。太短会丢失状态，太长浪费内存 |
| fail-open 的风险 | 攻击时等于没有防护。可以用本地兜底限流补偿 |
| 429 响应要带什么 | `Retry-After` 头，告诉客户端多久后重试。当前已实现 |
| 限流阈值怎么定 | 压测得到单实例容量，按业务峰值倒推。10 和 2 是学习值 |
| 分布式限流还有什么方案 | Redis 计数器、Sentinel、网关层限流。令牌桶的优点是平滑 |
| 限流和熔断的区别 | 限流控制进入的流量，熔断控制对下游的调用。两者方向相反 |
| 白名单怎么做 | key 里判断用户或 IP 是否在集合内，命中直接放行。当前没有 |
| 为什么 `PEXPIRE` 每次都要设 | 滑动过期，保证活跃 key 不会在请求中途消失 |

## 10. 异步消息链路

### 10.1 失败窗口推演

点赞成功后要给作者发通知。最直觉的写法是「写完库，发一条消息」。

```text
t1  写 article_likes 成功，事务提交
t2  进程崩溃 / 网络断开 / Redis 超时
t3  XADD 没执行
```

结果：数据库里有这条点赞，作者永远收不到通知，而且没人知道漏了。

把顺序反过来（先发消息再写库）问题更严重。消息发出去了，消费方去查文章作者，发现点赞根本不存在，或者查到一条不存在的资源。

这个窗口无法用重试解决，因为程序已经死了，没人知道要重试什么。

### 10.2 outbox 的核心一句话

把「要发消息」这件事，变成数据库里的一行数据，和业务写入同事务提交。

```go
// 源码摘录：internal/event/event.go
func Emit(ctx context.Context, tx *gorm.DB, p Payload) error {
    row := &model.OutboxEvent{
        EventID:       p.EventID,
        EventType:     p.Type,
        AggregateType: p.Target.Type,
        AggregateID:   p.Target.ID,
        Payload:       payload,
        Status:        model.OutboxPending,
    }
    return tx.WithContext(ctx).Create(row).Error
}
```

事务提交成功，这行 `pending` 一定在。事务回滚，它一定不在。数据库的原子性把「写业务」和「记事件」绑成一个不可分割的动作。

剩下的事就是「怎么把 pending 变成已投递」，这部分允许失败、允许重试，因为它不影响业务数据的正确性。

### 10.3 三个状态

| 状态 | 含义 | 谁会改它 |
| --- | --- | --- |
| `pending` | 还没投进 Stream | 业务事务写入 |
| `published` | `XADD` 成功 | relay |
| `failed` | 重试到上限 | relay 的 `markFailure` |

`failed` 不是死信队列，只是一行状态标记。要排查时查 `WHERE status = 'failed'`，看 `attempts` 和 `payload`。

没有「已消费」状态。消费侧的成功与否由 Stream 的 ACK 表达，不需要回写 MySQL。这是有意的：让 outbox 只管「投递」，不管「消费」。

### 10.4 relay 的循环

```go
// 源码摘录：internal/worker/relay.go
ticker := time.NewTicker(relayInterval)   // 200ms
for {
    select {
    case <-ctx.Done(): return
    case <-ticker.C: r.PublishBatch(ctx)
    }
}
```

```go
// 源码摘录：internal/worker/relay.go
r.db.WithContext(ctx).
    Where("status = ?", model.OutboxPending).
    Order("id ASC").Limit(relayBatchSize).  // 100
    Find(&events)
```

| 参数 | 值 | 依据 |
| --- | --- | --- |
| 轮询间隔 | 200ms | 通知延迟可接受上限。太短会增加无谓查询 |
| 批量大小 | 100 | 单次事务与内存的折中 |
| 排序 | `id ASC` | 先进先出，事件顺序大致保持 |
| 最大重试 | 5 | 超过说明不是瞬时故障 |

为什么用轮询不用触发器。MySQL 触发器里没法发 Redis 命令。轮询简单、可观测、失败可控。

轮询的成本：每 200ms 一次 `WHERE status='pending' ORDER BY id LIMIT 100`。有 `status` 索引，空表时几乎零成本。生产环境量大了会改成「有事件才唤醒」，用 `LISTEN/NOTIFY` 或消息通知，当前不做。

### 10.5 投递与失败处理

```go
// 源码摘录：internal/worker/relay.go
_, err := r.rdb.XAdd(ctx, &redis.XAddArgs{
    Stream: event.StreamKey,
    Values: map[string]interface{}{
        "event_id": e.EventID,
        "type":     e.EventType,
        "payload":  e.Payload,
    },
}).Result()
if err != nil {
    r.markFailure(ctx, e)
    continue
}
r.db.Model(&model.OutboxEvent{}).Where("id = ?", e.ID).
    Update("status", model.OutboxPublished)
```

三个细节。

`continue` 而不是 `return`。单条 `XADD` 失败通常是偶发，后面的消息大概率能成功。整批放弃会让一条坏消息卡住后面所有事件。

`Update` 失败直接 `return`。这说明数据库连接不可用或 ctx 已取消，继续处理没意义。

`XADD` 与 `Update` 不是原子的。极端情况下 `XADD` 成功、`Update` 失败，下轮会重复投递同一条事件。这就是「至少一次」。

### 10.6 消费组与 PEL

```go
// 源码摘录：internal/worker/notification.go
_ = w.rdb.XGroupCreateMkStream(ctx, event.StreamKey, event.NotifyGroup, "0").Err()

for {
    w.consume(ctx, "0")   // 补上次没 ACK 的
    w.consume(ctx, ">")   // 阻塞读新消息
}
```

`XGROUP CREATE ... MKSTREAM`：组不存在就建，流不存在也建。重复创建返回 `BUSYGROUP`，忽略即可。

`"0"` 与 `">"` 的区别。

| 起点 | 含义 | 是否阻塞 |
| --- | --- | --- |
| `">"` | 组里还没投递过的新消息 | 是，`BLOCK` 生效 |
| `"0"` | 当前 consumer 的 PEL 里所有未 ACK 的消息 | 否，传 `Block: -1` 立即返回 |

先读 `"0"` 再读 `">"` 的顺序很重要。上次进程崩溃前处理到一半的消息留在 PEL 里，先补完才不会漏。如果先读 `">"`，新消息不断进来，PEL 里的旧消息可能一直排不上。

`Block: -1` 的细节。go-redis v9 里只有 `Block >= 0` 才会发送 `BLOCK` 参数。传 `-1` 让这次读立即返回，循环不会卡住。

#### 读命令的六个参数

消费的核心就是一条命令。

```go
// 源码摘录：internal/worker/notification.go（形态）
w.rdb.XReadGroup(ctx, &redis.XReadGroupArgs{
    Group:    event.NotifyGroup,     // forum:notify:v1
    Consumer: w.consumer,            // worker-1
    Streams:  []string{event.StreamKey, cursor},
    Count:    10,
    Block:    blockDuration,
    NoAck:    false,
})
```

| 参数 | 取值 | 影响 |
| --- | --- | --- |
| `Group` | `forum:notify:v1` | 消费组名。换个名字等于换一条独立的消费进度 |
| `Consumer` | `worker-1` | 消费者名。同名即同一个 PEL |
| `Streams` | `[stream, cursor]` | 两个元素，前一个是 key，后一个是起点 |
| `Count` | 10 | 单次最多拉多少条。太大则一批处理时间长，崩了要重放的多 |
| `Block` | 正数毫秒或 `-1` | 正数表示阻塞等这么久，`-1` 表示不阻塞立即返回 |
| `NoAck` | `false` | 必须为 `false`。设成 `true` 就不进 PEL，等于放弃重试能力 |

`NoAck: true` 是个陷阱。它让消费变成「读走就算」，吞吐高一点，代价是进程崩了消息直接消失。只有「丢了也无所谓」的场景才用，比如纯统计打点。

#### 一个 Stream 上挂多个消费组

这是 Stream 相对 List 的核心优势，也是这套代码后面要扩的地方。

```text
forum:events:v1
  └─ 组 forum:notify:v1   → 消费者 worker-1   → 写 notifications 表、推 WebSocket
```

| 场景 | 用同组多消费者 | 用多消费组 |
| --- | --- | --- |
| 语义 | 分摊，一条消息只给一个人 | 广播，每个组都拿到全量 |
| 进度 | 共享一个 last-delivered-id | 每组各自维护 |
| 典型用途 | 提高消费吞吐 | 一份事件喂给多个下游 |

关键在于**同一个事件被两个完全不同的下游消费**。通知关心「谁给谁点了赞」，搜索关心「哪篇文章变了」。用多消费组，两边进度互不干扰：搜索侧重建索引要回放三天前的消息，不会把通知侧的进度拖回去。

这也是为什么通知消费者读到不认识的事件类型时，必须直接 ACK 丢弃，而不能默认当点赞或评论处理。否则一旦 Stream 里混进不认识的事件类型，它就会拿着文章事件去查文章作者、给自己发一条「你点赞了自己的文章」的通知。

#### PEL 的三种异常状态

| 状态 | 表现 | 处理 |
| --- | --- | --- |
| 正常在途 | 消息在 PEL，消费者活着，正在处理 | 等它 `XACK` |
| 消费者已死 | 消息在 PEL，无人持有 | 重启后读 `"0"` 补，或 `XAUTOCLAIM` 接管 |
| 毒消息 | 反复处理失败，一直不 `XACK` | 需要最大投递次数加人工介入 |

第二种当前的处理方式是「重启后自己补」。单实例部署下这够用，因为同一个消费者名 `worker-1` 重启后拿到的还是自己那份 PEL。

第三种当前没有兜底。一条永远处理失败的消息会留在 PEL 里，每轮 `doConsume("0")` 都会重试一次。实际代码里大部分失败路径都主动 `return nil` 当成成功（文章已删、自己给自己点赞），真正会卡住的只有数据库写失败这类有界故障。

想看清 PEL 里有什么，用 `XPENDING`。

```text
> XPENDING forum:events:v1 forum:notify:v1
1) (integer) 3                 未确认总数
2) "1762800000000-0"           最小消息 ID
3) "1762800001200-0"           最大消息 ID
4) 1) 1) "worker-1"            消费者名
      2) "3"                   它持有 3 条
```

带 `- + 10` 参数会返回明细，每条带 `idle` 毫秒数与 `delivery count`。

```text
> XPENDING forum:events:v1 forum:notify:v1 - + 10
1) 1) "1762800000000-0"
   2) "worker-1"
   3) (integer) 84213          闲置 84 秒
   4) (integer) 5              投递过 5 次
```

`delivery count` 到 5 以上基本可以判定是毒消息。真要做兜底，就在 `consumeLoop` 里加一次 `XPENDING` 扫描，把 `idle` 超过阈值且 `delivery count` 超上限的消息 `XACK` 掉并落一条失败日志。当前没做。

接管别人遗留的消息用 `XAUTOCLAIM`。

```text
> XAUTOCLAIM forum:events:v1 forum:notify:v1 worker-2 60000 0-0 COUNT 10
```

意思是「把闲置超过 60 秒的消息转给 `worker-2`」。它比 `XCLAIM` 好用，因为一次能扫一批，不用先查 `XPENDING` 再逐条认领。多实例部署时这是标准做法。

#### ACK 的时机

```go
// 源码摘录：internal/worker/notification.go（形态）
if err := w.handle(ctx, msg); err != nil {
    return err          // 不 ACK，留在 PEL 里下轮重试
}
w.rdb.XAck(ctx, event.StreamKey, event.NotifyGroup, msg.ID)
```

顺序不能反。

- 先 ACK 再写库，写完库崩了，消息已经确认，通知永久丢。
- 先写库再 ACK，写完库崩了，消息还在 PEL，下轮重放，靠唯一索引去重。

后者的代价是可能重复处理，收益是不丢。这是「至少一次」的落地方式。

还有一个更细的点。`XAck` 自己也可能失败，此时消息留在 PEL，会被重放。所以 `XAck` 的错误不需要特殊处理，只需要在下一轮能读到。但如果 `XAck` 失败而业务确实成功了，PEL 里的 `delivery count` 会一直涨，靠 `XPENDING` 能看出来。

#### XADD 的 MAXLEN 与 PEL 的冲突

Stream 是一个只增不减的结构，不做裁剪就会一直涨。标准做法是 `XADD ... MAXLEN ~ 100000`。

但这里有个反直觉的坑。**`MAXLEN` 裁掉的条目如果还在某个组的 PEL 里，消费者去读 `"0"` 时会拿到一条内容为 nil 的记录。**

原因是裁剪删的是消息本体，PEL 里只留了 ID。消费者按 ID 去取，取不到内容。规范里把这个情况定义为「该条目被删除」，客户端拿到的是空 body，处理时很容易直接 panic。

所以加 `MAXLEN` 时要保证「裁掉的都是已经被三个组全部 ACK 的」。可行的做法是留足够大的冗余，比如按峰值 QPS 算出一个远大于 PEL 最大深度的值。想精确就查 `XINFO GROUPS` 里每组的 `lag` 和 `pending`，取最小值决定能裁到哪。

当前代码没加 `MAXLEN`，原因是数据量还小，而且加错比不加危险。这一条写进 10.11 的边界表。

### 10.7 幂等落在数据库

```go
// 源码摘录：internal/worker/notification.go
res := w.db.WithContext(ctx).Clauses(clause.OnConflict{
    Columns:   []clause.Column{{Name: "event_id"}},
    DoNothing: true,
}).Create(notice)
```

配合 `notifications.event_id` 上的唯一索引 `uk_notify_event`。

为什么不用内存去重。进程重启后内存清零，去重表丢失。多实例各有各的内存，互相不知道。

为什么不用 `SELECT` 再 `INSERT`。两个消费者同时查到「不存在」，然后都插入，其中一个必然失败。让唯一索引裁决，代码更短也更准。

`event_id` 的生成方式。

```go
// 源码摘录：internal/event/event.go
b := make([]byte, 16)
rand.Read(b)
hex.EncodeToString(b)   // 32 字符
```

16 字节随机数的碰撞概率可以忽略，比引入 uuid 依赖更轻。

注意 `event_id` 是 32 字符，字段声明 `varchar(36)`。36 是 UUID 带连字符的长度，留了余量。如果将来换成 UUID，字段不用改。

### 10.8 瘦事件与类型分发

```go
// 源码摘录：internal/event/event.go
type Target struct {
    Type string `json:"type"`
    ID   uint   `json:"id"`
}

type Payload struct {
    EventID    string  `json:"event_id"`
    Type       string  `json:"type"`
    ActorID    uint    `json:"actor_id"`
    Target     Target  `json:"target"`
    Created    *Target `json:"created,omitempty"`
    OccurredAt int64   `json:"occurred_at"`
}
```

只带 ID，不带标题、用户名、正文。

`Target` 在所有事件里含义一致，动作作用的对象。点赞与评论都指向文章，关注指向用户。`Created` 是动作新建出来的实体，可选，评论带它、点赞不带。

点赞事件 5 个字段，评论事件 6 个。两个事件因此落在同一个 outbox 聚合（article）上，`AggregateType` 不会一类记 article 另一类记 comment。

好处：事件体积小，Stream 内存占用低；新增行为只多一种 `target.type` 取值，Payload 结构不变；消费端看到的永远是最新数据。

代价：消费端要多查一次数据库。`resolveArticleAction` 里查文章作者就是这次回查。

```go
// 源码摘录：internal/worker/notify_resolver.go
var resolverByType = map[string]resolver{
    event.TypeLikeCreated:    resolveArticleAction,
    event.TypeCommentCreated: resolveArticleAction,
}
```

`handle` 按 `p.Type` 查这张表，拿到 resolver 后只消费它返回的 `notifySpec`。回查文章、判断自己动作、文章已删这三个提前返回都收在 resolver 里，返回 nil 就 ACK。

**两类事件怎么共用一条链路**

| 环节 | 文件 | 是否区分事件类型 |
| --- | --- | --- |
| 事件常量 | `internal/event/event.go` | `TypeLikeCreated` 与 `TypeCommentCreated` 并列定义 |
| 生产 | `internal/service/like.go`、`comment.go` | 都调 `event.EmitCreated`，参数里没有具体业务字段 |
| 搬运 | `internal/worker/relay.go` | `WHERE status = 'pending'`，不看类型 |
| 分发 | `internal/worker/notify_resolver.go` | `handle` 按 `p.Type` 查注册表，两类都指向 `resolveArticleAction` |
| 落库与推送 | `internal/worker/notification.go` | 对所有类型一视同仁，只消费 `notifySpec` |

`event.EmitCreated` 把 `NewPayload` 与 `Emit` 合成一步。点赞传 `Target{article, articleID}` 与 `nil`，评论传 `Target{article, articleID}` 与 `Target{comment, m.ID}`。公共入口的参数表不随行为种类增长。

通知的跳转对象由 `jumpTarget` 决定，有 `Created` 用它，没有就用 `Target`。评论通知跳那条评论，点赞通知跳文章。

前端靠 `data.type` 区分 `like.created` 与 `comment.created`，外层 `type` 恒为 `notification.created`。跳转目标看 `data.target_type` 与 `data.target_id`，`article_id` 只作列表展示用的文章上下文。

**新增一种行为要改哪些地方**

以关注为例。收件人是被关注的用户，与文章无关，现有「回查文章作者」那条逻辑完全用不上。

| 步骤 | 改动 |
| --- | --- |
| 1 | `internal/event/event.go` 加 `TypeFollowCreated` 常量 |
| 2 | 关注 service 调 `EmitCreated(ctx, tx, TypeFollowCreated, actorID, Target{TargetUser, followeeID}, nil)` |
| 3 | `notify_resolver.go` 写 `resolveFollow`，把 `p.Target.ID` 直接放进 `notifySpec.UserID` |
| 4 | `resolverByType` 注册一行 |

`handle`、落库、`OnConflict`、WS 推送、通知表、DTO 全部不用改。这次重构买的就是这个扩展性。

**为什么不能用业务字段当判别式**

上一版把 `comment_id` 是否为 0 当成事件类型的隐含信号。做关注、收藏、回复时，Payload、通知表、DTO 都要跟着加列，公共入口的参数表也会越排越长，每一处新字段又变成新的隐式信号。判别落在 `type` 这个显式字段上，负载只描述对象，分工更稳。

辩证地看，事件种类长期只有两三个时，平铺字段写起来更快，通用 Target 会多一层间接。这套结构为「行为会持续增加」这个假设付成本，假设不成立时它属于过度设计。

**如果以后做楼中楼回复**

当前 `Comment` 只有 `article_id`，没有 `parent_id`，楼中楼不存在，两个字段够用。顶楼评论的 `Target` 是文章，`Created` 是它自己。

真要做「回复某条评论」，结构依然够用，只是把 `Target` 换成被回复的那条评论。

| 事件 | Target | Created | 收件人 |
| --- | --- | --- | --- |
| `like.created` | article/7 | 无 | 文章作者 |
| `comment.created` | article/7 | comment/34 | 文章作者 |
| `reply.created` | comment/34 | comment/56 | 被回复评论的作者 |

`reply.created` 要新写一个 `resolveReply`，因为收件人不在文章上。它还需要文章 id 给通知列表用，回查 `Created` 那条评论的 `article_id` 就能一次拿到两件事。

`Target` 的含义没有为回复扩张，它始终是动作作用的对象。顶楼评论与回复的边界靠 `Target.Type` 区分，不靠某个 id 是否为零。

现在不做，因为功能本身不存在。提前加 `parent_id` 或 `ReplyTo` 属于为假设付成本，与这次删掉兼容字段是同一个判断。

**旧消息与未注册类型**

| 情况 | 处理 |
| --- | --- |
| Stream 里残留旧格式消息 | 不做解码兼容。重启前 `redis-cli DEL forum:events:v1` 清空流与消费组，从空流开始 |
| 旧格式消息没清干净 | 解出零值 Target，`articleIDOf` 返回 0，事件被 ACK 掉且不产生通知 |
| 新事件忘了注册 resolver | `handle` 记日志并直接 ACK，通知静默丢失，靠注册表测试把关 |
| 搜索同步的 `article.created` 混进 Stream | 未注册，直接 ACK，不会误发通知，也不会卡在 PEL |

删掉兼容字段换来解码器只有一种格式要理解。代价是 key 名还叫 `v1`，格式已变，正式跨版本发布应升 `StreamKey` 版本号并让旧 key 自然过期。学习项目直接用清空流的方式过渡。

`model.Notification` 换成 `target_type` 加 `target_id` 之后要重启服务触发 AutoMigrate 加列。

### 10.9 至少一次与恰好一次

| 语义 | 含义 | 代价 |
| --- | --- | --- |
| 至多一次 | 可能丢，不重复 | 不做重试 |
| 至少一次 | 不丢，可能重复 | 消费者必须幂等 |
| 恰好一次 | 不丢不重 | 需要分布式事务或幂等加去重表 |

本系统的组合是「至少一次投递 + 幂等消费」，效果上等价于恰好一次的处理结果。

做不到真正恰好一次的原因：`XADD` 与 `Update status` 不在同一事务，中间可能崩。要消除这个窗口，得让 Redis 和 MySQL 参与同一个分布式事务，代价远大于收益。

面试时的标准答法：不追求恰好一次，追求「至少一次 + 幂等」，最终结果是恰好一次。

### 10.10 为什么不用 Kafka

| 维度 | Redis Stream | Kafka |
| --- | --- | --- |
| 部署 | 已有 Redis | 独立集群、ZooKeeper 或 KRaft |
| 吞吐 | 十万级 | 百万级 |
| 持久化 | 内存为主，RDB/AOF | 磁盘顺序写，保留期长 |
| 消费模型 | 消费组 + PEL | 分区 + offset |
| 运维 | 几乎零 | 重 |

当前量级用 Stream 足够，而且复用已有的 Redis 客户端，没有新增组件。要换 Kafka 的信号是：消息量到百万级、需要长期保留、需要多团队订阅同一份数据。

### 10.11 已知边界

| 边界 | 影响 | 正式方案 |
| --- | --- | --- |
| Stream 没有 `MAXLEN` | 长期运行内存持续增长 | 按 `XINFO GROUPS` 的 `lag` 定裁剪线再加 `MAXLEN ~ N`，见 10.6 的冲突说明 |
| `outbox_events` 没有归档 | 表无限增长，`pending` 查询变慢 | 定时把 `published` 迁到历史表或删除 |
| consumer 名固定 `worker-1` | 多实例共用同一个 PEL，重放会重复处理 | 用 `hostname` 或 `uuid` 做 consumer 名 |
| 单消费者 | 消费吞吐有限 | 多 consumer 分摊，配合 `XAUTOCLAIM` 接管超时消息 |
| 没有 `XAUTOCLAIM` | 消费者崩溃后 PEL 里的消息要等它重启才能补 | 定时扫描空闲超过阈值的消息并认领 |
| relay 单实例 | 多实例同时跑会重复投递 | 用 `SELECT ... FOR UPDATE SKIP LOCKED` 抢占 |

第 3 条最容易被追问。两个实例都叫 `worker-1`，Redis 认为它们是同一个消费者，PEL 混在一起。消息不会丢，但一个实例崩溃后，另一个实例读 `"0"` 会把对方未 ACK 的消息也读出来重放。好在幂等索引兜住了，最终结果正确。

正确的做法是消费者名带上实例唯一标识。

### 10.12 异步消息面试问答

| 问题 | 回答要点 |
| --- | --- |
| 为什么需要 outbox | 写库与发消息不在同一事务，中间崩溃会丢事件。outbox 把事件变成数据库的一行 |
| 为什么不能先发消息再写库 | 消息发出后数据库回滚，消费方会收到一个不存在的事实 |
| outbox 保证什么 | 保证「业务成功则事件必被记录」。投递是至少一次 |
| relay 为什么要轮询 | 触发器发不了 Redis 命令。轮询简单可控，量大了再换通知机制 |
| 重复投递怎么办 | 消费端幂等。`event_id` 唯一索引加 `OnConflict DoNothing` |
| 为什么用 `event_id` 不用自增 id | 自增 id 在分库或重建时会重复，随机 ID 全局唯一 |
| PEL 是什么 | 待确认消息列表。消息已投给消费者但还没 ACK，存在这里 |
| 为什么要先读 `"0"` | 补上次没处理完的消息。先读新消息会让旧消息一直排队 |
| `Block: -1` 什么意思 | go-redis 里传负数不发 `BLOCK`，立即返回，避免循环卡住 |
| 怎么做到恰好一次 | 做不到严格恰好一次。用至少一次加幂等，效果等价 |
| 消费失败怎么重试 | 不 ACK，消息留在 PEL，下一轮读到再处理。没有次数上限，靠人工介入 |
| 为什么事件只带 ID | 体积小、字段稳定、消费端拿最新数据。代价是多一次查询 |
| 评论事件里的 `Target` 指什么 | 指评论作用的文章。刚插入的评论放在 `Created`，通知跳转用它 |
| 回复某条评论时事件怎么表示 | `Target` 换成被回复的那条评论，`Created` 仍是新评论，另写 `resolveReply`，见 10.8 |
| 自己给自己点赞要发通知吗 | 不发。`resolveArticleAction` 里判断 `article.UserID == p.ActorID`，返回 nil 让 `handle` 直接 ACK |
| 只有点赞会发通知吗 | 评论也会。`comment.created` 从 `CommentService.Create` 进 outbox，走同一个 relay 与同一个消费组 |
| 点赞与评论怎么避免写两套代码 | 生产端共用 `event.EmitCreated`，消费端按 `p.Type` 查 `resolverByType`，两类都指向 `resolveArticleAction` |
| 新增关注事件要改哪些地方 | 加类型常量、写 `resolveFollow`、注册表加一行。`handle`、通知表、DTO 都不动 |
| 前端怎么区分两类通知 | 外层 `type` 恒为 `notification.created`，靠 `data.type` 分流，跳转看 `data.target_type` 与 `data.target_id` |
| 用业务字段当判别式有什么问题 | 每加一种行为就要给 Payload、通知表、DTO 各加一列，这些零值字段又变成新的隐式信号。判别交给 `type` |
| 未知事件类型会怎样 | `handle` 记日志并直接 ACK，避免误发通知和毒消息。新事件忘注册时通知会静默丢失 |
| Stream 里的旧格式消息怎么办 | 不做兼容。重启前 `DEL forum:events:v1` 清空流，否则旧消息解出零值 Target 后被静默 ACK |
| 文章删了事件怎么办 | 查不到作者，当成处理成功并 ACK。重试没有意义 |
| 怎么监控积压 | `XLEN` 看流长度，`XPENDING` 看未 ACK 数量。当前没有接入 |
| 多实例消费要注意什么 | consumer 名要唯一，否则 PEL 混淆。还要处理超时消息认领 |
| 为什么不用数据库轮询代替 Stream | 消费端要记录进度、要处理并发、要实现重试。Stream 已经把这些做好了 |
| 一个 Stream 能挂几个消费组 | 任意个。同组是分摊，跨组是广播。通知和搜索各用一个组，进度互不干扰 |
| 加了搜索之后通知消费要改什么 | 必须加事件类型白名单。Stream 里从此混进 `article.created`，原逻辑会把文章事件当点赞处理 |
| `XPENDING` 怎么看 | 简要模式给总数与 ID 区间，明细模式给 idle 与 delivery count。后者到 5 以上是毒消息 |
| 消费者崩了消息怎么办 | 消息留在 PEL。同名消费者重启后读 `"0"` 自动补；换实例则用 `XAUTOCLAIM` 按闲置时间接管 |
| `XACK` 放在业务写之前还是之后 | 之后。先 ACK 崩了会永久丢，后 ACK 崩了只是重放，重放有唯一索引兜底 |
| `NoAck` 能开吗 | 只有「丢了无所谓」的场景能开。开了就不进 PEL，等于放弃重试 |
| `MAXLEN` 有什么风险 | 裁掉的条目如果还在 PEL 里，消费者读 `"0"` 会拿到 nil body，容易 panic |
| 怎么定 `MAXLEN` 的值 | 查 `XINFO GROUPS` 里各组 `lag` 与 `pending`，取最小值以下才安全 |

## 11. 评论链路

### 11.1 与文章的差异

评论几乎复用了文章的所有模式，差异只有三处。

| 维度 | 文章 | 评论 |
| --- | --- | --- |
| 排序 | `created_at DESC, id DESC`（新在前） | `created_at ASC, id ASC`（旧在前） |
| 缓存 | 详情走 Cache Aside | 不缓存，直接查库 |
| 事件 | 不发 | 发 `comment.created` |

评论不缓存的原因：单篇文章的评论通常只有几十条，`WHERE article_id = ?` 走索引足够快。加缓存要处理「发布评论后失效哪一页」，复杂度高于收益。

### 11.2 创建时的一次故意多余查询

```go
// 源码摘录：internal/service/comment.go
var article model.Article
if err := s.db.WithContext(ctx).First(&article, articleID).Error; err != nil {
    if errors.Is(err, gorm.ErrRecordNotFound) {
        return nil, fmt.Errorf("check article %d: %w", articleID, ErrNotFound)
    }
    return nil, err
}
```

这一步查了文章，后面插入时外键还会再校验一次。看起来多余。

它的价值是错误语义。外键冲突返回 `ErrForeignKeyViolated`，映射成 400「引用的资源不存在」；显式查一次能返回 404「文章不存在」，客户端能区分「参数错」与「资源没了」。

注释里写清了它不是并发安全的最终保证：查完到插入之间文章可能被删，真正的兜底是 RESTRICT 外键。

### 11.3 删除评论与删除文章的关系

`comments.article_id` 是 `ON DELETE RESTRICT`。删文章必须先删评论。

这就是 `ArticleService.Delete` 里三步顺序的由来。评论表自己不级联，所有清理逻辑集中在文章删除的事务里，只有一处需要维护。

### 11.4 评论面试问答

| 问题 | 回答要点 |
| --- | --- |
| 评论为什么不缓存 | 单篇评论量小，索引查询够快。缓存要处理分页失效，复杂度高 |
| 评论排序为什么升序 | 对话顺序要按时间正序，最新在最后。文章列表相反，最新的在最前 |
| 为什么先查文章存在 | 为了返回 404 而不是外键报 400。外键仍是并发安全的兜底 |
| 删文章怎么处理评论 | 同一事务里先删评论再删文章，顺序由 RESTRICT 外键强制 |
| 评论能不能分页缓存 | 可以，但失效粒度是「文章维度」，一有新评论就整个前缀失效。收益不大 |
| 评论要不要发通知 | 发 `comment.created`，作者收到「有人评论了你的文章」 |

## 12. 错误处理与响应约定

### 12.1 三层错误

| 层 | 形式 | 例子 |
| --- | --- | --- |
| 哨兵错误 | 包级 `var`，用 `errors.Is` 判断 | `ErrInvalidInput`、`ErrNotFound` |
| 包装错误 | `fmt.Errorf("...: %w", err)` | `fmt.Errorf("query article %d: %w", id, ErrNotFound)` |
| 框架错误 | GORM 翻译后的哨兵 | `gorm.ErrDuplicatedKey`、`gorm.ErrForeignKeyViolated` |

```go
// 源码摘录：internal/service/user.go
var (
    ErrInvalidInput       = errors.New("invalid input")
    ErrUserNameTaken      = errors.New("username already taken")
    ErrInvalidCredentials = errors.New("invalid username or password")
    ErrNotFound           = errors.New("not found")
)
```

四个哨兵覆盖了所有对外可解释的业务错误。其余一律当成 500。

`%w` 的作用是保留错误链，`errors.Is` 能穿透包装找到根因。`%v` 只能拼字符串，判断不了。

### 12.2 统一映射

```go
// 源码摘录：internal/handler/errors.go
switch {
case errors.Is(err, service.ErrInvalidInput):
    response.Error(c, http.StatusBadRequest, "参数不符合要求")
case errors.Is(err, service.ErrNotFound):
    response.Error(c, http.StatusNotFound, "资源不存在")
case errors.Is(err, gorm.ErrRecordNotFound):
    response.Error(c, http.StatusNotFound, "资源不存在")
case errors.Is(err, gorm.ErrForeignKeyViolated):
    response.Error(c, http.StatusBadRequest, "引用的资源不存在")
case errors.Is(err, gorm.ErrDuplicatedKey):
    response.Error(c, http.StatusConflict, "资源已存在")
default:
    logRequestError(c, operation, err)
    response.Error(c, http.StatusInternalServerError, "服务暂时不可用，请稍后重试")
}
```

大部分 handler 共用这一个函数。好处是口径统一：改文案只改一处，加错误类型只加一行。注册与登录例外，它们在 `user.go` 里自己写 switch，因为 409 用户名冲突、401 凭据错误这两种语义只有这两个接口有。

`logRequestError` 只在 default 分支调用。4xx 是可预期的客户端问题，记日志只会吵。5xx 才需要排查。

### 12.3 为什么把 403 合并成 404

删除文章时，`WHERE id = ? AND user_id = ?` 影响 0 行有两种原因：文章不存在，文章是别人的。两者都返回 404。

如果分开返回 403，攻击者可以逐个 id 试，通过 403 与 404 的差异枚举出「哪些 id 存在」。这叫资源枚举。

代价是正常用户看不到「这不是你的文章」的提示。这个体验损失远小于信息泄露。

### 12.4 日志只记一次

三层都有出错可能，但只有 handler 记日志。

| 层 | 记不记 | 理由 |
| --- | --- | --- |
| service | 不记 | 只返回带上下文的错误，让调用方决定 |
| handler default 分支 | 记 | 这是唯一知道「哪个请求、哪个操作」的地方 |
| GORM Logger | 只记 Warn 及以上 | 避免每条 SQL 都打 |

`logRequestError` 带上 `method`、`route`、`operation`。

```go
log.Printf("%s failed: method=%s route=%s error=%v", operation, c.Request.Method, c.FullPath(), err)
```

`c.FullPath()` 返回路由模板（`/api/articles/:id`），不是具体路径。这样日志可以按路由聚合，不会因为 id 不同被拆成一万条。

### 12.5 错误处理面试问答

| 问题 | 回答要点 |
| --- | --- |
| 为什么用哨兵错误不用错误码 | `errors.Is` 类型安全，编译期就能查。错误码要维护一张表，容易漂移 |
| `%w` 与 `%v` 的区别 | `%w` 保留错误链，支持 `errors.Is`、`errors.As`。`%v` 只拼字符串 |
| 为什么不把数据库错误直接返回给客户端 | 会泄露表结构、字段名、SQL 片段。客户端只需要知道「失败了」 |
| 500 为什么给统一文案 | 具体原因留在日志里。给客户端看也帮不上忙，还会暴露实现 |
| 4xx 要不要记日志 | 一般不记，属于预期内的客户端错误。频繁出现时可以在网关层统计 |
| 为什么 404 合并 403 | 防资源枚举。攻击者无法通过状态码判断资源是否存在 |
| 中间件出错怎么返回 | 直接 `response.Error` 加 `c.Abort()`，不进入 handler |
| 错误包装会不会丢原始类型 | 用 `%w` 不会。`errors.Is` 会逐层解开直到匹配 |
| 怎么区分「用户输入错」与「系统故障」 | 前者映射 400，后者 500。service 层用不同哨兵区分 |
| panic 怎么处理 | 当前没有 recovery 中间件。gin.Default() 自带 `Recovery()`，会返回 500 并打日志 |

## 13. 设计决策总表

面试时最值钱的一张表。每条都是「选了什么、放弃什么、什么时候该换」。

| # | 决策 | 选择 | 放弃 | 何时该换 |
| --- | --- | --- | --- | --- |
| 1 | 主键类型 | `bigint unsigned` 自增 | UUID 的分布式友好 | 分库分表、需要客户端生成 id |
| 2 | 外键 | 保留物理外键 + RESTRICT | 写入性能、分库灵活性 | 单表写入几千 TPS、要分库 |
| 3 | 点赞去重 | 联合唯一索引 | 应用层判重 | 不换，这是正确做法 |
| 4 | 点赞计数 | MySQL `COUNT(*)` | Redis 计数的低延迟 | 单篇点赞十万级且详情 QPS 上万 |
| 5 | 详情缓存 | Cache Aside 删缓存 | 双写更新缓存的低延迟 | 不换，删缓存更安全 |
| 6 | 缓存失效兜底 | TTL 加抖动 | 强一致 | 需要秒级一致时上 binlog 订阅 |
| 7 | 缓存穿透 | 空值哨兵 60 秒 | 布隆过滤器的低内存 | 恶意随机 id 攻击时 |
| 8 | 缓存击穿 | singleflight 进程内合并 | 分布式锁的跨实例合并 | 多实例下回源压力仍高时 |
| 9 | 热榜存储 | Redis ZSET 投影 | MySQL 实时聚合的强一致 | 不换，读多写少场景 ZSET 更合适 |
| 10 | 热榜重建 | ready 标记 + 懒加载 | 定时任务全量重建 | 需要预热、不能接受首个请求变慢 |
| 11 | 重建换榜 | 临时 key 加 `RENAME` | 直接 `DEL` 再 `ZADD` 的简单 | 不换，直接写会让并发读看到残缺榜 |
| 12 | 重建范围 | `ORDER BY ... LIMIT 500` | 全量聚合的完整性 | 榜单外文章也要精确排序时，加 `like_count` 列走索引 |
| 13 | 投影有效期 | `ready` 带 1 小时 TTL | 永不过期的稳定 | 榜单需要更实时时降到 10 分钟 |
| 14 | 重建失败 | 30 秒冷却加降级 | 立即重试的自愈速度 | 聚合能在预算内完成时，冷却不会触发 |
| 15 | 热榜评分 | 纯点赞数 | 时间衰减的公平性 | 老文章长期占榜、新内容上不来时 |
| 16 | 消息可靠性 | 同事务 outbox | 直接发消息的低延迟 | 不换，这是可靠投递的基线 |
| 17 | 消息通道 | Redis Stream | Kafka 的高吞吐与长期保留 | 百万级消息、多团队订阅 |
| 18 | 投递语义 | 至少一次 + 幂等消费 | 严格恰好一次 | 不换，严格恰好一次成本过高 |
| 19 | 幂等落点 | 数据库唯一索引 | 内存去重的低延迟 | 不换，内存去重重启即失效 |
| 20 | 事件内容 | 只带 ID 的瘦事件 | 富事件的少一次查询 | 消费端查询成为瓶颈时 |
| 21 | 限流算法 | 令牌桶 | 固定窗口的简单 | 不需要允许突发时可用固定窗口 |
| 22 | 限流存储 | Redis + Lua | 本地内存的无网络开销 | 单机部署、或需要极低延迟 |
| 23 | 限流故障策略 | fail-open | fail-closed 的安全性 | 明确处于被攻击状态时 |
| 20 | 认证 | 无状态 JWT | Session 的主动吊销 | 需要封号即时生效 |
| 21 | 密码哈希 | bcrypt cost 10 | argon2id 的更强抗 GPU | 安全要求提高时 |
| 22 | 分层 | handler / service 两层 | repository 接口抽象 | 需要 mock 数据库做单测时 |
| 23 | 依赖注入 | 显式 new 传参 | wire 的自动生成 | 组件超过二十个 |
| 24 | 迁移 | AutoMigrate | 版本化迁移 | 上生产前必须换 |
| 25 | 分页 | `LIMIT OFFSET` | 游标分页的稳定性 | 深翻页、数据量大 |
| 26 | 配置 | viper + 环境变量覆盖 | 纯环境变量 | 配置项多到需要分组管理时 |
| 27 | Swagger | 注解生成 + CI diff | 手写文档 | 不换 |
| 28 | 排序 | 常量 SQL 片段 | 用户可选排序 | 需要多排序时用白名单 map |

## 14. 面试速查

### 14.1 「这个功能怎么设计的」

按「事实来源 → 读写路径 → 一致性 → 边界」四段答。

以点赞为例。

1. 事实来源：`article_likes` 表，`(article_id, user_id)` 唯一索引。
2. 读写路径：写走事务，读走 `COUNT(*)` 走覆盖索引。
3. 一致性：点赞数与详情缓存靠「删缓存」保证最终一致，热榜靠绝对分数 `ZADD`。
4. 边界：点赞十万级之后要改成 Redis 累加加对账。

同样的四段可以套在缓存、热榜、限流、消息上。

### 14.2 「为什么不用 X」

| 被问 | 答题骨架 |
| --- | --- |
| 为什么不用 Kafka | 当前量级 Stream 够用，复用已有 Redis，零新增运维。换的信号是百万级消息量 |
| 为什么不用 Redis 计数 | 冷启动会错，Redis 清空后计数归零。MySQL 覆盖索引查询成本可接受 |
| 为什么不用 Session | 无状态便于水平扩展。代价是无法主动吊销，需要时上黑名单 |
| 为什么不用雪花 ID | 单库自增够用，且有序插入对 B+ 树友好 |
| 为什么不用 ORM 自动迁移上生产 | 没有版本记录、没有回滚、并发 DDL 有风险 |
| 为什么不缓存评论 | 单篇量小，索引查询够快，缓存失效粒度难处理 |
| 为什么不用布隆过滤器 | 空值哨兵已经能挡住重复查询，布隆过滤器有误判且要维护 |
| 为什么不用分布式锁 | 当前单实例，singleflight 够用。多实例再加锁 |
| 为什么不用 gRPC | 只有 HTTP 客户端，没有内部服务间调用 |
| 为什么不拆微服务 | 单体足够，拆了要处理服务发现、链路追踪、分布式事务 |

### 14.3 「这有什么问题」

主动说缺口比被问出来好。五个现成的。

1. `article_likes` 按 `user_id` 查全表扫，做「我点赞过的」要加索引。
2. `articles` 分页有 filesort，深翻页会慢。
3. `notifications` 与 `outbox_events` 表还没建，服务重启后才会 AutoMigrate。
4. 重榜评分没有时间衰减，老文章长期占榜。
5. Stream 没有 `MAXLEN`，长期运行内存会涨。

每条都要配一句「怎么修」。

### 14.4 「数据量大了怎么办」

按数据形态分。

| 数据 | 增长特征 | 应对 |
| --- | --- | --- |
| `article_likes` | 线性增长，单篇可能百万 | 按 `article_id` 分表，或计数改 Redis 加对账 |
| `articles` | 线性增长 | 分库分表、冷热分离、正文拆表 |
| `comments` | 线性增长，单篇可能十万 | 按文章分表，或冷数据归档 |
| `notifications` | 增长最快 | 定期归档已读、按用户分片 |
| `outbox_events` | 增长快但可清理 | `published` 状态的定期删除或归档 |
| Stream | 只增不减 | `XADD MAXLEN ~ N` 或定时 `XTRIM` |

### 14.5 现场画图题

被要求画架构时，按这个顺序画，每画一层说一句职责。

```text
客户端
  ↓ HTTP
gin.Engine（路由 + 中间件：limitBody / RateLimit / JWTAuth）
  ↓
handler（绑定、校验、DTO）
  ↓
service（业务、事务、缓存策略）
  ↓                    ↘
GORM → MySQL          go-redis → Redis
  │                    │
  │                ┌───┴────┬─────────┬──────────┐
  │             详情缓存  点赞Set  热榜ZSET   Stream
  │                                        │
  └── outbox_events ← 同事务写入            ↓
                        relay ────────→ 消费组 → notifications
```

画的时候强调两个闭合：写路径的「业务行 + 事件行同事务」，读路径的「Redis 未命中回源 MySQL 再回填」。

样本量极小，`EXPLAIN` 只能证明优化器选哪条路径，不能证明耗时。真实压测要自己造数据。

热榜那四条修复里，只有「临时 key 不存在」「`ready` 的 TTL 是 3600」「cooldown 默认不存在」这三条能用 `redis-cli` 直接看到。另外两条需要特殊条件：「聚合带 `LIMIT`」要开 general log 才能取证，「冷却期不再重试」要把超时临时调到纳秒级才能触发。这两条当前是代码结论，不是压测结论。
