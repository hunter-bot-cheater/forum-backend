## 0. 为什么这一章比再加一个功能值钱

### 0.1 功能可以被复制，数字不能

到目前为止，项目已经有缓存、限流、热榜、Outbox、WebSocket 等设计。这些能力任何一份教程都能抄到。面试官看简历时真正会停一下的地方，是「你验证过什么」。

| 写法 | 面试官的反应 |
| --- | --- |
| 使用 Redis 实现文章详情缓存，解决缓存击穿与穿透 | 「怎么解决的」「效果如何」两个问题之后就没了 |
| 详情读用 singleflight 合并回源，同 key 200 并发下回源 1 次，P99 3.2ms | 会问「怎么测的」，你打开结果表，他换下一个话题 |

差别不在技术含量，在于有没有数字，以及数字背后有没有一套能复现的方法。

### 0.2 「压测」和「容量结论」是两件事

很多人把这两件事混着说，于是两个都不成立。

| | 压测 | 容量结论 |
| --- | --- | --- |
| 产出 | 一条曲线：并发从 10 涨到 500，QPS 与延迟怎么变 | 一个上限：这套配置在哪一点先垮，垮在哪一层 |
| 需要的工具 | 压测客户端 | 压测客户端 + 服务端指标 + 一点算术 |
| 回答的问题 | 「现在多快」 | 「还能撑多少」「再加机器有没有用」 |
| 面试价值 | 中 | 高 |

这一章先做压测，再用压测数据做容量结论。

### 0.3 一个反直觉的起点

压测用固定并发打，那么：

```text
QPS = 并发数 / 平均延迟
```

这条式子来自 Little's Law，`L = λW`，在稳定系统里恒成立。它带来三个直接推论，后面每一节都会用到。

| 推论 | 含义 |
| --- | --- |
| 加并发不等于涨 QPS | 延迟同比例上涨时，QPS 一动不动。你只是在让请求排更长的队 |
| QPS 上不去，先看延迟 | 延迟涨了就说明系统里有一段在排队，不是客户端不够努力 |
| 延迟超过某个点，QPS 会掉 | 排队占满缓冲区之后，重试与超时开始吃掉有效吞吐，曲线会向下弯 |

所以压测报告里必须有延迟分位数。只有 QPS 一个数，什么也说明不了。

## 1. 先看清被测对象

压测之前先数清一次请求要碰几次外部依赖。这一步决定了后面看到瓶颈时能不能对上号。

### 1.1 五条路径的依赖次数

| 路径 | Redis 调用 | MySQL 查询 | 关键机制 |
| --- | --- | --- | --- |
| `GET /api/articles/:id`（缓存命中） | 限流脚本 1 次 + `GET` 1 次 | 0 | Cache Aside |
| `GET /api/articles/:id`（未命中） | 同上，另加 `SET` | `Preload("User")` 1 次 + `COUNT` 点赞 1 次 | singleflight 合并 |
| `GET /api/articles/hot` | `EXISTS` + `ZREVRANGE` + 限流 | `WHERE id IN (...)` 1 次 | ZSET 投影 |
| `PUT /api/articles/:id/like` | 限流 + `ZADD` / `ZREM` + `DEL` 缓存 | 事务内 `INSERT` + `COUNT` | 唯一索引幂等 |
| `GET /api/articles`（列表） | 限流 | `COUNT` + `LIMIT` 分页 | 无缓存 |

两个结论在压测前就该知道。

1. 每个 `/api` 请求都先过一次限流脚本。这是所有路径的共同前置成本，也是第 2.2 节要处理的东西。
2. 只有详情读有缓存。列表、热榜、点赞写都会打到 MySQL，它们的容量上限比详情读低一个数量级。

### 1.2 连接池现状

这两处是关键，压测结果会直接被它们限住。

| 资源 | 当前位置 | 值 | 后果 |
| --- | --- | --- | --- |
| Redis | `internal/config/redis.go` | `PoolSize: 10`，`MinIdleConns: 2` | 并发超过 10 的 Redis 操作在客户端排队 |
| MySQL | `internal/config/db.go` | 未设置，用 `database/sql` 默认 | `MaxOpenConns=0` 表示无上限，并发多大就开多少连接 |

MySQL 这一条要特别记住。Go 侧不设上限，等于把并发压力原样透传给 MySQL。MySQL 默认 `max_connections=151`，撑爆之后客户端不会变慢，会直接收到 `Error 1040: Too many connections`。压测时如果看到一批 500 且日志里是这个错误，不要怀疑代码，怀疑连接池。

```sql
-- 确认 MySQL 当前的连接上限
SHOW VARIABLES LIKE 'max_connections';
-- 压测过程中另开一个会话看实际连接数
SHOW STATUS LIKE 'Threads_connected';
```

### 1.3 限流参数

```go
// 源码摘录：internal/router/router.go
rateCfg := middleware.RateLimitConfig{
    Capacity:  10,
    Rate:      2,
    KeyPrefix: "forum:dev:rate:",
}
```

这两个数字决定了第 2.2 节的数学题。

## 2. 压测前必须处理的六个干扰项

这一节是整章最重要的部分。跳过它，后面所有数字都是假的。

### 2.1 干扰项一：每个请求都在打一行访问日志

```go
// 源码摘录：internal/router/router.go
r := gin.Default()
```

`gin.Default()` 等于 `gin.New()` 加 Logger 加 Recovery。Logger 会对每个请求往 stdout 写一行：

```text
[GIN] 2026/11/12 - 21:40:12 | 200 |     1.203ms |       127.0.0.1 | GET      "/api/articles/1"
```

这行日志在压测里是实打实的成本。写到终端时，Windows 控制台的输出是同步阻塞的，单行可能花上毫秒级；写到文件时快一些，但仍然占 CPU 与系统调用。

**怎么判断它是不是瓶颈**：压测时观察服务端进程 CPU 不高、QPS 却卡在一个整数附近不动，P99 抖动很大而 P50 很稳。这就是典型的「业务逻辑很快，日志写不出去」。

**处理办法**，从轻到重三种。

| 办法 | 做法 | 代价 |
| --- | --- | --- |
| 重定向到文件 | `go run ./cmd/server > server.log 2>&1` | 仍然有 IO，但比控制台快得多 |
| 关掉调试信息 | 启动前设 `GIN_MODE=release` | 只减少启动期输出，访问日志还在 |
| 临时去掉 Logger | `r := gin.New()` 后加 `r.Use(gin.Recovery())` | 压测期间看不到访问日志，压完改回来 |

推荐第二种加第一种组合。第三种改的是源码，容易忘记改回来，留下「生产环境没有访问日志」的隐患。

### 2.2 干扰项二：限流器会把结论锁死在每秒 2 次

这一条不处理，压测测的是限流器，不是你的系统。

先算一笔账。`Capacity=10`、`Rate=2`，令牌桶初值是满的 10 个，之后每秒补 2 个。用 50 并发打 10 秒，最多能通过的请求数是：

```text
10（初始满桶）+ 2 × 10（每秒补 2 个）= 30 个
```

剩下的全部返回 429。压测输出会长这样：

```text
requests   48213
qps        4819.7
status     429=48193 200=20
```

看起来 QPS 很高，实际上全是拒绝。这是最容易骗到自己的一个数字。

**为什么不能靠伪造请求头绕过去**：

```go
// 源码摘录：internal/router/router.go
// 不信任任何代理网段的 X-Forwarded-For。
// c.ClientIP() 退回 RemoteAddr，客户端伪造请求头无法绕过限流。
if err := r.SetTrustedProxies(nil); err != nil {
    return nil, fmt.Errorf("router: set trusted proxies: %w", err)
}
```

`SetTrustedProxies(nil)` 之后 `c.ClientIP()` 只认 `RemoteAddr`。本机压测所有请求的 RemoteAddr 都是 `127.0.0.1`，共享同一个令牌桶。加 `X-Forwarded-For` 没有用。

**处理办法**：压测前临时放大参数，压完改回原值。改之前先把原值记在结果表里，见第 7 节。

```go
// 压测专用，压完必须改回 Capacity: 10, Rate: 2
rateCfg := middleware.RateLimitConfig{
    Capacity:  1000000,
    Rate:      1000000,
    KeyPrefix: "forum:dev:rate:",
}
```

这不算绕过限流作弊。容量测试测的是业务路径的承载能力，限流是保护层，两者要分开测。限流本身怎么测见 04 章 4.9 节：把 `Capacity` 调小、`Rate` 调低，连打几次观察第几次开始返回 429，以及 `Retry-After` 头是否合理。

顺带一个真实的债：这套参数从配置文件读不了，只能改代码。要支持按环境切换，得在 `config` 里加两个字段并在 `router.New` 里读。这是已知的小债，不在这章处理。

### 2.3 干扰项三：MySQL 连接池没有上限

`internal/config/db.go` 里只做了 `gorm.Open` 与 `AutoMigrate`，没有调用 `SetMaxOpenConns`。`database/sql` 的默认值是 `MaxOpenConns=0`，含义是不限制，来多少并发就开多少连接。

压测详情读且缓存全未命中时，每个请求要两次查询。50 并发听起来不多，但如果延迟被 MySQL 拖到 200ms，50 个并发就会稳定占住 50 个连接；压到 300 并发就是 300 个连接，超过 MySQL 默认的 151。

**处理办法**：压测前先给连接池设上限，这是正确的工程做法，一石二鸟。

```go
// 增量修改：internal/config/db.go，在 AutoMigrate 之前
sqlDB, err := db.DB()
if err != nil {
    return nil, fmt.Errorf("get sql.DB: %w", err)
}
// 上限要小于 MySQL 的 max_connections。
// 剩下的留给 mysql-cli、备份、其他服务，不要吃满。
sqlDB.SetMaxOpenConns(20)
sqlDB.SetMaxIdleConns(10)
// 小于 MySQL 的 wait_timeout（默认 8 小时），避免拿到被服务端单方面关掉的连接。
sqlDB.SetConnMaxLifetime(time.Hour)
```

设了上限之后，并发超过 20 的请求会在 Go 的 `sql.DB` 里排队等连接，而不是把 MySQL 打死。排队会让延迟上升，但系统还在工作。这个取舍要能在面试里说出来：**限流的第一层在应用侧连接池，第二层才是 MySQL 自己的 max_connections。**

### 2.4 干扰项四：压测客户端自己会成为瓶颈

`http.Transport` 的 `MaxIdleConnsPerHost` 默认是 2。用它打 50 并发，等于 50 个协程抢 2 个空闲连接，剩下的每次都要重新三次握手。

结果是：你测到的延迟里大部分是客户端建连成本，服务端其实很闲。

`cmd/loadtest` 里已经处理了这件事：

```go
// 源码摘录：cmd/loadtest/main.go
// 默认的 MaxIdleConnsPerHost 是 2。
// 并发 50 而空闲连接只有 2 个时，压测客户端自己在反复建 TCP 连接，
// 测出来的延迟里大半是客户端握手成本，不是服务端处理时间。
transport := &http.Transport{
    MaxIdleConns:        *concurrency * 2,
    MaxIdleConnsPerHost: *concurrency,
    MaxConnsPerHost:     *concurrency,
    IdleConnTimeout:     30 * time.Second,
    // 压测不关心响应体内容，也不该让客户端花 CPU 解压。
    DisableCompression: true,
}
```

`DisableCompression: true` 也重要。如果服务端开了 gzip，客户端每个响应都要解压，CPU 会被自己吃掉，而这个开销跟被测系统毫无关系。

### 2.5 干扰项五：客户端与服务端在同一台机器上抢 CPU

这是本机压测的物理限制，无法消除，只能承认并记录。

50 并发打本机 8080，Go 运行时会在客户端和服务端各跑一批协程，两个进程抢同一批核心。你测到的 QPS 是「同机合计能力」，不是「服务端能力」。

| 做法 | 可信度 | 说明 |
| --- | --- | --- |
| 同一终端压测 | 低 | 客户端输出还会跟服务端日志抢同一个终端 |
| 两个终端，服务端日志重定向 | 中 | 本章推荐，够用来做前后对比 |
| 两台机器 | 高 | 有条件就这么做，需要把 `-url` 指向另一台的 IP |

即使只能同机压测，数字仍然有用，前提是**前后对比时环境一致**。比如验证 singleflight 是否生效，改前改后都在同一台机器、同样的并发、同样的时长下跑，比值是可信的，绝对值不必当真。

### 2.6 干扰项六：没有数据，压出来的是空路径

空库上压 `GET /api/articles/1`，走的是「查不到」分支：`queryDetail` 返回 `ErrNotFound`，写一个 60 秒的空标记，后续请求连库都不查。这个数字很好看，但它测的是空标记命中率，不是详情读能力。

压测前先造数据。

```sql
-- 造 1000 篇文章，作者固定为 1 号用户
-- 用递归 CTE 生成序列，MySQL 8.0 支持
INSERT INTO articles (user_id, title, content, like_count, created_at, updated_at)
WITH RECURSIVE seq(n) AS (
    SELECT 1 UNION ALL SELECT n + 1 FROM seq WHERE n < 1000
)
SELECT 1, CONCAT('压测文章 ', n), CONCAT('正文 ', n), 0, NOW(), NOW() FROM seq;

-- 每篇文章随机造 0 到 30 个点赞，用户 id 在 1 到 50 之间循环
-- 用 INSERT IGNORE 跳过唯一索引冲突
INSERT IGNORE INTO article_likes (article_id, user_id, created_at)
SELECT a.id, u.n, NOW()
FROM articles a
JOIN (WITH RECURSIVE s(n) AS (SELECT 1 UNION ALL SELECT n + 1 FROM s WHERE n < 30)
      SELECT n FROM s) u
WHERE u.n <= (a.id % 31);
```

确认数据进得去：

```sql
SELECT COUNT(*) FROM articles;
SELECT COUNT(*) FROM article_likes;
-- 热榜的真实分数，后面和对账结果比对用
SELECT article_id, COUNT(*) AS score FROM article_likes GROUP BY article_id ORDER BY score DESC LIMIT 10;
```

### 3.2 关键片段

完整文件在 `cmd/loadtest/main.go`。这里只摘三段需要注意的。

**预热**。压测开始前先串行打 20 个请求。

```go

// warmup 先串行打几个请求，把 TCP 连接与缓存都准备好。
// 不预热的话，前几十个样本里混着建连成本与冷缓存回源，P99 会被它们拉偏。
func warmup(client *http.Client, cfg requestConfig, ids []uint, useID bool) {
```

**主循环**。每请求重新生成 URL 与 body，请求结束读空 body 关闭。

```go
// 源码摘录：cmd/loadtest/main.go
start := time.Now()
resp, err := client.Do(req)
elapsed := time.Since(start)

if err != nil {
    if ctx.Err() != nil {
        // 压测结束导致的取消，不算错误样本。
        return
    }
    s.netErr++
    // 连接被拒时不留退避会纯空转：1 秒能打上万次失败，
    // 把本机 CPU 吃满，反而看不清到底是配置错还是服务没起。
    // 让出 1ms，失败场景下每秒最多几百次，够看清提示。
    time.Sleep(time.Millisecond)
    continue
}
io.Copy(io.Discard, resp.Body)
resp.Body.Close()
```

`io.Copy(io.Discard, resp.Body)` 不能省。不读空 body，连接无法复用，keep-alive 失效，每次都是新连接。

**统计**。每个协程自己 append，最后合并排序取分位，全程不加锁。

```go
// 源码摘录：cmd/loadtest/main.go
sort.Slice(all, func(i, j int) bool { return all[i] < all[j] })
...
fmt.Printf("latency    p50=%s p90=%s p99=%s max=%s\n",
    percentile(all, 0.50), percentile(all, 0.90), percentile(all, 0.99), percentile(all, 1.0))
```

## 4. 五条链路怎么压

每一节给：目的、命令、该看什么。

### 4.1 路径一：热缓存详情读

**目的**：拿到稳态读能力。这是最能代表「缓存生效后」的数字。

```bash
# 第一个终端：服务端，日志走文件，不要占终端
go run ./cmd/server > server.log 2>&1

# 第二个终端：先预热一次，让详情进缓存
curl -s http://127.0.0.1:8080/api/articles/1

# 压测
./bin/loadtest.exe -url "http://127.0.0.1:8080/api/articles/1" \
  -concurrency 50 -duration 15s
```

**该看什么**：

| 指标 | 期望 | 偏离说明什么 |
| --- | --- | --- |
| `status` | 只有 200 | 出现 429 是限流没关；出现 500 看日志 |
| P50 | 毫秒级，与 Redis RTT 同量级 | 明显偏大说明请求没命中缓存，在回源 |
| P99 与 P50 的比值 | 小于 5 | 比值大说明有长尾，通常是 GC、锁、或连接排队 |
| `failed` | 0 | 不为 0 先查客户端侧连接池 |

### 4.2 路径二：热点 key 并发（验证 singleflight）

**目的**：不是测容量，是验证「同 key 并发只有一个请求回源」这件事真的成立。

```bash
# 先把缓存删掉，强制所有并发都看到 miss
redis-cli -a 123456 DEL article:detail:v1:1

# 200 并发同时打同一个 id，只打 2 秒
./bin/loadtest.exe -url "http://127.0.0.1:8080/api/articles/1" \
  -concurrency 200 -duration 2s
```

这里遇到一个真实的缺口：**项目没有暴露 `CacheStats()` 的 HTTP 接口**。

```go
// 源码摘录：internal/service/article.go
// CacheStats 返回当前进程的缓存计数快照，供本地验收与将来的监控接入使用。
// 进程重启后计数归零，它不是持久化指标。
func (s *ArticleService) CacheStats() CacheStats {
    return s.metrics.snapshot()
}
```

方法在，但没有 handler 调它。`internal/handler` 下没有 debug 相关文件，路由表里也没有对应路径。所以压测期间在外部读不到 `Loads` 和 `Shares`。

三种办法，按成本排序。

| 办法 | 做法 | 适合 |
| --- | --- | --- |
| 看 MySQL 的查询计数 | 压测前后各查一次 `SHOW GLOBAL STATUS LIKE 'Com_select'`，差值就是回源次数 | 不改代码，最省事 |
| 临时加一个 debug 接口 | 见下方代码，压完删掉或加开关 | 需要精确区分 Loads 与 Shares |
| 写一个集成测试 | `httptest` 起路由，200 并发打同一个 id，断言 `Loads == 1` | 想进 CI，长期有效 |

第一种办法的具体用法：

```sql
-- 压测前
SHOW GLOBAL STATUS LIKE 'Com_select';
-- 压测后
SHOW GLOBAL STATUS LIKE 'Com_select';
-- 两次相减，再减去其他业务带来的查询，就是这个窗口里的回源次数
```

第二种办法的增量代码，只用于本地验证：

```go
// 增量新增：internal/handler/debug.go
// 只用于本地压测观察缓存命中情况，不要把这条路由带到线上。
func RegisterDebug(r gin.IRouter, articleSvc *service.ArticleService) {
    r.GET("/debug/cache-stats", func(c *gin.Context) {
        response.OK(c, articleSvc.CacheStats())
    })
}
```

**判据**：200 并发打同一个已删除缓存的 key，`Loads` 应该在个位数（1 到 3，取决于并发窗口的边界），`Shares` 接近 199。如果 `Loads` 接近 200，说明 singleflight 没生效，先确认 `ArticleService` 是单例（`main` 里只 `New` 一次，经 `router.New` 传下去）。

### 4.3 路径三：冷读与不存在的 id（验证防穿透）

**目的**：确认空标记真的挡住了对不存在 id 的重复查询。

```bash
# 打一批不存在的 id，每个只打一次
./bin/loadtest.exe -url "http://127.0.0.1:8080/api/articles/{id}" \
  -ids 900001-901000 -concurrency 20 -duration 5s
```

第一批会返回 404，同时写入 60 秒的空标记。再跑一次同样的命令，第二次的延迟应明显低于第一次。

```bash
# 第二次，空标记应该已经生效
./bin/loadtest.exe -url "http://127.0.0.1:8080/api/articles/{id}" \
  -ids 900001-901000 -concurrency 20 -duration 5s
```

**该看什么**：两次的 P50 对比。第一次含 MySQL 查询，第二次只有 Redis `GET` 加反序列化判定。差值就是这个空标记省下的时间。

这一组数字很适合放进面试答案，因为它直接对应一个具体问题：「缓存穿透你怎么解决的，有效果吗」。

### 4.4 路径四：热榜读

**目的**：热榜是 ZSET 投影，命中时不碰 MySQL，但会额外查一次 `articles` 表拿标题。

```bash
# 先触发一次投影重建
curl -s "http://127.0.0.1:8080/api/articles/hot?limit=20"

# 压测
./bin/loadtest.exe -url "http://127.0.0.1:8080/api/articles/hot?limit=20" \
  -concurrency 50 -duration 15s
```

**该看什么**：

| 现象 | 含义 |
| --- | --- |
| QPS 与详情读接近 | 正常，两者都是 Redis 为主 |
| QPS 明显更低 | 每次都要 `WHERE id IN (...)` 查 20 篇文章，MySQL 参与进来了 |
| 压测中 QPS 突然掉一截 | 可能是 ready TTL 到期触发了一次 rebuild，`GROUP BY` 上线了 |

第三种现象值得单独提。`hotReadyTTL` 是 1 小时，压测 15 秒基本碰不到，但如果你把 TTL 调短做实验，会看到周期性的性能凹坑。那个凹坑就是重建成本，可以直接写进容量结论：**每小时的固定成本是 500 条 ZADD 加一次 `GROUP BY`，它不随 QPS 变化。**

### 4.5 路径五：点赞写

这条最难压，因为需要登录态，而且**同一个用户对同一篇文章重复点赞不会真的写入**。

```go
// 源码摘录：internal/service/like.go
if add {
    err := tx.Create(&model.ArticleLike{ArticleID: articleID, UserID: userID}).Error
    if err == nil {
        changed = true
    } else if errors.Is(err, gorm.ErrDuplicatedKey) {
        return nil //说明唯一索引拦住了这一次操作 重复点赞了
    }
```

所以用同一个 token 反复打 `PUT /api/articles/1/like`，第一次写入，后面全部命唯一索引返回「未变化」。你测到的是「重复点赞的幂等路径」，不是真实写入。

**要压真实写入，得准备多用户与多 token**。步骤：

1. 造 50 个用户，密码统一。
2. 用 `POST /api/login` 逐个换 token，存到文件。
3. 压测时每个请求用一个不同的 token。

```bash
# 第一步：注册 50 个用户（幂等，重复跑会 409，无所谓）
for i in $(seq 1 50); do
  curl -s -X POST http://127.0.0.1:8080/api/register \
    -H "Content-Type: application/json" \
    -d "{\"username\":\"loaduser$i\",\"password\":\"Passw0rd!23\"}" > /dev/null
done

# 第二步：换 token，一行一个存进文件
: > tokens.txt
for i in $(seq 1 50); do
  curl -s -X POST http://127.0.0.1:8080/api/login \
    -H "Content-Type: application/json" \
    -d "{\"username\":\"loaduser$i\",\"password\":\"Passw0rd!23\"}" \
    | python -c "import sys,json;print(json.load(sys.stdin)['data']['token'])" >> tokens.txt
done
```

`cmd/loadtest` 现在只支持单个 `-token`，压真实写入需要它每次从列表里取一个。这是工具的一个已知限制，两条路：

| 做法 | 成本 | 说明 |
| --- | --- | --- |
| 分 50 次跑，每次换 token | 零改动 | 每次压 1 个用户对 1 篇文章的点赞，50 次就是 50 条真实写入 |
| 给工具加 `-token-file` | 十几行 | 每个请求随机取一个 token，能压出真实并发写入 |

本章选第一种，因为压点赞写的目的是验证三件事，QPS 只是附带产物：

1. 事务里 `INSERT` 加 `INSERT outbox_events` 是否真的原子。
2. 唯一索引在并发下会不会冲突（会，代码已处理 `ErrDuplicatedKey`）。
3. 事务提交后 `ZADD` 与 `DEL` 缓存是否需要额外延迟。

这三件事用 50 次串行压测就能看出来，不需要模拟高并发写。真要知道写入容量，直接看 MySQL 的单表写入能力，那个数字比 HTTP 层更接近上限。

## 5. 服务端指标怎么读

客户端只有 QPS 与延迟。判断瓶颈在哪一层，要看服务端。

### 5.1 进程侧：当前没有 /metrics

项目里没有 Prometheus 客户端，也没有 pprof 路由。这是已知缺口，第 9 节会把它列为「值得补但本章不做」。

压测期间能用的替代手段：

| 想看的 | 替代办法 |
| --- | --- |
| 缓存命中率 | `CacheStats()` 没有 HTTP 入口，用 `Com_select` 差值代替，或临时加 debug 路由（4.2 节） |
| goroutine 是否泄漏 | 压测前后看 `runtime.NumGoroutine()`，只能靠加代码；或压测结束后静置 1 分钟看连接数是否回落 |
| GC 压力 | 启动时加 `GODEBUG=gctrace=1`，输出里看 GC 频率 |
| CPU 热点 | 加 `net/http/pprof`，用 `go tool pprof` 抓 30 秒 |

`GODEBUG=gctrace=1` 是最省事的一个，不用改代码：

```bash
GODEBUG=gctrace=1 go run ./cmd/server > server.log 2>&1
# 日志里会出现 gc 1 @0.123s 0%: ... 这样的行，GC 太频繁说明分配太快
```

### 5.2 MySQL 侧

```sql
-- 连接数水位，压测中反复执行
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Threads_running';

-- 有没有慢查询
SHOW VARIABLES LIKE 'slow_query_log';
SHOW VARIABLES LIKE 'long_query_time';

-- 查询次数，用来算回源量
SHOW GLOBAL STATUS LIKE 'Com_select';

-- 行锁等待，写压测时才需要
SHOW STATUS LIKE 'Innodb_row_lock_waits';
```

判据很直接：

| 现象 | 结论 |
| --- | --- |
| `Threads_running` 长期接近 `max_connections` | 连接被打满，回到 2.3 节设上限 |
| `Threads_running` 不高但延迟很高 | 有慢查询或锁等待，看 `SHOW PROCESSLIST` |
| `Innodb_row_lock_waits` 持续增长 | 写冲突，点赞压测里通常来自唯一索引竞争 |

### 5.3 Redis 侧

```bash
redis-cli -a 123456 INFO clients
redis-cli -a 123456 INFO stats
redis-cli -a 123456 INFO commandstats
```

| 字段 | 含义 | 关注点 |
| --- | --- | --- |
| `connected_clients` | 当前连接数 | 应稳定在 10 附近（`PoolSize: 10`） |
| `rejected_connections` | 因 `maxclients` 被拒的连接 | 大于 0 说明连接不够 |
| `instantaneous_ops_per_sec` | 当前 QPS | 与本机压测的 QPS 对照，正常应约为请求数的 2 倍（限流加读缓存） |
| `evicted_keys` | 因内存淘汰的 key | 大于 0 说明内存不够，缓存命中率会莫名下降 |

`INFO commandstats` 里能看到 `evalsha` 与 `get` 的调用次数与平均耗时。这两个数直接对应第 1.1 节的依赖表，可以用来验证「一次请求是不是只碰了两次 Redis」。

### 5.4 Redis 连接池的排队

`PoolSize: 10` 这个数字在压测里会显形。判断方法：

```bash
# 压测中看，正常应该稳定在 10 左右，持续顶到 10 说明池子满了
redis-cli -a 123456 INFO clients | grep connected_clients
```

如果 `connected_clients` 一直等于 10，且客户端延迟随并发线性上涨，说明瓶颈在 Redis 连接池，不在 Redis 本身。这时候调 `PoolSize` 会有立竿见影的效果。

这个结论可以直接写进面试答案：「瓶颈定位到 Redis 连接池只有 10 个连接，调到 50 之后 P99 从 X 降到 Y」。它有验证过程，不是猜的。

## 6. 容量结论怎么算

有了压测数据，这一步是把「多快」变成「能撑多少、先垮在哪」。

### 6.1 Little's Law 的三种用法

```text
QPS = 并发数 / 平均延迟
```

| 用法 | 算式 | 场景 |
| --- | --- | --- |
| 已知并发与延迟，求 QPS | `QPS = C / L` | 校验压测工具的数字对不对 |
| 已知目标 QPS 与延迟，求需要的并发 | `C = QPS × L` | 估算要开多少连接 |
| 已知 QPS 与并发，求系统里的平均在途请求数 | `L_sys = QPS × 延迟` | 估算连接池与 goroutine 数量 |

第三个用法最实用。假设详情读实测 3000 QPS、平均延迟 3ms，那么在途请求数是 `3000 × 0.003 = 9` 个。这意味着 10 个 Redis 连接刚好够，不需要调大。如果实测延迟 30ms，在途请求变成 90 个，10 个连接立刻成为瓶颈。

### 6.2 Redis 连接池给的上限

```text
理论上限 = PoolSize / 单次操作耗时
```

`PoolSize=10`，每次详情读要两次 Redis 操作（限流脚本加读缓存）。若单次操作耗时 0.3ms：

```text
10 / 0.0003 ≈ 33000 次/秒
```

再除以每请求 2 次操作：约 16000 QPS。这是 Redis 池的理论天花板，实际会低不少，因为 Go 的调度、序列化、网络栈都要时间。

算这个数的意义不在于精确，在于知道量级：**Redis 池不是第一个瓶颈，除非单次 RTT 涨到毫秒以上**（跨机房部署就会）。这就解释了为什么本机压测时调 `PoolSize` 可能没效果，因为瓶颈在别处。

### 6.3 MySQL 连接数给的上限

```text
并发上限 = MaxOpenConns
QPS 上限 = MaxOpenConns / 单请求占用连接时间
```

设 `MaxOpenConns=20`，未命中路径每次占连接约 2ms（两次查询）：

```text
20 / 0.002 = 10000 次/秒
```

这个数只在缓存全部失效时才有意义。缓存命中时 MySQL 完全不参与，所以详情读的真实上限由 Redis 与 CPU 决定，不是这个数。

**这里有一个面试常问的陷阱**：缓存命中率 90% 时，QPS 上限不是简单加权。要分开算。

```text
总 QPS = Q_redis + Q_mysql
Q_redis 受 Redis 池限制
Q_mysql 受 MySQL 连接池限制
两者共享同一批并发协程，所以真实上限是「按比例分配并发后，两段都不超限」的那个点
```

一句话总结：**缓存的命中率决定了 MySQL 只承担多少比例的流量，不改变 MySQL 自己的容量。**

### 6.4 Relay 的理论吞吐

这条链路的容量不靠压测，靠读代码就能算。

```go
// 源码摘录：internal/worker/relay.go
const (
    relayInterval       = 200 * time.Millisecond  //轮询间隔 200ms
    relayBatchSize      = 100 //每次最多搬100条
    maxPublishAttempts  = 5 //最大重试次数
)
```

```text
理论上限 = 100 条 / 0.2 秒 = 500 条/秒
```

这个上限有两层含义。

1. 每秒新增的事件（点赞加评论）超过 500 条时，outbox 的 `pending` 会持续增长，积压不会自己消失。
2. 每条事件要一次 `XADD` 加一次 `UPDATE`。如果这两次往返加起来超过 2ms，单批 100 条要 200ms，轮询间隔就被吃满，实际吞吐会低于 500。

**这就是一个可以直接写进简历的容量结论**：消息链路的投递能力上限是每秒 500 条事件，由轮询间隔与批大小共同决定，超过之后 `pending` 开始积压，需要调小间隔、调大批量，或改为事件驱动（用 `LISTEN` 或数据库 trigger 通知，本项目没做）。

### 6.5 通知消费者的理论吞吐

```go
// 源码摘录：internal/worker/notification.go
const (
    notifyConsumer = "worker-1"
    readBlock      = 2 * time.Second
    readBatchSize  = 20
)
```

消费者是**单协程串行**处理：读一批 20 条，逐条处理，每条一次查文章加一次插入通知加一次 WS 推送。

```text
吞吐上限 = 1 / 单条处理时间
```

若单条处理 2ms，上限 500 条/秒；若单条 5ms，上限 200 条/秒。它与 Relay 的 500 条/秒是同一量级，意味着两者会同时到达极限，不会出现「投递快、消费慢」的长期积压。

`readBatchSize=20` 与 `readBlock=2s` 不影响吞吐上限，它们只影响延迟与空轮询频率。这一点容易看错：`20 条 / 2 秒` 不是 10 条/秒，因为阻塞读在有消息时会立即返回。

### 6.6 取最小值

系统的容量由最窄的那一段决定。把上面的数放在一起：

| 环节 | 理论上限 | 依据 |
| --- | --- | --- |
| Redis 连接池 | 约 16000 QPS（本机 RTT 0.3ms 假设） | `PoolSize=10`，每请求 2 次操作 |
| MySQL 连接池 | 约 10000 QPS（未命中路径） | `MaxOpenConns=20`（建议值），每请求 2ms |
| Relay 投递 | 500 条/秒 | 200ms 轮询，批 100 |
| 通知消费 | 200 到 500 条/秒 | 单协程串行，每条 2 到 5ms |
| Gin 加日志 | 未知，取决于日志去向 | 第 2.1 节 |

结论写成一句话：**读路径的瓶颈在 Redis 连接池与 CPU，写事件链路的瓶颈在 Relay 的 500 条每秒，两者相差一个数量级以上。所以这个项目在压测里先垮的一定是读，不是消息。**

这句话的价值在于它有可推演的依据，即使没实测也站得住。实测数据只是用来验证推演对不对。

## 7. 记录结果的模板

压测最容易犯的错是「只记一个 QPS」。三天后回来看，这个数字无法解释，也无法复现。

### 7.1 六个必须同时记录的环境量

| 项 | 怎么取 | 为什么必须记 |
| --- | --- | --- |
| CPU 核数 | `nproc` 或任务管理器 | 8 核与 16 核的 QPS 不可比 |
| 内存 | 同上 | 影响 GC 频率 |
| Go 版本 | `go version` | 不同版本的 GC 与调度有差异 |
| 限流参数 | 当时 `Capacity` 与 `Rate` 的值 | 忘了改回来会让数字完全失真 |
| MySQL 连接池 | 当时 `MaxOpenConns` 的值 | 未设置与设 20 是两个系统 |
| 数据量 | `articles` 与 `article_likes` 行数 | 空库与 10 万行的查询计划不同 |

### 7.2 结果表

把下面这张表填满，就是你的「性能档案」。**这一版是空模板，数字需要你自己跑。**

| 场景 | 并发 | 时长 | QPS | P50 | P99 | 错误率 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 详情读（命中） | 50 | 15s | | | | | |
| 详情读（命中） | 200 | 15s | | | | | |
| 详情读（200 并发同 key，缓存已删） | 200 | 2s | | | | | 验证 singleflight，看 `Loads` |
| 不存在 id（首次） | 20 | 5s | | | | | 404 也算成功样本 |
| 不存在 id（空标记生效后） | 20 | 5s | | | | | 与上一行对比 |
| 热榜读 | 50 | 15s | | | | | |
| 点赞写（单用户重复） | 20 | 10s | | | | | 只测幂等路径 |
| 列表读 | 50 | 15s | | | | | 无缓存，基线 |

### 7.3 三条记录纪律

1. **每次只改一个变量**。改并发就不要再改限流参数，否则数字没法归因。
2. **记录失败的那次**。压测失败（比如 429 占满、连接打满）比成功更有信息量，它直接告诉你上限在哪。删掉失败记录等于丢掉了容量结论。
3. **绝对值只在本机有效**。同机压测的数字不要写成「系统支持 X QPS」，写成「本机 8 核、客户端与服务端同机，50 并发下 X QPS」。这个限定词反而显得可信。

## 8. 瓶颈定位：按现象查

压测出问题时的排查顺序。按表从上往下查，不要跳。

| 现象 | 第一嫌疑 | 验证 | 结论怎么写 |
| --- | --- | --- | --- |
| QPS 卡在每秒个位数，`status` 全是 429 | 限流没关 | 看 `status` 分布 | 「压测未绕开限流，数据无效，重跑」 |
| QPS 上不去，服务端 CPU 很低 | 访问日志写终端 | 把 stdout 重定向到文件再跑 | 「日志 IO 是首位瓶颈」 |
| 延迟随并发线性上涨，QPS 不动 | 某一段在排队 | 看 Redis `connected_clients` 与 MySQL `Threads_running` | 「瓶颈在 X 连接池」 |
| 出现一批 500，日志是 `Error 1040` | MySQL 连接打满 | `SHOW STATUS LIKE 'Threads_connected'` | 「未设 `MaxOpenConns`，透传打爆 MySQL」 |
| QPS 正常但 P99 是 P50 的 20 倍 | 长尾，GC 或锁 | `GODEBUG=gctrace=1` 看 GC 频率 | 「GC 压力大，分配过多」 |
| 压测中途 QPS 掉一截又恢复 | 周期任务 | 对照 `hotReadyTTL` 与重建日志 | 「每小时一次热榜重建的成本」 |
| `failed` 很高，服务端日志干净 | 客户端侧问题 | 看 `netstat` 端口数、客户端 CPU | 「客户端连接池或端口耗尽，不是服务端」 |
| 内存持续上涨不回落 | goroutine 或连接泄漏 | 压测后静置，看连接数与内存 | 「有泄漏，先修再谈容量」 |

最后一条要特别重视。压测不只看峰值，还要看**停下来之后能不能回到基线**。回不去就是泄漏，这时候报的 QPS 再高也没意义。

## 9. 简历与面试

### 9.1 三句模板

数字用你自己跑出来的填，占位符不要原样留在简历上。

> 详情读路径用 Cache Aside 加 singleflight 与空值标记，实测同 key 200 并发下回源 1 次，P99 从 _ ms 降到 _ ms。

> 对读路径做容量摸底，定位到 Redis 连接池（`PoolSize=10`）为首位瓶颈，调到 _ 后 P99 由 _ ms 降至 _ ms；MySQL 侧补齐 `MaxOpenConns` 上限，避免并发透传打满连接。

> 消息链路按轮询间隔与批大小推算出投递上限每秒 500 条事件，据此判断读路径先于消息链路到达瓶颈。

### 9.2 追问与回答

| 追问 | 回答要点 |
| --- | --- |
| 你怎么保证数字不是客户端瓶颈 | 客户端 `MaxIdleConnsPerHost` 设成并发数、关 gzip、单独终端跑、失败样本剔除。这三条都做了才敢用这个数 |
| 压测时限流怎么办 | 说明是分开测的：容量测试临时放大限流参数并记录原值，限流本身另用 `Capacity=1` 单独验证 |
| 为什么 P99 比 P50 重要 | P50 好看不代表用户不难受。接口里只要有一个环节偶尔排队，P50 完全看不到，P99 会翻十倍 |
| 你项目能扛多少 QPS | 给限定条件下的数字：本机 X 核、同机压测、50 并发、缓存命中，Y QPS，瓶颈在 Z。不说「支持十万并发」 |
| 加机器能提升多少 | 读路径受 Redis 与 CPU 限制，加应用实例能线性提升到 Redis 成为瓶颈为止；消息链路因为 relay 与 consumer 都是单实例轮询，加实例要靠改消费组分配，当前代码里 consumer 名字写死为 `worker-1` |
| 怎么证明瓶颈在连接池不是数据库 | 两件事：把 `PoolSize` 从 10 调到 50 后 QPS 上升，把 `MaxOpenConns` 从 20 调到 5 后延迟上升。两个方向都动过才叫定位 |

最后一条追问很有杀伤力，它区分了「我猜是连接池」和「我验证过是连接池」。面试前把这两个方向都跑一遍。

### 9.3 不要写的话

| 不要写 | 原因 |
| --- | --- |
| 支持 10 万 QPS | 单机论坛的后端撑不到，一测就露 |
| 通过压测优化性能提升 300% | 没有基线，300% 无意义 |
| 使用 JMeter 完成全链路压测 | 你没用过就别写，问一个元件配置就穿帮 |
| 高并发架构设计 | 这个项目的并发量级配不上「高并发」四个字，写了反而减分 |

## 10. 常见坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 忘了把限流改回来 | 线上突然大量 429 | 改之前把原值写进结果表，压完立刻还原并再跑一次冒烟 |
| 压测前没预热 | P99 极高，前几百个样本耗时是后面的十倍 | `loadtest` 已内置预热，手工压时先 `curl` 几次 |
| 只压一个接口 | 详情读很好看，一压列表就崩 | 五条路径都压，列表读是无缓存基线 |
| 压测中改了数据 | 前后两次数字不可比 | 压测窗口内不要手工点赞、不要删文章 |
| 用 `redis-cli FLUSHALL` 清缓存 | 顺手把限流桶、热榜、outbox 消费组全清了，服务行为变形 | 只 `DEL` 具体的 key |
| 空库压测 | 全部走 404 或空标记，数字虚高 | 先按 2.6 节造数据 |
| 只看 `top` 里的 CPU | Go 程序的瓶颈经常在网络等待，CPU 不高 | 同时看延迟分位与连接数 |
| 压测期间开着浏览器或下载 | 系统里多一个抢占资源的进程 | 关掉一切不相关的东西 |
