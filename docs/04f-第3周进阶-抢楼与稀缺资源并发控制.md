## 0. 从一次必然超发说起

### 0.1 普通写入与稀缺资源分配

发一条评论是普通写入。两个人同时发，数据库插两行，各有各的自增 id，谁也不挡谁。

抢楼是稀缺资源分配。中奖楼层只有 3 个，1000 个人来抢。普通写入只回答「这条数据存哪里」，抢楼要回答的是「这 3 个名额归谁」。一旦判定放错位置，就会把同一个名额给两个人，活动直接失去公信力。

区别写在这里：

| | 普通写入 | 稀缺资源分配 |
| --- | --- | --- |
| 资源数量 | 无限，来一条插一条 | 有限，发完就没了 |
| 并发下最怕什么 | 丢数据、写错字段 | 同一个名额给两个人（超发） |
| 判定该放哪 | 数据库自增或应用层生成 | 必须有一个所有人共用的仲裁者 |

**仲裁者**是关键字。应用层里每个请求都有自己的内存，谁也不知道别人抢到几号。能当仲裁者的只有两类东西：一个所有请求排队访问的单点（Redis 单线程命令），或者一个自带约束的存储（MySQL 唯一索引）。这一章两样都用，分工不同。

### 0.2 两种必然超发的写法

**写法一：`SELECT COUNT(*) + 1` 算楼层号**

```text
请求 A: SELECT COUNT(*) FROM floor_winners WHERE event_id=1  -> 7
请求 B: SELECT COUNT(*) FROM floor_winners WHERE event_id=1  -> 7
请求 A: 我是第 8 楼，中奖了，INSERT
请求 B: 我也是第 8 楼，中奖了，INSERT
```

两个请求读到同一个快照，`COUNT` 与 `INSERT` 之间没有锁，于是都认为自己是第 8 楼。这类竞态在 QPS 低的时候可能几百次才出现一次，压测才抓得到，最容易混上线。

**写法二：先查有没有人抢过，再插入**

```text
请求 A: SELECT ... WHERE floor=8  -> 空
请求 B: SELECT ... WHERE floor=8  -> 空
请求 A: INSERT floor=8
请求 B: INSERT floor=8
```

把「查」和「插」拆成两条语句，中间就是竞态窗口。加锁能堵住窗口，但会把所有抢楼请求排成一队，吞吐掉一个量级。

正确姿势是把判定合并进写入本身：**抢的动作就是 `INSERT`，由唯一索引决定谁成功**。数据库在同一时刻只会让一行 `(event_id=1, floor=8)` 存在，第二个 `INSERT` 必然撞键。应用层不需要提前知道答案。

## 1. 数据模型

两张新表，定义在 `internal/model/floor.go`，已加进 `internal/config/db.go` 的 `AutoMigrate` 列表。

```go
type FloorEvent struct {
    ID          uint
    ArticleID   uint      // 普通列，刻意不建外键
    Title       string
    LuckyFloors string    // "8,88,888"，创建时固定，之后不提供修改接口
    StartsAt    time.Time
    EndsAt      time.Time
    CreatedAt   time.Time
}

type FloorWinner struct {
    ID        uint
    EventID   uint      // 联合唯一索引 uk_floor_event_floor 的第 1 列
    Floor     int       // 联合唯一索引 uk_floor_event_floor 的第 2 列
    UserID    uint
    Content   string
    CreatedAt time.Time
}
```

三个设计决定值得单独说：

**`LuckyFloors` 用逗号分隔的字符串，不建关联表。** 这个集合创建之后就不再变，每次抢楼都要读一遍。拆成 `floor_prizes` 关联表会多一次 JOIN，收益只是「看起来更规范化」。字符串配合 `joinLuckyFloors` 做排序去重，落库形状稳定。

**`ArticleID` 不建外键。** 活动是一份独立配置。文章被删之后，这份配置还要留着给人复盘「当时设了哪些奖」，所以不跟着文章级联消失。

**中奖楼层创建后不许改。** 先抢的人面对 `{8,88}`，后抢的人面对 `{8,88,888}`，活动就没有统一规则了。所以这一版只提供创建接口，没有修改接口，也没有删除接口。

唯一索引的 tag 长这样：

```go
EventID uint `gorm:"uniqueIndex:uk_floor_event_floor,priority:1;not null"`
Floor   int  `gorm:"uniqueIndex:uk_floor_event_floor,priority:2;not null"`
```

`priority` 指定联合索引里的列顺序。`internal/config/db.go` 里 `gorm.Open` 打开了 `TranslateError: true`，撞唯一键时 GORM 会转成 `gorm.ErrDuplicatedKey`，service 里用 `errors.Is` 就能捕获，不用去匹配 MySQL 的 `Error 1062` 字符串。

## 2. 抢楼五步

核心在 `internal/floor/service.go` 的 `Grab`。

```text
  客户端                floor.Service              Redis              MySQL
    |                        |                       |                   |
    |-- POST /grab --------->|                       |                   |
    |                        |-- 1. SELECT 活动配置 -------------------->|
    |                        |<----------------- 活动行 -----------------|
    |                        |                       |                   |
    |                        |-- 2. 校验时间窗 (本地计算，快速失败)        |
    |                        |                       |                   |
    |                        |-- 3. INCR floor:event:v1:{id}:next ------>|
    |                        |<---------------- N (全局唯一) -------------|
    |                        |                       |                   |
    |                        |-- 4. N 命中中奖集合？                      |
    |                        |     否 -> 直接返回，不写库                  |
    |                        |     是 -> 继续                            |
    |                        |                       |                   |
    |                        |-- 5. INSERT floor_winners ---------------->|
    |                        |<-- 成功 / ErrDuplicatedKey ----------------|
    |<-- {floor, won} -------|                       |                   |
```

**第 1 步**读活动，拿到中奖楼层集合和活动起止时间。活动不存在返回 `domain.ErrNotFound`，映射成 404。

**第 2 步**校验时间窗（`checkWindow`）。这是应用层快速失败，让已结束的活动别白白消耗一个号。它属于弱校验：检查通过之后活动仍可能被改掉，真正决定归属的是第 5 步。

**第 3 步**`INCR`。Redis 单线程执行命令，N 个并发请求各拿不同的号，天然不会撞。key 拼法收在 `internal/keys/keys.go` 的 `FloorNextKey`，和其它 Redis key 一个地方管。

**第 4 步**判断这个号有没有命中中奖集合。`containsFloor` 是显式线性扫描，中奖楼层最多 20 个，比每次抢楼都建一个 map 更省。没命中就直接返回 `won=false`，连数据库都不写。

**第 5 步**命中就 `INSERT floor_winners`。没有 `SELECT`，没有 `UPDATE`，没有应用层判断。谁先插进去谁拿奖，第二个人撞 `uk_floor_event_floor`。

## 3. 零超发到底由谁保证

### 3.1 `INCR` 只负责「号不同」

`INCR` 保证的是：同一时刻的一堆请求，各自拿到一个不同的整数。它不保证这个整数对应的奖还在，也不保证拿到号的人一定能写库成功。

把「号不同」交给 Redis，是因为这件事对一致性要求低。号发重了，最坏结果是两个人抢同一个楼层号，而第 5 步的唯一索引会拦住第二个，奖仍然只发一份。

### 3.2 唯一索引负责「奖不超发」

这条约束写在数据库里，任何写入路径都绕不开：

```sql
UNIQUE KEY uk_floor_event_floor (event_id, floor)
```

应用层所有判断都可以出错，代码可以有 bug，Redis 可以被清空重来，只要这条索引在，`(event_id=1, floor=8)` 就只可能有一行。这是零超发的硬保证。

### 3.3 两者不能互换

试一下把职责调过来会怎样：

| 换法 | 后果 |
| --- | --- |
| 用 MySQL 行锁串行分配号，Redis 只做缓存 | 所有抢楼请求排队，吞吐掉一个量级，但号连续、不跳 |
| 用 Redis `SETNX` 抢名额，MySQL 只存结果 | Redis 与 MySQL 两份事实，Redis 挂了或数据丢了就没有权威来源，还要写对账 |
| 只靠 `INCR`，不加唯一索引 | Redis 被 `FLUSHDB` 后计数器归零，重复发号，超发 |

这一版的选择是：**发号用 Redis 换吞吐，归属用 MySQL 换正确性**。中间那段不一致的窗口，靠唯一索引兜住，代价写在下一节。

## 4. 发号器与数据库不同步的三个后果

`INCR` 在 MySQL 事务之外，它不会回滚。这是整个设计里最需要诚实交代的部分。

### 4.1 号不连续（跳号）

第 3 步发出 8 号，第 5 步 `INSERT` 因为数据库抖动失败了，8 号已经消耗掉，后面的请求从 9 开始。`floor_winners` 表里永远不会有第 8 楼。

这一版里，非中奖号码本来就不写库（第 4 步直接返回），所以表里本来就只有 8、88、888 这几行，看起来「不连续」是常态。**真正的问题是：8 号正好是中奖楼层时，这次失败会永久作废一个中奖名额**，因为 `INCR` 不会退回去，没人能再拿到 8。

### 4.2 Redis 计数器被重置

Redis 重启且没开持久化，或者有人手滑 `DEL` 了 `floor:event:v1:1:next`，计数器从 1 重新发号。

后果：已经拿过号的用户再抢会拿到重复号。非中奖号重复无所谓；中奖号重复时，第二次 `INSERT` 撞唯一键，`Grab` 返回 `domain.ErrFloorTaken`，映射成 409「这一楼已经被抢走了」。**奖不会超发，但用户会看到一堆 409**。

### 4.3 时间窗是弱校验

`checkWindow` 读的是「这次请求读到的活动配置」。检查和 `INCR` 之间活动可能被结束，那个请求仍然会发号。影响面很小（多发几个号），但要知道它不是强一致。

### 4.4 三个改进方向（第 1 条已实现）

第一版故意停在最小可用。要更严谨可以按活动的重要程度选一条：

1. **奖品池模型**（已实现，见第 10 节）：把中奖楼层预先写成 `floor_prizes` 表的行，抢的动作改成 `UPDATE ... SET winner_id=? WHERE event_id=? AND floor=? AND winner_id IS NULL`，靠 `RowsAffected` 判定谁抢到。名额作废变得可查，代价是每次中奖判定都要打一次数据库。发号器仍在 Redis，4.1 与 4.2 的成因还在，变化的是归属判定方式。
2. **定时对账**（呼应 `05b`）：扫 `LuckyFloors` 里没有 winner、且 `next_floor` 已经超过它的楼层，报出来给运营补发或作废。能发现名额作废，不能自动修复。
3. **发号器持久化 + 启动时校准**：Redis 开 AOF，服务启动时用 `MAX(floor)` 校准计数器，避免重置。能压住 4.2，压不住 4.1。

**第 2、3 条和「中奖名额作废」的告警仍未实现**。真要拿这个模块办有奖品的活动，第 2 条至少补上。

## 5. 接口

四条路由，都在 `internal/router/router.go` 注册。统一响应壳是 `{ code, message, data }`。

| 方法 | 路径 | 登录 | 作用 |
| --- | --- | --- | --- |
| `POST` | `/api/floor-events` | 需要 | 创建活动 |
| `GET` | `/api/floor-events/{id}` | 公开 | 活动详情、发到几楼、中奖名单 |
| `POST` | `/api/floor-events/{id}/grab` | 需要 | 抢一次楼 |
| `GET` | `/api/floor-events/{id}/mine` | 需要 | 我抢到的中奖楼层 |

创建活动的请求体（时间用 RFC3339，`time.Time` 绑定失败直接 400）：

```json
{
  "article_id": 1,
  "title": "开服第 1 弹",
  "lucky_floors": [8, 88, 888],
  "starts_at": "2026-11-14T20:00:00+08:00",
  "ends_at": "2026-11-15T20:00:00+08:00"
}
```

抢楼的请求体只有一个字段。请求体里伪造 `floor`、`user_id` 会被 `encoding/json` 忽略：

```json
{ "content": "冲！" }
```

抢楼返回：

```json
{ "code": 0, "message": "ok", "data": { "floor": 8, "won": true, "message": "恭喜抢到中奖楼层" } }
```

`won=false` 表示这次没中奖，不是失败。失败走 HTTP 状态码：400 参数、401 未登录、404 活动不存在、409 活动未在进行中或这一楼已被抢走。

`domain` 里为这个模块加了两个错误哨兵（`ErrFloorNotActive`、`ErrFloorTaken`），映射集中在 `internal/httputil/response.go`，和 `gorm.ErrDuplicatedKey` 一样落到 409。加在 `domain` 而不是模块内部，理由是 `httputil` 要 `errors.Is` 判定，两边必须引用同一个变量。

## 7. 怎么自己验证

下面这些步骤 2026-11-14 在真实 MySQL 上全部跑过。先看 7.0 的实测结果，再按 7.1 往后复现。

### 7.0 实测结果

以下五轮跑的是第一版实现（唯一索引 + `INSERT`）。当前代码的实测数字在第 10.3 节。

环境：MySQL 8.0.45（`forum` 库）、Redis、Windows、Go 服务单实例，客户端和服务端在同一台机器。数字是本机回环下的相对量，不能当生产容量。压测前按 7.1 把限流参数临时放大到 `Capacity: 1000000`、`Rate: 1000000`，压完已改回 `10 / 2`。

| 轮次 | 场景 | 并发 × 时长 | 请求数 | QPS | P50 / P99 | 状态码 |
| --- | --- | --- | --- | --- | --- | --- |
| A | 单用户，20 个中奖楼层 | 50 × 5s | 34036 | 6807 | 7.39ms / 10.19ms | 200=34036 |
| B | 5 个用户，中奖楼层 1..20 | 5×20 × 4s | 28916 | 7228 | 14.57ms / 17.45ms | 全 200 |
| C | 5 个用户，中奖楼层分散 | 5×20 × 4s | 28796 | 7199 | 14.42ms / 18.83ms | 全 200 |
| D | 清空 Redis 计数器后重抢 | 20 × 2s | 14223 | 7110 | 2.78ms / 4.19ms | 200=14203, 409=20 |
| E | 修复限流脚本后，与 A 同参数 | 50 × 5s | 74074 | 14813 | 3.03ms / 11.75ms | 200=74074 |

零超发核验全部通过：

- 活动 A 设了 20 个名额，落库 20 条 winner，`COUNT(DISTINCT floor)=20`。
- 活动 C 的 17 个名额分发到 5 个不同 `user_id`（5 / 3 / 4 / 4 / 1），楼层无重复。
- 全局 `GROUP BY event_id, floor HAVING COUNT(*) > 1` 始终返回空。
- 轮次 D 是最硬的一条：`DEL floor:event:v1:2:next` 之后号码从 1 重发，前 20 个已占用楼层全部撞唯一键，正好 20 个 409，`floor_winners` 仍是 20 条、零新增。发号器作废时数据库仍能兜住归属。

发号器对账：每轮 Redis 计数器增量比客户端观测到的响应数多 2 到 13 个。串行对照实验确认「一次带 body 的 200 请求对应一次 `INCR`」，空 body 请求返回 400 且不发号。多出来的号来自压测结束瞬间被取消的在途请求，服务端日志里有对应的 `context canceled`，客户端在 ctx 取消分支直接丢弃样本。这是压测工具的统计口径，不是超发。

**顺带修掉的一个真 bug**：压测时服务日志刷出 `Error compiling script (new function): user_script:30: 'end' expected ...`。`internal/middleware/ratelimit.go` 的 Lua 脚本最后一行中文说明漏了 `--` 前缀，被 Redis 当成 Lua 代码，脚本每次都编译失败，中间件走 fail-open 分支，限流从未生效。轮次 A 到 D 因此不受限流保护。修复后连续 20 次 GET，前 10 次 200、之后出现 429 且带 `Retry-After: 1`，限流恢复正常。轮次 E 的 QPS 是 A 的 2.2 倍，主要差别是错误日志不再每请求刷一条（压测期间 stderr 从 19MB 降到 5KB）。fail-open 有隐性成本，日志刷屏会把吞吐吃掉一半以上。

还有一个容易误读的现象：`cmd/loadtest` 的 warmup 用空 body 发 20 次 POST，全部返回 400、不计入样本、也不发号。所以号码是从 1 开始的，7.3 里「把中奖楼层设小」不会因为预热被吃掉。

### 7.1 先处理限流

`/api` 组上挂着令牌桶（`Capacity: 10`、`Rate: 2`，见 `internal/router/router.go`）。不处理的话，并发压测打出来的全是 429，测到的是限流器，不是抢楼逻辑。`05a` 文档第 2 节讲了压测前的处理方式，照做。

### 7.2 起服务并拿 token

```bash
go run ./cmd/server

curl -s -X POST http://127.0.0.1:8080/api/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"floor_tester","password":"pass1234"}'

curl -s -X POST http://127.0.0.1:8080/api/login \
```

### 7.5 核对零超发

```bash
curl -s http://127.0.0.1:8080/api/floor-events/1
```

要检查三件事：

1. `winners` 里每个 `floor` 只出现一次（唯一索引生效）。
2. `winners.length <= lucky_floors.length`，绝不会超。
3. `next_floor` 大致等于总请求数减去被限流/失败的数量，说明 `INCR` 在持续发号。

想直接查库更准：

```sql
SELECT event_id, floor, COUNT(*) FROM floor_winners
GROUP BY event_id, floor HAVING COUNT(*) > 1;   -- 必须返回空
```

### 7.6 验证 Redis 重置后的兜底

```bash
redis-cli DEL floor:event:v1:1:next
```

再跑一次 7.4。预期：计数器从 1 重新发号，命中 2、3、5 的 `INSERT` 撞唯一键，客户端收到 409，`floor_winners` 行数不变。**奖没有超发，但会看到一批 409**，这就是 4.2 描述的现象。

### 7.7 观察名额作废

这一版没有自动告警。要人为制造 4.1，可以在第 8 号命中时让数据库写入失败（比如临时把 `floor_winners` 表锁住或改列类型），再查 `LuckyFloors` 里有没有「`next_floor` 已超过、但没有 winner」的楼层。这个实验有破坏性，建议在单独的测试库上做。

## 8. 面试怎么讲

**问：抢楼和秒杀有什么区别？**

秒杀的库存是一个数字，扣减用 `UPDATE stock SET n=n-1 WHERE n>0`，靠 `RowsAffected` 判定。抢楼的每个名额有独立身份（第 8 楼和第 88 楼不是同一个东西），所以用「一行一个名额 + 唯一索引」更贴切。两者共通的是：判定必须落在数据库的一次写入里，不能拆成「先查再写」。

**问：为什么用 Redis `INCR`，不用数据库自增？**

`INCR` 是单条命令、内存操作，不需要事务，吞吐高。数据库自增要插一行才拿得到号，而抢楼里绝大多数号都不中奖、根本不需要落库。代价是发号器与数据库不同步（第 4 节），这一版靠唯一索引把正确性兜回来。

**问：Redis 挂了会怎样？**

`INCR` 报错直接返回 500，抢楼不可用，但不会发错奖。Redis 恢复后如果计数器丢了，会重复发号，唯一索引拦住重复中奖，用户看到 409。所以是「可用性受损 + 用户体验变差」，不是「数据错」。要说清这个区分。

**问：怎么保证不超发？**

第一版的答案是 `(event_id, floor)` 联合唯一索引：抢就是 `INSERT`，第二个撞键。当前实现改成 `UPDATE ... WHERE winner_id IS NULL`，靠 `RowsAffected` 判定，见第 10 节。两种写法共通的一点是判定必须落在数据库的一次写入里，应用层不做「先查再写」。前面所有优化（Redis 发号、时间窗校验）都可以在这条约束下退化，但不会破坏正确性。

**问：这一版有什么没做的？**

诚实说：中奖名额因事务失败作废没有告警和自动补发，Redis 计数器重置没有校准，活动没有修改/删除接口，没有管理后台，没有集成测试和多实例压测。两种实现的并发链路都在真实 MySQL 上跑过（第 7.0、10.3 节），但只覆盖本机单实例。下一步是第 4.4 节的定时对账。

## 9. 诚实 caveat

- **实测只覆盖本机单实例**。MySQL 8.0.45 与 Redis 都在本机回环，没有多实例、没有网络延迟、没有真实用户分布。第一版中奖路径的 `INSERT` 每场只发生 17 到 20 次，当前实现的 `UPDATE` 每场只发生 10 次，样本都太小，不给中奖路径单独的性能结论；7.0 与 10.3 表里的 QPS 主要反映「读活动配置 + `INCR` + 未中奖返回」这条路径。
- **没有中奖名额作废的告警和自动补发**，4.1 的后果存在但系统不会报。奖品池模型让作废名额可以直接查出来（`winner_id IS NULL` 且号码已发过），这个查询还没做成接口或对账任务。
- **没有 Redis 计数器校准**，4.2 会退化成一批 409，靠条件 UPDATE 的 `winner_id IS NULL` 保住正确性。第一版轮次 D 与当前实现 10.3 的 P2 都实测到了这个现象。
- **时间窗是弱校验**，4.3 的窗口存在。
- **限流必须先处理**。修复 Lua 脚本之后限流是真的生效的，而且按客户端 IP 分桶（三个源地址实测生成三个独立 Redis key）。7.1 不放大参数就只会测到限流器。
- **单测只覆盖纯逻辑**（解析、规范化、去重、命中判断、时间窗、`RowsAffected` 判定），`Grab` 里的五步没有 mock 测试，也没有集成测试。7.0 与 10.3 的实测是手工压测加查库对账，不是可重复运行的自动化测试。
- **奖品池的并发验证只覆盖跨轮重复号码**，没有做「两个事务同一瞬间抢同一行」的微基准。正确性依据是 InnoDB 行锁与当前读语义，加上 `RowsAffected` 判定。
- `cmd/loadtest` 单进程只带一个 token。多用户场景用 5 个进程各带一个 token 同时打（轮次 B、C），但进程启动有先后：中奖楼层集中在前 20 号时会被先启动那个用户的协程全部拿走（B 轮 20 个名额全归同一个 `user_id`）。把中奖楼层分散到整个时段才看出多用户分布（C 轮 5 个用户都中奖）。这只是发号顺序决定归属，不是超发。

## 10. 实现升级：奖品池模型

4.4 的第 1 条已经落地，**当前代码走的是这一节描述的方案**。第 0 到 8 节保留第一版（唯一索引 + `INSERT`）的推演，用来对照两种仲裁方式；7.0 的实测数字属于第一版。

### 10.1 表与写入

`internal/model/floor.go` 里 `FloorWinner` 换成 `FloorPrize`。创建活动时在**一个 MySQL 事务**里写 `floor_events` 一行，再给每个中奖楼层写一行 `floor_prizes`，`winner_id` 初始为 NULL。活动和奖品行必须同生共死，否则会出现「活动在、名额不在」的坏活动。

建表结果（MySQL 8.0.45 实测）：

```sql
CREATE TABLE floor_prizes (
  id         bigint unsigned NOT NULL AUTO_INCREMENT,
  event_id   bigint unsigned NOT NULL,
  floor      bigint NOT NULL,
  winner_id  bigint unsigned DEFAULT NULL,
  content    text,
  won_at     datetime(3) DEFAULT NULL,
  created_at datetime(3) DEFAULT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_floor_prize_event_floor (event_id, floor),
  KEY idx_floor_prizes_winner_id (winner_id)
);
```

`Grab` 的第 5 步换成条件 UPDATE：

```go
result := s.db.WithContext(ctx).
    Model(&model.FloorPrize{}).
    Where("event_id = ? AND floor = ? AND winner_id IS NULL", eventID, floorNo).
    Updates(map[string]interface{}{
        "winner_id": userID,
        "content":   content,
        "won_at":    now,
    })
if result.Error != nil { ... }
if err := judgePrizeUpdate(result.RowsAffected); err != nil { ... }
```

`judgePrizeUpdate` 是可单测的纯函数：`RowsAffected == 1` 才算抢到，`== 0` 返回 `domain.ErrFloorTaken`（映射成 409），`> 1` 当异常处理，因为唯一索引保证一个楼层只有一行。

并发时 InnoDB 给匹配行加排他锁。两个事务同时到达，后一个在当前读下重新检查 `winner_id IS NULL`，发现条件已不成立，更新不到任何行。判定和领取落在同一次写入里，应用层仍不做事先查询。

### 10.2 两版对照

| 项 | 第一版 | 当前 |
| --- | --- | --- |
| 名额载体 | 抢到才 `INSERT` 一行 `floor_winners` | 创建活动时预置 `floor_prizes` 行 |
| 仲裁语句 | `INSERT`，撞唯一键 | `UPDATE ... WHERE winner_id IS NULL` |
| 判失败 | `errors.Is(err, gorm.ErrDuplicatedKey)` | `RowsAffected == 0` |
| 名额作废 | 表里没有记录，只能靠号码推断 | 奖品行还在，`winner_id IS NULL` 可直接扫出来 |
| 中奖判定成本 | 一次 INSERT | 一次 UPDATE |

`Detail` 与 `Mine` 改为查 `floor_prizes` 里 `winner_id IS NOT NULL` 的行，响应字段名不变，前端不用改。奖品行的 `CreatedAt` 是活动创建时间，对外的 `created_at` 改填 `WonAt`。

### 10.3 实测（2026-11-14，真实 MySQL）

| 轮次 | 场景 | 并发 × 时长 | 请求数 | QPS | P50 / P99 | 状态码 |
| --- | --- | --- | --- | --- | --- | --- |
| P1 | 10 个名额，单用户 | 50 × 5s | 69714 | 13939 | 3.45 / 5.60 ms | 全 200 |
| P2 | 清空发号器后重抢 | 20 × 2s | 30102 | 15049 | 1.19 / 2.25 ms | 200=30092, **409=10** |

预置核验：创建时输入 11 个楼层（含一个重复值），落库正好 10 行奖品，`winner_id` 全为 NULL。P1 之后 10 行全部领取，`COUNT(DISTINCT floor)=10`，`won_at` 全部非空。P2 之后正好 10 个 409，每个已领取楼层各被撞一次，`winner_id`、`content`、`won_at` 均未被覆盖，名额数仍是 10。

P1 的 13939 QPS 与第一版修复后的 14813 接近，差距在系统负载范围内。中奖路径只执行 10 次 UPDATE，样本太小，不给它单独的容量结论。

### 10.4 当前仍有的边界

- 发号器仍是 Redis `INCR`，在 MySQL 之外。UPDATE 失败或事务回滚时号码已发出，奖品行仍为 NULL，这个名额会作废。奖品池让作废变得可查（`floor < next_floor AND winner_id IS NULL`），但没有自动补发或告警，4.4 的第 2 条还没做。
- Redis 被清空后仍会重复发号，条件 UPDATE 拦住重复领取，用户看到一批 409。4.4 的第 3 条还没做。
- 时间窗仍是应用层弱校验。
- 已有数据库里的 `floor_winners` 表不会被 `AutoMigrate` 删除，压测期间的 57 行旧数据成了孤儿数据，API 已不再读它。
- 没有做「两个事务同一瞬间抢同一行」的微基准。P2 验证的是跨轮重复号码被拦。
