>
> 目标：把「点赞、评论之后通知作者」做成一条能解释一致性、能验证、能被面试官追问三轮的异步链路。全部依赖只有项目里已经有的 MySQL 和 Redis，不安装 Kafka、RabbitMQ 或新的中间件。

## 0. 为什么要加这一章

### 0.1 demo 项目和工程项目的分界线

到 04 章结束，点赞接口在一次 HTTP 请求里同步做完四件事：写 `article_likes`、写 Redis Set、写热榜 ZSET、删详情缓存。这已经是一个能跑的功能。简历上如果只写「实现了点赞接口」，读的人很难把它和课程作业区分开。

真实系统里一次用户动作会长出更多副作用：通知作者、更新计数、写审计日志、刷新搜索索引、推送到客户端。这些副作用有两个共同点。

| 共同点 | 后果 |
| --- | --- |
| 它们不该决定主接口成败 | 通知发不出去，点赞本身仍然成功，客户端不该收到 500 |
| 它们不该凭空消失 | 进程崩了、Redis 重启了、网络抖了一下，事件要能补回来 |

把这两点同时守住，就需要一个「消息」。本章做的正是这件事的最小可验证版本。

### 0.2 一次点赞要牵动多少副作用

```text
PUT /api/articles/:id/like
  -> JWT 取 userID
  -> MySQL 事务：写 article_likes + 写 outbox_events
  -> 提交后：同步 Redis Set、ZSET、删详情缓存（04 章已有）
  -> 返回 200 给客户端                       HTTP 请求到此结束

后台 goroutine（不在请求里）
  -> relay 轮询 outbox_events 的 pending 行
  -> XADD 进 Redis Stream
  -> 标记 published
  -> 消费组 XREADGROUP 取出消息
  -> 查文章作者，写 notifications，XACK
  -> 作者下次 GET /api/notifications 看到红点
```

关键点在「HTTP 请求到此结束」这一行。通知链路的任何一步慢了或挂了，点赞接口都不等它，也不因此失败。

### 0.3 本章的验收合同

## 1. 先把失败窗口画出来

### 1.1 反例：在业务代码里直接发消息

最容易想到的写法是「写库成功之后顺手 `XADD`」。

**概念伪代码**：下面这段明显标记不能运行，只用来暴露问题，不要复制进项目。

```go
// 反例，不要照抄
err := db.Create(&like).Error
if err != nil { return err }
rdb.XAdd(ctx, &redis.XAddArgs{Stream: "forum:events", Values: ...})
return nil
```

把时间轴摊开，中间有三个位置可以掉链子。

| 时刻 | 发生了什么 | 结果 |
| --- | --- | --- |
| T1 | `Create` 成功 | 点赞关系已落库 |
| T2 | 进程崩溃或 Redis 超时 | `XADD` 没执行 |
| T3 | 客户端拿到 200 | 作者永远收不到通知，事件没有任何记录可补 |

把顺序倒过来先 `XADD` 再写库也不行。事务回滚时消息已经发出去了，消费端会通知一个不存在的点赞。Redis 不参与 MySQL 事务，两边没有共同提交点，换顺序解决不了。

还有一个更隐蔽的版本：把 `XADD` 放进事务函数里。MySQL 事务回滚时 Redis 命令不会跟着回滚，问题完全一样。

### 1.2 三种做法对比

| 做法 | 消息会不会丢 | 要引入什么 | 本项目的判断 |
| --- | --- | --- | --- |
| 写库后直接 `XADD` | 会丢，T2 窗口无法恢复 | 无 | 只适合能接受丢失的日志，通知不能这么写 |
| Transactional Outbox | 不会丢，事件随业务事务一起提交 | 一张 `outbox_events` 表、一个轮询器 | 本章采用 |
| CDC（监听 binlog，例如 Debezium） | 不会丢，且不改业务代码 | 独立进程、binlog 权限、运维配置 | 生产常见，本机学习项目扛不住这套依赖 |

03a 章用时间轴推缓存故障，本节用同一套方法推消息故障。结论是一致性问题几乎都长在两个存储之间没有共同提交点的地方。

### 1.3 Transactional Outbox 的最小定义

一句话：把「要发的消息」当成业务数据，写进同一个数据库、同一个事务。

```text
BEGIN
  INSERT INTO article_likes (...)
  INSERT INTO outbox_events (..., status = 'pending')
COMMIT
```

事务提交成功，两行一定都在。事务回滚，两行一定都不在。之后哪怕进程立刻崩了，事件也躺在表里，重启后 relay 扫到就补投。

代价是投递会重复。relay 把 `XADD` 做完、还没来得及把状态改成 `published` 就崩了，重启后会再投一次。所以消费端必须幂等。这一条是本章后面所有设计的地基，官方模式说明见第 11 节。

### 1.4 官方明文与工程惯例分开

| 结论 | 归属 | 依据 |
| --- | --- | --- |
| MySQL InnoDB 事务内的多条写入具备原子性 | MySQL 官方明文 | https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-model.html |
| Redis Stream 的消费组、PEL 与 `XACK` 语义 | Redis 官方明文 | https://redis.io/docs/latest/develop/data-types/streams/ |
| `XREADGROUP` 用 ID `0` 读自己的 pending 列表 | Redis 官方明文 | https://redis.io/docs/latest/commands/xreadgroup/ |
| outbox 模式、至少一次投递、消费端幂等 | 工程惯例 | https://microservices.io/patterns/data/transactional-outbox.html |
| 「轮询间隔 200ms」「重试 5 次转死信」 | 本项目约定 | 为了本机可观察，没有压测依据 |

最后一行要如实说。简历里不要把这些数字写成调优结果。

## 2. 数据模型与事件契约

### 2.1 两张表各自负责什么

| 表 | 归属 | 作用 |
| --- | --- | --- |
| `outbox_events` | 发布侧 | 暂存还没投出去的事件，是「消息不丢」的唯一保证 |
| `notifications` | 消费侧 | 站内信本身，带 `event_id` 唯一索引用来挡重复投递 |

把「消息」和「业务结果」分成两张表，才能分别回答「投出去了吗」和「用户看见了吗」。

### 2.2 完整文件：模型与状态常量

**完整文件**：`internal/model/event.go`。新建文件，保存后先跑 `go build ./internal/model`。

```go
// Package model 定义 GORM 数据模型。
package model

import "time"

// outbox 事件的三种状态。
const (
	OutboxPending   = "pending"   // 还没投进 Stream，等 relay 扫到
	OutboxPublished = "published" // 已经 XADD 成功
	OutboxFailed    = "failed"    // 重试到上限，留着给人工排查
)

// OutboxEvent 是事务发件箱里的一行。
// 业务写入和这一行由同一个 MySQL 事务提交，事件因此不会凭空消失。
type OutboxEvent struct {
	ID            uint      `gorm:"primaryKey" json:"id"`
	EventID       string    `gorm:"size:36;not null;uniqueIndex:uk_outbox_event" json:"event_id"`
	EventType     string    `gorm:"size:32;not null" json:"event_type"`
	AggregateType string    `gorm:"size:32;not null" json:"aggregate_type"`
	AggregateID   uint      `gorm:"not null" json:"aggregate_id"`
	Payload       string    `gorm:"type:text;not null" json:"payload"`
	Status        string    `gorm:"size:16;not null;index" json:"status"`
	Attempts      int       `gorm:"not null;default:0" json:"attempts"`
	CreatedAt     time.Time `json:"created_at"`
	UpdatedAt     time.Time `json:"updated_at"`
}

// Notification 是一条站内通知。
// EventID 上的唯一索引是消费端幂等的最后一道保证。
// TargetType 加 TargetID 表达这条通知指向什么，新增行为不用再加列。
// ArticleID 是列表展示用的文章上下文，非文章域事件存 0。
// 这些关联列都不加外键：文章或评论被删后，通知仍应保留，点进去 404 即可。
type Notification struct {
	ID         uint      `gorm:"primaryKey" json:"id"`
	UserID     uint      `gorm:"not null;index:idx_notify_user_read,priority:1" json:"user_id"`
	EventID    string    `gorm:"size:36;not null;uniqueIndex:uk_notify_event" json:"event_id"`
	ActorID    uint      `gorm:"not null" json:"actor_id"`
	Type       string    `gorm:"size:32;not null" json:"type"`
	ArticleID  uint      `gorm:"not null;default:0" json:"article_id"`
	TargetType string    `gorm:"size:32;not null;default:''" json:"target_type"`
	TargetID   uint      `gorm:"not null;default:0" json:"target_id"`
	IsRead     bool      `gorm:"not null;default:false;index:idx_notify_user_read,priority:2" json:"is_read"`
	CreatedAt  time.Time `json:"created_at"`
}
```

### 2.3 逐行拆解

| 代码 | 作用与设计理由 |
| --- | --- |
| `uniqueIndex:uk_outbox_event` | 事件 ID 全局唯一。relay 重复扫到同一行时不会生成两条不同的消息身份 |
| `status` 加普通索引 | relay 每 200ms 查一次 `WHERE status = 'pending'`，有索引才不会全表扫 |
| `attempts` | 记录投递失败次数，达到上限后转 `failed`，避免一条坏消息永远占用扫描批次 |
| `payload` 用 `text` | 事件内容是一小段 JSON，长度可控但比 `varchar(255)` 长 |
| `uniqueIndex:uk_notify_event` | 同一个事件重复消费时，第二条 INSERT 被数据库挡掉 |
| `idx_notify_user_read` | 通知列表按用户过滤，未读数按 `user_id + is_read` 过滤，复合索引覆盖这两个查询 |
| `OutboxFailed` 单独一个状态 | 死信留在表里，排查时能看见，不做自动删除 |

模型里没有给 `notifications` 加 `UpdatedAt`。标记已读只改 `is_read`，用不到 GORM 自动维护的更新时间，字段少一个就少一处要解释的东西。

### 2.4 事件契约只带 ID

事件 payload 采用瘦事件，只放定位数据需要的 ID，不放作者昵称、文章标题这些会变的内容。

点赞事件长这样：

```json
{
  "event_id": "4d1f...",
  "type": "like.created",
  "actor_id": 7,
  "target": {"type": "article", "id": 12},
  "occurred_at": 1762600000
}
```

评论事件多一个 `created`，指向刚插入的那条评论：

```json
{
  "event_id": "9ab2...",
  "type": "comment.created",
  "actor_id": 7,
  "target": {"type": "article", "id": 12},
  "created": {"type": "comment", "id": 34},
  "occurred_at": 1762600001
}
```

`target` 在所有事件里都是同一个含义，动作作用的对象。点赞作用在文章，评论也作用在文章，关注作用在用户，回复作用在被回复的评论。

`created` 是这次动作新建出来的实体，可选。评论通知点进去要定位到那条评论，所以带。点赞通知只需要跳到文章，多带一个 like id 没有消费方，所以不带。

字段个数固定，新增行为只多一种 `target.type` 取值。将来做关注，`target` 换成 `{"type":"user","id":9}`，整个 Payload 结构不用动。

消费端按 `type` 选 resolver，由 resolver 决定收件人。文章类动作回查 `articles.user_id`，关注类动作直接把 `target.id` 当收件人。多一次查询，换来三件事：文章作者改了不会让旧事件说谎，payload 不会随业务字段越滚越大，事件和消息体是同一份 JSON，relay 不需要理解内容。

这一条属于工程取舍，Redis 和 MySQL 官方都没有规定。写进简历时要说清「多一次查询换契约稳定」，别把它讲成唯一正确做法。

### 3.2 完整文件：事件契约与写入口

**完整文件**：`internal/event/event.go`。新建目录与文件。

```go
// Package event 定义领域事件契约，以及事务发件箱的写入口。
package event

import (
	"context"
	"crypto/rand"
	"encoding/hex"
	"encoding/json"
	"fmt"
	"time"

	"gorm.io/gorm"

	"forum-backend/internal/model"
)

const (
	TypeLikeCreated    = "like.created"
	TypeCommentCreated = "comment.created"
	StreamKey          = "forum:events:v1"
	NotifyGroup        = "forum:notify:v1"
)

// 目标对象的种类。新增行为时只新增一个取值，Payload 的字段个数不变。
const (
	TargetArticle = "article"
	TargetComment = "comment"
	TargetUser    = "user"
)

// Target 是对一个领域对象的引用。
// Type 说明去哪张表找，ID 说明找哪一行。
type Target struct {
	Type string `json:"type"`
	ID   uint   `json:"id"`
}

// Payload 是放进 outbox 与 Stream 的同一份 JSON。
// 字段只带 ID，消费端需要展示文案时自己回查数据库。
//
// Target 是动作作用的对象，所有事件共用这一个含义：
// 点赞作用在文章，评论作用在文章，关注作用在用户，回复作用在被回复的评论。
//
// Created 是这次动作新建出来的实体，可选。
// 评论的 Created 是那条新评论，通知点进去要定位到它。
// 点赞不填，通知只需要跳到文章，多带一个 like id 没有消费方。
// 字段带 omitempty，缺失时整个键都不出现。
type Payload struct {
	EventID    string  `json:"event_id"`
	Type       string  `json:"type"`
	ActorID    uint    `json:"actor_id"`
	Target     Target  `json:"target"`
	Created    *Target `json:"created,omitempty"`
	OccurredAt int64   `json:"occurred_at"`
}

// NewPayload 生成一个带全局唯一 ID 的事件。
// 参数按语义分：谁做的、作用在谁身上、新建了什么。
// 新增一种行为时不用改这个签名，只要传入新的 Target。
func NewPayload(eventType string, actorID uint, target Target, created *Target) (Payload, error) {
	b := make([]byte, 16)
	if _, err := rand.Read(b); err != nil {
		return Payload{}, fmt.Errorf("generate event id: %w", err)
	}
	return Payload{
		EventID:    hex.EncodeToString(b),
		Type:       eventType,
		ActorID:    actorID,
		Target:     target,
		Created:    created,
		OccurredAt: time.Now().Unix(),
	}, nil
}

// Encode 把事件序列化成 outbox 表里保存的字符串。
func (p Payload) Encode() (string, error) {
	b, err := json.Marshal(p)
	if err != nil {
		return "", fmt.Errorf("marshal event %s: %w", p.EventID, err)
	}
	return string(b), nil
}

// Decode 是消费端用的反序列化入口。
// 事件格式只有 Target 加可选 Created 这一种，解码不做字段补齐。
func Decode(raw string) (Payload, error) {
	var p Payload
	if err := json.Unmarshal([]byte(raw), &p); err != nil {
		return Payload{}, fmt.Errorf("decode event payload: %w", err)
	}
	return p, nil
}

// Emit 把一个事件写进 outbox。tx 必须是业务事务的句柄。
// 调用方如果把普通的 *gorm.DB 传进来，事件和业务写入就不在同一个事务里了，
// 这一章要守的保证会立刻失效。
func Emit(ctx context.Context, tx *gorm.DB, p Payload) error {
	payload, err := p.Encode()
	if err != nil {
		return err
	}
	row := &model.OutboxEvent{
		EventID:       p.EventID,
		EventType:     p.Type,
		AggregateType: p.Target.Type,
		AggregateID:   p.Target.ID,
		Payload:       payload,
		Status:        model.OutboxPending,
	}
	if err := tx.WithContext(ctx).Create(row).Error; err != nil {
		return fmt.Errorf("insert outbox event %s: %w", p.EventID, err)
	}
	return nil
}

// EmitCreated 是创建类事件共用的发事件入口。
// 两步合成一步：先生成带唯一 ID 的 Payload，再写进当前事务的 outbox。
// 参数里没有任何具体业务字段，新增关注、收藏、回复等事件都复用这个签名。
// 非创建类事件可以直接用 NewPayload 加 Emit，不必挤进这个函数。
// tx 必须来自业务事务，事件才能和业务写入一起提交或一起回滚。
func EmitCreated(ctx context.Context, tx *gorm.DB, eventType string, actorID uint, target Target, created *Target) error {
	p, err := NewPayload(eventType, actorID, target, created)
	if err != nil {
		return err
	}
	return Emit(ctx, tx, p)
}
```

### 3.3 逐行拆解与设计决策

| 代码 | 作用与设计理由 |
| --- | --- |
| `StreamKey = "forum:events:v1"` | key 带版本号，与 03a 章缓存 key 的规矩一致。本次删掉兼容字段后格式已变，开发环境清空 Stream 重跑；正式跨版本发布应升版本号 |
| `NotifyGroup` | 消费组名单独成常量，relay 与 worker 用同一份定义，不会一边写 `notify` 另一边写 `notification` |
| `crypto/rand` 生成 ID | 事件 ID 要跨进程、跨重启唯一。自增 ID 在投递重试时无法当幂等键 |
| `Emit` 收 `tx *gorm.DB` | 签名本身就在提醒调用方：这里必须是事务句柄。换成 `*gorm.DB` 的普通句柄，编译照样过，语义就错了 |
| `Target` 统一是作用对象 | 点赞与评论都指向文章，聚合类型不会一类事件记 article 另一类记 comment |
| `Created` 用指针 | 结构体值配 `omitempty` 不会被省略，会多带一个空对象。指针的 nil 才会真正省掉 |
| `Decode` 只做反序列化 | 不做字段补齐。契约只有一种格式，解码器不背历史包袱 |
| `AggregateType` 取 `p.Target.Type` | outbox 的聚合类型跟着作用对象走，同一篇文章的点赞与评论落在同一个聚合上，关注事件自然记成 `user` |
| `EmitCreated` 合成两步 | 参数里没有具体业务字段，点赞、评论、未来的关注调用点形状完全相同 |
| `tx.WithContext(ctx)` | 事务已经继承了上下文，再写一次保证 `Create` 也遵守请求超时 |
| payload 与 Stream 里是同一份字符串 | relay 只搬运，不解析、不改写，少一处能把数据改坏的地方 |

**为什么不用 `comment_id` 这类字段区分行为**。上一版把一个业务字段当成隐式判别式，消费端看到非零就当评论处理。做关注、收藏、回复时，每加一种行为就要给 Payload、通知表、DTO 各加一列，公共入口的参数表也会越排越长。判别应该落在 `type` 这个显式字段上，负载只负责描述对象。这一条属于设计取舍，事件少的时候平铺字段写起来更快，事件一多维护成本会反过来。

被放弃的方案：把事件写成 Go 结构体再让 GORM 用 `datatypes.JSON` 存。那样能少一次 `json.Marshal`，但要引入新依赖，且 Stream 里仍然要字符串，转换还是躲不掉。

**旧消息直接丢掉**。本章不保留 v1 解码兼容字段。重启新代码前先清空 Stream，否则残留的旧格式消息会解出零值 Target，`articleIDOf` 返回 0，事件被 ACK 掉且不产生任何通知。

```powershell
redis-cli DEL forum:events:v1
```

`DEL` 会一并删掉挂在这个 key 上的消费组与 PEL，开发环境从空流开始即可。生产环境更稳的做法是给 `StreamKey` 升版本号，旧消息留在旧 key 里自然过期，避免误删仍在投递的数据。本次按学习项目处理，没有升版本，key 名里的 `v1` 与实际格式已不完全对应，这是省掉兼容代码付出的代价。

### 3.4 增量修改：点赞的写入方法

**增量修改**：打开 `internal/service/like.go`，把整个 `writeRelation` 方法替换成下面这一版。`apply`、`countLikes`、`syncHotScore` 等其它方法一个字都不用改，import 里新增 `forum-backend/internal/event`。

```go
// writeRelation 把点赞关系与领域事件放进同一个事务。
// 只有真正新增了一行、且这次是点赞，才写事件；
// 重复点赞与取消点赞都不通知作者。
func (s *LikeService) writeRelation(ctx context.Context, articleID, userID uint, add bool) (bool, error) {
	changed := false
	err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		if add {
			err := tx.Create(&model.ArticleLike{ArticleID: articleID, UserID: userID}).Error
			if err == nil {
				changed = true
			} else if errors.Is(err, gorm.ErrDuplicatedKey) {
				return nil
			} else {
				return fmt.Errorf("insert article like: %w", err)
			}
		} else {
			res := tx.Where("article_id = ? AND user_id = ?", articleID, userID).
				Delete(&model.ArticleLike{})
			if res.Error != nil {
				return fmt.Errorf("delete article like: %w", res.Error)
			}
			changed = res.RowsAffected > 0
		}

		if !changed || !add {
			return nil
		}
		// 点赞作用在文章上，Target 就是这篇文章。
		// Created 不填，通知跳文章即可，like id 没有消费方。
		target := event.Target{Type: event.TargetArticle, ID: articleID}
		return event.EmitCreated(ctx, tx, event.TypeLikeCreated, userID, target, nil)
	})
	if err != nil {
		return false, err
	}
	return changed, nil
}
```

改动点只有三处，逐条对得上 04 章 4.4 的 v3 版本。

| 改动 | 原来 | 现在 |
| --- | --- | --- |
| 外层包事务 | 直接 `s.db.WithContext(ctx).Create` | `s.db.WithContext(ctx).Transaction(...)` |
| 事务内句柄 | `s.db` | `tx` |
| 新增事件 | 无 | `changed && add` 时 `event.EmitCreated` |

`gorm.ErrDuplicatedKey` 能生效，靠的是 `internal/config/db.go` 里已经打开的 `TranslateError: true`。04 章 4.2 定过这条，本章不改。

要注意一个顺序问题：`apply` 里的 `syncLikeSet`、`syncHotScore` 和删详情缓存都在事务提交之后，本章没动它们。事件写进事务，Redis 投影留在事务外，这个界线是刻意的。Redis 不参与 MySQL 事务，硬把它塞进事务函数只会制造「事务已回滚、Redis 已写入」的假象。

### 3.5 增量修改：评论的写入方法

**增量修改**：打开 `internal/service/comment.go`，把整个 `Create` 方法替换成下面这一版，import 里新增 `forum-backend/internal/event`。校验逻辑、文章存在性检查和 `ErrNotFound` 转换保持原样。

```go
// Create 在指定文章下发表一条评论，并在同一事务里写出领域事件。
// 评论的主键要等 INSERT 之后才有，所以事件必须写在事务内部、Create 之后。
func (s *CommentService) Create(ctx context.Context, articleID, userID uint, content string) (*model.Comment, error) {
	content = strings.TrimSpace(content)
	if content == "" {
		return nil, fmt.Errorf("%w: content is required", ErrInvalidInput)
	}
	if len(content) > 10000 {
		return nil, fmt.Errorf("%w: content too long", ErrInvalidInput)
	}

	var article model.Article
	if err := s.db.WithContext(ctx).First(&article, articleID).Error; err != nil {
		if errors.Is(err, gorm.ErrRecordNotFound) {
			return nil, fmt.Errorf("check article %d: %w", articleID, ErrNotFound)
		}
		return nil, fmt.Errorf("check article %d: %w", articleID, err)
	}

	m := &model.Comment{
		ArticleID: articleID,
		UserID:    userID,
		Content:   content,
	}
	err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		if err := tx.Create(m).Error; err != nil {
			return fmt.Errorf("create comment for article %d: %w", articleID, err)
		}
		// m.ID 由 tx.Create(m) 回填，必须在 INSERT 之后才能生成事件。
		// Target 是评论作用的文章，收件人靠它回查作者。
		// Created 是刚插入的这条评论，通知点进去要定位到它。
		// 消费端按事件类型分发，不再靠某个字段是否为 0 猜类型。
		target := event.Target{Type: event.TargetArticle, ID: articleID}
		created := event.Target{Type: event.TargetComment, ID: m.ID}
		return event.EmitCreated(ctx, tx, event.TypeCommentCreated, userID, target, &created)
	})
	if err != nil {
		return nil, err
	}
	return m, nil
}
```

文章存在性检查留在事务外，和 03 章 6.7 的理由一样：它只负责给出明确的 404，真正的兜底是 `comments.article_id` 上的 RESTRICT 外键。把它挪进事务不会变得更安全，只会让事务持锁时间变长。

## 4. 第 2 步：Relay 把 outbox 投进 Redis Stream

### 4.1 为什么用 Redis Stream

项目里已经有 Redis，Stream 提供三样刚好够用的东西：消息按顺序追加、消费组记录读到哪、没 ACK 的消息留在 PEL 里可以重放。比起自己用 List 加 `BRPOP` 实现，Stream 少写一套「处理中」状态机。

| 需求 | Stream 给的 |
| --- | --- |
| 消息不因消费者掉线而消失 | 消费组与 PEL |
| 重启后接着读 | `XREADGROUP` 与 `XACK` |
| 本机一条命令可观察 | `XLEN`、`XPENDING`、`XRANGE` |

`LPUSH/BRPOP` 也能做队列，但消息弹出时就从队列消失，消费者崩了要靠额外状态补。选 Stream 的理由就这一条。

### 4.2 完整文件：发布侧

**完整文件**：`internal/worker/relay.go`。新建目录与文件。

```go
// Package worker 放后台任务：发布 outbox 事件、消费事件生成站内通知。
package worker

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
	"gorm.io/gorm"

	"forum-backend/internal/event"
	"forum-backend/internal/model"
)

const (
	relayInterval       = 200 * time.Millisecond
	relayBatchSize      = 100
	maxPublishAttempts  = 5
)

// Relay 把 outbox 里 pending 的事件投进 Redis Stream。
type Relay struct {
	db  *gorm.DB
	rdb *redis.Client
}

func NewRelay(db *gorm.DB, rdb *redis.Client) *Relay {
	return &Relay{db: db, rdb: rdb}
}

// Run 按固定间隔扫表，ctx 取消后退出，由 main 的 WaitGroup 等它收尾。
func (r *Relay) Run(ctx context.Context) {
	ticker := time.NewTicker(relayInterval)
	defer ticker.Stop()
	for {
		select {
		case <-ctx.Done():
			return
		case <-ticker.C:
			if err := r.PublishBatch(ctx); err != nil {
				log.Printf("relay publish batch: %v", err)
			}
		}
	}
}

// PublishBatch 一次最多投 relayBatchSize 条。
// 单独导出成方法，是为了能在测试里不启动 goroutine 就调用它。
func (r *Relay) PublishBatch(ctx context.Context) error {
	events := make([]model.OutboxEvent, 0)
	err := r.db.WithContext(ctx).
		Where("status = ?", model.OutboxPending).
		Order("id ASC").Limit(relayBatchSize).
		Find(&events).Error
	if err != nil {
		return fmt.Errorf("load pending events: %w", err)
	}

	for _, e := range events {
		_, err := r.rdb.XAdd(ctx, &redis.XAddArgs{
			Stream: event.StreamKey,
			Values: map[string]interface{}{
				"event_id": e.EventID,
				"type":     e.EventType,
				"payload":  e.Payload,
			},
		}).Result()
		if err != nil {
			log.Printf("relay xadd %s: %v", e.EventID, err)
			r.markFailure(ctx, e)
			continue
		}
		err = r.db.WithContext(ctx).Model(&model.OutboxEvent{}).
			Where("id = ?", e.ID).
			Update("status", model.OutboxPublished).Error
		if err != nil {
			return fmt.Errorf("mark published %s: %w", e.EventID, err)
		}
	}
	return nil
}

// markFailure 累加失败次数，到上限后把事件留在 failed 状态等待排查。
func (r *Relay) markFailure(ctx context.Context, e model.OutboxEvent) {
	updates := map[string]interface{}{
		"attempts": gorm.Expr("attempts + 1"),
	}
	if e.Attempts+1 >= maxPublishAttempts {
		updates["status"] = model.OutboxFailed
	}
	err := r.db.WithContext(ctx).Model(&model.OutboxEvent{}).
		Where("id = ?", e.ID).Updates(updates).Error
	if err != nil {
		log.Printf("mark outbox failure %s: %v", e.EventID, err)
	}
}
```

### 4.3 逐行拆解

| 代码 | 作用与设计理由 |
| --- | --- |
| `Order("id ASC")` | 同一篇文章的点赞与评论按发生顺序投递，避免通知顺序看起来倒着 |
| `Limit(relayBatchSize)` | 一次最多 100 条，避免停机很久后重启时一个批次把 Redis 打满 |
| `XAdd` 的 `Values` 只放三个字段 | `payload` 原样搬运，`event_id` 与 `type` 便于 `XRANGE` 时肉眼排查 |
| 先 `XAdd` 再改 `status` | 顺序反了会丢消息。现在这个顺序最坏是重复投递，由消费端幂等兜住 |
| `markFailure` 用 `gorm.Expr("attempts + 1")` | 一条 UPDATE 完成自增，不先把旧值读出来再写，避免并发下覆盖 |
| `OutboxFailed` 不自动重试 | 死亡消息留在表里，人工看完可以手工把 status 改回 `pending` |
| `Run` 用 `select` 等 ctx | Ctrl+C 时能干净退出，不靠 `for {}` 死循环 |

`XAdd` 成功、改状态失败这个窗口，就是本章反复强调的至少一次投递。它不会造成数据错误，因为 `notifications.event_id` 有唯一索引。

### 4.4 投递失败与死信

| 状态 | 谁写 | 下一步 |
| --- | --- | --- |
| `pending` | 业务事务 | relay 扫到就投 |
| `published` | relay | 不再扫，消费组负责后续 |
| `failed` | relay 重试到上限 | 留表待查，改回 `pending` 可手动重投 |

`published` 的行会一直留在表里。清理策略（归档或定期删）属于运维动作，本章明确不做，9.2 会列出来。

## 5. 第 3 步：消费组生成通知，幂等是硬要求

### 5.1 消费组的三个词

| 词 | 含义 |
| --- | --- |
| `XREADGROUP ... >` | 只取从未发给任何消费者的新消息 |
| PEL | 已投递但还没 `XACK` 的消息列表，按消费者分开保存 |
| `XREADGROUP ... 0` | 读回自己 PEL 里的旧消息，用来处理上次崩溃留下的尾巴 |

循环里先用 `0` 清自己的 PEL，再用 `>` 阻塞读新消息。这样进程重启后，没 ACK 的消息会被重新处理，不需要额外的补偿脚本。这是单机单消费者版本的最小写法，多实例边界在 9.2。

### 5.2 完整文件：消费侧

> **实现现状（2026-11）**：下面这段代码讲的是每一步在做什么，内容仍然成立，但位置变了。
> 循环骨架（建组 → 读 PEL → 读新消息 → 成功才 ACK → 读失败退避）已经抽到
> `internal/event/consumer.go` 的 `Consumer`，通知 worker 与私信推送 worker 共用它，
> 各自只声明消费组名和 `handle` 函数。`readBlock = 2s`、`readBatchSize = 20`
> 变成了 `Consumer` 的默认值，含义没变。
> 顺带修掉的一个问题：早先读失败会立刻重试，Redis 断连时变成零延迟热循环；
> 现在按 100ms 起步、翻倍到 2 秒封顶退避。

**完整文件**：`internal/worker/notification.go`。新建文件。

```go
package worker

import (
	"context"
	"errors"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
	"gorm.io/gorm"
	"gorm.io/gorm/clause"

	"forum-backend/internal/event"
	"forum-backend/internal/model"
)

const (
	notifyConsumer = "worker-1"
	readBlock      = 2 * time.Second
	readBatchSize  = 20
)

// NotificationWorker 从消费组取事件，写成站内通知。
type NotificationWorker struct {
	db  *gorm.DB
	rdb *redis.Client
}

func NewNotificationWorker(db *gorm.DB, rdb *redis.Client) *NotificationWorker {
	return &NotificationWorker{db: db, rdb: rdb}
}

// Run 先确保消费组存在，再循环处理 PEL 与新消息。
func (w *NotificationWorker) Run(ctx context.Context) {
	// 重复启动会返回 BUSYGROUP，组已存在正是我们要的状态，忽略即可。
	_ = w.rdb.XGroupCreateMkStream(ctx, event.StreamKey, event.NotifyGroup, "0").Err()

	for {
		if ctx.Err() != nil {
			return
		}
		w.consume(ctx, "0") // 先补上次没 ACK 的
		w.consume(ctx, ">") // 再阻塞读新消息
	}
}

// consume 读一批消息，逐条处理，成功才 ACK。
func (w *NotificationWorker) consume(ctx context.Context, start string) {
	block := readBlock
	if start == "0" {
		// go-redis v9 里只有 Block >= 0 才发 BLOCK 参数。
		// 传 -1 让这次读立即返回，不阻塞循环。
		block = -1
	}
	streams, err := w.rdb.XReadGroup(ctx, &redis.XReadGroupArgs{
		Group:    event.NotifyGroup,
		Consumer: notifyConsumer,
		Streams:  []string{event.StreamKey, start},
		Count:    readBatchSize,
		Block:    block,
	}).Result()
	if errors.Is(err, redis.Nil) {
		return
	}
	if err != nil {
		if ctx.Err() != nil {
			return
		}
		log.Printf("read group from %s: %v", start, err)
		return
	}

	for _, stream := range streams {
		for _, msg := range stream.Messages {
			if err := w.handle(ctx, msg); err != nil {
				// 不 ACK，消息留在 PEL，下一轮用 "0" 重新读到。
				log.Printf("handle event %s: %v", msg.ID, err)
				continue
			}
			if err := w.rdb.XAck(ctx, event.StreamKey, event.NotifyGroup, msg.ID).Err(); err != nil {
				log.Printf("ack event %s: %v", msg.ID, err)
			}
		}
	}
}

// handle 把一条事件变成一条通知。重复事件由唯一索引挡住。
// 事件类型决定用哪个 resolver，落库与推送对所有类型一视同仁。
func (w *NotificationWorker) handle(ctx context.Context, msg redis.XMessage) error {
	raw, ok := msg.Values["payload"].(string)
	if !ok {
		return fmt.Errorf("event %s: payload is not a string", msg.ID)
	}
	p, err := event.Decode(raw)
	if err != nil {
		return err
	}

	resolve, ok := resolverByType[p.Type]
	if !ok {
		// 没有注册 resolver 的事件，通知消费端不处理。
		// 直接 ACK，避免未知类型永远留在 PEL 变成毒消息。
		log.Printf("no notification resolver for %s, ack event %s", p.Type, msg.ID)
		return nil
	}
	spec, err := resolve(ctx, w.db, p)
	if err != nil {
		return err
	}
	if spec == nil {
		// resolver 明确说这条事件不产生通知，比如自己给自己点赞。
		return nil
	}

	notice := &model.Notification{
		UserID:     spec.UserID,
		EventID:    p.EventID,
		ActorID:    p.ActorID,
		Type:       spec.Type,
		ArticleID:  spec.ArticleID,
		TargetType: spec.TargetType,
		TargetID:   spec.TargetID,
	}
	res := w.db.WithContext(ctx).Clauses(clause.OnConflict{
		Columns:   []clause.Column{{Name: "event_id"}},
		DoNothing: true,
	}).Create(notice)
	if res.Error != nil {
		return fmt.Errorf("insert notification %s: %w", p.EventID, res.Error)
	}
	return nil
}
```

上面省略了 `hub.Push` 那一段，它在 04c 章才接入。分发与落库的主干与当前源码一致。

`resolverByType` 定义在 `internal/worker/notify_resolver.go`，这是新增行为时唯一要动的地方：

```go
// notifySpec 是一条通知该长什么样。
type notifySpec struct {
	UserID     uint
	Type       string
	ArticleID  uint
	TargetType string
	TargetID   uint
}

// resolver 把一种事件翻译成通知规格。
// 返回 nil 表示这条事件不产生通知，handle 会直接 ACK。
type resolver func(ctx context.Context, db *gorm.DB, p event.Payload) (*notifySpec, error)

var resolverByType = map[string]resolver{
	event.TypeLikeCreated:    resolveArticleAction,
	event.TypeCommentCreated: resolveArticleAction,
}
```

`resolveArticleAction` 回查文章作者，把 `p.Target` 原样写进 `notifySpec`。将来做关注事件，写一个 `resolveFollow` 把 `target.id` 直接当收件人，再加一行注册即可，`handle` 与落库代码不用改。

### 5.3 逐行拆解

| 代码 | 作用与设计理由 |
| --- | --- |
| `XGroupCreateMkStream` | 组不存在时连 Stream 一起建，空库第一次启动也能跑 |
| 忽略 `BUSYGROUP` | 重启是常态，不该把它当错误刷日志 |
| `start == "0"` 时 `Block = -1` | go-redis v9.23.0 的 `XReadGroupArgs` 里 `Block >= 0` 才追加 `BLOCK`。传 0 会变成 `BLOCK 0`，那是无限阻塞，整个循环会卡死在补 PEL 这一步。这是查 `go-redis@v9.23.0/stream_commands.go` 得到的版本相关结论，升级依赖后要重看 |
| 失败不 ACK | 消息留在 PEL，下一轮 `start="0"` 会再取一次，不写额外重试队列 |
| `resolverByType[p.Type]` | 按事件类型选处理逻辑。新增行为只加一行注册，`handle` 不变 |
| 未注册类型直接 ACK | 搜索同步一类的事件混进 Stream 时，不会误发通知，也不会卡在 PEL |
| `spec == nil` 直接返回 | resolver 自己决定这条不通知，回查文章与自己动作的判断都收在 resolver 里 |
| `Select("id", "user_id")` | 只取两个字段，通知不需要文章正文 |
| 文章不存在返回 nil | 事件是历史事实，文章删了只是没有收件人，ACK 掉避免坏消息永久卡在 PEL |
| `clause.OnConflict{DoNothing: true}` | 重复投递时 INSERT 变成 0 行，不报错。幂等落在数据库约束上，不靠内存去重 |
| `notifyConsumer = "worker-1"` | 单机单消费者。多实例要每个实例用不同名字，并改用 `XAUTOCLAIM` 处理别人的 PEL |

### 5.4 幂等到底由谁保证

```text
event.Emit 生成 event_id（32 位十六进制）
  -> outbox_events.event_id 唯一索引     挡住同一事件的重复入库
  -> Stream 消息的 payload 里带同一个 event_id
  -> notifications.event_id 唯一索引     挡住重复消费
  -> OnConflict DoNothing                让重复变成「成功但零行」
```

三层用同一个 ID，任何一层重复都不会让作者收到两条通知。面试官如果问「为什么不用 Redis SETNX 做幂等」，答案是它会引入新的双写窗口，而数据库唯一索引已经和通知写入在同一个事务里。

### 5.5 常见错误对照

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 服务启动后 CPU 空转，通知一条都不来 | `consume(ctx, "0")` 传了 `Block: 0`，被 Redis 当成无限阻塞 | 按 5.2 改成 `-1` |
| 通知重复出现 | 漏了 `clause.OnConflict`，或唯一索引没建成 | 查 `SHOW CREATE TABLE notifications` |
| 坏消息永远卡在 PEL | `handle` 返回错误后仍 `XACK` | 只在 `handle` 返回 nil 时 ACK |
| 文章删掉后日志一直刷同一条错误 | 没把 `ErrRecordNotFound` 当成「无收件人」 | 按 5.2 直接返回 nil |
| 重启后旧消息不再被处理 | 只写了 `>` 分支 | 补上 `start="0"` 的 PEL 重放 |
| `XGroupCreateMkStream` 每次启动刷一条 BUSYGROUP 错误日志 | 把它的错误当真错打印 | 忽略即可 |

// List 返回当前用户的通知分页、总数与未读数。
// 三条查询各开一条新链，不复用带 Where 的中间变量，理由见 03 章 3.5。
func (s *NotificationService) List(ctx context.Context, userID uint, page, pageSize int) ([]*model.Notification, int64, int64, error) {
	if page < 1 || pageSize < 1 || pageSize > 50 {
		return nil, 0, 0, fmt.Errorf("%w: invalid pagination", ErrInvalidInput)
	}

	var total int64
	err := s.db.WithContext(ctx).Model(&model.Notification{}).
		Where("user_id = ?", userID).Count(&total).Error
	if err != nil {
		return nil, 0, 0, fmt.Errorf("count notifications: %w", err)
	}

	var unread int64
	err = s.db.WithContext(ctx).Model(&model.Notification{}).
		Where("user_id = ? AND is_read = ?", userID, false).Count(&unread).Error
	if err != nil {
		return nil, 0, 0, fmt.Errorf("count unread notifications: %w", err)
	}

	list := make([]*model.Notification, 0)
	err = s.db.WithContext(ctx).
		Where("user_id = ?", userID).
		Order("id DESC").
		Offset((page - 1) * pageSize).Limit(pageSize).
		Find(&list).Error
	if err != nil {
		return nil, 0, 0, fmt.Errorf("list notifications: %w", err)
	}
	return list, total, unread, nil
}

// MarkAllRead 把当前用户的未读通知一次改完，返回受影响行数。
func (s *NotificationService) MarkAllRead(ctx context.Context, userID uint) (int64, error) {
	res := s.db.WithContext(ctx).Model(&model.Notification{}).
		Where("user_id = ? AND is_read = ?", userID, false).
		Update("is_read", true)
	if res.Error != nil {
		return 0, fmt.Errorf("mark notifications read: %w", res.Error)
	}
	return res.RowsAffected, nil
}

## 7. 第 5 步：main 里启动 worker 与优雅关闭

### 7.1 完整文件：入口

**完整文件**：`cmd/server/main.go`。整体覆盖 04 章的版本。04b 章会在这个文件上再加通用 API 注解与一个空白导入，两章的先后顺序不能颠倒。

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"net/http"
	"os"
	"os/signal"
	"sync"
	"syscall"
	"time"

	"forum-backend/internal/config"
	"forum-backend/internal/router"
	"forum-backend/internal/worker"
	"forum-backend/pkg/jwt"
)

func main() {
	cfg, err := config.Load()
	if err != nil {
		log.Fatalf("加载配置失败: %v", err)
	}

	db, err := config.InitDB(&cfg.MySQL)
	if err != nil {
		log.Fatalf("连接数据库失败: %v", err)
	}
	sqlDB, err := db.DB()
	if err == nil {
		defer sqlDB.Close()
	}

	rdb, err := config.InitRedis(&cfg.Redis)
	if err != nil {
		log.Fatalf("连接 Redis 失败: %v", err)
	}
	defer rdb.Close()

	jwtManager, err := jwt.NewManager(cfg.JWT.Secret, cfg.JWT.Expire)
	if err != nil {
		log.Fatalf("JWT 配置错误: %v", err)
	}
	r, err := router.New(db, jwtManager, rdb)
	if err != nil {
		log.Fatalf("注册路由失败: %v", err)
	}

	// 一个信号源同时管 HTTP server 与两个后台 worker。
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	relay := worker.NewRelay(db, rdb)
	notifier := worker.NewNotificationWorker(db, rdb)

	var wg sync.WaitGroup
	wg.Add(2)
	go func() {
		defer wg.Done()
		relay.Run(ctx)
	}()
	go func() {
		defer wg.Done()
		notifier.Run(ctx)
	}()

	addr := fmt.Sprintf(":%d", cfg.Server.Port)
	srv := &http.Server{Addr: addr, Handler: r}

	go func() {
		<-ctx.Done()
		shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
		defer cancel()
		if err := srv.Shutdown(shutdownCtx); err != nil {
			log.Printf("shutdown server: %v", err)
		}
	}()

	log.Printf("server start at %s", addr)
	if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
		log.Fatalf("启动服务失败: %v", err)
	}

	// 等两个 worker 收完手，再让 main 返回、defer 关连接池。
	wg.Wait()
}
```

### 7.2 装配链总图

```text
main.go
  -> config.Load / InitDB / InitRedis / jwt.NewManager
  -> router.New(db, jwtManager, rdb)
       -> NewNotificationService(db)
       -> NewNotificationHandler(svc)
       -> auth.GET("/notifications") / auth.PUT("/notifications/read-all")
  -> signal.NotifyContext
       -> go Relay.Run(ctx)                 扫 outbox_events，XADD
       -> go NotificationWorker.Run(ctx)    XREADGROUP，写 notifications
  -> http.Server.ListenAndServe
       -> 收到信号后 srv.Shutdown，ctx 同时通知两个 worker
  -> wg.Wait
```

`router.New` 的签名没变。这一点很要紧，03 章 7.2 和 04 章 0.5 定过的三层装配链不能因为加 worker 就重排。worker 是 main 层的并列组件，不塞进 router，也不让 handler 持有它。

### 7.3 为什么这段能写进简历

三条能讲清的工程事实，都有代码位置。

| 事实 | 依据 |
| --- | --- |
| 通知链路不拖慢主接口 | 事件随事务落库，HTTP 请求在事务提交后就返回 |
| 停机不丢消息 | `outbox_events` 是持久化事实，重启后 relay 扫 `pending` 自动补投 |
| 关停有序 | 同一个 `ctx` 通知 server 与 worker，`WaitGroup` 等 goroutine 退出后才关连接池 |

第三点在 04 章是缺的。原来 `r.Run(addr)` 阻塞且无法响应信号，00 章上线检查里的「优雅关闭」一直只是目标状态。本章把它兑现成可运行代码，顺带给了 worker 一个干净的退出点。

主接口在停机瞬间仍可能成功写入业务数据和事件，然后进程退出、relay 没来得及投。事件留在 `pending`，下次启动补投。这个窗口正是 outbox 存在的理由，讲的时候要主动说出来。

第二个测试守的是 2.4 的瘦事件约定。有人往 payload 里塞文章标题时测试会失败，提醒他同步改本章的契约说明。点赞事件 5 个字段，评论事件 6 个（多一个 `created`）。差异来自 `Created` 这个可选指针，与事件类型无关，核对字段数时要点明用的是哪种事件。

项目里已经落了真实测试 `internal/event/event_test.go`，覆盖 round trip、瘦事件的固定五个字段、以及评论事件的 `created` 透传。`internal/worker/notify_resolver_test.go` 守的是注册表键集合、`articleIDOf` 的三种情况与 `jumpTarget` 的优先级。

### 8.2 端到端手动验收顺序

沿用 03 章的 `base_url`、`token`、`article_id`。再准备第二个用户 `token_b`，让 `token_b` 点赞 `token` 写的文章。

```powershell
curl.exe -X GET "$env:base_url/api/notifications" `
  -H "Authorization: Bearer $env:token"

curl.exe -X PUT "$env:base_url/api/articles/$env:article_id/like" `
  -H "Authorization: Bearer $env:token_b"
```

按 03 章的约定，PowerShell 示例里的 JSON 要注意引号转义；本章这两个请求没有请求体，不受影响。

| 步 | 动作 | 核对 |
| --- | --- | --- |
| 1 | `token_b` 给文章点赞 | `outbox_events` 多一行 `like.created / pending` |
| 2 | 等 1 秒 | 该行变 `published`，`XLEN forum:events:v1` 增加，`XPENDING` 为空 |
| 3 | 用 `token` 查通知列表 | 能看到一条 `like.created`，`unread_count` 为 1 |
| 4 | 用 `token_b` 评论同一篇文章 | 多一条 `comment.created` |
| 5 | `token` 给自己文章点赞 | 通知数不增加 |
| 6 | 手工把第 1 步的 payload 再 `XADD` 一次 | 通知数仍不增加，`XPENDING` 为空 |
| 7 | `PUT /api/notifications/read-all` | `affected` 等于之前未读数，再查列表 `unread_count` 为 0 |
| 8 | 按 7.4 的方法停 worker 再点赞 | 事件保持 `pending`，重启后自动补齐 |
| 9 | 删掉被点赞的文章后再投一次同类事件 | 日志无异常，消息被 ACK |

第 6 步是幂等的关键证据。用 `redis-cli XRANGE forum:events:v1 - + COUNT 1` 拿到第一条消息的三个字段，再用 `redis-cli XADD forum:events:v1 * event_id <原值> type like.created payload <原 JSON>` 造一条重复消息。

```sql
SELECT event_id, type, article_id, target_type, target_id, is_read FROM notifications ORDER BY id DESC LIMIT 5;
SELECT status, attempts, COUNT(*) FROM outbox_events GROUP BY status, attempts;
```

## 9. 设计决策、边界与面试追问

### 9.1 方案对比

| 决策点 | 选了什么 | 放弃了什么 | 代价 |
| --- | --- | --- | --- |
| 消息落地 | MySQL `outbox_events` | 事务里直接 `XADD` | 多一张表、多一次轮询，换来消息不丢 |
| 消息通道 | Redis Stream 消费组 | Kafka、RabbitMQ、List + BRPOP | 复用已有 Redis，无新中间件；Stream 的持久化和多消费者能力弱于 Kafka |
| 事件内容 | 瘦事件，只带 ID | 胖事件，带标题与昵称 | 消费端多一次回查，换来契约稳定 |
| 投递语义 | 至少一次 | 恰好一次 | 消费端必须幂等 |
| 幂等位置 | `notifications.event_id` 唯一索引 | 内存 SETNX、Redis 去重 | 依赖数据库约束，与通知写入同事务 |
| 崩溃恢复 | 启动时用 `XREADGROUP 0` 重放 PEL | `XAUTOCLAIM`、独立补偿脚本 | 只适用于单机单消费者 |
| 关停 | `signal.NotifyContext` + `WaitGroup` | `r.Run` 阻塞直退 | main 多二十行，换来优雅关闭 |

### 9.2 明确不做

| 未做 | 为什么写在这里 |
| --- | --- |
| Kafka、RabbitMQ、CDC、Debezium | 需要新中间件或 binlog 权限，本机学习环境不具备；简历上要如实说「用 Redis Stream 做的轻量实现」 |
| 多实例 relay 抢占（`FOR UPDATE SKIP LOCKED`）与 `XAUTOCLAIM` | 单机单消费者足够验证语义。多实例会重复投递，靠 `event_id` 幂等兜住，不会写坏数据，但会浪费一次 `GROUP BY` 之外的查询 |
| outbox 表归档、`published` 行清理 | 属于运维策略。表会随事件量持续增长，生产要加定期归档 |
| Stream `MAXLEN` 裁剪 | 裁剪可能丢掉未消费消息，要先有 PEL 监控再决定阈值 |
| 真实推送（WebSocket、邮件、App Push） | 本章只做站内信落库，读接口拉 |
| 通知聚合（「3 人赞了你的文章」） | 需要额外的聚合键与合并窗口 |
| 死信重放界面、投递延迟指标 | 只有日志与 `status` 字段，没有监控面板 |
| 分布式事务、Saga | 项目只有一个 MySQL 实例，用不上 |
| 压测数字 | 没做过压测，不写 QPS 与延迟结论 |

### 9.3 面试追问准备

| 追问 | 应答要点 |
| --- | --- |
| 为什么不用 Kafka | 项目已有 Redis，Stream 提供消费组与 PEL，本机一条 `redis-cli` 就能验；Kafka 要额外部署与运维，学习阶段收益低。要主动补一句它没有 Kafka 的持久化和多订阅者能力 |
| 消息会不会丢 | 事务提交后事件在表里，relay 崩了重启补投；Redis 挂了 `XADD` 失败会重试并留 `pending` |
| 会不会重复 | 会。`XAdd` 成功与改状态之间崩溃会重投，靠 `notifications.event_id` 唯一索引和 `OnConflict DoNothing` 挡住 |
| 「恰好一次」能不能做到 | 跨 MySQL 与 Redis 没有共同提交点，通常说的是至少一次投递加幂等消费，效果等价但机制不同 |
| 为什么 payload 只带 ID | 瘦事件不会因文章改名说谎，relay 不需要理解业务；代价是消费端多查一次 |
| outbox 表一直涨怎么办 | 定期归档 `published` 与 `failed`，归档前确认消费组 PEL 为空。本项目没做 |
| 进程重启后没 ACK 的消息怎么办 | 每轮先用 `XREADGROUP ... 0` 读自己的 PEL，成功才 ACK；多实例要换 `XAUTOCLAIM` |
| 和 04 章热榜懒加载自愈有什么关系 | 都是「恢复动作放在常驻路径」，热榜靠 `ready` 标记让读路径发现，通知靠 outbox 让 relay 发现。热榜修的是 Redis 投影，Outbox 修的是跨存储双写 |
| 为什么 `Block = -1` | go-redis v9 里 `Block >= 0` 才发 `BLOCK`，传 0 会变成无限阻塞。这是读源码得到的版本相关结论 |

最后一条特别适合展示「遇到框架行为会去查依赖源码」，比背概念更能拉开差距。
