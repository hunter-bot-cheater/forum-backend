# 05b · 第 4 周进阶：一致性对账任务（把已知缺陷变成自愈机制）

> 这一章接在 `05a` 之后，和第 3 周的几个进阶专题一样不占周次。
>
> 目标：给系统装一个能定期发现「Redis 里的投影与 MySQL 里的真相不一致」的任务，能修的自己修，修不了的报出来。这件事的价值不在代码量，在于它把 `04` 章自己承认的那个「毫秒级窗口」从「已知缺陷」变成了「有兜底的已知缺陷」。

## 0. 从一个已知缺陷说起

### 0.1 那个毫秒级窗口

`04` 章修热榜重建时，把「Del 后逐条 ZAdd」改成了「写临时 key 再 RENAME」。这个改动解决了两个问题：重建期间不会读到残缺榜单，重建期间的点赞不会被全量覆盖。

但它没有解决全部。`rebuild` 的执行顺序是这样：

```text
1. SELECT article_id, COUNT(*) ... LIMIT 500     <- T1
2. ZADD 到 hot:articles:v1:tmp                    <- T2
3. RENAME tmp -> hot:articles:v1                  <- T3
```

如果一次点赞发生在 T1 与 T3 之间，会发生什么：

```text
T1  读出文章 7 有 100 个赞
T1.5 用户点赞，article_likes 变成 101，syncHotScore 把 ZSET 写成 101
T3  RENAME 换榜，ZSET 里文章 7 的分数变回 100
```

那一次点赞的分数被换榜覆盖了。窗口是毫秒级，但存在。

`syncHotScore` 用了一个很聪明的办法让它自愈：**写绝对值，不写增量**。

```go
// 源码摘录：internal/service/like.go
// syncHotScore 把热度写成分数绝对值。
// count 来自 MySQL，重复调用、Redis 清空、之前算错的分都会在下一次写入时被纠正。
// count 为 0 时直接删掉这一个成员，不做整榜扫描。
//
// 写绝对值还顺带补住了 rebuild 的一个窄缝：重建从 SQL 读完到 RENAME 换榜之间，
// 落在这段间隙里的 ZINCRBY 会被新榜覆盖掉。这段间隙通常是毫秒级，
// 而它造成的偏差会在该文章下一次被点赞时，用 MySQL 的真实计数覆盖回来。
// 如果这里改成 ZINCRBY 增量累加，这条自我修正的路径就断了。
```

所以这类漂移不是永久性的，它会在**下一次有人给这篇文章点赞时**被纠正。

到这里问题出现了：如果那篇文章再也没有人点赞呢？比如它是一篇老爆款，热度已经过去，榜单上还挂着，但没人再点了。那这 1 分的偏差会一直在，直到下一次重建。

### 0.2 三种处理方式

面对这类不一致，工程上有三条路。

| 方式 | 做法 | 成本 | 适用 |
| --- | --- | --- | --- |
| 消除 | 加分布式锁、用 Lua 把 SELECT 与 RENAME 做成原子 | 高，锁本身是新的瓶颈与故障源 | 数据不能有任何偏差时 |
| 容忍 | 承认偏差，靠 TTL 与下次写入自愈 | 低 | 偏差有时限、影响可接受 |
| 自愈 | 定期跑对账，发现并修正 | 中 | 偏差不会自己消失，或消失得太慢 |

项目已经在用第二种：`hotReadyTTL` 1 小时意味着每小时会有一次重建，重建会把所有分数刷成 MySQL 的真值。这是「最终一致」里那个「最终」。

第三种是这一章要加的。理由是：**有一类不一致永远不会自愈**，无论等多久。

### 0.3 一个真实的例子

`DELETE /api/articles/:id` 删掉一篇文章之后，会发生这些事：

```text
1. articles 里那一行没了
2. article_likes 里对它的点赞行，因为外键 RESTRICT，必须被显式删掉才能删文章
3. hot:articles:v1 里它还在，没人会去删它
```

第 3 步为什么没人删：`syncHotScore` 只在点赞、取消点赞时被调用。文章都删了，不会再有人给它点赞，`syncHotScore` 永远不会为它执行。

它就成了榜单里的一个僵尸成员。`loadByIDs` 查不到这篇文章，`byID[id]` 是零值，接口会返回一条标题为空、正文为空、id 还是那个 id 的假文章。

```go
// 源码摘录：internal/service/hot.go
list := make([]HotArticle, 0, len(rows))
for _, r := range rows {
    a := byID[r.ArticleID]
    list = append(list, HotArticle{
        ArticleID: r.ArticleID,
        Score:     float64(r.Score),
        Title:     a.Title,
        LikeCount: r.Score,
    })
}
```

查不到就返回零值，代码没有过滤。这是真实存在的缺陷，而它有一个特点：**等多久都不会消失**。要等 `hotReadyTTL` 到期触发重建，重建时 `article_likes` 里已经没有这些行了，它们才会从榜单上掉下去。

所以对账要处理的第一类问题，就是这种「不会自愈」的不一致。

## 1. 系统里有几份「同一事实」

对账之前先要数清楚：同一件事，系统里存了几份，谁是源头。

### 1.1 点赞数：三份，其中一份是死的

| 副本 | 位置 | 谁写 | 是否可信 |
| --- | --- | --- | --- |
| 明细 | `article_likes` 表 | 点赞、取消点赞的事务 | **事实来源** |
| 投影 | `hot:articles:v1` 的分数 | `syncHotScore` 与 `rebuild` | 派生，可能有偏差 |
| 列 | `articles.like_count` | **没有人写** | 不可信，不要用它对账 |

第三行必须说清楚。`articles` 表里确实有一个 `like_count` 列：

```go
// 源码摘录：internal/model/models.go
LikeCount int64     `gorm:"default:0" json:"like_count"` // 与 Redis 计数最终一致
```

这行注释写着「与 Redis 计数最终一致」，但实际代码里**没有任何地方更新它**。详情接口显示点赞数时，是现算的：

```go
// 源码摘录：internal/service/article.go
// 详情要显示点赞数。articles.like_count 列始终不维护，
// 这里从 article_likes 现算一次，装进内存字段随文章一起写进缓存。
var likeCount int64
if err := s.db.WithContext(ctx).Model(&model.ArticleLike{}).
    Where("article_id = ?", id).Count(&likeCount).Error; err != nil {
    return nil, fmt.Errorf("count article likes %d: %w", id, err)
}
a.LikeCount = likeCount
```

所以这一列永远是 0。如果对账时拿它当基准，会报出「所有文章都不一致」，然后按 0 去写 ZSET，把热榜全清空。

这是一个典型的「注释与代码不一致」的坑。文档里的注释是意图，代码才是事实。

**结论：对账的事实来源只能是 `article_likes` 的 `COUNT(*)`。**

### 1.2 热榜可用性：ready 与 ZSET 的组合

| ready | ZSET | 含义 | 谁负责恢复 |
| --- | --- | --- | --- |
| 无 | 无 | 从没建过 | 下次 `Top` 触发 rebuild |
| 有 | 有 | 正常 | 无 |
| 有 | 无 | 真空榜（一篇点赞都没有）**或投影被删** | 前者正常，后者不会自愈 |
| 无 | 有 | 异常，只可能来自手工操作 | 下次 `Top` 会重建并覆盖 |

第三行是最麻烦的。`Top` 的判断只看 ready：

```go
// 源码摘录（节选，省略了 Redis 报错降级与冷却分支）：internal/service/hot.go
ready, err := s.rdb.Exists(ctx, hotReadyKey).Result() //只要全量重建过一次（哪怕是 0 条数据），
...
if ready == 0 {//如果 ready == 0（说明系统刚启动或 Redis 被清空了），
...
pairs, err := s.rdb.ZRevRangeWithScores(ctx, hotArticlesKey, 0, int64(n-1)).Result()//按分数（Score）从大到小，取出前 N 名，并且带出分数
```

ready 在就直接 `ZREVRANGE`。这时如果 ZSET 被删了，`ZREVRANGE` 返回空切片，不报错，接口返回空榜单。

这个状态会持续到 `hotReadyTTL`（1 小时）到期。原因可能是有人 `DEL hot:articles:v1` 忘了删 ready，也可能是 Redis 内存淘汰只淘汰了 ZSET（它是 ZSet 类型，内存占用比 ready 的 String 大，被淘汰的概率更高）。

这就是第 4.2 节要单独检查「投影丢失」的理由。

### 1.3 事件：outbox 与 Stream

| 副本 | 位置 | 谁写 | 语义 |
| --- | --- | --- | --- |
| 记录 | `outbox_events` 表 | 业务事务 | 状态机：`pending` → `published` / `failed` |
| 消息 | `forum:events:v1` Stream | relay 的 `XADD` | 只追加，不删除（除 `MAXLEN` 裁剪） |

这两者**不要求一致**。Stream 里可能有很多已发布的事件，outbox 里也有很多 published 的记录。对账不比对行数，只看两个滞后指标：

- `pending` 积压量：relay 是不是停了
- `failed` 数量：有没有死信需要人看

注意执行顺序的坑：relay 是「先 XADD 成功，再 UPDATE status」。如果 XADD 成功但 UPDATE 失败，事件会留在 pending，下一轮会**重复投递**。这是设计允许的，消费端的唯一索引 `uk_notify_event` 会挡住重复。

### 1.4 通知：notifications 与事件

| 关系 | 保证方式 | 会不会丢 |
| --- | --- | --- |
| 一条事件最多一条通知 | `uk_notify_event` 唯一索引 | 不会重复 |
| 每条事件都有通知 | 消费成功才 ACK | 可能丢：处理成功但 ACK 前崩溃会重投；ACK 之后进程崩溃不影响 |

对账**查不出丢失的通知**。因为「应该有几条通知」这件事，在 `notifications` 表里看不出来。要查就得拿 `outbox_events` 里所有 `like.created` 与 `comment.created` 去对，那是一次全表关联，成本远大于收益。

所以这一层只做一件事：报告 `failed` 数量。承认它查不到，比假装能查更有价值。

## 2. 哪些不一致会自愈，哪些不会

这张表是整章的核心。写完它，你就知道对账该管什么、不该管什么。

| 不一致 | 会自愈吗 | 靠什么 | 恢复时间 |
| --- | --- | --- | --- |
| 点赞后 ZSET 分数少 1（重建窗口覆盖） | 会 | 下次点赞时 `syncHotScore` 写绝对值 | 不确定，取决于下次点赞 |
| 取消点赞后 ZSET 分数多 1 | 会 | 同上 | 不确定 |
| Redis 被清空，ZSET 全丢 | 会 | ready 缺失，下次 `Top` 触发 rebuild | 下一次请求 |
| ZSET 分数被手工改错 | 会，但慢 | 下次点赞或下次 rebuild | 最多 1 小时 |
| 文章被删，ZSET 留下僵尸成员 | **不会** | 没有代码路径会碰它 | 只能等 rebuild（1 小时后） |
| 文章被删，榜单返回空标题的假文章 | **不会** | 同上，且 `loadByIDs` 不过滤 | 同上 |
| ready 在但 ZSET 被删 | **不会** | `Top` 只看 ready，直接读空 ZSET | 要等 ready 的 TTL 到期 |
| ZSET 里混进非数字成员 | **不会** | 没人会删它，`parse` 直接报错返回 | 永远 |
| outbox 事件进 `failed` | **不会** | relay 只扫 `pending` | 需要人工重放 |
| Stream 里 PEL 堆积 | 部分会 | 进程重启后 `consume(ctx, "0")` 重读 | 下次重启 |
| 通知重复 | 不会重复（幂等），但已重复的不会删 | 唯一索引只能挡新的 | 不会 |
| 通知丢失 | **不会补** | 无从得知丢了几条 | 永远 |

### 2.1 会自愈的那几行，为什么能自愈

共同点是：**写入路径写的是绝对值，而且还有别的写入路径会再碰它一次**。

```text
ZADD hot:articles:v1 <MySQL 的真实 count> <article_id>
```

只要该文章再被点一次赞，分数就被拉回真值。`rebuild` 也是一种「再碰一次」，所以每小时的 TTL 是第二道保险。

### 2.2 不会自愈的那几行，缺的是什么

共同点是：**没有任何代码路径会再碰它**。

僵尸成员缺的是「删除」这个动作。`syncHotScore` 只在 `count == 0` 时 `ZREM`，而 `count == 0` 要求有人对这篇文章取消点赞。文章都删了，没人能取消。

投影丢失缺的是「发现」。`Top` 的逻辑是「ready 在就相信 ZSET」，它没有能力发现 ZSET 不在。

非数字成员缺的是「校验」。`ZRevRangeWithScores` 把 member 当字符串返回，`ParseUint` 失败就报错，但报错不等于清理。

死信缺的是「重放」。`relay` 的 `Where("status = ?", model.OutboxPending)` 永远扫不到 `failed`。

### 2.3 结论

对账的职责边界由这张表划出来：

```text
对账只管「没有代码路径会再碰它」的那些不一致。
会自愈的不用管，管了就是重复劳动；
查不到的（通知丢失）要说清查不到，不要假装能管。
```

这句话可以直接当面试答案。它表明你先想清楚了哪些该管、哪些不该管，然后才动手写代码。

## 3. 对账与重建不是一回事

这两个概念最容易混淆，因为都涉及「让 Redis 与 MySQL 对上」。

| 维度 | 重建 rebuild | 对账 reconcile |
| --- | --- | --- |
| 触发条件 | ready 缺失（首次、Redis 清空、TTL 到期） | 定时任务或人工 |
| 输入 | MySQL 全量点赞聚合（`LIMIT 500`） | Redis 当前榜单的前 N 名 |
| 输出 | 一整份新榜单，RENAME 换上去 | 一份差异报告，加少量点对点修正 |
| 成本 | 一次 `GROUP BY` 加最多 500 条 `ZADD` | 一次 `ZREVRANGE` 加一次带 `IN` 的聚合 |
| 影响面 | 整榜替换，非原子窗口已用 RENAME 消除 | 只改有差异的那几个成员 |
| 解决的问题 | 投影不存在 | 投影在，但值不对，或指向了不该指向的东西 |
| 能替代对方吗 | 不能，重建发现不了僵尸以外的细粒度漂移 | 不能，对账不负责从零构建 |

### 3.1 为什么重建替代不了对账

重建确实能把所有分数刷成真值，看起来对账是多余的。三个理由说明它不是。

1. **重建 1 小时才跑一次**（`hotReadyTTL`）。僵尸成员在这 1 小时里一直挂在榜单上，用户会看到空标题的假文章。
2. **重建有 `LIMIT 500`**。榜单之外的文章就算分数错了，重建也不会修，因为根本不在结果集里。对账也只查前 N，这一点两者一样，但至少对账能及时覆盖前 200。
3. **重建不检查 ready 与 ZSET 的一致性**。它被调用的前提就是「ready 不在」，所以它永远不会发现「ready 在但 ZSET 没了」。

### 3.2 为什么对账替代不了重建

对账的输入是「Redis 当前榜单」，如果 ZSET 已经空了，它没有任何成员可以核对。这种情况下它只能报告 `projection_lost`，然后删掉 ready 让 `Top` 去重建。

也就是说，对账能发现「已经没有榜单了」，但造不出榜单。造榜单是 `rebuild` 的活。

## 4. 设计

### 4.1 检查范围：只查前 N

不做全量对账，理由和 `rebuild` 加 `LIMIT` 是同一个：全量要 `GROUP BY` 整张点赞表。

```go
// 源码摘录：internal/service/reconcile.go
// reconcileTopN 是单次对账默认检查的榜单深度。
// 不做全量对账：全量要 GROUP BY 整张点赞表，成本问题已经在 hot.go 的 rebuild 注释里论证过。
// 榜单之外的文章即使漂移也影响不到接口输出，等它们真上榜时 rebuild 会给一次正确值。
const reconcileTopN = 200
```

取 200 而不是 100，是因为对外接口最多返回 100 条，留一倍余量覆盖「第 100 名附近刚换位」的情况。

### 4.2 四道检查

| 检查 | 怎么做 | 发现什么 |
| --- | --- | --- |
| 投影丢失 | `ZCARD` 加 `EXISTS ready`，ZSET 为空时再查总点赞数 | ready 在但榜单空了 |
| 分数漂移 | `ZREVRANGE` 取前 N，`WHERE id IN (...)` 聚合 MySQL 计数，逐个比 | 分数错，或真实计数已归零 |
| 僵尸成员 | `SELECT id FROM articles WHERE id IN (...)`，不在结果集里的就是僵尸 | 文章已删，榜单还留着 |
| 消息积压 | `COUNT(outbox WHERE status)` 加 `XLEN` 加 `XPENDING` | relay 停摆、死信、PEL 堆积 |

四道检查全部只读，跑完不改变系统状态。这是 dry-run 模式能存在的前提。

### 4.3 报告是快照，不是状态机

`ReconcileReport` 只在 `Check` 期间填充，之后不再变化。`Fix` 读它决定改哪里，改完不修改它。

这样做的好处是：报告可以序列化成 JSON 存档，事后能查「那天发现了什么、修了什么」。如果用状态机边查边改，存档里就只剩一个「修了多少个」的数字，没有证据。

### 4.4 修正三原则

**第一，写绝对值，不写增量。**

```go
// 源码摘录：internal/service/reconcile.go
// Fix 按报告修正热榜。返回修正的成员数。
// 所有写入都是绝对值或删除，没有增量：增量会把已有的误差继续放大。
// 幂等，连跑两次第二次的 Drifts 应该为空。
```

如果修正写成 `ZINCRBY`（把差值加上去），那就等于假设「当前 Redis 的值除了这个差值之外都是对的」。这个假设在连续两次对账之间是不成立的。

**第二，先删后改。**

```go
// 源码摘录：internal/service/reconcile.go
// 先清僵尸，再改分数。僵尸的分数没有意义，改完还得再删一次。
```

**第三，真实计数为 0 时删成员，不写 0。**

```go
// 源码摘录：internal/service/reconcile.go
if d.InMySQL <= 0 {
    // 真实点赞已经归零，成员留着会让榜单出现一个 0 分的空壳。
    if err := r.rdb.ZRem(ctx, hotArticlesKey, member).Err(); err != nil {
```

写成 0 的后果是：`ZREVRANGE 0 99` 仍然会取到它（只要 ZSET 成员数少于 100），接口会返回一条点赞数为 0 的文章。删掉才对。

### 4.5 「发现」与「修复」分离

`Check` 与 `Fix` 是两个方法，CLI 默认只调第一个。

```bash
go run ./cmd/reconcile              # 只报告，退出码说明有没有问题
go run ./cmd/reconcile -fix         # 报告并修正，修完自动复查
```

这个设计不是洁癖。对账跑在生产上时，第一版应该是纯观察模式：先跑一周，看看到底有多少漂移、都是什么类型，再决定要不要自动修。

直接上自动修的风险是：如果 `diffHot` 的判定逻辑有 bug，它每小时都会主动把正确的数据改错，而且改得很规律，很难发现。

### 4.6 并发窗口

`Check` 与 `Fix` 之间不是原子的。假设检查完报告、还没开始修，这时有人给文章 7 点了赞：

```text
Check  报告里写：文章 7，Redis 100，MySQL 100（一致，不修）
点赞   article_likes 变成 101，syncHotScore 写 ZSET 101
Fix    报告里没有文章 7，不动它         <- 正确，这次没问题
```

再看一种：

```text
Check  报告里写：文章 9，Redis 50，MySQL 51（漂移，要修）
点赞   article_likes 变成 52，syncHotScore 写 ZSET 52
Fix    按报告写 ZSET 51                <- 覆盖掉了刚写的 52
```

第二次点赞被覆盖了。这个窗口从 `Check` 结束到 `Fix` 执行，取决于中间做了什么。CLI 里已经把 JSON 打印挪到 `Fix` 之后，就是为了缩短它：

```go
// 源码摘录：cmd/reconcile/main.go
// 开修时先动手、后打印。Check 到 Fix 之间是覆盖窗口：
// 这期间有人点赞，写回的就是旧计数。打印 JSON 要几毫秒到几百毫秒，
// 把它挪到后面，窗口缩到只剩两条 Redis 命令的间隔。
```

即使这样，窗口仍然存在（毫秒级）。接受它的理由和 `rebuild` 一样：下一次点赞会自愈，下一轮对账也会修回来。**对账是收敛型任务，不追求瞬时精确。**

如果要求更强，只有两条路：给单篇文章加锁（成本高于收益），或者用 Lua 把「读 MySQL 计数」与「写 ZSET」做成一个原子脚本（Redis 脚本里不能查 MySQL，做不到）。所以只能接受。

### 5.2 报告结构

```go
// 源码摘录：internal/service/reconcile.go

	ReadyMissing bool  `json:"ready_missing"`

	// 这是最危险的一种不一致：Top 看到 ready 就跳过重建，直接读一个空 ZSET，
```

### 5.3 Check 的主线

```go
// 源码摘录：internal/service/reconcile.go
pairs, err := r.rdb.ZRevRangeWithScores(ctx, hotArticlesKey, 0, int64(topN-1)).Result()
...
// 保持 Redis 返回的顺序，后面 diffHot 才能输出稳定的报告，
// 测试与人工比对都不用再排序。
ids := make([]uint, 0, len(pairs))
redisCounts := make(map[uint]int64, len(pairs))
for _, p := range pairs {
    member, ok := p.Member.(string)
    ...
}
rep.Checked = len(ids)

mysqlCounts, err := r.countLikes(ctx, ids)
alive, err := r.aliveArticles(ctx, ids)

rep.Drifts, rep.Zombies = diffHot(ids, redisCounts, mysqlCounts, alive)
```

`ZRevRangeWithScores` 返回的顺序就是榜单顺序（分数从高到低，同分按 member 字典序），保留它可以让报告直接对着榜单看。

`countLikes` 用一次带 `IN` 的 `GROUP BY`：

```go
// 源码摘录：internal/service/reconcile.go
// countLikes 用一次带 IN 的 GROUP BY 拿回这批文章的真实点赞数。
// IN 走了 uk_article_user 的最左前缀，所以每条只扫自己那段索引。
```

`article_likes` 上的 `uk_article_user(article_id, user_id)` 联合唯一索引，最左前缀是 `article_id`，所以 `WHERE article_id IN (...)` 能走索引，每组只扫自己那一段。这一点和 `rebuild` 的全表 `GROUP BY` 完全不同，成本低一个数量级。

### 5.5 projectionLost 这个判定的来历

写第一版时，判定条件是「ready 在 且 ZSET 空」。写完回头看 `rebuild` 的空结果分支，发现这个条件是错的：

```go
// 源码摘录：internal/service/hot.go
} else {
    // 一条点赞都没有时临时 key 不存在，RENAME 会报 key 不存在。
    // 空榜本来就该是空，直接删正式 key。
    pipe.Del(ctx, hotArticlesKey)
}
// rows 为空也要写标记。否则 ZSET 依然不存在，
// 空榜的每个请求都会重新走到这里。
pipe.Set(ctx, hotReadyKey, "1", hotReadyTTL) //把设置 ready 标志位的命令也塞进管道
```

**一篇文章都没被点赞时，rebuild 就是「删 ZSET + 写 ready」。** 这个合法状态和「ZSET 被误删」在 Redis 侧完全一样。

所以必须问 MySQL：

```go
// 源码摘录：internal/service/reconcile.go
// ZSET 为空时多查一次总点赞数，用来区分「真空榜」与「投影被删」。
// 只在罕见分支上付出这次 COUNT 的成本，正常压测与线上稳态都不会走到。
if rep.ZSetSize == 0 && !rep.ReadyMissing {
    var totalLikes int64
    err := r.db.WithContext(ctx).Model(&model.ArticleLike{}).Count(&totalLikes).Error
    ...
}
```

这个教训值得单独记一笔：**「A 状态看起来像故障」这件事，必须回到所有写入 A 状态的代码路径去验证，不能凭直觉。**

### 5.6 Fix 的边界

```go
// 源码摘录：internal/service/reconcile.go
// 投影整体丢失时，删掉 ready 标记就够了：下一次 Top 发现 ready 不在，
// 会自己走一次 rebuild 把榜单补回来。
// 不在这里调 rebuild，因为那是 HotService 的私有逻辑，
// 对账只负责指出问题、清掉挡路的标记，不越界替别人做重建。
if rep.ProjectionLost {
    if err := r.rdb.Del(ctx, hotReadyKey).Err(); err != nil {
        return fixed, fmt.Errorf("clear stale ready marker: %w", err)
    }
    fixed++
}
```

不调 `rebuild` 有三个原因：

1. 它是 `HotService` 的私有方法，`Reconciler` 跨对象调用私有逻辑，耦合会变差。
2. 重建是重操作，不该由对账任务触发。删掉 ready 之后，让真实流量的第一个请求去触发，重建用的是请求的上下文与超时，链路更正常。
3. 如果对账自己重建，那它就变成了「定时全量重建」，成本从「一次 ZREVRANGE」涨到「一次 GROUP BY」，失去了轻量的优点。

### 5.7 CLI 与退出码

```bash
# 只报告。有漂移时退出码 1，干净时 0，连不上库是 2
go run ./cmd/reconcile -top 200

# 报告并修正，修完自动复查
go run ./cmd/reconcile -top 200 -fix

# 加超时，防止库慢时任务挂住
go run ./cmd/reconcile -top 200 -timeout 10s
```

退出码是给自动化用的：

| 码 | 含义 | 定时任务该怎么反应 |
| --- | --- | --- |
| 0 | 一致，或修完已收敛 | 什么都不做 |
| 1 | 发现漂移、僵尸、投影丢失、死信 | 发通知，或看下一轮是否还在 |
| 2 | 运行失败 | 告警，这是任务本身坏了 |

区分 1 与 2 很重要。1 是「系统有问题但任务正常」，2 是「任务坏了」，两者的处理人可能不同。

## 6. 怎么证明它真的有效

这一节全部是手工操作，跑在自己的库上。**以下预期输出是推演的结构，你的 id 与分数会不同。**

先把服务起起来，触发一次重建，让榜单存在：

```bash
# 终端一
go run ./cmd/server > server.log 2>&1

# 终端二
curl -s "http://127.0.0.1:8080/api/articles/hot?limit=10"
redis-cli -a 123456 ZCARD hot:articles:v1
```

### 6.1 手法一：改错分数

```bash
# 把文章 1 的分数改成 9999，真实值肯定不是
redis-cli -a 123456 ZADD hot:articles:v1 9999 1

# 对账
go run ./cmd/reconcile -top 50
```

预期输出（结构）：

```json
{
  "checked_at": "2026-11-12T22:10:03+08:00",
  "top_n": 50,
  "zset_size": 37,
  "checked": 37,
  "ready_missing": false,
  "projection_lost": false,
  "drifts": [
    { "article_id": 1, "in_redis": 9999, "in_mysql": 12 }
  ],
  "zombies": [],
  "outbox_pending": 0,
  "outbox_failed": 0,
  "stream_len": 0,
  "stream_pending": 0
}
checked=37 drift=1 zombie=0 ready_missing=false projection_lost=false pending=0 failed=0 stream_len=0 stream_pending=0
```

退出码 1。这时候加 `-fix`：

```bash
go run ./cmd/reconcile -top 50 -fix
```

预期末尾：

```text
fixed=1
after fix: checked=37 drift=0 zombie=0 ... 
```

`after fix` 那行是复查结果，`drift=0` 说明收敛了。这一步很关键，它证明了 `Fix` 的写入是对的。

### 6.2 手法二：造僵尸成员

```bash
# 999999 这个文章不存在
redis-cli -a 123456 ZADD hot:articles:v1 5 999999

go run ./cmd/reconcile -top 50
```

预期：

```text
zombies: [999999]
```

修复后 `ZREM` 会把它删掉。

顺带可以验证这个僵尸真的会影响接口：访问热榜接口，会看到一条 `article_id` 为 999999、`title` 为空字符串的条目。这是 `loadByIDs` 不过滤的后果。

### 6.3 手法三：删 MySQL 的点赞，不动 Redis

```sql
-- 先记下文章 1 真实的点赞数
SELECT COUNT(*) FROM article_likes WHERE article_id = 1;
-- 假设是 12
```

```bash
redis-cli -a 123456 ZSCORE hot:articles:v1 1
# 应该是 12
```

```sql
-- 删掉一半
DELETE FROM article_likes WHERE article_id = 1 LIMIT 6;
```

这时 Redis 还是 12，MySQL 变成 6。对账会报 `in_redis: 12, in_mysql: 6`。

这条手法测的是 `Fix` 的 `ZAdd` 分支（写绝对值）。

再删干净：

```sql
DELETE FROM article_likes WHERE article_id = 1;
```

对账会报 `in_redis: 6, in_mysql: 0`。`Fix` 走 `ZRem` 分支。修复后确认：

```bash
redis-cli -a 123456 ZSCORE hot:articles:v1 1
# (nil)，成员已删
```

### 6.4 手法四：制造投影丢失

这是最值得测的一条，因为它对应一个 `Top` 自己修不好的故障。

```bash
# 只删 ZSET，保留 ready
redis-cli -a 123456 DEL hot:articles:v1
redis-cli -a 123456 EXISTS hot:articles:v1:ready
# 返回 1，标记还在

# 这时访问热榜接口，会返回空数组，而且不会触发重建
curl -s "http://127.0.0.1:8080/api/articles/hot?limit=10"
```

对账应该报出来：

```json
{
  "zset_size": 0,
  "checked": 0,
  "ready_missing": false,
  "projection_lost": true,
  "drifts": [],
  "zombies": []
}
```

注意 `checked` 是 0，`drifts` 是空的。如果只检查漂移，这个故障完全看不见。这就是 `projection_lost` 这个字段存在的理由。

修复会删掉 ready：

```bash
go run ./cmd/reconcile -top 50 -fix
redis-cli -a 123456 EXISTS hot:articles:v1:ready
# 返回 0

# 再访问热榜，Top 发现 ready 不在，触发重建
curl -s "http://127.0.0.1:8080/api/articles/hot?limit=10"
redis-cli -a 123456 ZCARD hot:articles:v1
# 恢复了
```

### 6.5 收敛验证

所有手法试完后，连跑两次：

```bash
go run ./cmd/reconcile -top 200
go run ./cmd/reconcile -top 200
```

两次的 `drift` 与 `zombie` 都应该是 0。如果有残留，说明 `Fix` 漏了分支，或者有并发写入在持续制造漂移。

### 7.2 Linux cron

```bash

*/30 * * * * cd /path/to/forum-backend && ./bin/reconcile -top 200 -fix >> reconcile.log 2>&1
```

### 7.3 什么时候不能自动修

| 情况 | 能不能自动修 | 原因 |
| --- | --- | --- |
| 分数漂移 | 能 | 真值来自 MySQL，写入幂等 |
| 僵尸成员 | 能 | 文章确实不存在，删除无损 |
| 投影丢失 | 能 | 只删 ready，重建由 `Top` 触发 |
| outbox `failed` | **不能** | 死信可能是永久失败（比如 payload 格式错误），自动重放会无限循环打爆消费端 |
| 通知缺失 | **不能** | 无从得知丢了什么 |

当前 `Fix` 只处理前三类，后两类只报告。这个边界要在代码里守住，也要能在面试里讲出来。

### 7.4 清理历史

`outbox_events` 里 `published` 的行会一直增长。这份对账不负责清理，但可以顺手加一个：

```sql
-- 只保留 7 天，避免表无限增长
DELETE FROM outbox_events
WHERE status = 'published' AND created_at < DATE_SUB(NOW(), INTERVAL 7 DAY)
LIMIT 1000;
```

用 `LIMIT` 分批删，一次删太多会长时间持锁。这件事和对账放在同一个定时任务里跑，但要分开记录结果，不要让清理失败影响对账的退出码。

## 8. 指标与告警

### 8.1 该盯的四个数

| 指标 | 正常值 | 超过就说明 |
| --- | --- | --- |
| `drift` | 0 | 有写入路径在制造偏差，或者 `Fix` 没生效 |
| `zombie` | 0 | 文章删除时没清榜单，需要检查 `ArticleService.Delete` |
| `projection_lost` | false | ZSET 被误删或内存淘汰，检查 `maxmemory-policy` |
| `outbox_failed` | 0 | 有死信，需要人工看 payload |

`pending` 与 `stream_pending` 短时间不为 0 是正常的在途量，不要拿它告警。这一点写在 `HasProblem` 的注释里：

```go
// 源码摘录：internal/service/reconcile.go
// pending 与 stream_pending 是滞后指标，短时间不为 0 属于正常在途。
```

### 8.2 阈值怎么定

不要设「> 0 就告警」。第一次上线时先跑一周只报告模式，看看噪音水平。

可能的情况：如果你在压测，点赞密集，`pending` 会有几十条在途，但对账每 30 分钟跑一次，撞上的概率不低。这时候「> 0 告警」会天天响，人就不看了。

经验值：

| 指标 | 告警阈值 | 依据 |
| --- | --- | --- |
| `drift` | 连续 2 轮大于 0 | 单轮可能是并发窗口造成的瞬间值 |
| `zombie` | 大于 0 | 僵尸不会自己出现又消失，出现就是有问题 |
| `projection_lost` | 立即 | 接口正在返回空榜 |
| `outbox_failed` | 大于 0 | 死信不会自愈 |
| `pending` | 大于 1000 且持续 10 分钟 | 对应 relay 停摆，500 条/秒乘以 2 秒的余量 |

### 8.3 为什么不用「不一致率」

`drift / checked` 看起来更直观，但它会掩盖严重程度。200 条里漂移 1 条是 0.5%，听起来很小；如果那一条正好是榜首，用户第一眼就看到错的数据。

对账报的是「哪几条错了」，不是「错了百分之几」。这个区别要讲清楚。

## 9. 面试怎么讲

### 9.1 90 秒版本

> 我的热榜是 Redis ZSET 投影，事实来源是 MySQL 的点赞明细。写入侧用绝对值而不是增量，所以大部分漂移会在下一次点赞时自愈。
>
> 但有一类不会自愈：文章被删之后，榜单里的成员没有任何代码路径会去碰它，会一直挂在榜上返回空标题。所以我加了一个对账任务，取榜单前 200 名，用一次带 IN 的聚合查真实计数，逐个比对，同时检查成员指向的文章是否还在。发现三类问题：分数漂移、僵尸成员、以及 ready 标记还在但 ZSET 被删的情况。
>
> 默认只报告不改数据，加参数才修。修完自动复查一次，确认收敛。差异判定抽成了纯函数，有十个单测，因为这段逻辑一旦错会主动改坏正确数据。

### 9.2 追问与回答

| 追问 | 回答要点 |
| --- | --- |
| 为什么不直接全量重建 | 重建是 `GROUP BY` 整张表加 500 条 `ZADD`，一小时一次的固定成本；对账只查前 200，是 `IN` 聚合，轻一个数量级。两者解决的不是同一个问题 |
| 对账为什么不全量 | 榜单之外的文章漂移影响不到接口输出，等它真上榜时重建会给一次正确值。全量的成本收益不划算 |
| 检查与修复之间有人写入怎么办 | 承认有毫秒级窗口，写回会覆盖。靠三个兜底：下次点赞的自愈、下一轮对账、每小时的重建。对账是收敛型任务，不追求瞬时精确 |
| 怎么区分「空榜」和「榜单丢了」 | 这是最容易写错的地方。rebuild 在空结果时就是「删 ZSET + 写 ready」，所以两者在 Redis 侧一样。必须查 MySQL 的总点赞数才能区分 |
| 为什么删 ready 而不直接重建 | 重建是 `HotService` 的私有逻辑；删掉标记让真实流量触发，用的是请求自己的上下文与超时，链路更正常 |
| 死信为什么不自动重放 | 死信可能是永久失败，自动重放会无限循环。只报告，人工看 payload 决定 |
| 你怎么知道对账本身没写错 | 判定逻辑是纯函数，十个单测覆盖六种漂移形态；`Fix` 只写绝对值，天然幂等；跑完自动复查，第二次必须干净 |

最后一条最关键。面试官问「你怎么保证修数据的代码不会把数据改坏」，这个问题比「你怎么实现对账」更能区分人。

### 9.3 不要说的三句话

| 不要说 | 原因 |
| --- | --- |
| 用定时任务保证 Redis 与 MySQL 强一致 | 对账给的是最终一致，说强一致会被立刻追问「窗口内不一致怎么办」 |
| 对账能修复所有不一致 | 通知丢失它就修不了，说了就是过度承诺 |
| 用了分布式锁保证对账原子性 | 当前没有，说有就是编 |

## 10. 与 04 章热榜四次返工的呼应

`04` 章记录了热榜的四次改写：从「每次读都 `GROUP BY`」到「ZSET 投影」，从「Del 后逐条 ZADD」到「临时 key 加 RENAME」，从「ready 永不过期」到「TTL 1 小时」，从「无冷却」到「失败退避」。

每一次都是被一个具体问题推着改的。对账是这个系列的第五次。

前四次改的是**写入路径**：让它更快、更原子、更新鲜。第五次改的是**验收路径**：承认写入路径不可能覆盖所有情况，所以加一个独立的眼睛。

这个递进关系本身就是面试素材。它说明你对「一致性」的理解分了三层：

```text
第一层  让写入路径尽量不产生偏差（绝对值、RENAME、事务）
第二层  让偏差有时限（TTL、重建）
第三层  承认前两层都有漏网，用独立任务补（对账）
```

大部分人的项目停在第一层。

## 11. 坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 拿 `articles.like_count` 当基准 | 报出「所有文章都不一致」，`Fix` 会把榜单清空 | 这一列从不维护，只能用 `article_likes` 的 `COUNT(*)` |
| 把「空榜」当「投影丢失」 | 每小时多一次无谓重建，日志里 `projection_lost=true` 反复出现 | 必须查 MySQL 总点赞数，见 5.5 |
| 修正写成 `ZINCRBY` | 漂移不收敛，越修越大 | 永远写绝对值 |
| 真值归零时写 0 而不是删成员 | 榜单出现点赞数为 0 的条目 | `ZRem` |
| 巡查顺序反了（先改分数再删僵尸） | 僵尸被改完又删，多做一次写 | 先删后改 |
| 对账直接上自动修复 | 判定逻辑有 bug 时，每 30 分钟主动改坏数据 | 先跑一周只报告 |
| 对账任务和压测同时跑 | 压测的密集点赞让 `pending` 很高，误告警 | 压测窗口内不跑对账，或只看热榜部分 |
| 用 `XINFO GROUPS` 不存在时直接报错 | 服务没起过时对账失败，退出码 2 | 按 0 处理，见 5.3 的 `XInfoGroups` 判断 |
| 定时任务里用相对路径 | 计划任务的工作目录不是你想象的那个，配置读不到 | 用绝对路径，或先 `cd` |
| 忘记清理 outbox | 表涨到百万行，relay 的 `WHERE status='pending'` 扫描变慢 | 按 7.4 分批删 published |
