# 01 · 项目介绍与技术栈

> 这是整套学习文档的第一份。读完你会知道项目是什么、为什么这样组织代码、从哪个文件开始读、机器上要装什么。

## 一、这是什么项目

一个用于练习 Go 后端开发的社区论坛项目，计划包含用户注册登录、文章、评论、点赞和热榜。

**先区分「计划功能」和「已完成代码」**。当前仓库已接通配置、MySQL、注册与登录、JWT、路由，以及文章与评论的读写 handler 与 service。Redis 客户端初始化、文章详情 Cache Aside 与 03a 章的缓存工程化加固都已落地；点赞、热榜、限流按 04 章十步跟做逐步落盘，源码状态以工作树为准（第 10 步会让文章详情显示点赞数并补写路径缓存失效）。功能状态以 `internal/router/router.go` 里实际注册的路由、对应实现和验收结果为准。文件存在不等于接口可用，端到端验收还没跑过的内容也不能写进简历。

## 二、为什么选这个项目

| 你已有的基础 | 这个项目里怎么用到 |
| --- | --- |
| 会用 Gin | 路由、中间件（鉴权、限流、日志）都会跑到 |
| 学过 GORM 与 MySQL | 三张表的建模、关联查询、分页 |
| 用过 Redis，没系统学 | 热点缓存、缓存三大问题、点赞计数、接口限流 |

论坛项目自带评论、点赞、热度排行，这些功能天然需要思考并发和数据一致性，面试可讲的点比单用户博客多。代价是业务规则更复杂，学习时要按 00 章的跟做闭环一次只做一个垂直切片。

## 三、技术栈清单

以仓库 `go.mod` 和实际代码为准：

| 类别 | 选择 | 说明 |
| --- | --- | --- |
| 语言 | Go 1.26.0（`go.mod`），本机实测 1.27.3 | 低版本可能无法构建，先跑 `go version` |
| Web 框架 | Gin v1.12.0 | 路由、中间件、参数绑定 |
| ORM 与数据库 | GORM v1.31.2、MySQL 8.x | 模型、迁移、关联查询 |
| 缓存 | go-redis v9.23.0 | `go.mod` 已含该依赖，客户端初始化函数已存在 |
| 鉴权 | golang-jwt/jwt v5 | 签发与校验 access token |
| 密码哈希 | golang.org/x/crypto/bcrypt | 只存哈希 |
| 配置读取 | Viper v1.21.0 | YAML 加环境变量覆盖 |
| 部署练习 | 本机 MySQL 与 Redis | 学习阶段不引入 Docker |
| 测试 | 标准库 testing 与 net/http/httptest | 仓库已有 `pkg/jwt/jwt_test.go` |

机器上要提前装好的环境：

1. **Go**。从 https://go.dev/dl/ 安装，命令行里 `go version` 能输出版本号即可。
2. **MySQL**。安装 Community Server，记下 root 密码与端口，默认 3306。
3. **Redis**。开始第 2 周练习时再准备。Windows 环境可用 WSL2 中的 Linux Redis，或选择受维护且兼容 go-redis 的服务，安装方式和网络地址按所选环境确认。
4. **编辑器**。VS Code 加 Go 插件。
5. **接口测试工具**。Postman 或 curl。

> 启动服务前必须先准备 MySQL。`cmd/server/main.go` 会读配置、调用 `config.InitDB` 连接数据库并执行 `AutoMigrate`，连不上就直接退出。当前 router 没有注册 `/ping`，已注册的是注册登录、文章与评论的读写路由，以 `internal/router/router.go` 为准。四个写接口都已在仓库源码实现：文章见 03 章 6.6，评论见 03 章 6.7，service 与 handler 的方法名统一口径见 03 章 1.2。`main.go` 已调用 `config.InitRedis`，Redis 连不上会直接退出，启动前要先起 Redis；三层装配见 03 章 7.2。旧版 01 章写「第一阶段只需 Go 即可启动 /ping」，与入口代码冲突，已删除。若 Redis 在 WSL2 中运行，Windows 里的 Go 程序也必须能连到它。配置文件在项目根目录下的 `config/config.yaml`。

## 四、分层架构：请求走过哪些代码

```text
请求 → router(路由) → middleware(中间件) → handler(控制器)
        → service(业务逻辑) → repository(数据访问，目标) → MySQL / Redis
```

| 层 | 职责 | 本仓库对应文件 | 认识什么 |
| --- | --- | --- | --- |
| router | 把 URL 映射到 handler，挂中间件 | `internal/router/router.go` | HTTP 路径、handler 指针 |
| middleware | 每个请求进来先过一遍 | `internal/middleware/jwt.go` | Authorization 请求头、JWT |
| handler | 收参数、调 service、返回 JSON | `internal/handler/user.go` | `gin.Context`、请求体、状态码 |
| handler 的响应契约 | 定义客户端能看见哪些字段 | `internal/handler/dto.go` | 响应结构体、model 到 DTO 的转换 |
| service | 业务规则 | `internal/service/user.go`、`article.go` | 输入校验、错误类型、GORM |
| repository | 读写 MySQL 与 Redis | `internal/repository/user.go`（当前空壳） | SQL、Redis 命令 |
| model | 定义表结构 | `internal/model/models.go` | 字段、tag、索引 |

**为什么这样分层（面试常问）**。改数据库不影响业务规则，改 JSON 字段不影响 SQL。service 可以脱离 HTTP 单独测试。每层只做一件事，排查问题时能快速定位到某一层。代价是文件数量变多，写一个小接口也要碰好几个文件。学习阶段值得付这个成本。

响应结构体单独放 `dto.go`，仍属于 handler 包。判断依据是依赖方向，当前只有 handler 一层需要这些类型。单独新建 `internal/dto` 会按「这是什么种类的类型」命名，Go 官方点名反对 `api`、`types`、`interfaces` 这类不表达职责的泛化包 [来源: https://go.dev/blog/package-names]。详细取舍见 02 章 8.0。

**也要看到反面**。Microsoft Learn 在 N-tier 架构的 Challenges 里写道，中间层若只做基础 CRUD，会增加延迟和复杂度却没有带来多少价值 [来源: https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/n-tier]。本项目坚持分层，主要价值在教学可迁移性，以及后续加入缓存、事务、测试时的隔离边界，当前规模下没有性能收益。分层属于架构惯例，Gin 与 GORM 都不强制这样组织，Gin 官方 Quickstart 就是一个单文件 main.go [来源: https://gin-gonic.com/en/docs/quickstart/]。Go 官方明文规定的是 Context 作为第一个参数传递，「每层都传 ctx」在 Gin 侧的具体写法属于工程惯例 [来源: https://go.dev/wiki/CodeReviewComments]。

**一个历史遗留的解释**。旧版 README 与 01 章写过「当前只有 /ping 接口」。`/ping` 来自 Gin 官方 Quickstart 的示例代码 [来源: https://gin-gonic.com/en/docs/quickstart/]，本项目 router 从未注册它。照抄教程示例却没同步实现，是学习文档最常见的失真来源之一。

**当前状态要诚实**：`internal/service/user.go` 直接持有 `*gorm.DB`，repository 层还没有成形。分层图在这套文档里同时表达「当前结构」和「目标结构」，别把目标当成已完成。

当前用户链路已经把 `context.Context` 从 `c.Request.Context()` 传到 `WithContext(ctx)`，请求取消时数据库查询跟着取消。文章链路的 `internal/service/article.go` 与 `comment.go` 也已经传了 ctx，这一项不需要再补。当前缺的是 handler 与 router 接线，按 03 章第 6 节贯通。Go 官方建议把 Context 作为函数第一个参数显式传递 [来源: https://go.dev/wiki/CodeReviewComments]。

## 五、从哪个文件夹开始学

编码顺序按依赖关系自底向上，阅读顺序可以反过来，先看入口再往下追。

| 顺序 | 文件夹 | 学什么 | 什么时候写 |
| --- | --- | --- | --- |
| 1 | `cmd/server/main.go` | 程序入口，先看它 | 第 1 周第 1 步 |
| 2 | `pkg/response` | 统一响应格式 | 第 1 周 |
| 3 | `internal/config` | Viper 配置加载与数据库初始化 | 第 1 周 |
| 4 | `internal/model` | GORM 模型与建表 | 第 1 周 |
| 5 | `internal/repository` | 数据访问层 | 第 1 周起逐步补 |
| 6 | `internal/service` | 业务规则 | 第 1 周起 |
| 7 | `internal/handler` | HTTP 层 | 第 1 周起 |
| 8 | `internal/middleware` | JWT 鉴权 | 第 1 周 |
| 9 | `internal/router` | 路由组装 | 第 1 周末 |
| 10 | 回改 `cmd/server/main.go` | 把依赖接进入口 | 每个新依赖加入时 |

记忆口诀：`pkg` 与 `config` 最底层，依次向上是 `model`、`repository`、`service`、`handler`、`middleware`、`router`、`main`。

每段代码都标明属于完整文件、增量修改或概念伪代码。动手前先确认输入文件和目标状态，完成后执行该节列出的命令与验收请求。**若示例与仓库实际代码冲突，以仓库源码为准**，先看 `go build ./...` 与 `go test ./...` 的实际结果，再把文档里的旧签名同步过来。旧版 03 章出现过文档写 `List` 返回 `[]model.Article`、仓库写 `ListArticles` 返回 `[]*model.Article` 的签名冲突；本轮已把仓库方法统一成 `ArticleService.List`（见 03 章 1.2），这类问题按此规则修正。
