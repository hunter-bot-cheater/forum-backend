# 11. 日常运维速查

部署流程在 `docs/10`，这一份只放「上线之后每天会敲的命令」：怎么看日志、怎么重启、怎么发版回退、怎么查数据库、磁盘满了怎么办。

所有命令默认在 `/opt/forum` 下执行，并且 `~/.bashrc` 里已经有这三段 `COMPOSE_FILE`：

```bash
export COMPOSE_FILE=/opt/forum/docker-compose.yml:/opt/forum/deploy/prod/docker-compose.prod.yml:/opt/forum/deploy/prod/docker-compose.artifact.yml
```

没设的话，`docker compose` 只认两份文件，`context` 会指回源码目录，`build` 又会去编译，2G 机器直接卡死。登录后先确认：

```bash
echo "$COMPOSE_FILE"
```

服务名一共五个：`mysql`、`redis`、`migrate`、`api`、`web`。`migrate` 是一次性容器，跑完就退出，不需要一直活着。

## 11.1 每次登录先看一眼

四条命令，十秒能跑完，能提前发现八成的故障：

```bash
cd /opt/forum
docker compose ps
curl -sS -o /dev/null -w '%{http_code}\n' https://jiushixixi.xyz/readyz
df -h / && free -h
```

探活必须走 `https://` 加域名。站点启用证书后，80 端口的 server 块只剩 `/.well-known/acme-challenge/`，
其余请求一律 `return 301 https://$host$request_uri`，所以 `curl http://127.0.0.1/readyz` 拿到的是 301，
看起来像故障，其实只是被跳转了。

怎么看结果：

- `docker compose ps` 里 `api`、`web`、`mysql`、`redis` 的 `STATUS` 要是 `Up`，mysql 还应该带 `(healthy)`。出现 `Restarting` 说明进程起来就崩，直接看日志。
- `readyz` 返回 `200`。返回 `301` 是打到了 80 端口，换成 `https://` 再试。返回 `000` 是没连上，`502` 是 Nginx 通了但后端没起。

想区分「后端挂了」和「Nginx 挂了」，绕开 Nginx 直接问容器：

```bash
docker compose exec -T api wget -qO- http://127.0.0.1:8080/readyz
```

容器内直连 api 的 8080 是明文 HTTP，这里用 `http://` 是对的，301 只发生在宿主机的 80 端口上。
- `df -h /` 的 `Use%` 超过 80% 要处理，Docker 的构建缓存很能吃盘。
- `free -h` 看 `available`。这台是 2G，`available` 长期低于 200M 时 MySQL 会被 OOM 杀掉。

## 11.2 看日志

### 应用日志

应用日志是 JSON，直接打到标准输出，由 Docker 的 json-file 驱动收走。每条长这样：

```json
{"time":"2026-11-18T01:02:03.456+08:00","level":"INFO","msg":"request","request_id":"...","method":"GET","path":"/api/articles","status":200,"cost_ms":3}
```

常用命令：

```bash
# 实时跟，Ctrl+C 退出
docker compose logs -f api

# 最近 100 行，排查时先看这个
docker compose logs --tail=100 api

# 最近半小时（支持 10s / 5m / 2h / 2026-11-18T01:00:00）
docker compose logs --since 30m api

# 只看错误
docker compose logs --since 2h api | grep '"level":"ERROR"'

# 只看某次请求的完整链路：先拿 request_id，再全量 grep
docker compose logs --since 1h api | grep 'request_id_here'
```

`level` 是大写的 `INFO` / `WARN` / `ERROR`，小写 grep 不到。

容器日志有上限：`deploy/prod/docker-compose.prod.yml` 里给 api 和 web 设了 `max-size: 10m`、`max-file: 3`，单个服务最多占 30MB，超了自动轮转，不会把 40G 系统盘写满。代价是更早的日志被删掉了，需要长期留的证据要另外收集。

注意 `--tail` 与 `--since` 可以叠加，查「某个时间段的最后 50 行」用：

```bash
docker compose logs --since 2026-11-18T00:00:00 --until 2026-11-18T01:00:00 api
```

### Nginx 日志

`web` 容器的 access log 与 error log 也走标准输出（官方 nginx 镜像把两个文件软链到 stdout/stderr）：

```bash
docker compose logs --tail=50 web

# 只看 5xx，排 502 时最有用
docker compose logs --since 1h web | grep -E '" (50[0-9]) '
```

`deploy/prod/nginx.conf` 里给静态资源（`/assets/`、`/uploads/`）关了 access_log，所以这里看到的请求数会比实际访问少，那些请求本来也不需要记。

### MySQL 日志

```bash
docker compose logs --tail=100 mysql
```

启动失败、连接数打满、InnoDB 报错都在这里。慢查询默认没开，要看的话见 11.6。

### migrate 的日志

`migrate` 用 `docker compose run --rm` 跑，容器结束就删了，历史日志不保留。要留证据就重定向一份：

```bash
docker compose run --rm migrate 2>&1 | tee -a logs/migrate.log
```

## 11.3 容器与服务

```bash
# 状态
docker compose ps

# 重启单个服务（改了 config/config.yaml 之后用这个）
docker compose restart api

# 停掉再起，等价于 restart 但没有优雅停止的等待
docker compose stop api && docker compose start api

# 只重建 api，不动 mysql / redis / web
docker compose up -d --no-deps api

# 进容器看文件，验证挂载对不对
docker compose exec api ls -l /app/config /app/uploads

# 进 MySQL（密码从容器环境变量取，不出现在宿主机 ps 里）
docker compose exec mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" forum'

# 资源占用，排查内存时看这个
docker compose stats --no-stream

# 健康检查状态
docker inspect --format '{{.State.Health.Status}}' "$(docker compose ps -q mysql)"

# 容器内进程（确认是 10001 那个用户跑的）
docker compose exec api id
```

改了 `config/config.yaml` 用 `restart` 就够，不需要重建镜像。但如果是用 `vi` 改的，先补一次属主，否则 api 重启后读不到文件：

```bash
chown 10001:10001 config/config.yaml && chmod 640 config/config.yaml
```

`vi` 保存是「写临时文件再改名」，新文件属主变成 root，容器里的 10001 读不了，日志里会是 `加载配置失败: read config: open /app/config/config.yaml: permission denied`。

## 11.4 发版

### 只改了后端

```bash
# 本机：先提交，脚本会拦下未提交的改动
cd /d/go学习/forum-backend
git add <改动的文件> && git commit -m "fix(api): ..." && git push
bash scripts/pack-linux.sh --api-only --tar
scp .build/forum-linux-amd64.tar.gz root@47.86.29.94:/tmp/

# 服务器
cd /opt/forum
tar -xzf /tmp/forum-linux-amd64.tar.gz -C /opt/forum
rm -f /tmp/forum-linux-amd64.tar.gz

sed -i '/^IMAGE_TAG=/d' .env && echo "IMAGE_TAG=$(cat .build/IMAGE_TAG)" >> .env
docker compose build api web
docker compose up -d --no-deps api
docker compose up -d --no-deps --force-recreate web
```

标签是打包时算好的（`月日-时分-commit短哈希`，如 `1118-0228-7d2ac1f`），写在 `.build/IMAGE_TAG` 里，服务器直接读，不要用 `date` 现算。

最后那条重建 web 不能省。Nginx 启动时把 upstream 里的 `api` 解析成 IP 缓存住，api 换容器就是换了 IP，Nginx 还在往旧 IP 发请求，结果是全站 502。

### 只改了前端

```bash
# 本机
git add <改动的文件> && git commit -m "fix(web): ..." && git push
bash scripts/pack-linux.sh --web-only --tar
scp .build/forum-linux-amd64.tar.gz root@47.86.29.94:/tmp/

# 服务器
cd /opt/forum
tar -xzf /tmp/forum-linux-amd64.tar.gz -C /opt/forum
rm -f /tmp/forum-linux-amd64.tar.gz

sed -i '/^IMAGE_TAG=/d' .env && echo "IMAGE_TAG=$(cat .build/IMAGE_TAG)" >> .env
docker compose build api web
docker compose up -d --no-deps --force-recreate web
```

两端一起 `build` 的理由：镜像 tag 是全局的，只构建一端会让新 tag 下少一个镜像，回退时会发现某个版本缺件。

### 改了表结构

在 `up -d api` 之前插一次迁移：

```bash
docker compose run --rm migrate
```

### 第一次发版后核对

```bash
cat .build/BUILD_INFO
docker compose ps
curl -sS -o /dev/null -w '%{http_code}\n' https://jiushixixi.xyz/readyz
```

`BUILD_INFO` 里的 `dirty` 不为 0，说明这份产物对应的代码还没进 git，排查问题时先记下这一点。

### 发版后清场

一次发版在服务器上留三样东西，只有第一样是真的垃圾：

| 留下的 | 位置 | 处理 |
|---|---|---|
| 上传的 tar 包 | `/tmp/forum-linux-amd64.tar.gz` | 解完就删，上面两条命令已经带上 |
| 上一版镜像 | `forum-api:<旧tag>`、`forum-web:<旧tag>` | 故意留的，回退要用，按版本数封顶 |
| 构建缓存 | `/var/lib/docker/buildkit` | artifact 构建只有 `COPY`，几乎不长 |

本机不用清。`scripts/pack-linux.sh` 每次先 `rm -rf .build/api`、`rm -rf .build/web` 再重建，`.build` 恒定在 60M 上下，tar 包同名覆盖。本机没有 Docker，也不会留镜像。想彻底清就 `rm -rf .build`，代价是下次打包少一份 `BUILD_INFO` 对照。

镜像封顶，只留最近 3 个版本：

```bash
docker image prune -f        # 先清同 tag 重建留下的悬空层

for t in $(docker images forum-api --format '{{.Tag}}' | tail -n +4); do
  echo "删除 $t"
  docker rmi "forum-api:$t" "forum-web:$t"
done
```

`docker images` 的输出按构建时间从新到旧排，`tail -n +4` 就是第 4 个及更早的。成对删是有意的：某一版只剩 api 或只剩 web，回退过去就会缺件，不如一起删掉。

两种报错都不影响结果：`No such image` 说明那版本来就只打了单端；`conflict` 说明这个镜像还被容器占着，也就是你算的保留数量少了一个，跳过就行。

留 3 个够不够：一个在跑、一个上一版、一个再上一版。发现问题时通常回退一两步就解决。真要腾大空间，先 `docker system df` 看是谁占的，多半是早期源码构建留下的 buildkit 缓存，不是镜像。

## 11.5 回退

```bash
docker images | grep forum-api
```

每一行是一次构建，第二列是 tag：

```
forum-api   1118-1012-7d2ac1f   a1b2c3d4e5f6   2 minutes ago   62MB
forum-api   1117-2310-3f91ab2   9f8e7d6c5b4a   3 hours ago     62MB
```

tag 结尾就是 commit，`git show 3f91ab2` 能确认这一版改了什么。

把 `.env` 里的 tag 改回旧值，重新起容器。镜像还在本地，不用构建：

```bash
sed -i '/^IMAGE_TAG=/d' .env && echo "IMAGE_TAG=1117-2310-3f91ab2" >> .env
docker compose up -d --no-deps api
docker compose up -d --no-deps --force-recreate web
```

回退时如果连表结构也变了，注意旧代码可能不认新列。迁移只往前的项目（没有 down 脚本）只能靠备份恢复，所以改表之前先备份：

```bash
BACKUP_MODE=docker scripts/backup.sh
```

## 11.6 数据库

### 进库

```bash
docker compose exec mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" forum'
```

### 常看的几条查询

```sql
-- 每张表的行数与占用
SELECT TABLE_NAME, TABLE_ROWS, ROUND(DATA_LENGTH/1024/1024, 1) AS data_mb
FROM information_schema.TABLES WHERE TABLE_SCHEMA = 'forum'
ORDER BY DATA_LENGTH DESC;

-- 当前连接
SHOW STATUS LIKE 'Threads_connected';

-- 正在执行的语句，看有没有长时间占着锁的
SELECT id, user, time, state, LEFT(info, 80) FROM information_schema.PROCESSLIST
WHERE command <> 'Sleep' ORDER BY time DESC;

-- 卡住的 InnoDB 事务
SELECT trx_id, trx_state, trx_started, trx_mysql_thread_id
FROM information_schema.INNODB_TRX;
```

### 慢查询

`deploy/prod/my.cnf` 里关掉了 `performance_schema` 省内存，慢日志也没有默认开。临时打开：

```bash
docker compose exec mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL slow_query_log_file = \"/var/lib/mysql/slow.log\";"'
```

日志在容器内 `/var/lib/mysql/slow.log`，对应宿主机的 mysql 数据卷：

```bash
docker compose exec mysql sh -c 'tail -50 /var/lib/mysql/slow.log'
```

重启 mysql 会回到配置文件的默认值，这是临时手段。

### 备份

```bash
cd /opt/forum
BACKUP_MODE=docker scripts/backup.sh
ls -lh backups/ | tail -3
```

脚本会 mysqldump 一份压缩 SQL，再把 `uploads/` 打成 tar.gz，最后做一次完整性校验。默认保留 7 天，改 `KEEP_DAYS=30` 可以留更久。

放进 crontab 每天跑：

```bash
0 3 * * * cd /opt/forum && BACKUP_MODE=docker scripts/backup.sh >> logs/backup.log 2>&1
```

### 恢复

```bash
gunzip -c backups/forum-20261118-030000.sql.gz \
  | docker compose exec -T mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" forum'
```

`-T` 不能省，不加的话 `exec` 会去申请终端，管道输入进不去。

## 11.7 证书

```bash
# 看剩余天数
docker run --rm -v /opt/forum/certbot/conf:/etc/letsencrypt certbot/certbot certificates

# 演练续期，不消耗正式配额
docker run --rm \
  -v /opt/forum/certbot/conf:/etc/letsencrypt \
  -v /opt/forum/certbot/www:/var/www/certbot \
  certbot/certbot renew --webroot -w /var/www/certbot --dry-run -v

# 真续期
docker run --rm \
  -v /opt/forum/certbot/conf:/etc/letsencrypt \
  -v /opt/forum/certbot/www:/var/www/certbot \
  certbot/certbot renew --webroot -w /var/www/certbot
docker compose exec -T web nginx -s reload
```

续期只能用 webroot，不能 standalone：80 端口一直被 web 容器占着，standalone 会报 `Address already in use`。

证书有效期 90 天，cron 每天跑一次 `renew`，剩余不足 30 天才真的续，其余情况直接退出。正式续期失败有次数限制（同一域名一周 5 次），所以排查阶段一律先 `--dry-run`。

## 11.8 磁盘与内存

```bash
# Docker 占了多少
docker system df

# 每个目录的大头
du -sh /var/lib/docker/* 2>/dev/null | sort -h | tail -5
du -sh /opt/forum/backups /opt/forum/uploads /opt/forum/.build 2>/dev/null

# 清构建缓存：安全，只删没在用的中间层
docker builder prune -f

# 清悬空镜像（没有 tag 的旧层），安全
docker image prune -f
```

不要随手 `docker image prune -a`。那会把所有没在运行的镜像删光，包括每一版 `forum-api:<tag>`，回退能力就没了。真要腾空间，先看 11.5 里还打算保留哪几个版本，手动 `docker rmi` 掉更早的。

2G 内存的护栏：

```bash
free -h
# 谁在吃内存，按 RSS 排序
docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}\t{{.CPUPerc}}'

# 有没有被 OOM 杀过
dmesg -T | grep -i -E 'killed process|out of memory' | tail -10
```

看到 `Killed process ... (mysqld)` 或 `(forum-server)`，说明内存确实不够用了。第一件事是确认 swap 还在：

```bash
swapon --show
```

空的就按 docs/10 第 5.3 节加 2G swap 文件。

## 11.9 故障对照

| 现象 | 先敲这条 | 大概率的原因 |
|---|---|---|
| 打开网站 502 | `docker compose ps` | api 没起，或 Nginx 缓存了旧 IP，`up -d --no-deps --force-recreate web` |
| 页面一直转圈 | `docker compose stats --no-stream` | 内存打满或磁盘满，看 `free -h`、`df -h /` |
| 接口 500 | `docker compose logs --since 10m api \| grep ERROR` | 看 `msg` 和 `request_id`，再按 id 捞整条链路 |
| 登录成功但刷新就掉 | `docker compose logs api \| grep -i token` | `refresh_tokens` 写不进 Redis，检查 redis 是否可写 |
| 头像上传 500 | `docker compose exec api ls -ld /app/uploads` | `uploads` 属主不是 10001，`chown -R 10001:10001 uploads` |
| api 起来就重启 | `docker compose logs --tail=50 api` | 多半是 `permission denied`（配置属主）或连不上 mysql |
| WebSocket 403 | 看 `config/config.yaml` 的 `ws.allowed_origins` | 少了当前域名，改完 `restart api` |
| 证书申请超时 | 本机 `curl -I http://域名/.well-known/acme-challenge/x` | 安全组没放 80，或 web 容器没起 |
| 磁盘满了 | `docker system df` | 构建缓存或旧镜像，`builder prune -f` |
| 时间差 8 小时 | `docker compose exec api date` | 容器没设 `TZ=Asia/Shanghai` |
| 改了配置没生效 | `docker compose exec api cat /app/config/config.yaml` | 挂载路径不对，或改完没 `restart` |

## 11.10 一张命令卡

贴在顺手的地方，日常八成操作都在这里：

```bash
cd /opt/forum

docker compose ps                                   # 谁活着
docker compose logs -f api                          # 实时日志
docker compose logs --since 30m api | grep ERROR    # 最近半小时的错误
docker compose restart api                          # 改完配置重启
docker compose up -d --no-deps api                  # 只重建 api
docker compose up -d --no-deps --force-recreate web # 修 502
docker compose exec api sh                          # 进容器
docker compose stats --no-stream                    # 谁吃内存
docker system df                                    # 谁占磁盘
docker builder prune -f                             # 清构建缓存
BACKUP_MODE=docker scripts/backup.sh                 # 备份
```
