# 第 3 周进阶 D：敏感词过滤与前缀树

论坛上线第一天，最可能出现的内容不是技术讨论，是「加微信 xxx 带你日赚三百」。本章自己写一个过滤器，把这类内容在入库前替换掉。

选择自己实现而不是找个库，是因为这件事的算法结构足够简单、又足够有讲头：一条文本、一本词库、一棵树，复杂度分析能写清楚，性能还能用 benchmark 量出来。

## 0. 为什么要加这一章

### 0.1 朴素做法的问题

最直接的想法是这样：

```go
var words = []string{"加微信", "代开发票", "刷单", "博彩"}

func containsBad(text string) bool {
	for _, w := range words {
		if strings.Contains(text, w) {
			return true
		}
	}
	return false
}
```

四个词没问题。麻烦在词库会长：一千个词就是一千次 `strings.Contains`，每次都要从头扫一遍正文。600 字的帖子扫 1000 次，等于 60 万次字符比较。

换一个角度：真正需要比较的次数，取决于正文里出现了哪些前缀，词库多大关系不大。文本里没有「加」字，所有以「加」开头的词都不必再试。这就是前缀树要解决的问题。

### 0.2 验收合同

| --- | --- | --- |

## 1. 从朴素匹配到前缀树

### 1.1 复杂度先算清楚

设正文长度 n（按字符），词库词数 m，平均词长 k。

| 做法 | 时间复杂度 | 600 字正文、1000 个三字词 |
| --- | --- | --- |
| 逐个 `strings.Contains` | O(n × m)，每次匹配内部还有失败回退 | 约 60 万次字符比较 |
| 前缀树单次匹配 | O(n × k)，与词数无关 | 约 1800 次节点跳转 |

注意 `strings.Contains` 在 Go 里不是纯朴素的逐字符比较，标准库对短子串用了汇编优化，实际常数很小。所以「理论快 300 倍」不等于「实测快 300 倍」。真实数字在 6.3 节，那里有实测对比，结论比这张表复杂。

### 1.2 树长什么样

词库有三条：「刷单」「刷单返利」「博彩」。

```text
            (root)
           /      \
         刷        博
         |         |
         单        彩 ← terminal
        /  \
   terminal  返
              |
              利 ← terminal
```

关键点：

1. 三个词只用了 7 个节点，公共前缀「刷单」只存一份。
2. 从根走到某个节点，路径上的字符连起来就是一个前缀。
3. 节点上的 `terminal` 标记表示「到这里刚好是一个完整的词」。「刷单」和「刷单返利」共用路径，只有末端有标记，中间那个节点也有标记，因为它自己也是个词。

匹配「刷单返利」的过程：从根出发，读到「刷」有分支，往下；读到「单」有分支，往下，此时节点 `terminal` 为真，记下候选长度 2；继续读到「返」，有分支；读到「利」，`terminal` 为真，更新候选长度为 4。文本结束，返回 4，取到了最长词。

如果走不到下一个字符，就停下，用当前候选长度。没有候选就返回 0，从下一个字符重新开始。

### 1.3 它不解决什么

前缀树能让「找词」这一步变快，有三件事它管不了：

| 问题 | 前缀树的答案 |
| --- | --- |
| 词与词之间有拼音、谐音、插入符号（「刷*单」） | 管不了。要专门的归一化层 |
| 简繁混写、全角半角混写 | 管不了。要 Unicode 归一化 |
| 判定之后该怎么办 | 不涉及。替换还是拒绝是业务决定 |

这三条都要写进边界，不然面试官一句「用户写『加 微 信』你怎么办」就问住了。

### 1.4 为什么不上 AC 自动机

AC 自动机是前缀树加失败指针，能做到严格的 O(n)，与词长无关。听起来更高级，本章不用，理由有三条：

1. 失败指针的构建要用 BFS，代码量翻倍，出错点从「一处」变成「五处」。
2. 只有在「大量文本 + 大量词 + 长词」时才明显快。本项目的场景是短文本、中等词库，省下的时间还不够抵消复杂度。
3. 前缀树的最坏情况是 O(n × k)，k 是词库最长词。实测最长的广告词也就十来个字，这个上界可以接受。

面试时被问到「能不能更快」，答 AC 自动机并讲清什么场景才值得，比直接堆代码有说服力。

如果将来要做「整站历史帖子的批量清洗」，那是几千万字乘以几千词，AC 自动机的优势就出来了。到时候换实现，接口不变，因为 `Filter.Replace` 的签名不用动。

## 2. 第 1 步：实现前缀树

### 2.1 完整文件：`internal/filter/trie.go`

新建文件。目录不存在就先 `mkdir -p internal/filter`，包名写 `package filter`。

这个文件只定义内部类型 `node` 与匹配逻辑，`Filter` 在 3.1 的 `filter.go` 里。同属 `package filter`，两个文件都写完才是一个能用的包，顺序见 0.4。

```go
// Package filter 用前缀树做敏感词检测与替换。
// 构建一次、只读使用，可以被多个请求 goroutine 共用。
package filter

import "unicode"

// node 是前缀树的一个节点。
// children 的键是 rune 不是 byte：中文一个字在 UTF-8 里占三字节，
// 按字节存会把一个字劈成三份，词库和文本永远对不上。
type node struct {
	children map[rune]*node
	terminal bool // 从根走到这里刚好是一个完整词
}

func newNode() *node {
	return &node{children: make(map[rune]*node)}
}

// Trie 是敏感词前缀树。
// 词库里 "abc" 和 "abd" 共用 a、b 两个节点，这是它比逐个 Contains 省时间的根本原因。
type Trie struct {
	root   *node
	maxLen int // 最长词长度，用来限制每个起点最多往前推几步
}

func NewTrie(words []string) *Trie {
	t := &Trie{root: newNode()}
	for _, w := range words {
		t.insert(w)
	}
	return t
}

// foldRune 把字符折成小写再入树、再比较。
// 不用 strings.ToLower 整串转换：某些 Unicode 字符小写后长度会变，
// 一旦长度变了，匹配出来的下标就和原文对不上，替换会切错位置。
func foldRune(r rune) rune {
	return unicode.ToLower(r)
}

func (t *Trie) insert(word string) {
	runes := []rune(word)
	if len(runes) == 0 {
		return
	}
	cur := t.root
	for _, r := range runes {
		key := foldRune(r)
		next, ok := cur.children[key]
		if !ok {
			next = newNode()
			cur.children[key] = next
		}
		cur = next
	}
	cur.terminal = true
	if len(runes) > t.maxLen {
		t.maxLen = len(runes)
	}
}

// hit 是一段命中区间，下标按 rune 计，左闭右开。
type hit struct {
	start int
	end   int
}

// Match 返回文本里所有命中区间。
// 命中后直接跳过整段，所以区间之间不会重叠，替换时不用处理交叉。
func (t *Trie) Match(text string) []hit {
	runes := []rune(text)
	hits := make([]hit, 0)
	i := 0
	for i < len(runes) {
		n := t.matchAt(runes, i)
		if n == 0 {
			i++
			continue
		}
		hits = append(hits, hit{start: i, end: i + n})
		i += n
	}
	return hits
}

// matchAt 从 start 出发沿树往下走，返回最长命中长度；没有命中返回 0。
// 取最长而不管第一个 terminal，是因为词库里同时有「敏感」和「敏感词」时，
// 短匹配会把长词截断，替换后语义就变了。
func (t *Trie) matchAt(runes []rune, start int) int {
	cur := t.root
	best := 0
	limit := start + t.maxLen
	if limit > len(runes) {
		limit = len(runes)
	}
	for i := start; i < limit; i++ {
		next, ok := cur.children[foldRune(runes[i])]
		if !ok {
			break
		}
		cur = next
		if cur.terminal {
			best = i - start + 1
		}
	}
	return best
}
```

### 2.2 逐行拆解

**为什么键是 `rune`**

Go 的字符串是按 UTF-8 存的。汉字「刷」的编码是 `E5 88 B7`，三个字节。如果树按 `byte` 建，「刷单」就是六个字节的路径，而正文里 `[]byte("刷单")` 也是六个字节。这看起来能对上，但出问题的是长度计算和切片：`s[0:3]` 切出来是一个字，`s[0:2]` 切出来是半个字，序列化出去就是非法 UTF-8。

用 `rune` 之后，一个汉字就是一个元素，所有下标、长度、切片都按「字」算，和人的直觉一致。

**不用 `strings.ToLower`**

这是个真实存在的坑。`strings.ToLower` 对绝大多数 ASCII 字符是等长替换，但对某些 Unicode 字符会改变长度。最典型的是土耳其语的大写 İ，小写后是两个码位。

一旦 `len([]rune(strings.ToLower(text))) != len([]rune(text))`，匹配出来的下标就和原文错位，替换会涂在错误的位置上。

`foldRune` 逐字符转换，长度永远不变，下标天然对齐。这是用 `unicode.ToLower` 而不是 `strings.ToLower` 的唯一理由，但那一个理由足够。

**`maxLen` 的作用**

```go
limit := start + t.maxLen
if limit > len(runes) {
	limit = len(runes)
}
```

没有这个上限，每个起点都要走到文本末尾，一棵只有三字词的树也要走 600 步，白费。设了上限，最多走 `maxLen` 步，实测通常在 10 步以内。

上限还有一个安全作用：防止病态输入让匹配退化。没有上限时，一棵高度很大的树配上很长的文本，最坏情况是 O(n²)。

**`best` 而不是「第一次命中就返回」**

```go
if cur.terminal {
	best = i - start + 1
}
```

`best` 会被后面更长的命中覆盖。这个写法支持「词库里有前缀关系」的情况。

如果写成「遇到 terminal 就 return」，词库同时有「敏感」和「敏感词」时，「敏感词」会被截成「敏感」加一个「词」，替换结果是「**词」，语义破坏。

**`i += n` 跳过整段**

这是「不重叠」策略。命中「刷单」后从「单」后面继续，不会从「单」本身再试一次。

代价是漏掉重叠词。词库有「AB」和「BC」，文本是「ABC」，只会命中「AB」。这个取舍在 7.1 的 `TestNoOverlap` 里明确固化成测试，将来有人改行为，测试会提醒。

要支持重叠，改造方法是 `i++` 而不是 `i += n`，然后替换时合并交叉区间。多出来的代码量不小，收益是覆盖极少数刻意构造的输入，不值得。

## 3. 第 2 步：替换

### 3.1 完整文件：`internal/filter/filter.go`

和 `trie.go` 同目录、同包。这个文件引用 `trie.go` 的 `node`，单独放着会报 `undefined: node`。

```go
package filter

import (
	"fmt"
	"os"
	"strings"
)

// maskChar 是替换用的字符。用 * 而不是删除，
// 是为了让文本长度和可读性尽量保持，读者知道这里被屏蔽过。
const maskChar rune = '*'

// Filter 是对外的过滤器，内部只有一棵树。
type Filter struct {
	trie *Trie
}

func New(words []string) *Filter {
	return &Filter{trie: NewTrie(words)}
}

// Load 从文本文件读词库：一行一个词，# 开头是注释，空行跳过。
// 启动时调一次，得到的 Filter 之后只读，并发安全。
func Load(path string) (*Filter, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return nil, fmt.Errorf("read word list %s: %w", path, err)
	}
	words := make([]string, 0)
	for _, line := range strings.Split(string(data), "\n") {
		line = strings.TrimSpace(line)
		if line == "" || strings.HasPrefix(line, "#") {
			continue
		}
		words = append(words, line)
	}
	if len(words) == 0 {
		// 词库空了等于没有防护，启动阶段就该暴露，别等到线上才发现。
		return nil, fmt.Errorf("word list %s contains no word", path)
	}
	return New(words), nil
}

// Replace 把命中的词整段换成等长的 *，同时返回命中原文。
// 返回命中原文是为了打日志、做审核队列；调用方不需要可以只取第一个返回值。
func (f *Filter) Replace(text string) (string, []string) {
	hits := f.trie.Match(text)
	if len(hits) == 0 {
		return text, nil
	}

	orig := []rune(text)
	out := make([]rune, len(orig))
	copy(out, orig)

	words := make([]string, 0, len(hits))
	for _, h := range hits {
		// 先取原文再涂掉，顺序反了就取到一串 ***。
		words = append(words, string(orig[h.start:h.end]))
		for i := h.start; i < h.end; i++ {
			out[i] = maskChar
		}
	}
	return string(out), words
}

// WordCount 返回词库里的词数，供启动日志打印。
func (f *Filter) WordCount() int {
	n := 0
	var walk func(*node)
	walk = func(cur *node) {
		if cur.terminal {
			n++
		}
		for _, next := range cur.children {
			walk(next)
		}
	}
	walk(f.trie.root)
	return n
}
```

### 3.2 逐行拆解

**为什么要拷一份 `out`**

```go
orig := []rune(text)
out := make([]rune, len(orig))
copy(out, orig)
```

命中词需要从原文取（返回给调用方），替换要写在另一份上。如果直接在 `orig` 上涂，后面再取「命中原文」时取到的就是一串 `*`。注释里那句「顺序反了就取到一串 ***」说的就是这个。

也可以反过来：先把所有命中原文取完，再涂 `orig`。但那样要两轮循环，多写几行，好处只是少一次拷贝。600 字的一次拷贝是 2.4 KB，成本可以忽略，可读性更重要。

**替换为什么是等长**

「刷单」两个字换成「**」两个星号，而不是删掉或者换成一个星号。

三个理由：

1. 长度不变，前端不需要重新计算文本位置，高亮、折叠都不受影响。
2. 读者能看出这里被处理过，删掉会让人以为原文就是这么写的。
3. 不会因为屏蔽导致句子完全读不通，多数情况下还能猜出大意。

另一种常见做法是保留首字，变成「刷*」。这样可读性更好，但对某些词反而提示了内容。本项目选全屏蔽。

**`Load` 里的空词库判断**

词库文件存在但里面只有注释，`words` 就是空的。这时候如果照常返回一个空 `Filter`，所有 `Replace` 都原样返回，看起来一切正常，实际上防护完全失效。

这种「静默失效」是最难发现的故障。所以在 `Load` 里直接报错，让启动失败。启动失败比线上裸奔好。

### 3.3 命名上的一处妥协

`trie.Match` 返回的 `hit` 是包内私有类型，`Filter.Replace` 把它转成 `[]string` 给外部。为什么不在树里直接返回 `[]string`：

树需要的是位置，用来涂字符；调用方需要的是词，用来打日志。在树里把位置转成词，等于让树知道「哪些位置该被涂」，职责越界。分开之后，树只管「哪里命中了」，替换逻辑全在 `Filter` 里，换一种屏蔽方式（保留首字、打码成拼音）时只改一处。

## 4. 第 3 步：词库加载

### 4.1 词库文件格式

**完整文件**：`config/sensitive_words.txt`

```text
# 示例词库：一行一个词，# 开头是注释，空行与注释行都会被跳过。
# 换成自己的词库时保持这个格式即可，不需要改代码。
加微信
加QQ
代开发票
刷单
博彩
私聊我
免费领取
点击链接
高薪兼职
日赚
刷信誉
casino
porn
```

格式选纯文本而不是 JSON 或 YAML，理由是维护它的人可能不是开发。运营要加一个词，打开文件加一行、保存、重启即可，不需要懂缩进和引号。

`#` 开头是注释，这一条必须支持，否则词库里没法写说明，下次维护的人不知道该不该删某一行。

### 4.2 为什么要单独建文件

三个理由：

| 理由 | 说明 |
| --- | --- |
| 变更频率不同 | 词库可能一周改一次，代码一个月改一次，绑在一起每次都要重新编译部署 |
| 维护人不同 | 运营改词库，开发改代码，分开之后权限也能分开 |
| 审查需要 | 词库本身是敏感资产，独立文件便于做变更记录 |

代价是多一个部署产物。Docker 镜像里要把 `config/` 一起拷进去，本地跑要注意工作目录。这个坑在 7.2 的验收里会踩到。

### 4.3 热更新要不要做

现在的方式是启动时加载一次。改词库要重启。

热更新有几种做法，都不难，但都有代价：

| 做法 | 代价 |
| --- | --- |
| 定时检查文件 mtime，变了就重建 | 重建期间的请求要用旧树或新树，需要 `atomic.Pointer` 换指针 |
| 监听文件变化（fsnotify） | 多一个依赖，容器里的文件挂载变化不一定触发事件 |
| 存 Redis，定期拉 | 多一份数据源，要考虑拉不到时用哪份 |

本章不做热更新，原因是：词库变更通常几分钟内完成重启，收益不大；而热更新要求 `Filter` 指针可替换，所有持有它的 service 都要改成每次取最新值，牵动的代码比过滤器本身还多。

真要做，最干净的方式是把 `Filter` 换成 `atomic.Pointer[Filter]` 的持有者，`Replace` 里先 load 再调。这一步列在 8.2 的明确不做里。

## 5. 第 4 步：接入业务

### 5.1 为什么放 service 层

三个候选位置：

| 位置 | 优点 | 问题 |
| --- | --- | --- |
| handler | 能直接返回 400 | 绕过 HTTP 的调用路径没有保护；handler 会变胖 |
| service | 所有写路径都经过；业务规则的家 | 无 |
| model 钩子（`BeforeCreate`） | 自动生效，不会漏 | 隐式行为，排查时看不到；测试要连库 |

选 service。判断标准是「这条规则是不是业务规则」。敏感词过滤是业务规则，不是传输层的事，也不是 ORM 的事。

`model` 钩子那个方案特别要警惕：它看起来最省事，但会在任何 `Create` 时静默改写数据，包括数据迁移脚本和测试。隐式改写的调试成本极高，不值得。

### 5.4 过滤后入库意味着什么

这个决定有三个后果，都要提前想清楚。

**后果一：原文不可恢复**

数据库里存的是 `**`，用户申诉「我发的是正常内容」时，服务端拿不出原文。要能申诉，就得在别处留原文（单独的表、对象存储），那又是新的合规风险。

本项目的取舍是：不留原文。理由是这个论坛没人申诉，留原文反而是负担。真实业务里要按合规要求决定。

**后果二：读路径不需要再过滤**

因为入库前已经处理过，详情、列表、缓存、搜索索引里拿到的都是干净文本。这省掉了一整层读路径改造，也是选「入库前替换」而不是「展示时替换」的关键理由。

如果选展示时替换，详情缓存里存的还是脏数据，每个读接口都要过滤一遍，漏一个地方就漏一处。

**后果三：命中记录只剩日志**

`log.Printf` 打出来的命中词只在本机日志里，重启就没了。要做审核队列，得把命中写进一张 `content_audits` 表。本章不做，列在 8.2。

| --- | --- | --- |
| `Search` | 能 | 搜索是增强功能，没装搜索引擎论坛照常运行 |
| `Filter` | 不能 | 没有过滤器等于没有防护，这个状态不该被悄悄接受 |

判断标准是「这个组件的缺失会不会造成安全或正确性问题」。搜索不会，过滤会。所以前者降级、后者 fail fast。

如果哪天想让过滤也可选（比如开发环境嫌麻烦），正确做法是在配置里加一个显式的开关 `filter.enabled: false`，让关闭这个动作被写下来、被 review 到，而不是靠传 nil 隐式达成。

## 6. 性能：实测与诚实的结论

### 6.1 完整文件：`internal/filter/filter_bench_test.go`

同目录、同包 `filter`，`_test.go` 后缀。基准测试不进 `go test ./...` 的常规耗时统计里，要显式加 `-bench` 才会跑。

```go
package filter

import (
	"strings"
	"testing"
)

// benchText 约 600 个汉字，接近一篇中等长度帖子的正文。
var benchText = strings.Repeat("这是一段正常的正文内容，用来模拟真实长度和真实汉字比例。", 20)

// makeWords 造一个去重的三字词库，用常见字拼，保证与 benchText 有交集。
func makeWords(n int) []string {
	runes := []rune("这是一段正常的正文内容用来模拟真实长度和汉字比例广告诈骗刷单博彩违法信息低俗辱骂")
	seen := make(map[string]struct{}, n)
	words := make([]string, 0, n)
	for i := 0; len(words) < n && i < n*50; i++ {
		a := runes[i%len(runes)]
		b := runes[(i*7+3)%len(runes)]
		c := runes[(i*13+5)%len(runes)]
		w := string([]rune{a, b, c})
		if _, ok := seen[w]; ok {
			continue
		}
		seen[w] = struct{}{}
		words = append(words, w)
	}
	return words
}

func BenchmarkReplace20Words(b *testing.B) {
	f := New(makeWords(20))
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		f.Replace(benchText)
	}
}

func BenchmarkContains20Words(b *testing.B) {
	words := makeWords(20)
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		for _, w := range words {
			_ = strings.Contains(benchText, w)
		}
	}
}

func BenchmarkReplace500Words(b *testing.B) {

	b.ResetTimer()
	for i := 0; i < b.N; i++ {

	}
}

func BenchmarkContains500Words(b *testing.B) {

```

跑法：

```bash
go test -run xxx -bench . -benchmem -count 3 ./internal/filter
```

`-run xxx` 是让单元测试别跑，只跑基准。`-count 3` 跑三轮看稳定性。

### 6.2 实测结果

本机 i7-14650HX，600 字正文，三轮取范围。

| 场景 | 耗时 | 内存 | 分配次数 |
| --- | --- | --- | --- |
| 20 词，前缀树 | 13.7 到 14.2 µs | 2304 B | 1 |
| 20 词，逐个 Contains | 10.0 到 10.1 µs | 0 B | 0 |
| 500 词，前缀树 | 28.5 到 29.8 µs | 2304 B | 1 |
| 500 词，逐个 Contains | 40.5 到 45.1 µs | 0 B | 0 |

### 6.3 怎么读这组数字

**词库小的时候，前缀树更慢。** 20 个词，`Contains` 快 40%，而且零分配。

原因有三层：

1. Go 标准库的 `strings.Contains` 对短子串走汇编实现，用的是 SIMD 思路，一次比对多个字节。逐 rune 走 map 的树比不了。
2. 前缀树每次 `Replace` 都要把字符串转成 `[]rune`，600 字就是一次 2.4 KB 分配。这一项就够 `Contains` 跑完 20 次了。
3. `children` 是 `map[rune]*node`，每次跳转都是一次哈希查找。map 的常数不小。

**词库大的时候，前缀树反超。** 500 个词，快 30%。这个交叉点的位置取决于词库、文本长度、CPU 缓存，不能一概而论，必须自己测。

**趋势比单点更重要。** `Contains` 的耗时与词数线性相关，1000 个词就是 500 个词的两倍。前缀树的耗时与词数无关，只跟文本长度和最长词长度有关。词库继续涨，差距会拉大。

这三条合起来给一个诚实的结论：

> 词库在几十个词的规模，用 `strings.Contains` 更省事也更快。前缀树的价值在词库上百之后，以及「无论词库怎么涨，延迟都不变」这个可预期性上。

面试时把这句话说出来，比背「前缀树比暴力快」有分量。多数候选人只会讲理论复杂度，说不出标准库有 SIMD 优化、说不出 `[]rune` 转换的分配成本。

### 6.4 还能怎么优化

顺带把优化方向列出来，不必都做。

| 方向 | 收益 | 代价 |
| --- | --- | --- |
| 树改用 `[256]*node` + 哈希回退 | 常见字符跳转省掉哈希 | 每个节点占 2 KB，词库大时内存暴涨 |
| 文本先转 `[]rune` 再传进来，避免重复转换 | 省掉一次分配 | 接口变形，调用方要配合 |
| 命中位置直接记录，替换时复用同一份 runes | 省掉 `copy` | 少一次 2.4 KB 拷贝，收益有限 |
| 用 `strings.Index` 快速预筛，命中才走树 | 无词文本快很多 | 逻辑分叉，判断条件变复杂 |

第一条是最值得做的，但它会把内存从「按词数」变成「按节点数乘以 2 KB」，词库一万个词时就是几十 MB。本项目的场景不需要。

```go
	dir := t.TempDir()
	path := filepath.Join(dir, "words.txt")
	content := "# 注释行\n\n刷单\n  \n博彩\n"
	if err := os.WriteFile(path, []byte(content), 0o600); err != nil {
		t.Fatalf("write temp word list: %v", err)
	}
	f, err := Load(path)
	if err != nil {
		t.Fatalf("Load: %v", err)
	}
	if got := f.WordCount(); got != 2 {
		t.Fatalf("WordCount = %d, want 2", got)
	}
}

func TestLoadRejectsEmptyList(t *testing.T) {
	dir := t.TempDir()
	path := filepath.Join(dir, "empty.txt")
	if err := os.WriteFile(path, []byte("# 只有注释\n\n"), 0o600); err != nil {
		t.Fatalf("write temp word list: %v", err)
	}
	if _, err := Load(path); err == nil {
		t.Fatal("Load should fail on a word list with no word")
	}
}
```

`TestReplaceKeepsRuneAlignment` 值得多说一句。它同时断言了「替换结果正确」和「rune 长度不变」。只断言前者的话，一个用 `[]byte` 涂 `*` 的实现可能在某些输入下也碰巧过；加上后者，字节与字符的混淆一定会被抓住。

## 8. 边界与面试追问

### 8.1 这个过滤器挡不住什么

把话说全，这比吹优点更有用。

| 绕过手法 | 例子 | 本章能不能挡 |
| --- | --- | --- |
| 插入干扰字符 | 加*微*信 | 挡不住 |
| 全角与半角 | 加ＱＱ | 挡不住，除非词库同时收录 |
| 简繁混写 | 加微信写成「加微信」的繁体 | 挡不住 |
| 同音替换 | 加薇信 | 挡不住 |
| 拼音与首字母 | jwx | 挡不住 |
| 图片承载文字 | 发一张带二维码的图 | 完全超出文本过滤范围 |

要挡前四种，得加一层归一化：去掉非文字字符、全角转半角、繁转简、同音字映射。这层逻辑比前缀树本身复杂得多，而且每加一条规则都可能误伤正常文本（比如把「银行」的同音映射误用）。

真实产品通常是「机器初筛 + 人工复审 + 用户举报」三层。本章只做第一层里最基础的部分。

### 8.2 明确不做

| 未做 | 原因 |
| --- | --- |
| 词库热更新 | 见 4.3，牵动的代码比过滤器本身多 |
| 归一化层（全角、繁体、干扰符） | 见 8.1，复杂度高且容易误伤 |
| AC 自动机 | 见 1.4，当前场景收益不抵复杂度 |
| 命中入库做审核队列 | 需要新表和审核页面，属于另一个功能 |
| 按用户统计命中次数做风控 | 依赖上面那条 |
| 正则规则 | 正则表达力强但性能不可控，高危模式另建一套更合适 |

### 8.3 面试追问

**问：为什么用前缀树，不用正则？**
答：正则的匹配引擎有回溯，词库是用户输入时容易写出性能炸弹。前缀树的复杂度确定，最坏 O(n × 最长词长)，不会因为词库内容变化而突然变慢。另一个原因是正则合并且几千个词会生成超长的表达式，编译本身就慢。

**问：前缀树的时间复杂度是多少？**
答：构建 O(总字符数)。单次匹配我这里的实现是 O(n × k)，k 是最长词长度，因为每个起点最多推进 k 步，命中后跳过整段。严格的 O(n) 要 AC 自动机，用失败指针避免回退。

**问：为什么不用 map 存所有词，直接查？**
答：只能判断「整段文本是不是某个词」，判断不了「文本里含不含有某个词」。要做子串检测，必须对每个起点都试一次，等于 O(n × m)，退化成暴力。

**问：600 字的帖子，过滤一次多久？**
答：实测 500 词库约 29 微秒，20 词库约 14 微秒。发一篇文章要写库、删缓存、发事件，总耗时在毫秒级，过滤占不到 1%。这个结论反过来说明：为过滤做极致优化没有意义，把词库维护好更重要。

**问：词库十万个词会怎样？**
答：构建时间变长，内存变大，但单次匹配耗时基本不变，因为匹配只跟文本和最长词有关。构建十万个词大约几十毫秒，放在启动阶段可以接受。真正的问题在内存，`map[rune]*node` 每个节点约 100 字节，十万个三字词最多三百万个节点，上百 MB，这时候要考虑换成双数组 Trie。

**问：为什么要返回命中词？**
答：为了可观测。只返回替换后的文本，线上出了问题你没法知道是哪个词触发的、用户写了什么。日志里有命中词，才能判断是词库误伤还是真的违规。这也是我把它做成返回值而不是内部日志的原因：调用方可以选择记日志、写审核表，或者丢弃。

**问：过滤在入库前还是读出来时？**
答：入库前。入库前做一次，之后所有读路径（详情、列表、缓存、搜索索引）拿到的都是干净数据。读出来时做，意味着每个出口都要记得过滤，漏一处就漏一片。代价是原文不可恢复，申诉时拿不出证据，这个取舍要看业务合规要求。
