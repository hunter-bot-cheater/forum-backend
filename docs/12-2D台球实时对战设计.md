# 12. 2D 台球实时对战设计

这一份是开工前的设计冻结稿。目标是把 `3d8balls`（pooltool 的桌面 3D 台球）里真正值钱的东西搬进本项目的网站，前端改成竖版 2D，做到双人实时对战。

读完这份文档应当能回答四个问题：物理在哪算、状态归谁管、前端画什么、出问题时怎么恢复。

---

## 12.1 范围与不做的事

**第一版要做**

- 竖版 2D 球台，手机与电脑同一套玩法，参照微信视频里那套界面布局。
- 单人练习（不需要登录也能试玩）与双人实时对战两种模式。
- 邀请关注的人开局：从关注列表挑人发起邀请，对方收到站内通知，点开即进同一间房。
- 服务端权威：球位、回合、犯规、胜负全部由服务端算，客户端只负责渲染与收集输入。
- 断线重连、每杆 30 秒读秒、对手掉线判负。
- 战绩落库、对局回放、Elo。

**第一版不做**

- 3D 视角与视角切换。视频里那套也是近似俯视，2D 能还原九成观感。
- 观战。协议与数据结构预留 `seat=spectator`，界面放到 M9。
- 跳球与扎杆的立体表现。物理照样算 z 轴，2D 只把 z 画成阴影偏移与球体缩放。
- 随机匹配。先用 6 位房间号邀请，匹配池等有量再做。
- 服务端重启后的对局恢复。内存态对局重启即失效，文档里明确写在已知限制。

## 12.2 视频里的界面拆成哪几块

按视频逐块落成组件，尺寸按 390×844 的竖屏基准写，等比放大到平板与桌面。

| 区域 | 视频里的样子 | 本项目对应 |
|---|---|---|
| 顶部左卡 | 对手头像、等级徽章、昵称、剩余球小圆点 | `SeatCard` 组件，`side=opponent` |
| 顶部中 | 比分 0-0 | `ScoreBoard` |
| 顶部右卡 | 自己头像、称号、剩余球 | `SeatCard`，`side=self` |
| 顶部跑马灯 | 喇叭图标加一行系统文案 | `NoticeBar`，犯规、连杆、倒计时提示都走这里 |
| 右侧竖列 | 暂停、礼物、表情、母球视角角度、母球图标 | `SideRail`，第一版只保留暂停。母球视角不做：2D 俯视图本身就是全部信息，多一个机位反而让「球在哪」变模糊 |
| 右侧力度条 | 瞄准时出现的竖向滑块 | `PowerSlider` |
| 底部微调尺 | 刻度尺风格，带球杆图形与力度数字 | `FineTuneRail`，左右各 0.1° 微调，拖动可改力度 |
| 球台 | 竖版台面，六个袋，库边有白色方向标记 | `PoolTable`（Canvas） |
| 右下角 ping | `132ms` 小标签 | `PingBadge` |
| 台下球架 | 双方剩余球横排，带号码 | 与顶部剩余球同源，二选一显示 |

视频里没拍到的两个界面按下面设计，逻辑与主流台球手游一致。

**换人横幅**：屏幕上方 96px 高的圆角条，从顶部滑入，停留 1.6 秒后滑出。内容是双方头像、`轮到你了` 或 `对手回合`、当前球组、倒计时起点。`pointer-events: none`，不遮挡球台操作。

**自由球**：母球进入半透明拖拽态，球下方跟一只手型图标，合法落点范围用淡色描边圈出；首杆的开球手中球只允许放在开球线之后。松手即落位，不需要二次确认。

### 邀请关注的人开局

大厅页的主路径是「挑一个人，发邀请」，输房间号只是备用入口。选人范围就是现有的关注列表，不需要另建好友体系。

```text
我点「邀请」→ 拉 GET /api/users/:id/following 选人
   → POST /api/pool/invites {to_user_id}
   → 服务端建房（6 位房间号）+ 落一条 notification + realtime.Push
   → 对方任何页面收到邀请卡片：接受 / 忽略
   → 接受走 POST /api/pool/invites/:id/accept，拿到 match_id 与一次性 token
   → 双方进 /pool/match/:id，WS 连上后各自发 join
```

四条约束，写在实现里而不是只写在文档里。

| 约束 | 理由 |
|---|---|
| 只能邀请自己关注的人 | 复用 `follow` 表判断，避免陌生人骚扰 |
| 一人在同一时刻只能有 1 条待接受的邀请 | 否则可以刷列表，服务端拒绝第二条 |
| 邀请 60 秒过期 | 过期的邀请点开只回一句「邀请已失效」，不再接受迟到进房 |
| 被邀请方在房里等 90 秒 | 超时房间自动解散，避免房间号被长期占用 |

邀请本身不进 `pool_match`。它只活在内存里（`map[inviteID]*Invite` 加一个过期清扫），落库的东西只有通知那一条，因为通知要能离线查看。对局真正建 `pool_match` 是在双方都进房、`status` 从 `waiting` 转 `playing` 的时候。

## 12.3 总体架构

```text
手机/电脑浏览器
  Canvas 2D 渲染 + 手势输入 + HUD(Vue)
        │  WebSocket /api/ws/game（JSON）
        ▼
Go api 进程
  internal/pool
    manager  对局登记表，一局一个 actor
    actor    状态机 + 八球规则 + 计时器
    conn     WS 读写、心跳、慢客户端剔除
        │  内网 HTTP POST /simulate（只在出杆瞬间）
        ▼
pool-sim 容器（Python + pooltool）
  纯函数：给定球位与杆法，返回事件与轨迹关键帧
        │
        ▼
MySQL  pool_match / pool_shot / pool_rating
```

一次击球的完整时序：

1. 客户端把 `{phi, power, theta, a, b}` 发到 `/api/ws/game`。
2. actor 校验轮次、合法性与参数区间，不合法直接回 `error`，不改状态。
3. actor 调 `sim.Client.Simulate`，带上当前 16 颗球的位置。
4. `pool-sim` 跑 12ms 左右，返回事件、30Hz 关键帧、终局球位。
5. actor 用八球规则判定犯规、进球、换人、胜负。
6. 广播 `shot` 给两名玩家（以后加观战者），同时写 `pool_shot`。
7. 客户端播放轨迹，播放结束落到终局球位，等下一次 `turn` 或 `result`。

## 12.4 六个关键决策

### 决策一：物理留在 pooltool，Go 只做权威状态

`pooltool` 的物理是 7.7k 行 Python，含四次方程求根、库边 Stronge 接触模型、球球摩擦，这套东西重写一遍必然走样。它也被实测过，满台开球 12ms。

Go 侧只做纯函数调用，不算物理。

代价是必须多一个 Python 容器，并且 `pooltool/__init__.py` 会连带导入 `panda3d`，容器里得装这个包（不建窗口就不吃显存）。镜像大约 700MB，磁盘现有 40G 用 21%，可以接受。

备选方案是把物理移植到 Go，能省掉一个容器与一次跨语言调用，但没有两三周做不完，而且手感一定跑偏。除非以后 Python 容器成为运维负担，否则不换。

### 决策二：对局状态与规则归 Go，Python 保持无状态

上一版方案里我倾向让 Python 持有对局对象，直接复用 `Ruleset.process_and_advance`。改成 Go 持有出于三个现实原因。

- 断线重连、超时判负、观战快照这些逻辑都要读对局状态，放在 Go 里不用跨语言往返。
- Python 无状态就是纯函数，崩了重启不影响任何对局，也不用担心内存里堆着几百个 `System` 对象。
- 规则要在 Go 里写测试，20 个边界用例跑一遍几百毫秒，比驱动 Python 跑规则快一个数量级。

代价是八球规则要在 Go 里重写一份，约 400 行。用 pooltool 的 `eight_ball.py` 当参考实现，同一批球局两边各跑一次对比结论，作为金样例。

### 决策三：不单独建网关

`/api/ws/game` 直接挂在现有 api 进程上，和 `/api/ws/notifications` 并列。

理由是这个接口需要 JWT 校验、用户资料、MySQL 写入、限流，这些 api 进程全都有。单独起一个网关要复制四套能力，只在「对局服务需要独立扩缩容」的时候才划算。当前一台 2G 机器，加了也是白加。

保留拆分余地：`internal/pool` 只依赖 `pkg/jwt`、`internal/user` 的读接口和自己的 `store`，真要拆的时候把这三块搬走就行。

### 决策四：一局一个 actor goroutine

```text
Manager.mu 保护 map[uint64]*Match
Match.cmd   chan command（容量 64）
Match.run() 单 goroutine 串行处理所有命令
```

所有状态改动只在 `run()` 里发生，规则、计时、落库都在这条协程上排队，因此不需要给每个字段上锁，也不会出现「读到半个状态」的问题。

广播要出锁（出协程）：actor 只往每个连接的 `send` channel 投递，真正的网络写在连接的写协程里。慢客户端塞不进去就断开，由前端重连补齐，不排队。

### 决策五：通信走 JSON，暂不上二进制

单杆轨迹 30Hz、16 颗球、约 6 秒，JSON 序列化后 40 到 60KB。一局 20 秒左右一杆，带宽压力可以忽略。JSON 的好处是抓包能直接看，调试成本低。

如果以后要上观战且人数很多，再换 msgpack，协议留好 `v` 字段做版本切换。

### 决策六：2D 用原生 Canvas，不引渲染库

三种选择里 Canvas 2D 最合适。

| 方案 | 体积 | 适合度 |
|---|---|---|
| Canvas 2D 手写 | 0 | 16 颗球加台面，画一次不到 1ms，够用 |
| PixiJS | 约 400KB | WebGL 精灵批处理，这个场景用不上 |
| three.js 正交相机 | 约 600KB | 已经有 2D 方案，没必要背 3D 库 |

球的画法是径向渐变加号码贴图，贴图用离屏 canvas 生成 16 份缓存，不加载任何图片。整页除字体外零外部资源，首屏比现在的文章列表还轻。

## 12.6 协议

邀请与战报走 REST，对局过程走 WebSocket。分开的理由是邀请卡片要能被通知中心拉取，刷新页面、换设备都不该丢。

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/pool/invites/pending` | 我收到的、还没过期的邀请 |
| `POST` | `/api/pool/invites` | `{to_user_id}`，只能发给关注的人 |
| `POST` | `/api/pool/invites/:id/accept` | 回 `{match_id, room_code, ws_token}` |
| `POST` | `/api/pool/invites/:id/decline` | 忽略，邀请方收到 `peer.declined` |
| `POST` | `/api/pool/rooms` | `{room_code}` 手动进房，备用入口 |
| `GET` | `/api/pool/matches/:id` | 战绩详情 |
| `GET` | `/api/pool/matches/:id/replay` | 按 `seq` 返回全部 `pool_shot` |

邀请到达时同时做两件事：写一条 `notification`（`type=pool_invite`，带 `invite_id` 与发起人资料），以及通过 `/api/ws/notifications` 推一条即时消息。前端的通知铃铛与大厅页共用同一份 `pending` 列表，点开哪个入口行为一致。

对局过程统一信封，`type` 定路由，`seq` 用于请求应答配对，`ts` 供客户端算延迟。

```json
{ "type": "shoot", "seq": 31, "ts": 1732000000123, "data": { } }
```

**客户端上行**

| type | data | 说明 |
|---|---|---|
| `join` | `{room_code, practice}` | 进房，practice 为 true 时直接开练习局 |
| `ready` | `{}` | 双方都 ready 才开球 |
| `place_cue` | `{x, y}` | 手中球落位 |
| `aim` | `{phi, power, theta, a, b}` | 可选，10Hz 节流，用于让对手看到你的杆头 |
| `shoot` | `{phi, power, theta, a, b, client_seq}` | 出杆，`client_seq` 防重复提交 |
| `resume` | `{match_id, token}` | 重连续局 |
| `leave` | `{}` | 主动退出，判负 |

**服务端下行**

| type | data | 说明 |
|---|---|---|
| `joined` | `{match_id, seat, token, config}` | `token` 存本地，重连凭证 |
| `state` | 完整快照 | 进房、重连、观战统一用这一条 |
| `turn` | `{seat, deadline_ms}` | 换人，含读秒截止时间 |
| `shot` | `{seq, seat, params, frames, events, final, sim_ms}` | 一杆的结果 |
| `foul` | `{reason, ball_in_hand}` | 犯规，文案已本地化 |
| `result` | `{winner, reason, rating_delta}` | 结算 |
| `peer` | `{event}` | `joined` / `left` / `offline` / `declined` 四类 |
| `error` | `{code, message, seq}` | 业务错误，`seq` 与请求配对 |

快照结构，前后端共用一份 TS 类型与 Go struct，字段名一致。

```json
{
  "match_id": 41,
  "status": "playing",
  "seat": 0,
  "turn": 1,
  "deadline_ms": 21000,
  "balls": [
    { "id": "cue", "x": 0.495, "y": 0.990, "z": 0.0286, "on_table": true },
    { "id": "8", "x": 0.512, "y": 1.502, "z": 0.0286, "on_table": true }
  ],
  "group": { "0": "solids", "1": "stripes" },
  "ball_in_hand": false,
  "shot_seq": 7,
  "players": [
    { "user_id": 15, "nickname": "明天也是晴天", "avatar": "/uploads/..." },
    { "user_id": 21, "nickname": "氪星", "avatar": "/uploads/..." }
  ]
}
```

`frames` 只放运动中的球，静止球不出现在关键帧里，体积能砍掉一半以上。单帧结构 `[t, [[id, x, y, z], ...]]`，浮点保留 4 位小数，0.1mm 精度远超绘制需要。

## 12.7 规则

采用中式八球简化规则，与 pooltool 默认规则集的差异列在后面。

| 场景 | 判定 |
|---|---|
| 开球 | 母球必须过开球线撞到球堆，且至少 1 颗球进袋或 4 颗球碰库，否则对手可选择重开或接着打 |
| 定组 | 开球进球不定组；开球后第一次合法进球按该球定组，同时进的另一组球不算 |
| 常规击球 | 母球必须先碰到本方球，之后有球进袋或有球碰库，否则犯规 |
| 母球落袋 | 犯规，对手手中球（可任意摆放） |
| 空杆 | 犯规，同母球落袋 |
| 8 号球提前进袋 | 判负 |
| 8 号球与犯规同杆 | 判负 |
| 8 号球合法进袋 | 本方球全部清完则胜，否则判负 |
| 连续两次超时 | 判负 |
| 主动退出 | 判负 |

与 pooltool 默认规则的三处差异，写进代码注释，避免以后对照源码时困惑。

1. 开球 8 号球进袋按重摆处理，pooltool 按重开整局处理。
2. 第一版不做指袋，8 号球进任一袋都算合法。
3. 三库连续犯规的判负规则不做。

规则写成纯函数，`rules.go` 只接收「上一份状态 + 这一杆的结果」，返回「新状态 + 事件列表」。这样规则测试不需要起对局、不需要网络、不需要数据库。

## 12.8 仿真服务契约

`POST /simulate`

```json
{
  "table": "seven_foot",
  "balls": [ { "id": "cue", "x": 0.495, "y": 0.990, "z": 0.0286 } ],
  "cue": { "phi": 12.5, "power": 0.62, "theta": 0.0, "a": 0.0, "b": -0.25 },
  "sample_hz": 30
}
```

响应：

```json
{
  "duration": 6.08,
  "events": [
    { "t": 0.31, "type": "ball_ball", "a": "cue", "b": "1" },
    { "t": 1.02, "type": "cushion", "a": "1" },
    { "t": 2.44, "type": "pocket", "a": "3", "pocket": "lb" }
  ],
  "frames": [ [0.0, [["cue", 0.495, 0.990, 0.0286]]] ],
  "final": [ { "id": "cue", "x": 0.62, "y": 1.31, "z": 0.0, "on_table": false } ],
  "sim_ms": 12
}
```

约定与边界：

- 入参 `power` 是 0 到 1，服务端映射到 `V0 = min + power * (max - min)`，映射表写在 `simulate.py` 并测试。
- 出参 `phi` 一律用度，`a`、`b` 是杆法偏移比例，与 pooltool 的 `Cue.set_state` 参数一一对应。
- 超过 20 秒仍未收敛视为异常，返回 422，actor 判这一杆无效并提示重试。
- 失败重试一次，仍失败则对局暂停并提示「服务繁忙」，不静默吞掉。
- 启动时 `warmup.py` 跑一杆开球，把 numba 的 7.5 秒冷编译摊到容器启动阶段。

## 12.9 前端设计

### 画布与坐标

台面真实尺寸取自 pooltool 的七尺台，宽 0.9906 米，长 1.9812 米，球半径 0.028575 米，底袋半径 0.062 米，中袋 0.0645 米。

画布只做一次世界到屏幕的仿射变换，命中检测用它的逆变换。这样所有几何代码都在米制下工作，换屏幕只需要改一个缩放系数。

```text
scale = min((canvasW - 2*margin) / tableW, (canvasH - 2*margin) / tableL)
```

竖版摆放时把世界的 y 轴映射到屏幕纵向，母球开球点在下方三分之一，与视频一致。

### 绘制分层

| 层 | 内容 | 重绘时机 |
|---|---|---|
| 静态层 | 台呢、库边、袋口、开球线 | 尺寸变化时画到离屏 canvas |
| 动态层 | 球、阴影、瞄准线、幽灵球、球杆 | 每帧 |
| 覆盖层 | 选中高亮、拖拽落点提示 | 每帧 |

静态层离屏缓存能把每帧绘制从 100 多次降到 30 次以内，低端手机也稳 60fps。

### 交互状态机

```text
idle ──按下并拖动──▶ aiming ──松手──▶ charging ──点出杆──▶ shooting
  ▲                    │                                    │
  └──── 播放结束 ◀──────┴──────── ball_in_hand 子状态 ◀──────┘
```

- `aiming`：拖动改变 `phi`，拖动距离不影响力度，避免误触。
- `charging`：竖向拖动或拖右侧滑块改力度。
- `shooting`：锁定输入，播放服务端轨迹，禁止二次提交。
- `ball_in_hand`：母球跟随手指，合法区域外显示红色描边。

事件统一走 `pointerdown/move/up`，鼠标与触摸一套代码。桌面额外绑键盘，方向键微调 0.1 度，上下键调力度，空格出杆，方便精确操作。

### 手感细节

- 瞄准线只画到第一颗球，画第一段反射，跟视频一致。超过一次反弹的预测会误导用户。
- 力度条从下往上填充，末端 20% 用暖色，给「大力」一个视觉提醒。
- 球速快时给运动模糊一帧的残影，成本低，观感提升明显。
- 播放速度固定为真实时间，服务端返回的 `duration` 就是播放时长，不做加速。
- ping 超过 200ms 时在右上角标黄，提示可能卡顿。

### 与视频的差异

视频顶部有真人头像与称号、右侧有礼物与表情入口，这些属于社交与商业化，第一版不做，位置先留白，避免以后改布局。其余布局按视频来。

## 12.10 断线重连

- 进房成功后服务端发 `joined`，带 `match_id` 与一次性 `token`，客户端存 `localStorage`。
- 连接断开后客户端按 1s、2s、4s、8s 退避重连，最长 30 秒。
- 重连成功先发 `resume`，服务端校验 `user_id + token` 与对局是否还在，通过后回 `state`。
- 若这一杆正在播放，`state` 里的 `shot_seq` 与客户端本地缓存不一致，客户端重放缺失的最后一条 `shot`，并把播放进度快进到已过去的时间。
- 对手断线 60 秒判负，期间横幅显示「对手掉线，58 秒后判胜」。
- 双方都断线，对局在内存里保留 5 分钟，超时回收并写入 `abandoned`。

## 12.11 多对局与观战

- `Manager` 是全局单例，`map[uint64]*Match`，每个对局一条 goroutine，两到三个计时器。
- 并发上限由配置控制，默认 200 局，超过返回「房间已满」。
- 观战在第一版只留数据结构：`seat` 有三种取值，观战者加入时收到 `state` 与后续广播，无法上行 `shoot`。
- 观战者数量上限 10，超过不再接受，避免一个热门对局把连接打满。
- 广播函数按连接列表逐个投递，观战者与玩家同一条通道，不需要两份逻辑。

容量估算，按现有机器：4 个容器约 700MB，`pool-sim` 限 512MB，Go 进程增加的内存主要是连接与对局对象，一局几百 KB。50 局同时在线没有压力，200 局需要观察。

## 12.12 数据模型

```sql
CREATE TABLE pool_match (
  id           BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  room_code    CHAR(6) NOT NULL,
  p0_id        BIGINT UNSIGNED NOT NULL,
  p1_id        BIGINT UNSIGNED NOT NULL,
  status       VARCHAR(16) NOT NULL,
  winner_id    BIGINT UNSIGNED NULL,
  win_reason   VARCHAR(32) NULL,
  shot_count   INT NOT NULL DEFAULT 0,
  started_at   DATETIME NOT NULL,
  ended_at     DATETIME NULL,
  KEY idx_p0 (p0_id, started_at),
  KEY idx_p1 (p1_id, started_at)
);

CREATE TABLE pool_shot (
  id          BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  match_id    BIGINT UNSIGNED NOT NULL,
  seq         INT NOT NULL,
  shooter_id  BIGINT UNSIGNED NOT NULL,
  params      JSON NOT NULL,
  events      JSON NOT NULL,
  frames      MEDIUMBLOB NOT NULL,
  sim_ms      INT NOT NULL,
  created_at  DATETIME NOT NULL,
  UNIQUE KEY uk_match_seq (match_id, seq)
);

CREATE TABLE pool_rating (
  user_id    BIGINT UNSIGNED PRIMARY KEY,
  elo        INT NOT NULL DEFAULT 1000,
  wins       INT NOT NULL DEFAULT 0,
  losses     INT NOT NULL DEFAULT 0,
  updated_at DATETIME NOT NULL
);
```

- `frames` 用 msgpack 压过再存 MEDIUMBLOB，一杆 15KB 左右，一万杆 150MB，可接受。
- 回放就是把 `pool_shot` 按 `seq` 读出来重放，前端复用 `animator`。
- 上面是等价 SQL，实际建表走 GORM。三个模型写进 `internal/model/pool.go`，**必须同时补进 `internal/config/db.go` 的 `Migrate()` 列表**，那个列表是手写的，漏了就只会得到一个「表不存在」的运行时错误，`cmd/migrate` 不会报任何异常。

## 12.13 测试策略

分四层，每层只测自己该管的事。

| 层 | 工具 | 覆盖 |
|---|---|---|
| 规则 | Go table test | 20 个边界用例，含开球、定组、犯规、8 号球、连续超时 |
| 对局 actor | Go 并发测试 | `-race` 下并发投递命令，断言状态一致；断线、超时、重复 `shoot` |
| 协议 | Go httptest | 假 `sim.Client` 通过接口注入，不走网络 |
| 仿真契约 | pytest | 请求响应字段、力度映射、异常收敛、五条金样例轨迹（容差 1e-6） |
| 前端纯逻辑 | vitest | 几何变换、瞄准求交、力度映射、帧插值、状态归并 |
| 前端组件 | vitest + test-utils | HUD 三件套的显示状态、换人横幅、结算抽屉 |

变异验证至少做三处，证明断言不是假绿。

1. 规则里去掉「先碰本方球」判断，对应用例必须红。
2. 超时改判为 120 秒，读秒用例必须红。
3. 重连校验里去掉 `token` 比对，重连用例必须红。

前端 canvas 不做像素比对，只做「装载不抛错、尺寸变化后重算缩放、点击命中正确」的冒烟测试。

## 12.15 部署变更

`docker-compose.yml` 增加一个服务，不发布端口，只在内网被 api 调用。

```yaml
services:
  pool-sim:
    build:
      context: ./pool-sim
      dockerfile: Dockerfile
    expose:
      - "8000"
    environment:
      TZ: Asia/Shanghai
      NUMBA_CACHE_DIR: /tmp/numba
    mem_limit: 512m
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request;urllib.request.urlopen('http://127.0.0.1:8000/healthz')"]
      interval: 30s
      timeout: 5s
      retries: 3
```

api 增加环境变量 `POOL_SIM_URL=http://pool-sim:8000`，`config.yaml` 里给默认值。

三个部署注意点。

1. `pool-sim` 首次 build 要装 numpy、numba、panda3d、scipy，服务器 2G 内存解压 wheel 没问题，但耗时会到两三分钟。建议和 api 分开 build，别一次跑两个。
2. 容器启动后有 8 秒左右的预热窗口，`healthcheck` 的 `start_period` 设 30 秒，避免没预热完就被判不健康。
3. Nginx 只需要一处确认。对局 WS 挂在 `/api/ws/game`，正好落进现有的 `location /api/ws/`，那里已经写好 Upgrade 头与 `proxy_read_timeout 300s`，心跳 25 秒远小于它，不用改配置文件。若把路径写成 `/ws/game`，就会掉进普通 `location /api/`，缺 Upgrade 头，握手直接 426。

生产叠加层里的 `ports: !override` 不用动，新服务没有宿主机端口。

## 12.16 已知限制与风险

| 风险 | 影响 | 处理 |
|---|---|---|
| pool-sim 单 worker | 一局出杆排队 | 12ms 一杆，50 局也排不满；不够再加副本 |
| pooltool 版本升级 | 轨迹手感变化 | `requirements.txt` 锁 0.6.0，升级前跑金样例 |
| 服务重启丢对局 | 进行中的对局中断 | 第一版接受，界面提示「对局已中断」 |
| 规则与 pooltool 有差异 | 对照源码时困惑 | 差异写在 12.7 与代码注释里 |
| 手机横屏 | 布局错位 | 竖屏为主，横屏给旋转提示 |
| 观战者过多 | 带宽与连接数 | 每局上限 10，超出拒绝 |

## 12.17 开工顺序

先做 M0 与 M1，只碰前端，不动后端。理由有两个。

- 渲染与交互是这一版最大的不确定性，先把「看起来像不像」验证掉。
- 后端与仿真容器都依赖前端定义好的数据结构，等类型定下来再写 Go，返工最少。

M1 的验收标准写死三条：390×844 下球台完整可见且不被 HUD 压住，1440×900 下居中且左右留白对称，窗口缩放后球位不漂移。
