# 12. 2D 台球实时对战设计

这一份是开工前的设计冻结稿。目标是把 `3d8balls`（pooltool 的桌面 3D 台球）里真正值钱的东西搬进本项目的网站，前端改成竖版 2D，做到双人实时对战。

读完这份文档应当能回答四个问题：物理在哪算、状态归谁管、前端画什么、出问题时怎么恢复。

---

## 12.1 范围与不做的事

**第一版要做**

- 竖版 2D 球台，手机与电脑同一套玩法，参照微信视频里那套界面布局。
- 单人练习（不需要登录也能试玩）与双人实时对战两种模式。
- 邀请关注的人开局：从关注列表挑人发起邀请，对方收到站内通知，点开即进同一间房。
- 服务端权威：球位、回合、犯规、胜负全部由服务端算，客户端只负责渲染与收集输入。
- 断线重连、每杆 30 秒读秒、对手掉线判负。
- 战绩落库、对局回放、Elo。

**第一版不做**

- 3D 视角与视角切换。视频里那套也是近似俯视，2D 能还原九成观感。
- 观战。协议与数据结构预留 `seat=spectator`，界面放到 M9。
- 跳球与扎杆的立体表现。物理照样算 z 轴，2D 只把 z 画成阴影偏移与球体缩放。
- 随机匹配。先用 6 位房间号邀请，匹配池等有量再做。
- 服务端重启后的对局恢复。内存态对局重启即失效，文档里明确写在已知限制。

## 12.2 视频里的界面拆成哪几块

按视频逐块落成组件，尺寸按 390×844 的竖屏基准写，等比放大到平板与桌面。

| 区域 | 视频里的样子 | 本项目对应 |
|---|---|---|
| 顶部左卡 | 对手头像、等级徽章、昵称、剩余球小圆点 | `SeatCard` 组件，`side=opponent` |
| 顶部中 | 比分 0-0 | `ScoreBoard` |
| 顶部右卡 | 自己头像、称号、剩余球 | `SeatCard`，`side=self` |
| 顶部跑马灯 | 喇叭图标加一行系统文案 | `NoticeBar`，犯规、连杆、倒计时提示都走这里 |
| 右侧竖列 | 暂停、礼物、表情、母球视角角度、母球图标 | `SideRail`，第一版只保留暂停。母球视角不做：2D 俯视图本身就是全部信息，多一个机位反而让「球在哪」变模糊 |
| 右侧力度条 | 瞄准时出现的竖向凹槽滑块，贴着库边（离外框 12px 左右） | `PowerSlider`，挂在球台外层 24px 处，不贴屏幕右边缘 |
| 底部微调尺 | 刻度尺风格，带球杆图形与力度数字 | `FineTuneRail`，`−0.1° / 当前角度 / +0.1°` 三个元素，按住连发，键盘方向键也行；力度只在右侧 `PowerSlider` 上给 |
| 球台 | 竖版台面，六个袋，库边有白色方向标记 | `PoolTable`（Canvas） |
| 右下角 ping | `132ms` 小标签 | `PingBadge` |
| 台下球架 | 双方剩余球横排，带号码 | 与顶部剩余球同源，二选一显示 |

视频里没拍到的两个界面按下面设计，逻辑与主流台球手游一致。

**换人横幅**：屏幕上方 96px 高的圆角条，从顶部滑入，停留 1.6 秒后滑出。内容是双方头像、`轮到你了` 或 `对手回合`、当前球组、倒计时起点。`pointer-events: none`，不遮挡球台操作。

**自由球**：母球从台面上消失，换成一颗半透明白球加一圈虚线（`renderer.drawGhostBall`），
指针指到哪它跟到哪：桌面端悬停即可，手机端拖动，点一下台面也只是挪过去。
位置看好再点底栏的「放这里」落位。**不要做成松手即落位**——手一抖就落定，
下一次能再摆要等下一杆犯规，真人台球里这颗球本来就是自己拿着比的。
首杆的开球手中球只允许放在开球线之后。

### 从点进台球到开局的三段

开局不是「点一下就直接打」，但也不需要先申请、再进房、再准备地跳三次页面。
大厅本身就是「我的房间」：点进台球就有一间自己的房，房号摆在屏幕上，
对面那个位置空着等人。

```text
① 大厅 /pool ＝ 我的房间
   进页面 → POST /api/pool/rooms/my
      没有就开一间（6 位房号），有就返回同一间——刷新多少次都是同一个号
   卡片：左边我的头像，右边空位（或对手），上面房号 + 复制
   找人打：GET /api/pool/online 拉在线名单 → 点「邀请」
          → POST /api/pool/invites {to_user_id}（对方必须在线）
          → 服务端把这间房的房号推给他
   被人打：把房号报给对方，他输进「有房号？直接进」
          → POST /api/pool/rooms/join {room_code}

② 请求弹层（对方当前所在页面，不跳走）
   收到 pool_invite 推送 → InviteRequest 弹出：谁邀请你、房号、两个按钮
   接受 → POST /api/pool/invites/:id/accept → 坐到邀请人那间房的座位 1
        → 跳 /pool，也就是「对方的房间」
   拒绝 → 只收起卡片；房间留着，房号还能给别人用
   忽略 → 只关弹层，60 秒内还能从通知中心点回来

③ 准备与开局（还在 /pool）
   对面有人之后，「准备」按钮才可点；两边都 ready=true 时服务端置 playing
   → 返回的快照里 status=playing → 两边各自 router.replace('/pool/match/:id')

④ 对局页 /pool/match/:id
   全屏 Canvas + HUD，逻辑见 12.9
```

**大厅就是房间**的理由：房号是这一屏上最重要的信息，多一层跳转只会让人找不到它。
「点开台球 → 看到自己的房 → 把号报出去」是一条直线，
中间插一页「房间」反而要多回答一次「我现在这间房是哪间」。

**弹层不跳页**的理由：对方可能正在写文章或看私信，直接把人拽走是最容易引起反感的行为。
弹层只占屏幕中间一块，接受才走，拒绝就留在原地。

**大厅必须能单独刷新**：它的全部状态都来自 `POST /api/pool/rooms/my`，
不依赖上一页的内存态。刷新之后还是同一间房、同一个房号。

**准备状态要能撤销**：*取消准备* 在开局前随时可以点，
但它只影响 `ready`，不会把对面请出去。

五条约束，写在实现里而不是只写在文档里。

| 约束 | 理由 |
|---|---|
| 邀请不限关注，但对方必须在线 | 台球不该是只有互相关注才能玩的游戏；而离线的邀请只能干等一分钟，对方根本不会知道 |
| 一个人同时只在一间房里等 | 进别人的房间时，自己原来那间作废。留着它会「我的房间」在两行之间来回跳 |
| 一人在同一时刻只能有 1 条待接受的邀请 | 否则可以刷列表，服务端拒绝第二条 |
| 邀请 60 秒过期 | 过期的邀请点开只回一句「邀请已失效」，不再接受迟到进房 |
| 房间超时自动回收 | 内存里十分钟没人跟它说话就收；库里两小时还没开打标 expired |

邀请本身不进 `pool_match`。它只活在内存里（`map[inviteID]*Invite` 加一个过期清扫），
落库的东西只有通知那一条，因为通知要能离线查看。`pool_match` 在**开房时**就建，
`status=waiting`、`p1_id` 为空；有人输房号进来才补上 `p1_id`，双方准备齐了才转 `playing`。

`p1_id` 用 NULL 而不是 0 表示空位：0 不是合法用户，用它会让每个读这行的地方
都得多一条「0 是不是真的没人」的特例。

## 12.3 总体架构

```text
手机/电脑浏览器
  Canvas 2D 渲染 + 手势输入 + HUD(Vue)
        │  WebSocket /api/ws/game（JSON）
        ▼
Go api 进程
  internal/pool
    manager  对局登记表，一局一个 actor
    actor    状态机 + 八球规则 + 计时器
    conn     WS 读写、心跳、慢客户端剔除
        │  内网 HTTP POST /simulate（只在出杆瞬间）
        ▼
pool-sim 容器（Python + pooltool）
  纯函数：给定球位与杆法，返回事件与轨迹关键帧
        │
        ▼
MySQL  pool_match / pool_shot / pool_rating
```

一次击球的完整时序：

1. 客户端把 `{phi, power, theta, a, b}` 发到 `/api/ws/game`。
2. actor 校验轮次、合法性与参数区间，不合法直接回 `error`，不改状态。
3. actor 调 `sim.Client.Simulate`，带上当前 16 颗球的位置。
4. `pool-sim` 跑 12ms 左右，返回事件、30Hz 关键帧、终局球位。
5. actor 用八球规则判定犯规、进球、换人、胜负。
6. 广播 `shot` 给两名玩家（以后加观战者），同时写 `pool_shot`。
7. 客户端播放轨迹，播放结束落到终局球位，等下一次 `turn` 或 `result`。

## 12.4 六个关键决策

### 决策一：物理留在 pooltool，Go 只做权威状态

`pooltool` 的物理是 7.7k 行 Python，含四次方程求根、库边 Stronge 接触模型、球球摩擦，这套东西重写一遍必然走样。它也被实测过，满台开球 12ms。

Go 侧只做纯函数调用，不算物理。

代价是必须多一个 Python 容器，并且 `pooltool/__init__.py` 会连带导入 `panda3d`，容器里得装这个包（不建窗口就不吃显存）。镜像大约 700MB，磁盘现有 40G 用 21%，可以接受。

备选方案是把物理移植到 Go，能省掉一个容器与一次跨语言调用，但没有两三周做不完，而且手感一定跑偏。除非以后 Python 容器成为运维负担，否则不换。

### 决策二：对局状态与规则归 Go，Python 保持无状态

上一版方案里我倾向让 Python 持有对局对象，直接复用 `Ruleset.process_and_advance`。改成 Go 持有出于三个现实原因。

- 断线重连、超时判负、观战快照这些逻辑都要读对局状态，放在 Go 里不用跨语言往返。
- Python 无状态就是纯函数，崩了重启不影响任何对局，也不用担心内存里堆着几百个 `System` 对象。
- 规则要在 Go 里写测试，20 个边界用例跑一遍几百毫秒，比驱动 Python 跑规则快一个数量级。

代价是八球规则要在 Go 里重写一份，约 400 行。用 pooltool 的 `eight_ball.py` 当参考实现，同一批球局两边各跑一次对比结论，作为金样例。

### 决策三：不单独建网关

`/api/ws/game` 直接挂在现有 api 进程上，和 `/api/ws/notifications` 并列。

理由是这个接口需要 JWT 校验、用户资料、MySQL 写入、限流，这些 api 进程全都有。单独起一个网关要复制四套能力，只在「对局服务需要独立扩缩容」的时候才划算。当前一台 2G 机器，加了也是白加。

保留拆分余地：`internal/pool` 只依赖 `pkg/jwt`、`internal/user` 的读接口和自己的 `store`，真要拆的时候把这三块搬走就行。

### 决策四：一局一个 actor goroutine

```text
Manager.mu 保护 map[uint64]*Match
Match.cmd   chan command（容量 64）
Match.run() 单 goroutine 串行处理所有命令
```

所有状态改动只在 `run()` 里发生，规则、计时、落库都在这条协程上排队，因此不需要给每个字段上锁，也不会出现「读到半个状态」的问题。

广播要出锁（出协程）：actor 只往每个连接的 `send` channel 投递，真正的网络写在连接的写协程里。慢客户端塞不进去就断开，由前端重连补齐，不排队。

### 决策五：通信走 JSON，暂不上二进制

单杆轨迹 30Hz、16 颗球、约 6 秒，JSON 序列化后 40 到 60KB。一局 20 秒左右一杆，带宽压力可以忽略。JSON 的好处是抓包能直接看，调试成本低。

如果以后要上观战且人数很多，再换 msgpack，协议留好 `v` 字段做版本切换。

### 决策六：2D 用原生 Canvas，不引渲染库

三种选择里 Canvas 2D 最合适。

| 方案 | 体积 | 适合度 |
|---|---|---|
| Canvas 2D 手写 | 0 | 16 颗球加台面，画一次不到 1ms，够用 |
| PixiJS | 约 400KB | WebGL 精灵批处理，这个场景用不上 |
| three.js 正交相机 | 约 600KB | 已经有 2D 方案，没必要背 3D 库 |

球的画法是径向渐变加号码贴图，贴图用离屏 canvas 生成 16 份缓存，不加载任何图片。整页除字体外零外部资源，首屏比现在的文章列表还轻。

## 12.6 协议

邀请与战报走 REST，对局过程走 WebSocket。分开的理由是邀请卡片要能被通知中心拉取，刷新页面、换设备都不该丢。

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/pool/rooms/my` | 我的房间：没有就开一间，有就返回同一间。大厅每 2 秒（对面有人）/10 秒（独自）轮询它 |
| `POST` | `/api/pool/rooms/join` | `{room_code}`：房号进别人的房间，坐到座位 1 |
| `POST` | `/api/pool/rooms/leave` | 退出别人的房间（只认「我是客人」那一间） |
| `POST` | `/api/pool/rooms/reopen` | 换一间：当前这间作废，另开一间新房号。对面关掉页面不走时用 |
| `GET` | `/api/pool/rooms/:id` | 房间快照。按 id 取，越权（不在房里）回 403 |
| `POST` | `/api/pool/rooms/:id/ready` | `{ready}`，双方齐了服务端置 `playing` |
| `GET` | `/api/pool/online` | 现在在线、且没在打的人；关注的排前面，上限 30 |
| `GET` | `/api/pool/invites/pending` | 我收到的、还没过期的邀请 |
| `POST` | `/api/pool/invites` | `{to_user_id}`，对方必须在线，不再要求关注 |
| `POST` | `/api/pool/invites/:id/accept` | 坐到邀请人那间房的座位 1，回 `{match_id, room_code}` |
| `POST` | `/api/pool/invites/:id/decline` | 忽略，邀请方收到 `pool_invite_declined`；房间不跟着收 |
| `GET` | `/api/pool/matches/:id/replay` | 按 `seq` 返回全部 `pool_shot`，只有当事人能看 |
| `GET` | `/api/pool/live` | 正在进行的对局（观战入口） |
| `GET` | `/api/pool/records` | 我的战绩（界面不显示积分） |

邀请到达时同时做两件事：写一条 `notification`（`type=pool_invite`，带 `invite_id` 与发起人资料），以及通过 `/api/ws/notifications` 推一条即时消息。前端的通知铃铛与大厅页共用同一份 `pending` 列表，点开哪个入口行为一致。

### `/api/ws/notifications` 上的四条台球帧

这四条都走全局通知连接，不占对局连接——邀请与「有人进房」要能到达任何页面。

| type | data | 收件人 | 用途 |
|---|---|---|---|
| `pool_invite` | `{invite_id, match_id, room_code, from, expires_in}` | 被邀请人 | 弹请求卡 |
| `pool_invite_accepted` | `{match_id, room_code}` | 邀请人 | 把人带回大厅（对面已经坐了人） |
| `pool_invite_declined` | `{match_id, room_code}` | 邀请人 | 收起等待卡并提示 |
| `pool_room_joined` | `{match_id, room_code, player}` | 房主 | 对面那个空位立刻换成人 |

`pool_room_joined` 是房间轮询能降到十秒的前提：没有它，对面进来这件事只能靠轮询发现。
它带完整玩家资料，是因为房主那一屏要立刻画出头像与昵称，只给 id 还得再请求一次。
推送丢了也不致命——下一轮轮询会补上，最坏晚十秒。

对局过程统一信封，`type` 定路由，`seq` 用于请求应答配对，`ts` 供客户端算延迟。

```json
{ "type": "shoot", "seq": 31, "ts": 1732000000123, "data": { } }
```

**客户端上行**

| type | data | 说明 |
|---|---|---|
| `join` | `{room_code, practice}` | 进房，practice 为 true 时直接开练习局 |
| `place_cue` | `{x, y}` | 手中球落位 |
| `aim` | `{phi, power, theta, a, b}` | 可选，10Hz 节流，用于让对手看到你的杆头 |
| `shoot` | `{phi, power, theta, a, b, client_seq}` | 出杆，`client_seq` 防重复提交 |
| `resume` | `{match_id, token}` | 重连续局 |
| `leave` | `{}` | 主动退出，判负 |

**服务端下行**

| type | data | 说明 |
|---|---|---|
| `joined` | `{match_id, seat, token, config}` | `token` 存本地，重连凭证 |
| `state` | 完整快照 | 进房、重连、观战统一用这一条 |
| `turn` | `{seat, deadline_ms}` | 换人，含读秒截止时间 |
| `shot` | `{seq, seat, params, frames, events, final, sim_ms}` | 一杆的结果 |
| `foul` | `{reason, ball_in_hand}` | 犯规，文案已本地化 |
| `result` | `{winner, reason, rating_delta}` | 结算 |
| `peer` | `{event}` | `joined` / `left` / `offline` / `declined` 四类 |
| `error` | `{code, message, seq}` | 业务错误，`seq` 与请求配对 |

大厅（房间阶段）不连对局 WebSocket。准备是低频动作，轮询 `POST /api/pool/rooms/my` 就够，
看到 `status` 变成 `playing` 再 `replace` 到对局页——这样 `房间 → 对局` 不涉及连接迁移，
也就没有「刚连上就要重连」的空窗。

轮询分两档，按「对面有没有人」切换：

| 状态 | 间隔 | 理由 |
|---|---|---|
| 只有自己 | 10 秒 | 对面进人由 `pool_room_joined` 推送补位，快轮询只是白烧请求 |
| 对面有人 | 2 秒 | 对方的准备状态要尽快看到，差两秒可接受，再慢就有错位感 |

限流是按 IP 的令牌桶（容量 10、每秒补 2），首屏一次要发九个请求，本来就贴着上限；
如果房间每两秒问一次，同一个人开两个页面就会把额度烧光，别的页面开始弹「请求太频繁」。

快照结构，前后端共用一份 TS 类型与 Go struct，字段名一致。

```json
{
  "match_id": 41,
  "status": "playing",
  "seat": 0,
  "turn": 1,
  "deadline_ms": 21000,
  "balls": [
    { "id": "cue", "x": 0.495, "y": 0.990, "z": 0.0286, "on_table": true },
    { "id": "8", "x": 0.512, "y": 1.502, "z": 0.0286, "on_table": true }
  ],
  "group": { "0": "solids", "1": "stripes" },
  "ready": [true, false],
  "ball_in_hand": false,
  "shot_seq": 7,
  "players": [
    { "user_id": 15, "nickname": "明天也是晴天", "avatar": "/uploads/..." },
    { "user_id": 21, "nickname": "氪星", "avatar": "/uploads/..." }
  ]
}
```

`ready` 是房间页的两个准备标记，对局开始后恒为 `[true, true]`。客户端不按它推断能不能出杆，能不能出杆只看 `status` 与 `turn`。

`frames` 只放运动中的球，静止球不出现在关键帧里，体积能砍掉一半以上。单帧结构 `[t, [[id, x, y, z], ...]]`，浮点保留 4 位小数，0.1mm 精度远超绘制需要。

## 12.7 规则

采用中式八球简化规则，与 pooltool 默认规则集的差异列在后面。

| 场景 | 判定 |
|---|---|
| 开球 | 母球必须撞到球堆，且至少 1 颗球进袋或 3 颗球碰库，否则犯规、对手手中球 |
| 定组 | 开球进球不定组；开球后第一次合法进球按该球定组，同时进的另一组球不算 |
| 常规击球 | 母球必须先碰到本方球，之后有球进袋或有球碰库，否则犯规 |
| 母球落袋 | 犯规，对手手中球（可任意摆放） |
| 空杆 | 犯规，同母球落袋 |
| 8 号球提前进袋 | 判负 |
| 8 号球与犯规同杆 | 判负 |
| 8 号球合法进袋 | 本方球全部清完则胜，否则判负 |
| 连续两次超时 | 判负 |
| 主动退出 | 判负 |

开球门槛取三颗而不是官方的四颗：官方那条是按职业开球（母球 30 km/h 以上）定的，
本仿真的满力只有 7 m/s（`pool-sim` 的 `MAX_BALL_SPEED`），实测同一杆开球要到 0.9
力度才第一次凑到四颗碰库，照四颗判，玩家用中档力度开球必然犯规，开局第一杆就把
手中球送给对手。三颗对应半力以上开球，轻碰一下仍然算没打开。

与 pooltool 默认规则的三处差异，写进代码注释，避免以后对照源码时困惑。

1. 开球 8 号球进袋按重摆处理，pooltool 按重开整局处理。
2. 第一版不做指袋，8 号球进任一袋都算合法。
3. 三库连续犯规的判负规则不做。

规则写成纯函数，`rules.go` 只接收「上一份状态 + 这一杆的结果」，返回「新状态 + 事件列表」。这样规则测试不需要起对局、不需要网络、不需要数据库。

## 12.8 仿真服务契约

`POST /simulate`

```json
{
  "table": "seven_foot",
  "balls": [ { "id": "cue", "x": 0.495, "y": 0.990, "z": 0.0286 } ],
  "cue": { "phi": 12.5, "power": 0.62, "theta": 0.0, "a": 0.0, "b": -0.25 },
  "sample_hz": 30
}
```

响应：

```json
{
  "duration": 6.08,
  "events": [
    { "t": 0.31, "type": "ball_ball", "a": "cue", "b": "1" },
    { "t": 1.02, "type": "cushion", "a": "1" },
    { "t": 2.44, "type": "pocket", "a": "3", "pocket": "lb" }
  ],
  "frames": [ [0.0, [["cue", 0.495, 0.990, 0.0286]]] ],
  "final": [ { "id": "cue", "x": 0.62, "y": 1.31, "z": 0.0, "on_table": false } ],
  "sim_ms": 12
}
```

约定与边界：

- 入参 `power` 是 0 到 1，服务端映射到 `V0 = min + power * (max - min)`，映射表写在 `simulate.py` 并测试。
- 出参 `phi` 一律用度，`a`、`b` 是杆法偏移比例，与 pooltool 的 `Cue.set_state` 参数一一对应。
- 超过 20 秒仍未收敛视为异常，返回 422，actor 判这一杆无效并提示重试。
- 失败重试一次，仍失败则对局暂停并提示「服务繁忙」，不静默吞掉。
- 启动时 `warmup.py` 跑一杆开球，把 numba 的 7.5 秒冷编译摊到容器启动阶段。

## 12.9 前端设计

### 画布与坐标

台面真实尺寸取自 pooltool 的七尺台，宽 0.9906 米，长 1.9812 米，球半径 0.028575 米，底袋半径 0.062 米，中袋 0.0645 米。

画布只做一次世界到屏幕的仿射变换，命中检测用它的逆变换。这样所有几何代码都在米制下工作，换屏幕只需要改一个缩放系数。

```text
scale = min((canvasW - 2*margin) / tableW, (canvasH - 2*margin) / tableL)
```

竖版摆放时把世界的 y 轴映射到屏幕纵向，母球开球点在下方三分之一，与视频一致。

### 视觉规范（照参考录屏取色）

球台外框宽高比固定为 `(0.9906 + 2×0.1058) / (1.9812 + 2×0.1058) = 1.2022 / 2.1928`，
容器按这个比例撑开（`.fs-table-stage` + `.fs-table-box`，对局 / 观战 / 回放三处共用）。
容器比例一旦和球台对不上，`fitTable` 就会在画布里补一圈黑边：球台白白小一圈，
挂在台边的力度条也被推远。竖屏下按宽度推高度，横屏下按高度推宽度，两个方向都要覆盖。

**但这两档各自只认一个方向**：手机竖屏且浏览器工具栏吃掉一百多像素时（100dvh 只剩六百来像素），
按宽度推出来的高度超出这一栏，球台又是居中的，于是上下各溢出一截——压在顶栏的头像与燃烧条上，
底部顶住微调尺。有容器查询的浏览器改用 `min(100cqw, calc(100cqh × 1.2022 / 2.1928))`：
两个方向取更紧的那条边，永远塞得进这一栏，代价是矮屏上球台两侧留白变宽。
`@supports (width: 1cqw)` 兜住老浏览器，它们仍走上面那两档媒体查询。

**球台宽度 = 可用高度 × 0.548。** 这是竖版画法的硬约束：想让 390 宽的屏幕被球台占满，
高度得有 711px，手机竖屏怎么都拿不出来。所以「球台再大一点」只能从**纵向的界面高度**里挤，
`@media (max-width: 720px) and (max-height: 780px)` 那一档专门干这件事：

| 收掉的地方 | 省下 | 说明 |
|---|---|---|
| 顶栏 68 → 58 | 10px | 座位卡自身 54 高，58 刚好放得下 |
| 已进袋那排 | 30px | 席位卡上已经写着各自剩几颗，这排只是「按顺序」的补充 |
| 微调尺 42 → 34、按钮 34 → 30 | 8px | 角度读数 15px，按钮 13px |
| 底栏留白与球台下方内边距 | 12px | 这一段是纯留白 |

合计 60px，换成宽度是 33px：390×720 的机器上球台从 305 宽变成 338（占屏 87%），
390×616 的机器上从 248 变成 281（72%）。判别用 780px：再高的屏幕上球台已经是被宽度卡住的，
收高度只会多出上下留白，那排已进袋的球就不该被牺牲。
音效开关同时从「已进袋那排」里挪出来，绝对定位到右下角——不然那一排一收，开关也跟着没了。

| 元素 | 颜色 | 说明 |
|---|---|---|
| 页面底 | `#2d2e3b → #171720` 径向渐变 | 不是纯黑，纯黑会把中灰外框和绿呢一起压死 |
| 外框 | `#454a50 → #35383c → #24272b` 斜向渐变 | 石墨灰，不是棕色木纹；整块单色会像一张压平的卡纸 |
| 库边 | `#0a4a2d` | 比台呢暗一档，球台才有纵深 |
| 台呢 | `#1f8a58`，中心受光到 `#2aa267` | 中间一块横向椭圆的受光（灯罩是长条形）+ 四角 18% 暗角 + 4px 织物颗粒 |
| 袋口 | `#04060a` + 22% 的灰边 | 灰边是皮口倒角，没有它就是一个黑贴纸 |
| 库边标记 | 白色菱形，长库 7 个（中袋位置空着）、短库 3 个 | 也是瞄准时的角度参照 |

**球按物理直径的 1.2 倍画**（`BALL_DRAW_SCALE`）。真实比例下球径只占台面宽的 5.8%，
手机上只有十几像素，看着像撒了一把彩点；参考录屏是 7.2%，主流台球手游都在 1.2 倍上下。
只放大「画」出来的半径，物理坐标与判定一动都不动，代价是摆在一起的球会有轻微视觉重叠——
这正是这类 App 看起来「球大好打」的原因，不要试图去修。

### 绘制分层

| 层 | 内容 | 重绘时机 |
|---|---|---|
| 静态层 | 台呢、库边、袋口、开球线 | 尺寸变化时画到离屏 canvas |
| 动态层 | 球、阴影、瞄准线、幽灵球、球杆 | 每帧 |
| 覆盖层 | 手中球虚影（半透明白球 + 虚线外圈） | 每帧，只在自由球时画 |

球杆长度取 34 倍球半径：真实球杆是 50 倍半径，但画布只比球台大一圈，
按真实长度画，杆尾会甩出画布被切掉。34 倍是这条约束下的折中。

**位图倍率 = 设备像素比 × 超采样系数。** 设备像素比是下限（一个 CSS 像素至少落到
整数倍的物理像素上），系数在 1x 屏上取 1.75、2x 取 1.4、3x 取 1.2，再受一帧 4.8M
物理像素的预算约束（`PIXEL_BUDGET`）。球缘、袋口圆弧、瞄准线都是矢量绘制的，超采样
之后多一像素的过渡余地，边缘才是圆滑而不是台阶。球面贴图的边长上限 `SPRITE_MAX_SIDE`
跟着抬到 128，否则超采样之后贴图反而被放大，号码会更糊。

静态层离屏缓存能把每帧绘制从 100 多次降到 30 次以内，低端手机也稳 60fps。

### 交互状态机

```text
idle ──指针进台面──▶ aiming ──点一下台面──▶ locked ──拖力度条──▶ shooting
  ▲                     │                       │                  │
  └──── 播放结束 ◀───────┴─── 再点一下解锁 ◀─────┘                  │
  └────────────────────── 播放结束 ◀───────────────────────────────┘
```

`ball_in_hand` 是 `aiming` 前面的一层子状态：先把球放下，再谈瞄准。

- `aiming`：指针指到哪，瞄准线就指到哪（桌面靠悬停，手机靠拖动）。键盘左右键 ±0.1°、按住 Shift ±1°，这是唯一不会把指针带偏的微调方式。
- `locked`：点一下台面把方向定住，球杆同时换成暖色。这一下是必需的：不锁的话，手从球台移到右侧力度条这一路会把方向一路带偏，最后一杆朝哪打取决于鼠标怎么划过去的。
- `shooting`：松手出杆后锁输入，播放服务端轨迹，禁止二次提交。
- `ball_in_hand`：母球是半透明虚影加虚线外圈，指针指到哪跟到哪，点台面只挪位置，点底栏「放这里」才落位，可以反复挪。

事件统一走 `pointerdown/move/up`，鼠标与触摸一套代码。

球杆沿击球方向的**反方向**伸出去，杆头贴在母球后面，力度越大杆子拉得越远——这一笔同时是瞄准指示与力度反馈，台面上不用第二条力量条。

### 手感细节

- 瞄准线只画到第一颗球，画第一段反射，跟视频一致。超过一次反弹的预测会误导用户。
- 力度条从下往上填充，末端 20% 用暖色，给「大力」一个视觉提醒。
- 球速快时给运动模糊一帧的残影，成本低，观感提升明显。
- 播放速度固定为真实时间，服务端返回的 `duration` 就是播放时长，不做加速。
- ping 超过 200ms 时在右上角标黄，提示可能卡顿。

### 加塞与引导线

瞄准线由三段组成，全部来自 `game/aim.ts`（几何）与 `game/predict.ts`（物理）的同一套数学：

| 段 | 含义 | 端点 |
| --- | --- | --- |
| 母球线 | 母球沿 `phi` 走到第一次接触 | 母球表面 → 幽灵球心 |
| 目标球线 | 被撞的球沿球心连线出去 | 目标球表面 → 第一颗挡路的球／库边／长度上限 |
| 母球切线 | 母球撞完沿切线分开，正碰时没有这一段 | 幽灵球表面 → 同上 |

三条线都会在「第一颗挡路的球」处断开：线画到哪，球就能走到哪。以前只按长度上限截断，
去路上五厘米外杵着一颗球时线会径直穿过去，玩家照着线判断走位必然对不上。

**瞄准线的精度靠两件事保证。**

第一是接触时刻。碰撞原来按「整步走完」的位置取法向，母球满速一步走 18.3 毫米，
球心连线被这半个球半径的穿透量带偏，打薄球时目标球能飞出五到九度，而线还是老方向。
现在每步先用二次方程解出「本步内真正相切」的时刻，把两颗球退回那一刻再算冲量
（`contactTime` / `separate`），实测把偏差压到 0.5 度以内，`predict.spec.ts` 里
按六种厚度 × 三档力度锁死。

第二是贴球。母球紧贴着另一颗球是很常见的摆位，射线求交如果在圆上起步，
会滑到二次方程的远端根，把幽灵球摆到那颗球的**另一侧**，线就穿过了整颗球
（照着打其实是当场撞上去）。现在起点落在圆内或圆上时直接判「立刻接触」。

**加塞**走协议里早就留着的 `a`（左右塞）、`b`（高低杆），取值都是 -1 到 1。

- `a` 折算成绕竖直轴的侧旋，撞库时兑现：库边把它的一部分换成切向速度，
  顺塞放大反弹角、反塞收窄，同一副塞在相对的两条库上方向相反。二维模型里
  竖直轴的旋转不产生弧线，也不去模拟抬杆的横轴旋转（`theta` 仍恒为 0）。
- `b` 在母球第一次撞球时结算：正数沿来球方向送出去（高杆跟进），负数拉回来（低杆），
  力度按**撞前**球速算——按出杆初速算的话，远距离低杆会夸张得像倒车。
- **塞在撞球那一刻也起作用**（`applyEnglish`）。母球带塞撞上目标球时接触点有侧向
  滑动，摩擦力把目标球从球心连线推开，这就是真实台球的**甩球**（throw）。
  量按 Dr. Dave 的实测标定（`THROW_MAX_DEG`）：

  | 条件 | 甩球角 |
  | --- | --- |
  | 满塞、2 m/s 左右 | 约 1° |
  | 半颗塞、慢球、中杆 | 最大，约 5° |
  | 再往满塞推 | 反而变小（接触点从抓得住变成打滑） |
  | 高杆／低杆 | 压到四分之一上下 |
  | 4 m/s 的球 | 只剩零点几度 |

  方向是「右塞把目标球往连线左侧甩，左塞反之」。同时目标球被搓出一点反向侧旋
  （两颗球像齿轮），它接着撞库时能看出来；母球自己留下四分之三的侧旋。
- **引导线的目标球段跟着甩球角一起偏**（`aimGuides` 的 `spin` 参数），用的是同一个
  `spinThrowDeg`，两边差一点点玩家都能在袋口看出来。

有意不做的两件事，都不是漏了：

- **偏杆**（squirt / deflection）：真实里满塞会让母球出射方向偏离球杆指向 2~3°。
  做了之后引导线画的就不是球实际走的方向，玩家立刻会说「线在骗人」。
- **切角甩球**（CIT）：不加塞的斜切也会被甩 1~2°。它跟加塞无关，却会让「什么塞都
  没加」的球也偏离引导线，代价比收益大。

界面对着一张参考图做：收起态是右下角一颗小球（红点即击球点，角度标签挂在球的正下方），
点开后是一块盖在球台上的面板——球面上一横一竖两条虚线是中杆基准，
红点离开哪条线就是加了哪一项，左上「重置」回中杆，右上角读数是百分点。
拖出球面时沿半径夹到 0.92，不会因为手指滑出去而清零。

### 与视频的差异

视频顶部有真人头像与称号、右侧有礼物与表情入口，这些属于社交与商业化，第一版不做，位置先留白，避免以后改布局。其余布局按视频来。

## 12.10 断线重连

以下是实现后的版本（与设计稿初版有出入，以这里为准）。

- 握手带 `token` 与 `match_id`，服务端在 `Upgrade` **之前**认人认座位：
  升级之后响应头已经发出，再返回 401 浏览器只会看到一次莫名的连接失败。
- **断线不判负。** 连接断开只做两件事：把这条件从登记表摘掉、给对手发 `peer offline`。
  摘的时候只摘「仍登记着的这一条」——玩家可能已经用新连接重连上来，
  旧连接的退出回调晚到一步时不能把新连接一起清掉。读秒照常走。
- 重连就是重新 `Join` 同一个座位：顶掉旧连接，回 `joined` + 一份完整 `state`。
  没有增量补发，也没有 `resume` 消息——快照本身就是收敛点。
- 客户端退避 1s、2s、4s、8s…（8 次，单次封顶 8s，合计约 47 秒），
  所以「拔网半分钟」不需要用户做任何事，时序在 `web/src/game/protocol.ts`。
- 窗口走完才 `gaveup`：整屏拦一下，给「重新连接」与「回大厅」两个出口。
  `connect()` 内部复位重试计数，人工重试是一轮全新的退避。
- 重连后客户端按快照整份重建场景（球位、轮次、定组、手中球、读秒上限），
  不与本地状态合并。
- 断线期间读秒到点由服务端照常处理：一次换人、连续两次判负。规则不因为掉线暂停。

**验收**：`pool-reconnect.mjs` —— 掐断一条真实 WS，对手收到 `offline`；
三秒后重连拿到 16 颗球的快照并接着出杆成功；另一方断开 32 秒回来，
对局仍是 `playing`。

## 12.11 多对局与观战

- `Manager` 是全局单例，`map[uint64]*Match`，每个对局一条 goroutine，两到三个计时器。
- **没有对局数上限**。第一版靠两条清扫规则兜住「空房堆积」：内存里收掉十分钟没人理的
  waiting 房（`reap idle pool match`），库里每分钟把两小时前的 waiting 标 `expired`。
  真要加硬上限，位置在 `Manager.Create` 之前，返回一个 503 而不是让开房卡住；
  现在没加，是因为高峰期真正吃内存的是 `pool-sim`（满力开球那一刻冲到 768M），
  挡住 api 里的几百 KB 对局对象没什么意义（见 12.16）。
- 观战用 `SeatSpectator = -1` 表示：它不占座位、不参与读秒、不影响开局条件，只收广播。
- 观战者上限 10，按**连接**计（同一个人开两个标签页算两条）。
  满了在 **Upgrade 之前**就返回 HTTP 409：WebSocket 里拿不到状态码，
  升级之后再发 error 帧再关闭，浏览器只会看到一次莫名其妙的断连。
- 预检通过、actor 里却满了（两条连接抢最后一个位置）这件事，只能在
  **握手之后**才知道。这时用关闭码 `4001` 告诉浏览器：HTTP 状态码读不到，
  关闭码读得到。前端收到 4001 直接置终态、给「回大厅」，
  不再走 47 秒的退避——重试必然是同一个结果。
- 观战者的快照里 `seat` 也是 -1，前端据此关掉所有操作入口；
  它发上来的任何命令都由 `dispatch` 直接回 `观战中不能操作`，不进规则层
  （否则会被拒成「还没轮到你出杆」——观战者永远轮不到）。
- 观战者进出**不发** `peer` 事件：玩家那条连接上的 peer 表示「对手回来了 / 掉线了」，
  给观战者的进出也发 peer，玩家会看到「对方回来了」而后台其实没人回来。
- 同理，晚到的断线回调（重连之后旧连接的 `close` 才到）**不发** peer：
  只有真的把那条连接从座位上摘掉时才算「对手掉线」，否则提示会一直挂着。
- 观战入口读 `GET /api/pool/live`（内存里正在打的对局，按 match_id 倒序），
  不进库：正在打的对局在被回收前都还在 `Manager` 里，库里那一行反而没有实时球位。
  数据来自 actor 每条命令处理完后发布的 `LiveInfo`（一个 atomic 指针），
  **不进命令队列**：一局在算杆时 actor 是阻塞的，串行问五十局会拖成几十秒，
  而这个列表每十秒拉一次。读摘要永远是 O(1)，代价只是「比真实状态晚一杆」。
  曾经写成「每局并发取快照 + 300ms 超时」，那是拿错误换错误：
  正在出杆的那一局必然超时被丢掉，前端整表替换，面板每十秒闪一次。
- 大厅里自己正在打的那一局给「回到对局」而不是「观战」：
  点观战会以局中人身份被安排座位，等于用第二条连接顶掉自己的对局连接。
  观战页收到非 -1 的座位时也自动让位回 `/pool/match/:id`。
- 广播函数按连接列表逐个投递，观战者与玩家同一条通道，不需要两份逻辑；
  `broadcastState` 给观战者只算一份中立快照（它们的视角完全一样）。

容量估算，按现有机器：五个容器的常驻内存见 docs/10 第 1.2 节，mysql 约 300MB 是最大头，`pool-sim` 常态两百多兆、满力开球那一刻才冲到 768M 的上限。Go 进程增加的内存主要是连接与对局对象，一局几百 KB。50 局同时在线没有压力，200 局需要观察。

## 12.12 数据模型

```sql
-- 表名用 GORM 的默认复数形式（模型上没有 TableName 覆盖）
CREATE TABLE pool_matches (
  id           BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  room_code    VARCHAR(6) NOT NULL,
  p0_id        BIGINT UNSIGNED NOT NULL,
  -- 可空：房间建好时可以只有房主，等对方输房号进来（或接受邀请）再补上
  p1_id        BIGINT UNSIGNED NULL,
  status       VARCHAR(16) NOT NULL DEFAULT 'waiting',
  winner_id    BIGINT UNSIGNED NULL,
  win_reason   VARCHAR(32) NOT NULL DEFAULT '',
  shot_count   INT NOT NULL DEFAULT 0,
  started_at   DATETIME NULL,          -- 房间阶段还没有开局时间
  ended_at     DATETIME NULL,
  created_at   DATETIME NOT NULL,
  updated_at   DATETIME NOT NULL,
  UNIQUE KEY uk_pool_room (room_code),
  KEY idx_pool_p0 (p0_id),
  KEY idx_pool_p1 (p1_id)
);

CREATE TABLE pool_shots (
  id          BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  match_id    BIGINT UNSIGNED NOT NULL,
  seq         INT NOT NULL,
  shooter_id  BIGINT UNSIGNED NOT NULL,
  seat        INT NOT NULL DEFAULT 0,
  params      JSON NOT NULL,
  events      JSON NOT NULL,
  frames      MEDIUMBLOB NOT NULL,
  duration_ms INT NOT NULL DEFAULT 0,
  sim_ms      INT NOT NULL DEFAULT 0,
  created_at  DATETIME NOT NULL,
  UNIQUE KEY uk_pool_shot_seq (match_id, seq)
);

CREATE TABLE pool_ratings (
  user_id    BIGINT UNSIGNED PRIMARY KEY,
  elo        INT NOT NULL DEFAULT 1000,
  wins       INT NOT NULL DEFAULT 0,
  losses     INT NOT NULL DEFAULT 0,
  updated_at DATETIME NOT NULL
);
```

- `frames` 是 gzip 之后的 JSON 存 MEDIUMBLOB：一杆 130 帧的 JSON 约 60KB，压完 8-10KB。
- 回放就是把 `pool_shots` 按 `seq` 读出来重放，前端复用 `animator`。
- **房号唯一索引**是并发建房的唯一可靠判据：查重与插入之间有窗口，撞了就换个号重试。
- **抢座位靠条件 UPDATE**（`p1_id IS NULL AND p0_id <> ?`）而不是「先查空位再写」：
  两个人几乎同时输同一个房号时，先查再写会让两个人都以为自己抢到了。
- 上面是等价 SQL，实际建表走 GORM。三个模型写进 `internal/model/pool.go`，**必须同时补进 `internal/config/db.go` 的 `Migrate()` 列表**，那个列表是手写的，漏了就只会得到一个「表不存在」的运行时错误，`cmd/migrate` 不会报任何异常。
- 从旧版本升级时唯一需要人看一眼的是 `p1_id`：早先它是 `NOT NULL`，
  现在要允许空。`AutoMigrate` 一般能改，但服务器上若已有表，
  部署前先跑一次 `ALTER TABLE pool_matches MODIFY p1_id BIGINT UNSIGNED NULL;` 更稳。

## 12.15 部署变更

`docker-compose.yml` 增加一个服务，不发布端口，只在内网被 api 调用。

```yaml
services:
  pool-sim:
    build:
      context: ./pool-sim
    restart: unless-stopped
    environment:
      NUMBA_CACHE_DIR: /tmp/numba
    expose:
      - "8000"
    deploy:
      resources:
        limits:
          memory: 768M
    healthcheck:
      test:
        - "CMD"
        - "python"
        - "-c"
        - "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/healthz', timeout=3)"
      interval: 15s
      timeout: 5s
      retries: 5
      start_period: 40s
```

api 增加环境变量 `POOL_SIM_URL=http://pool-sim:8000`，`config.yaml` 里给默认值，并让 api 在 `depends_on` 里只等它 `service_started`——预热没完时出杆会拿到 `ErrUnavailable`，玩家重试一次就好，而把 api 一起拖着不启动会连文章都看不了。

四个部署注意点。

1. `pool-sim` 首次 build 要装 numpy、numba、pooltool，都是现成的 manylinux wheel，2G 内存解压没问题，但耗时会到两三分钟。建议和 api 分开 build，别一次跑两个。
2. 容器启动后要先跑一杆满台开球做 JIT 预热（约五秒），`start_period` 给到 40 秒，避免没预热完就被判不健康。
3. 内存限 768M 而不是 512M：满力开球那一杆 numba 的临时数组最占内存，512M 会在那一刻被 OOM 杀掉。要调小之前先开一局满力开球，同时 `docker stats pool-sim` 看真实峰值。
4. 它**不在「本机编译」那套里**（`deploy/prod/docker-compose.artifact.yml` 只覆盖 api、migrate、web），所以服务器上要单独 `docker compose build pool-sim`，源码也必须在服务器上留着。它同样不跟 `IMAGE_TAG` 走，回退版本时带不回旧的物理服务。日常运维见 docs/10 第 13.6 节。

Nginx 只需要一处确认。对局 WS 挂在 `/api/ws/game`，正好落进现有的 `location /api/ws/`，那里已经写好 Upgrade 头与 `proxy_read_timeout 300s`，心跳 25 秒远小于它，不用改配置文件。若把路径写成 `/ws/game`，就会掉进普通 `location /api/`，缺 Upgrade 头，握手直接 426。

生产叠加层里的 `ports: !override` 不用动，新服务没有宿主机端口。

### 12.15.1 「我的房间」这一轮没有新增基础设施

房间、在线名单、退房都是 api 进程里的接口，不新增服务、不新增端口、不新增环境变量：

- 四条路由（`/pool/rooms/my`、`/pool/rooms/join`、`/pool/rooms/leave`、
  `/pool/rooms/reopen`）和 `/pool/online` 都挂在现有的 `/api/` 下，
  Nginx 与 compose 都不用动；
- 库表没有新增，只是 `p1_id` 从「必填」变成「可为空」。
  服务器上若是**首次**部署台球，AutoMigrate 直接建成可空，什么都不用做；
  若之前已经建过表，部署前先跑一次：

  ```sql
  ALTER TABLE pool_matches MODIFY p1_id BIGINT UNSIGNED NULL;
  ```

- api 启动后多一个后台协程 `pool.ExpireRooms`（每分钟一次，把开了两小时还没开打的房间标成
  `expired`）。它跟 `Manager.Janitor` 一样挂在 `main` 的走停组里，日志里能看到
  `expired stale pool rooms`，条数为 0 时不打日志。
- 内存侧：`Manager.Janitor` 的清扫多了一条规则，收掉「还没开局、并且十分钟没人跟它说话」的房间
  （`reap idle pool match`）。点进台球就开一间房，不收拾的话一局一个 goroutine 会一直挂着。

## 12.16 已知限制与风险

| 风险 | 影响 | 处理 |
|---|---|---|
| pool-sim 单 worker | 一局出杆排队 | 12ms 一杆，50 局也排不满；不够再加副本 |
| pooltool 版本升级 | 轨迹手感变化 | `requirements.txt` 锁 0.6.0，升级前跑金样例 |
| 服务重启丢对局 | 进行中的对局中断 | 第一版接受，界面提示「对局已中断」 |
| 规则与 pooltool 有差异 | 对照源码时困惑 | 差异写在 12.7 与代码注释里 |
| 手机横屏 | 布局错位 | 竖屏为主，横屏给旋转提示 |
| 观战者过多 | 带宽与连接数 | 每局上限 10，超出拒绝 |
| 按 IP 限流撞上首屏请求 | 大厅偶发「请求太频繁」 | 首屏一次要发九个请求，令牌桶容量 10、每秒补 2，本来就贴着上限；`/api/ws/*` 已单独用一个容量 30 的桶（429 在 WebSocket 里拿不到状态码，客户端分不清是被限流还是断网）。房间轮询按两档降频（独自 10 秒 / 对面有人 2 秒），在线名单与观战列表都是 10 秒；撞上时各面板都有「重试」入口 |
| 房号被别人试出来 | 陌生人进到房间里 | 六位数字、只对 `waiting` 的房间有效，一局开始即作废；他一进来房主就在屏幕上看到名字，可以退出重开一间（拿新房号）。不做密码：这是个「报个数字就能一起玩」的功能 |
| 房间号资源 | 六位数字被慢慢占满 | 两小时未开打的房间自动 `expired`，房号随即可被重新生成；建房撞号会换号重试 5 次 |
| 对面关掉页面不再回来 | 房主面对一个永远不会点准备的人，那间房凑不齐也开不了 | 房主点「换一间」把旧房作废、另开一间新房号；即使他不动，两小时后那条清扫也会把房标 `expired` |
| 同一人两个标签页同时进大厅 | 可能各建一间房，多出一条空房 | 查询与插入之间没有锁，靠「取 id 最新的一条」收敛：两边下一次轮询都会落到同一间，多余那行等两小时清扫收掉。为这点残留加分布式锁不值得 |
| 抢到座位后某一步失败 | 房主看到一个不会点准备的人 | 座位是条件 UPDATE 抢的，之后任何一步失败都走 `rollbackSeat` 把座位退回去；同一个人以客人身份坐过的旧房间由 `ClearGuestSeats` 腾出座位（房留着，房主还能继续等别人） |

### 实施记录：M5 之后补的两条协议约定

设计稿里没写、实现时才暴露的两件事，补在这里免得后面又踩：

1. **一杆结束必须补一份完整 `state`。** `shot` / `foul` / `turn` 都是增量：
   前者有轨迹，中者只有文案，后者只有读秒，都不带「定组结果」与「手中球」。
   少了它，前端第一次进球之后仍显示未定组、犯了规拿不到 `ball_in_hand`，
   于是没法落位母球，只能反复出杆被拒——对局就卡死在那里。
   前端在动画播放期间会把这份快照压住，播完再应用，否则球会瞬移到终局位置。
2. **未定组在协议里是空串，不是 `'none'`。** 后端 `GroupNone` 用 Go 零值当哨兵，
   「没赋值」与「故意置空」因此是同一件事，零值的 `RuleState` 天然表示未定组。
   前端写成 `'none'` 会让未定组走进「已清台、该打黑八」的展示分支。

### 实施记录：连续对局的大比分与对手镜像

**大比分。** 每次「再约一局」都是新的一行 `pool_matches`，单看当前这一局，
界面只知道本局 0:0——两个人连着打了五局，顶上还是 0:0。所以另有一本进程内的账
（`internal/pool/series.go`）：

- 按「一对 userID」记账，与座位、与谁先开球都无关；同一对人换边打，账还是这一本。
- 开局时读进 `MatchState.Series`（房间走 `handleReady`、再约走 `Manager.Create`），
  结算时在 `finish()` 里给赢家 +1。三条结算路径（正常、判负、离场）都汇到这一个函数。
- 快照带 `series`，**结果帧也带一份**：判负与离场之后服务端不再补快照，
  只靠快照会让顶上的比分停在开打前，要等下一局才开始跳。
- TTL 三小时。隔了大半天再碰上从 0:0 重新开始，比接着 7:5 打更清楚。
  进程重启即清零——正式战绩在 `pool_matches` 里，这是另一套。
- 前端顶栏正中显示「我 : 对手」，座位是 1 号时左右换过来；结算帧到了之后
  以结果帧里的那份为准，新的一局开始（收到 `playing` 的快照）再让位给快照。

**对手的力度与击球点。** `aim` 帧原来只带角度与力度，现在把 `a`、`b` 也一起搬
（服务端只做区间夹取，不拦整帧）。对面右下那一条力度条与加塞球变成只读镜像：

- 同一个位置、同一套外观，只是不给拖，也不压暗（压暗一条正在动的滑轨像掉线了）。
- 力度条顶上挂一枚「对方」小标签。不加的话，对面推力度时我这边也有一条在动，
  会以为是自己那根。标签排在聊天入口**上面**（`bottom: calc(100% + 44px)`，
  与滑轨同轴居中）：入口占着「力度条往上 10~38px」那一段，两者原来挤在一起，
  蓝气泡被「对方」压掉半个。现在中间留 6px，两个形状都读得完整。
- 远端每 60ms 才来一帧，填充与红点都补了 90ms 的线性过渡，否则是一格一格跳的。
- 自己那一份在出杆后清零，所以换人的瞬间不会把上一杆的塞画成对面的。

### 实施记录：力度曲线、音效与「球没停杆先出来」

**力度条的分档：最后回到线性。** `speed = 0.05 + power × 4.35`，
拉一半就是一半球速。中间试过改成平方（想让低端更细腻），实机被否掉了：
一半力度只剩 1.14 m/s、滚 3.2 米，常规一杆要拉到 60% 以上才够，条子下半截等于没有。

原因在于「玩家心里的力度」其实是距离，不是初速。滚动段几乎全是与速度成正比的
阻尼，速度按指数衰减，总路程 `d ≈ v0 / k`——距离几乎正比于初速，于是**线性的球速
恰好等于线性的距离**：

| 力度 | 10% | 20% | 30% | 40% | 50% | 70% | 100% |
|---|---|---|---|---|---|---|---|
| 平方 | 0.06m | 0.33m | 0.94m | 1.91m | 3.18m | 6.09m | 12.0m |
| 线性（现在） | 1.10m | 1.82m | 3.20m | 5.06m | 5.62m | 7.67m | 11.35m |

（实测口径：单球沿长边中线自由滚，累加 120Hz 关键帧之间的位移，含库边反弹损耗。
60% 以后曲线开始变缓，因为低速段多了一份末段阻尼，见下一节。）

上限仍是 4.4：开球靠它，不能因为改曲线把开球改软。

**音效全部现场合成，不带音频文件。** 五类声音（击球、撞球、撞库、落袋、结算）
都在 `web/src/game/audio.ts` 里用振荡器与滤波噪声拼出来。理由不是省流量，
是「跟着力度变」——采样要为每一档录一份，而合成只改两个参数。细节：

- 一杆开播之前先把事件流翻译成「第几秒响什么」（`buildShotSfx`），播放时按
  时间游标往外放。不在每帧里扫事件表，掉帧也不会漏响或重响。
- 音量按**撞击前**的球速算（事件本身不带力度，从轨迹前后 20ms 的位移反推），
  方位按球的横向位置给声像。一杆开球里既有 4 m/s 的正碰也有 0.2 m/s 的轻擦，
  一个音量会让整杆听起来像一个人在鼓掌。
- 环境音是很低的两音垫音加一层底噪，音量压到「关掉时才注意到刚才有声音」。
- 浏览器不给没手势的页面出声：`AudioContext` 在页面第一次 pointerdown 时才建，
  环境音也在那一刻起。开关记在 `forum_sound`，刷新仍然安静。
- 开球那一杆几十颗球同时响，母线后面挂了一个压限器，否则会削顶（爆音）。

**「球还没停下来，杆已经出现了」。** 根因是两边的动画不是同时开始的：出杆那一
侧松手就播（本地预测），另一侧要等服务端把 `shot` 帧转过来，差一个来回。先播完
的那一方如果还在打（进了球就还是他），他新一杆的 `aim` 帧会在我这边球还滚着的
时候到达，照画就是「球没停，杆先架上去了」。

修法是在显示层加闸：`peerAimLive` 在 `shooting` 期间返回 null（观战页是
`aimLayer` 在 `rolling` 期间返回 null）。帧照收不误，只是不画——动画一结束，
最新那一帧立刻显示出来，不会因为对面停手不动而丢杆。

### 实施记录：末段收尾、0.8 倍速回放与母球红点

**末段：从「看得见的位移」到「看得见的减速」。** 收尾原来只有常数项加粘性项，
纯指数衰减。数学上很绵，屏幕上却不是：球从 0.1 m/s 到静止要三秒多，这三秒只走
一两厘米——1 米约 300 像素，折算下来**最后 0.6 秒只动 1.4 个像素**，玩家看到的是
「滚到某个位置忽然定住」，然后再等两秒才轮到下一手。

第一版在低速段加了一份随速度增大的阻尼 `TAIL_DECEL × (1 − v / TAIL_SPEED)`：
位移有了（最后 0.6 秒 20 像素），但形状不对——减速度全堆在最后半秒，前 1 秒每
0.1 秒只少 0.4 像素（几乎匀速），最后 0.4 秒从 57 px/s 直落 6 px/s。观感就是
「匀速滚完，啪一下刹住」，被玩家否掉了。

现在是恒减速：进 `TAIL_SPEED`（0.4 m/s）之后，在 `TAIL_RAMP`（0.22 m/s）这段
速度区间里用 smoothstep 把额外阻尼升到 `TAIL_DECEL`（0.16），再往下一直保持。
用 smoothstep 是为了两端一阶导都为零，减速度曲线自己没有折点，速度曲线上就看不
出「从哪一刻开始刹车」的接缝。

| 方案 | 收尾时长 | 最后 0.6 秒位移 | 末段总位移 |
|---|---|---|---|
| 纯指数 | 7.6s | 1.4px | 约 2px |
| 线性增大（0.35 / 0.45） | 1.61s | 20px | 108px |
| 恒减速（0.4 / 0.16，现在） | 2.5s | 12px | 约 175px |

最后 0.6 秒的位移反而比上一版少，但这正是「一点点停」该有的样子：新方案每 0.1 秒
走 7.3 → 6.6 → 6.0 → 5.4 → … → 1.1 → 0.5 像素，稳定递减；上一版是
9.6 → 9.3 → … → 2.1 → 0.9 → 0.2，前面几乎不变、最后忽然掉到零。玩家感觉到的
是减速的**过程**，不是最后那几像素。

用例除了「最后 0.6 秒 ≥ 8 像素」，还断言最后 1.2 秒里每 0.1 秒的位移单调不增、
且没有哪一段比前一段少七成以上——「塌陷」正是上一版的特征。

代价是极低速段的滚距短了：两成力度 1.82 → 1.84 米（几乎不变，它的距离主要来自
中高速段），一成力度 1.10 → 0.42 米。那 1.1 米里大半是「最后三秒只走一两厘米」的
爬行，收尾一压缩就没了；轻推本来就是贴球用的，0.42 米仍在可用范围。

**一杆按 0.8 倍速播。** `animator.ts` 的 `SHOT_PLAY_RATE`，四处在用：对局页自己
出杆、对局页播对手的帧、观战、回放。物理仍按真实时间算——`playShot` 回调出来的
`elapsed` 是物理时间，倍速只拉长墙上时间，所以音效时间轴不用单独调速，也不会
和画面脱节。慢放一档的副作用是一杆变长（50% 力度从 6 秒到 7.6 秒），换来的是
末段看得清。

**母球红点改在屏幕空间画。** 原来红点烘焙在球面贴图里。贴图坐标就是球面法线
（u = sinθ），一颗落在赤道上的圆点投到屏幕上会被径向压扁、贴着球缘摊成一道弧，
四颗连起来就是「白球四周镶了一圈红边」。现在渲染层按球面朝向逐颗画正圆
（`drawCueDots`），点位是球面三根正交轴的六个极点（上下左右前后，与练习球一致），
并且越靠球缘越淡（`nz` 小于 0.02 不画）。局部坐标轴相对视线固定转过一个立方体
对角线的角度：不转的话四颗赤道点正好压在轮廓上、一颗在背面，静止时只剩正中心一颗，
看着像掉了四个；转过之后静止时能看到三颗，滚起来其余的点依次从边缘转进来。

**微调步长 0.05°。** 底部两个按钮、方向键都是 0.05°，按住 Shift 或连发是老逻辑；
读数仍是两位小数（0.05 的一半就会进位，一位小数看不出变化）。

### 实施记录：对局内聊天

**协议。** 上行 `chat`、下行 `chat`，载荷 `ChatData{seat, text, id, ts}`。只做实时
转发，不落库、不进快照：对局内的聊天是「打这一局时说的话」，局散了没有回看价值，
存下来还要处理清理与隐私。观战者收得到（他们看的是同一块屏），但发不了——没有座位。

服务端两道闸门都在 actor 里（单写者，不用加锁）：正文按**字符**截到 120——按字节
限长会把一句中文截成半句；同一座位两次发言至少隔 700 毫秒。两条有一条不满足就静默
丢掉：为一句闲聊回一条错误，只会让面板上多一行红字。

**前端。** 聊天入口挂在力度条正上方（与滑轨同一根竖轴），未读时右上角亮数字，点开是
底部抽屉：消息列表（自己的靠右、台呢绿）、一排 emoji、随内容长高的输入框。入口原本
贴在左侧库边的 46% 处，那儿正好是长库中间的袋口，气泡压掉了半个洞；台面右外侧整条
都是留白，压不到任何球洞，也不挡球。自己发的那条**先落本地再上行**——服务端不回显给
发送方，等回音的话要等对面收到才出现，看起来像没发出去。纯表情的消息去掉气泡底色、
放大成贴纸（判据是「剥掉表情之后什么都不剩」，「好🎯」仍然是字）。

**头像旁飘一条。** 面板收起时对面说的话只能看到一颗红点，看不到内容。现在每一句
都在**说话人那一侧**的头像下面飘 4 秒，自己发出去的那句也飘一下：
发完就收起面板时，得有个「确实送到对面了」的落点。**必须按侧分开挂**：座位卡恒定
「我在左上、对手在右上」，早先两边的气泡都挂在右上，人机局里就成了「我发的话从
机器人头像下面冒出来」，读起来像它在说话——人人局同样有这个毛病，只是对手是真人时
不那么刺眼。实现上仍是同一个 `chatToasts` 数组，`computed` 过滤出两份给两个容器，
过期撤条只认 id；三条上限改成**按侧各算**，对方连发表情时不该把我刚发的那句顶掉。
这条提示不拦点击，也不进面板的列表——列表是全量记录，提示只管「刚刚发生了什么」。
淡出写进 CSS 动画，到点从数组里撤掉时节点正好透明，看不出跳变。字号 15px、
气泡最多两行 280 宽；右侧整摞从屏幕右边缘往中间挪 56px（右端刚好落在对手头像右缘），
左侧缩进 40px（左边只有 10px 页边距，56 会顶到中间的读秒），圆角整套镜像——
12px 只有四秒可读，贴着屏幕边缘看着像系统通知而不是「他说了句话」。

**面板宽度。** 手机上是通栏抽屉；桌面（≥721px）收成 560px 的浮层（900 高的屏幕上
球台 409 宽，正好「比球台宽一些」），居中、四角圆、离底 18px。居中用 `margin: 0 auto`
而不是 `transform: translateX(-50%)`：进出动画动的就是 transform，叠在一起会让面板
滑入时横向跳一下。

**入口要显眼。** 28px 实心蓝（`linear-gradient(160deg,#3b95ff,#1659cf)`）+ 外发光，
有未读时用 `box-shadow` 做一圈呼吸光（不触发布局，`prefers-reduced-motion` 下关掉）。
之前是 34px 半透明灰，在绿呢与深灰底上几乎是隐形的；34px 那版又压到球台木框，
收到 28px 之后才有地方摆。**横轴必须与滑轨同轴**：滑轨 12px 在 44px 的 `.pm__power`
里居中，中心离右沿 22px，28px 的按钮要落在那儿得 `right: 8px`——原来贴列的外沿
（`right: 0`），实测中心比滑轨偏右 8px，看着像两颗东西各站一边。代价是左沿压球台
木框 6px，比偏 8px 更容易被读成「歪」，而且下方加塞球（46px）本来就压着同一段框 15px。

**音效。** 收发各一条合成音（`chatIn` / `chatOut`），与整套音效同一套 Web Audio，
不需要音频文件。曾经做过一版「把对方的文字念出来」（浏览器 `speechSynthesis`），
后来去掉了：对局里突然有人声比听提示音更打扰，而且念得准不准全看设备装了什么中文
语音。

**回车发送。** 输入框是 textarea（要能看全长句），默认回车是换行——对局里没人有空按
两次。现在回车直接发，Shift+回车才是换行。两件事不能交给模板修饰符 `.enter.exact`：
中文候选词还没上屏时按的回车是「选这个字」，判断在 `isComposing` 上，不是在按键上；
也不能漏掉 `preventDefault`，否则字发出去了框里还留一个空行。

### 实施记录：全屏（添加到主屏幕）

球台宽度正比于可用高度，而浏览器工具栏在手机上要吃掉 120~150px。**iPhone 的 Safari
没有全屏 API**（`requestFullscreen` 在 iPhone 上不存在，只有 iPad 有），网页自己
调不起来。唯一可靠的路径是把站点做成可安装的网页应用：

- `public/manifest.webmanifest`：`display: standalone`、`start_url: /pool`、
  192/512 图标，Chrome/Android 认这一份；
- `index.html`：`apple-mobile-web-app-capable`、`apple-mobile-web-app-status-bar-style:
  black-translucent`、`apple-touch-icon`，iOS 认这一套；
- `viewport-fit=cover` + `.pm` 上的 `padding: env(safe-area-inset-top/bottom)`：
  全屏时页面铺到刘海与底部指示条下面，靠这两条让开。

从主屏图标启动后没有地址栏，`100dvh` 就是整块屏幕——390×844 的机器上球台直接
按宽度卡到 344（占屏 88%），比浏览器里多出一条工具栏的高度。

iOS 上这一步只能由玩家手动完成，所以大厅顶部有一条一次性提示（`forum_a2hs_hint`
记「已关」）：只在 iPhone/iPad 的 Safari 里出现，已是 standalone 或微信/QQ 内置
浏览器时不出现——后者底部根本没有「添加到主屏幕」。

nginx 那边要给 manifest 显式定类型（`types {}` + `default_type
application/manifest+json`）：Chrome 只认这个 MIME，而 nginx 自带 `mime.types`
里有没有这一条要看版本。

### 实施记录：人机对战

没有第二个人在线时，这一页就只有「等」。人机对战要解决的就是这一段空窗：
大厅右上角的「人机对战」点一下，`POST /api/pool/rooms/bot` 直接开一局
`status=playing` 的对局，玩家恒坐 0 号位并且先开球。

**为什么机器人坐在服务端。** 出杆的物理一直以客户端为准（客户端带 `result` 上行，
服务端只校验形状 + 判规则）。机器人没有客户端，所以它走的是另一条路：actor 自己
调 pool-sim 算这一杆，再走**同一个** `playShot`。两条路只在「谁算物理」这一步分开，
规则、换人、落库、下一杆归谁全都共用，不会跑出一条真人局没有的路径。

**触发。** `MatchState.Bot` 记着机器人坐哪（-1 表示没有，普通对局的零值必须显式写掉，
否则座位 0 会被当成机器人）。每次 `playShot` 之后、开局与超时换人之后都调一次
`armBot(after)`：轮到机器人就装一个 `time.AfterFunc`，回调只做一件事
——把 `cmdBotShoot` 投回 actor。**回调里不能直接改状态**：它可能正撞在别的命令中间，
读到的球位是半截的。

**出杆时机 = 这一杆在客户端播完 + 1 秒。** 服务端算完就把帧发走了，客户端却是
按 0.8 倍速（`SHOT_PLAY_RATE`）慢慢放的——只按服务端的「算完了」计时，机器人会在
玩家屏幕里球还在滚的时候出杆。`shotPlayDelay(shot) = shot.Duration / ShotPlayRate`
（与前端同一个常量口径，`ShotPlayRate` 写在 `match.go` 里），再加上
`BotThinkDelay 1.0s + 抖动 0.3s`；开局与超时没有新轨迹，`after` 传 0。

撞上这一条的症状不只是「节奏怪」：客户端手里只有一组 `pendingState/pendingFoul/pendingTurn`
单槽，两杆的帧叠在一起时，早先那一杆的 `foul` 会盖在**新一杆的 state** 上，
界面以为手里有自由球、服务端其实已经把球判给对面了，一摆就是
「这一杆不能自由摆放母球」。现在两边各加一道闸门：

- 服务端按 `shotPlayDelay` 等动画播完；
- 客户端把「上一杆还没播完时到的 shot」排进 `pendingShot`，播完再起，
  不再中途切动画；`applyFoul` 也只在**对手犯规**时才顺手采纳 `ball_in_hand`
  （自己犯规时采纳会把「轮次还是我」误解成「我可以摆球」）。

**怎么选球。** `bot.go` 是纯几何，不看物理：

1. 目标球：还没定组时打全部非 8 号球；定了组只打自己那组；清完了打 8 号。
2. 对每颗目标球 × 六个袋口算幽灵球（ghost ball）：从目标球球心沿「袋口反方向」
   退一个球直径，那就是母球要撞的点。
3. 两道过滤：切角余弦 < 0.34（约 70°）的太薄，不打；母球到幽灵球、目标球到袋口
   这两条线段上球心距 < 两个半径的，被挡，不打。
4. 打分 `cosCut / (母球段 + 袋口段 × 0.5)`，取前三套。
5. 力度按两段路的总长估：`0.26 + 总长 × 0.11`，封顶 0.62。

前三套会**逐套真算一次物理**，只要有一套不犯规就用它。全犯规时认罚打完第一套——
停在那儿不出杆的话，玩家要对着不动的球桌等四十秒读秒。

**兜底。** 一条能进的线都没有时（母球被围、或者只剩对手的球），退回「朝最近的
己方球轻推」。空杆（母球什么都没碰到）是犯规，碰到一颗自己的球起码不送自由球。

**落位。** 母球摔袋之后机器人要先摆球：先沿中线从开球端往远端找一个干净点，
不行再全台面扫描。约束与 `handlePlaceCue` 完全一致（台内、不压球、开球线后），
直接用同一条命令，不另写一份校验。

**入口与大比分。** 空房那颗大按钮写着「等对手进来」，容易被读成「不等人就打不了」，
所以空房下面补一行「自己也想打？先和机器人练一杆」，走 `onPlayBot`。
页头原来还有一颗同名的 `pl__tool--bot`，后来撤掉了：两个入口说的是同一件事，
都要占最显眼的位置，而这一行离「等对手进来」更近、场景更对。撤掉之后
「房间没开出来」那个状态没有任何打球入口，所以那儿也补了一行同样的按钮。
结算卡在 `snapshot.bot` 不为 -1 时
把「再约一局」换成「再打一局」——人机那边没有第二个人，原来那条路会让服务端回
一句「对手不在了」。机器人的 `user_id` 恒为 0，`Store.FinishMatch` 正是靠
「对手 id 为 0」跳过 Elo 计算，不会给一个真人记上败绩。

### 实施记录：台呢质感、木框立体感与落袋动画

**台呢不再是一块纯色。** 现在四层叠上去：4px 的织物颗粒瓦片、横向椭圆受光、四角
暗角、库边压在布上的双层暗影（近处一窄条压深、远处一宽带淡出，叠出来的剖面才够
「先平后降」）。

颗粒用固定序列（`(x*7 + y*13 + x*y*3) % 16`）而不是 `Math.random`：同一张台子每次
打开长得一样，不会「刷新一下布就换了纹理」。它铺在底色之上、受光之下——亮处能看见
细碎高光，暗处也不会被上一层暗角吃掉。

受光从正圆改成横向椭圆（`translate` + `scale(0.72, 1)`）：灯罩是长条形，打在台面上
本来就是一块横椭圆；正圆的亮斑会让台面看起来像个倒扣的碗。

**木框从单色改成斜向渐变 + 内侧暗边。** 这么大一片面积上没有任何明暗变化，看着就是
一张压平的卡纸。渐变取左上亮、右下暗（`#454a50 → #35383c → #24272b`），再沿库边外沿
压一道暗边（库边是立起来的斜面，会挡光，紧挨它的框面永远是暗的），外面再叠一道更宽
更淡的内阴影，两道合起来才有「抬起来的一层」的厚度。

**落袋动画的时长按球消失前的速度算。** 取最后一帧位置到袋口中心的距离，除以
「上一帧到这一帧的位移 ÷ 间隔」，夹在 90~320ms 之间：快球几十毫秒就没了，慢球才在
袋口磨一下。位移也从平方曲线改成线性——平方曲线正是「越靠近袋口越快」，也就是
玩家说的「像被吸进去」：球明明已经慢下来了，最后那一下却突然加速。缩放与淡出保留
一点加速度，球是往下掉进洞里的，那一下「沉」靠缩放表达就够。

### 实施记录：帧尾按球速判，不再「慢慢滚着忽然加速停下」

**症状换了两次皮，根子是同一个。** 先是被反馈「球慢慢停下后会瞬移一小段」，于是
在动画结束处加了一段补间（`settleBalls`）把画面搬到权威球位；接着又被反馈
「明明慢慢滚快停下了，却突然加速到一个位置」——那段补间就是新的「加速」。

**真正的错在截断判据。** `pool-sim` 要把 pooltool 那截「球以毫米级速度继续爬」的
尾巴砍掉，原来的判据是**每帧位移 > 2mm**。位移里藏着帧率：机器人那一路是 30Hz 采样，
2mm/帧 等于 66mm/s，球还在肉眼可见地滚就被判成静止。线上量出来的缺口是 16~22mm
（`pool_shots` 里相邻两杆的「上一杆末帧」与「下一杆首帧」相差），补间用 160~520ms
把这段走完，看上去就是「球忽然加了速滑到某个位置」。

现在判据换成**速度**（`STOP_SPEED = 10mm/s`，用「位移 / 这一帧的时长」算，帧率变了
判据也不变）。10mm/s 在手机上约 0.1 像素/帧，看着就是停了；此时离真正静止还剩
不到 1mm，`settleBalls` 里「差 < 1mm 直接对齐」那条分支就能兜住，视觉上没有跳变。
代价是机器人那几杆的动画比原来长 0.4~0.6 秒——那是真实存在的滚动，不是静止画面。

`trim_still_tail` 的单元测试钉住三件事：30Hz 下 1mm/帧（30mm/s）不许砍、120Hz 下
同样的位移（120mm/s）也不许砍、只有 3mm/s 才允许砍；落袋那一帧（球从帧里消失）
仍然算「动过」，否则进袋的最后一下会被砍掉。

### 实施记录：分享链接——一群人抢一张球桌

**链接不再只是「发给某一个人」。** 原来的分享入口是一颗小按钮，语义上像一次
一对一邀请；现在它是一条整宽的卡片，说明写着「发到群里，谁先点开谁上桌」。
球桌仍然只坐两个人，所以「多人」这件事落在**并发**上而不是座位上：谁能坐上
取决于谁先点到，服务端那条带条件的
`UPDATE ... WHERE p1_id IS NULL`（`Store.JoinRoom`）本来就是唯一判据。

**来晚的人要看到「人满」，而不是一句含糊的「已经有人了」。** 409 现在带
`error_code = room_full`（`response.ErrCodeRoomFull`），文案改成
「房间人满，这张球桌已经坐满了」；邀请接受那条路（`AcceptInvite`）也走同一个码，
前端只写一处分支。大厅按这个码在页面顶部留一条说明（暖色、8 号球图标、「知道了」
可关），**不弹 toast**：toast 一秒就飘走，来晚的人只会以为链接坏了。说明下面照样把
他自己的房间开出来——人都到台球页了，与其停在一张别人的满桌上，不如就着自己的
空桌再拉人。其它失败（房号过期、链接被改过）只有 toast + 开自己的房间，不留说明。

**链接自带台球元素。** 三处：网页里那条分享卡片是桌呢绿底 + CSS 画的 8 号球；
系统分享面板的标题是「🎱 台球对战邀请」，正文写清「一张桌子只坐两个人，先到先得」；
走剪贴板时连说明一起复制（只给一条网址，粘到群里就是一串看不出用途的字符）。

**桌面不碰 `navigator.share`。** 电脑版 Chrome / Edge 也有这个 API，接的是
Windows 系统分享，点下去只会弹一个「共享失败」，用户还得再点一次卡片。所以面板
只在触屏设备上试（`isMobileClient()`：UA 里带 Android / iPhone / iPad / Mobile，
或 Macintosh + 多触点认 iPadOS），桌面一律走剪贴板，卡片右侧文案也跟着从「发链接」
变成「复制链接」，点一下就复制并提示「链接已复制，粘贴给对方就行」。剪贴板 API
被拒（老浏览器、WebView）时再试一次 `execCommand('copy')`，两条路都不通才弹一个
带链接原文本的弹窗让人手动选中。

## 12.17 开工顺序

先做 M0 与 M1，只碰前端，不动后端。理由有两个。

- 渲染与交互是这一版最大的不确定性，先把「看起来像不像」验证掉。
- 后端与仿真容器都依赖前端定义好的数据结构，等类型定下来再写 Go，返工最少。

M1 的验收标准写死三条：390×844 下球台完整可见且不被 HUD 压住，1440×900 下居中且左右留白对称，窗口缩放后球位不漂移。
