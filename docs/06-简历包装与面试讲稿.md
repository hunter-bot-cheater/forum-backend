**写简历的三条原则**：

1. 每条写一句话技术加一句效果，避免「使用了 XXX」这类空话。
2. 量化要能复现，例如「接口响应从 X 毫秒降到 Y 毫秒」要能说出测量环境与方法。
3. 只写自己真能做出来、面试敢被深挖的内容。

### 讲稿 6：WebSocket 实时通知（完成 04c 章验收后填写）

> 背景：异步通知要等用户下次刷新才看得见，体验上有明显滞后。
> 方案：`Hub` 用两层 map 按用户登记连接，推送时只持读锁拷一份连接清单、在锁外发送；每条连接读写分离，`send` 通道有界，满了直接踢掉慢客户端；token 走查询参数因为浏览器 WebSocket 构造器不支持自定义头；关停时先 `CloseAll` 再 `Shutdown`，因为已升级的连接不受 `Shutdown` 管辖。
> 效果：在 [多标签页同时收到 / 无 token 401 / 慢客户端被剔除 / 在线数准确] 的验收条件下观察到 [可复现的结果]，当前限制是 [单进程 Hub，多实例需要 Redis 扇出，推送不保证送达]。

动笔前先读 `docs/04c-第3周进阶-WebSocket实时通知.md` 第 9 节。别把「实时」说成「可靠」，通知的真相源始终是 MySQL 那张表。

追问准备：为什么不用 SSE？一条连接占多少资源？怎么发现连接断了？客户端网络闪断服务端多久知道？持锁写 socket 会有什么后果？`Shutdown` 为什么关不掉 WebSocket？多实例部署怎么办？

### 讲稿 7：热榜重建的四次返工（完成 04 章第 7 步后填写）

> 背景：热榜用 MySQL 的 `GROUP BY` 现算，点赞表一过百万就扫穿全表，同库的其它查询跟着变慢。改成把聚合结果投影进 Redis ZSET，读路径只剩 `ZREVRANGE`。
> 方案：第一版直接把 `GROUP BY` 结果塞进 ZSET，压测暴露四个问题，逐个修。聚合加 `ORDER BY` 与 `LIMIT 500` 并依赖 `uk_article_user` 的覆盖索引；重建写临时 key 再 `RENAME` 原子换榜，避免并发读看到残缺榜、也避免重建期间的点赞被全量覆盖；`ready` 标记从永不过期改成 1 小时 TTL，让榜单不会冻结成首建快照；重建失败打 30 秒冷却标记，避免超时后每个请求都去重试把数据库打得更死。
> 效果：在 [`FLUSHDB` 后首次访问自动补齐 / 重建期间并发读不出现空榜 / 一小时后再读触发重排 / 把超时调到纳秒级后只失败一次] 的验收条件下观察到 [可复现的结果]，当前限制是 [聚合仍要过一遍索引、无时间衰减、多实例会各重建一次、未在千万级数据上压测]。

这段适合用来展示「工程直觉」。四个缺陷不是从书上学来的，是压测和推演出来的，讲的时候要按「现象 → 原因 → 修法 → 残余风险」四段说，每段一句话。

残余风险一定要主动交代，否则会被追问到哑口。最值得说的一条：`RENAME` 消除了大面积覆盖，但没消除「SQL 返回结果到换榜执行」这几毫秒内的点赞丢失。补它的方式是 `syncHotScore` 写 MySQL 算出的绝对分数，下一次点赞自动纠正回来。如果当时图省事写成 `ZINCRBY` 累加，这条自我修正的路就断了。

追问准备：`GROUP BY` 加 `LIMIT` 到底省了什么？为什么不给 ZSET 设 TTL 只给标记设？`RENAME` 为什么能保证原子？为什么不用 `ZUNIONSTORE ... AGGREGATE MAX` 合并新旧榜？冷却标记为什么必须用 `WithoutCancel` 写？重建要不要加分布式锁？

## 三、Golang 高频知识点速查

**基础语法**

- slice 与 array 的区别，slice 底层结构（ptr、len、cap）与扩容规则。
- 切片扩容会分配新数组，旧数组若仍被指针引用就继续存活，指针仍然有效，后果是新旧数据不同步。03 章第 3.4 节有完整辨析。
- map 底层是哈希表，并发读写为什么 panic，`sync.Map` 适用场景。
- string 不可变，rune 与 byte 的区别，`len(string)` 得到的是字节数。

**并发**

- goroutine 与 channel，channel 的缓冲与关闭。
- context 的作用，包含取消、超时与跨层传值。
- Mutex、RWMutex、WaitGroup 与死锁。
- GMP 调度模型，能讲清为什么 Go 可以开大量协程，以及调度成本在哪里。
- 数据竞态与 `go test -race`。

**运行时**

- 内存逃逸分析。
- 垃圾回收的大致原理。
- defer 的执行顺序。

**框架与数据库**

- GORM：N+1、事务、Preload、Finisher 方法后复用链的风险。本项目模型没有 `DeletedAt` 字段，软删除尚未启用，面试提到时要说清这一点。
- Redis：穿透、击穿、雪崩与缓存一致性，各自的边界。
- 数据库：索引原理、事务隔离级别、慢查询优化。

## 四、面试场景题

常见题：设计一个短链系统、点赞系统、热榜、消息队列或通知系统。04a 章已经给出一条能落盘的轻量消息链路，答题时可以把「我做过」和「我会怎么设计」分开讲：项目里是 Outbox 加 Redis Stream 的单机版本，生产设计要补多实例抢占、CDC 或 Kafka、归档与监控。

通用应答套路：

1. 先问清量级，QPS 多少、数据量多大、一致性要求多强。
2. 定技术选型，说明为什么用 Redis 或关系型数据库，放弃了什么。
3. 讲清读写链路，请求进来走哪几步，哪一步可能失败。
4. 讲瓶颈和优化，哪里会先扛不住，怎么验证优化有效。

自己做的项目就是最好的素材，可直接迁移去答点赞系统、热榜这类题。答题时把「我做过」和「我会怎么设计」分开说，避免把学习片段讲成生产实现。

## 五、准备实习与面试

**投递前**

- 不必机械地按「完成第几周」决定是否投递。先确认自己能运行项目、解释已完成的代码，并诚实说明未实现的部分。
- 简历让懂行的人帮忙改一版，改完自己逐条复述，确认每条都能被追问三轮。

**渠道**

- 招聘平台、学校就业服务和目标公司的官方招聘页面都可以关注。岗位、平台和招聘时间会变化，投递前核实职位仍在招聘、岗位要求和截止日期，别只依赖固定月份的经验。

**面试过程**

- 准备三个版本的自我介绍，1 分钟、5 分钟和 HR 面版。HR 面少讲技术，多讲协作与学习习惯。
- 技术面围绕基础知识点、项目深挖、场景题和算法。
- 面试录音复盘，整理自己的面经，比看现成面经记得牢。
- 不会的题坦诚说「这块没深入了解」，再讲自己会怎么查，别乱答。

**心态**

- 一份对口的实习对后续求职有帮助，值得花力气，收益也受岗位匹配度影响。
- 岗位数量随市场和地区变化，投递前查一下当前情况。投不中很正常，多投加复盘更有效。
